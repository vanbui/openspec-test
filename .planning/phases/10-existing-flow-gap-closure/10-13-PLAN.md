## Recorded planning decisions

- **Registry reads.** `latestForRequest(requestId, viewerDocumentId)` in the questionnaire registry returns the active job for the request, else the retained terminal job with the latest `queuedAt`, as `{ job: publicJob(job), canRetry: viewerDocumentId === job.initiatingAnalystDocumentId }`, or `null`; it runs `cleanup()` first and does not call `authorize` or touch `lastAccess`. `latestForQuestionnaire(questionnaireId, viewerDocumentId)` in the draft registry does the same through `jobsByQuestionnaire`.
- **Workflow.** `getRequestGenerationJobs({ strapi, requestId, viewerDocumentId })` in `questionnaire-generation-workflow.ts` throws 404 for a missing request, projects the questionnaire job with `projectQuestionnaireGenerationJob` (loading the generated questionnaire for a completed job, as `job()` does), and asks `assessment-workflow.ts` for the draft job through a new exported `latestAssessmentDraftJobForQuestionnaire(strapi, questionnaireId, viewerDocumentId)` that uses `projectAssessmentDraftJob`.
- **Spec schemas.** `RequestGenerationJobsResponse` wraps `RequestGenerationJobs` (both properties required, each `null` or an object `{ job, canRetry }` referencing `QuestionnaireGenerationJob` and `AssessmentDraftJob`), all closed. The path copies the by-id job read's parameters, tag and error responses (`QuestionnaireBadRequest`, `QuestionnaireForbidden`, `QuestionnaireNotFound`), with operationId `questionnaire-generation/get-request-generation-jobs`.
- **Web parser.** `requestGenerationJobsResponseSchema` reuses the two closed job schemas. Their identifier bounds are grandfathered today under `getQuestionnaireGenerationJob` and `getAssessmentDraftJob`; the new label must not join `boundaryGrandfathered`, so register each boundary path the parity guard reports in `narrowedPaths` with the reason "reuses the closed job parsers, whose identifier bounds the by-id job operations declare later (D-27, Phase 13)".
- **Second analyst.** The harness creates `second.analyst@example.test` with the Security Analyst role, active, as identity `second-analyst`, exposed as `identities.secondAnalyst` and `users.secondAnalyst`. No matrix actor is added; the matrix keeps its six actors.
