# Phase 10 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

**Source and scope.** Seeded on 2026-09-27 from `10-RESEARCH.md` § "Validation Architecture", before any plan exists. It maps every requirement, finding and decision to an automated proof:
- the seven requirements: REQ-07, QUES-08, QUES-09, ASSESS-06, ASSESS-07, ADMIN-05 and UX-06;
- all 23 findings;
- the locked decisions D-01 to D-48 in `10-CONTEXT.md` (D-41 to D-48 were recorded after the first plan check: the orchestrator's decisions on the plan check's blocker, and the delegated decisions that change this phase).

**How the maps are filled.**
- **Per-task map:** the planner replaced the research's fifteen seeded rows with one row per task of the 23 plans (`10-01-01` to `10-23-03`), taken from each task's `<automated>` verify block (the gate's checkpoint row names its resume signal instead); the plan check verifies them (Dimension 8).
- **Plan numbering:** the plans split the research's fifteen suggested plans into 23 (serialised by shared files, D-40). `10-UI-SPEC.md` §19 names plans by the research numbering; each plan states which §19 rows it changes. Research to final: 10-01→10-01; 10-02→10-02; 10-03→10-03; 10-04→10-04; 10-05→10-05; 10-06→10-06 (codes) and 10-07 (copy); 10-07→10-08; 10-08→10-09; 10-09→10-10, 10-11 and 10-12; 10-10→10-13 and 10-14; 10-11→10-15; 10-12→10-16 and 10-17; 10-13→10-18, 10-19 and 10-20; 10-14→10-21; 10-15→10-23 (the phase gate). Plan 10-22 (control titles, D-46) has no research counterpart: decision 15 moved the titles into Phase 10 after research.
- **Order:** every plan runs alone in its own wave, plan 10-NN in wave NN. The first plan set ran two plans in each of waves 1 and 2; they now run one at a time (`depends_on` makes 10-02 follow 10-01 and 10-04 follow 10-03), because each runs Playwright on the same E2E ports, SQLite file, Next build and `apps/strapi/dist` (orchestrator execution note, 2026-09-27).
- **Markers:** "❌ W0" marks a test file that the owning plan's first RED task creates (the project convention).
- **Status:** every status starts as ⬜ pending.

**Known infrastructure facts.**
1. **Shared `dist`:** the orchestrator's dev Strapi (1337) and Next (3000) are running during planning. Anything that compiles Strapi shares `apps/strapi/dist`: the Strapi suite, a single Strapi file and `served-operations:write`. So does a Playwright run. All of these wait until the servers are stopped. A task executed while they run records those proofs as pending for the plan's end.
2. **No hosted AI:** automated suites pin the deterministic provider, and no proof calls the hosted provider. Unit fixtures cover the hosted provider's section layout (`section-N` from order 0), not live generation (see Manual-Only).
3. **Jobs are process-local:** generation and draft jobs do not survive a Strapi restart (R-08-36). No E2E relies on a job outliving a restart.
4. **Generated file:** `apps/web/next-env.d.ts` is untracked and ignored (`.gitignore:6`).
5. **Windows vitest:** vitest can fail with `EPERM: rename`. Rerun that file alone before treating it as a real failure.
6. **Fixtures:** the questionnaire and release journeys use one-shot seeded fixtures. New Phase 10 journeys create their own records through the UI, as `questionnaire-generation-workflow.spec.ts` does (the 06.9 lesson).
7. **Clean tree (D-48):** a Playwright run leaves the tree clean by design (`apps/web/playwright.config.ts:31-38`, Phase 8 D-12). No plan restores a file after a run; each checks that `git status --porcelain` shows nothing the run changed, and a dirty tree is a harness defect to record and report.
8. **Seeded library:** the mounted harness and the E2E run seed the full 2,646-control library through `seedCsrmData`, so after plan 10-22 every seeded control in a test database carries a title.

## Sampling Rate

- **After every task commit:**
  - Run the touched web test files by path (under 20 s each).
  - Run `typecheck` when types change, and `api:check` after any spec change.
  - Run the touched Strapi files by path only with the dev servers stopped; otherwise record them as pending for the plan's end.
- **After every plan wave:**
  - Run the full web suite, `typecheck` and `api:check`.
  - Run the full Strapi suite after every plan that edits Strapi: 10-06, 10-10, 10-11, 10-13, 10-15, 10-16, 10-17, 10-18 and 10-22.
  - Run each plan's targeted Playwright specs once at its end.
  - Plans 10-01 (the shell's time-zone sync), 10-03 (the shared radio wrapper) and 10-08 (guarded navigation links) end with one full Playwright run, because every journey passes through what they change.
- **Before `/gsd-verify-work`:** full suite must be green. That means the phase gate above (plan 10-23), recorded with counts, duration, flaky count and the empty `git status`, followed by the orchestrator's browser walk (plan 10-23 Task 2, a blocking checkpoint).
- **Max feedback latency:** 90 seconds at task level. The production-build E2E runs only at plan level. A plan's closing task that runs a full suite or a production-build journey is that plan's plan-level gate; the orchestrator accepted that latency on 2026-09-27 (plan check Warning 6).
