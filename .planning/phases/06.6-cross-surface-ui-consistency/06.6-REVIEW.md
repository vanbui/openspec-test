# Phase 06.6: Code Review Report

**Reviewed:** 2026-09-11T00:00:00Z
**Depth:** deep
**Files Reviewed:** 61
**Status:** issues_found

## Summary

Reviewed the committed Phase 06.6 changes since `b89c520` and the stated working-tree additions. Record-link targets and the route-level service-before-fixture order were checked across the scoped surfaces. No confirmed authorization bypass was found in those routes. Four warning-level defects remain in the reusable table/state contracts and their regression coverage.

## Warnings

### WR-01: Optional sorting capability can remain disabled after its handler is supplied

**File:** `apps/web/src/components/csrm/data-table.tsx:175-196`

**Issue:** `tableColumns` derives `enableSorting` from `onSortingChange`, but the memo only depends on `columns`. A caller that initially renders a stable column array without a handler (for example while its capability/data state resolves) and later provides one retains columns with sorting disabled. The component exposes optional capabilities specifically for reuse, so this is a real backwards-compatibility failure for dynamic callers.

**Fix:** Include `onSortingChange` in the memo dependencies, or build column metadata independently of the handler and gate the click handler separately. Add a test that rerenders with the same `columns` reference and changes `onSortingChange` from absent to present.

### WR-02: The list-state guard can be bypassed by an ordinary feature-owned component

**File:** `apps/web/scripts/verify-shared-list-states.mjs:12-52`

**Issue:** The guard rejects only a narrow helper-name pattern and literal HTML tags inside `stateSlots`. A feature can define `const Notice = () => <section ...>` (or import a feature-local component) and use `stateSlots={{ empty: <Notice /> }}`; neither regex matches, so the guard reports no violation even though the list state is feature-owned. This undermines the stated regression guarantee and makes future drift easy to introduce.

**Fix:** Parse the TSX AST and require each `stateSlots` value to resolve to an approved shared-state primitive, or at minimum add a conservative component-reference detector plus a negative fixture for a locally defined, neutrally named component.

### WR-03: Fixture authorization test does not exercise the Requestor isolation claim

**File:** `apps/web/src/lib/testing/e2e-ui-state-route-authorization.test.tsx:43-55,73-85`

**Issue:** Every case sets the session to `Security Analyst`, and the route services are replaced with mocks that return either success or a prebuilt 403. The test consequently proves only that a mocked service result is consulted before the fixture selector; it does not prove the required Requestor case cannot receive analyst-only records. A service/route regression that returns analyst data to a Requestor would still pass this matrix.

**Fix:** Add a Requestor-session case for each restricted review/administration route using the real authorization boundary or capability-aware service double. Assert the service denial occurs before fixture resolution, no fixture boundary is rendered, and no restricted record title/identifier is present.

### WR-04: Error and permission fixtures expose nested assertive live regions

**File:** `apps/web/src/lib/testing/e2e-ui-state.ts:57-61`; `apps/web/src/components/states/states.tsx:95,111`

**Issue:** `E2eUiStateBoundary` gives error and permission fixtures `role="alert"`, while `ErrorState` and `PermissionDeniedState` each render their own `role="alert"`. The newly wrapped fixture paths therefore contain nested assertive live regions, which can announce the same failure twice or interrupt itself in assistive technology.

**Fix:** Let the shared state primitive own alert semantics. Make the harness boundary a neutral `div`/`section` with only `data-ui-state` for error and permission, retaining its loading status behaviour if needed. Add a DOM assertion that each fixture has exactly one alert.

## Unconfirmed Concerns

None. The authorization and data-loading order in the reviewed server routes was confirmed statically: service resolution precedes fixture selection, and authoritative errors return outside the fixture boundary.

## Resolution

All four warnings were confirmed and fixed before the phase closed.

- **WR-01 — fixed.** `sortable = Boolean(onSortingChange)` drives `enableSorting` and is part of the column memo key. A new unit test rerenders with the same `columns` reference and checks that a handler supplied after the first render enables sorting.
- **WR-02 — fixed.** The guard now resolves every component rendered inside a `stateSlots` object: it must be a shared primitive, or a same-file wrapper whose body renders a primitive and no state markup of its own. Neutrally named local components and imported components are reported as feature-owned. Fixture cases cover both bypasses and the legitimate wrapper; the real source stays clean.
- **WR-03 — fixed.** The fixture authorization test now signs in as the Requestor for every restricted route. Administration is denied at its capability gate, with no service read, fixture resolution or fixture boundary. The three review routes have no page-level gate by design (Strapi is the authority), so their cases use the service denial Strapi returns to a Requestor and assert that the fixture selector never runs, no boundary renders, a permission alert shows, and no restricted record appears.
- **WR-04 — fixed.** The E2E fixture boundary no longer sets `role="alert"` or a label on error and permission states, so the shared primitive is the only alert; loading keeps its busy status region. The conformance suite now asserts exactly one alert inside each failure boundary.
