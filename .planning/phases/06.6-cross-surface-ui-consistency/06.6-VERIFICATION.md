# Phase 06.6: Cross-Surface UI Consistency Verification Report

**Phase Goal:** as either actor, the same kind of thing looks and behaves the same way on every screen
it appears on, so that what is learned on one list transfers to the next.

All six criteria are met. Following the scope decision for this phase, every criterion is verified by
comparing surfaces against each other, not by checking each screen alone.

## Criteria

| # | Criterion | Status | Evidence |
|---|---|---|---|
| 1 | Record links resolve to the same computed colour and decoration at rest on every list surface, compared across surfaces | **Met** | `design-contract.spec.ts` compares `a.record-link` colour, weight, decoration line and decoration colour on eleven list surfaces and dashboard record links against the first surface, at 1440px and 375px, then checks the reference against `--text-link`. |
| 2 | No record type renders as a card on one surface and a table row on another at the same breakpoint | **Met** | Every list surface renders through DataTable. The comparative suite asserts the desktop table at 1440px and the labelled card list (`role="list"` of `role="listitem"`) at 375px on all eleven surfaces. |
| 3 | No hand-rolled empty, error, permission or loading block remains under `src/features/` | **Met** | The list-state guard runs in the unit suite over real source and reports nothing. It resolves every component rendered in a state slot, so neutrally named or imported components cannot bypass it. The comparative suite asserts that each surface's empty, error and permission fixture renders the shared primitive with identical heading typography and the same recovery control. The dashboard widget empty states were also migrated. |
| 4 | Scrolling the Risk Register horizontally keeps the row identifier visible; eight-column density stays usable at 1440px | **Met** | At 1024px the labelled, focusable region is the element that overflows and scrolls, and every visible identifier cell stays within its bounds. | 6 | The design-contract harness asserts criteria 1–5 plus the 06.5 type and casing contract, and fails on regression | **Met** | `design-contract.spec.ts` asserts criteria 1–5. ## Automated Evidence

- `design-contract.spec.ts` 2/2 and `design-system-conformance.spec.ts` 3/3 pass in the isolated Playwright harness, including axe (serious and critical) and console-error checks.
- Unit suite: all files pass, including the guard, DataTable, state-primitive and route-authorization suites. Typecheck and lint pass.

## Browser Verification

Checked against the development stack in a real browser at 1440px, 1024px and 375px:
- **Requestor:** My Requests, My Questionnaires, My Risk Assessments and the dashboard.
- **Security Analyst:** both analyst review lists, questionnaire review, the Risk Register and Administration.

No console errors appeared. This found defects that no unit test caught, and all were fixed before commit:
- DataTable row dividers drew in the text colour.
- Mobile cards ran the identifier and title together.
- The labelled Risk Register region was not the element that scrolled.
- The table state wrapper nested two frames.
- The app icon was missing, which logged a console error on every page.

## Code Review

`06.6-REVIEW.md`: no critical findings and four warnings. All four are fixed, and each fix has tests:

- Nested fixture alerts.

## Deviations

- **The 06.5 type contract lives in the conformance spec.** The comparative spec covers criteria 1–5 and does not duplicate the conformance suite's document-driven type parser; two parsers of the same values would drift. The harness is the pair of suites.
- **No UI-SPEC.** The design direction remained the sole value-bearing authority, and `06.6-CONTEXT.md` carried the per-surface decisions.
