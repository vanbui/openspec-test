## Phase Goal

**As a** Requestor or Security Analyst, **I want to** have a sectioned sidebar and a Home that leads with my next action, **so that** I always know where my work is and what to do next.

This plan's slice: a person's own requests can be listed by who holds each one, from the server, so Home and My requests can separate "Needs your action" from "With the Security Analyst".

<objective>
Serve the catalogue-reserved `GET /v1/my_requests` (D-03) with an owner predicate from the policy and a holder predicate built from the review queue's lifecycle facts (D-02 item 6, D-20), projecting each item's holder, stage, next action, age, return facts and questionnaire progress; add holder counts to the status summary; and complete the chain: specification, generated client, closed web parser and service function, catalogue note in both copies, served-operations inventory and the six-actor matrix row.

Purpose: UAT-003. The stored status alone cannot say who holds a request (`questionnaire-in-progress` covers three holders); this operation gives Home, My requests and the sidebar counts one server definition.
Output: the route, controller and service with integration proofs; `byHolder`; the contract chain; `listMyRequests` and its parser.

Edits Strapi? Yes. Changes the specification and the catalogue? Yes, alone in its wave (D-05). Runs Playwright? No (the operation's first web surface is plan 11-11).
</objective>

## Recorded planning decisions

- **Reuse, do not copy (research Pattern 4).** Export `questionnaireReleased`, `questionnaireSubmitted` and `assessmentExists` from `review-queue-repository.ts` (they take a knex sub-query builder and alias the outer request as `r`). `applyRequestHolder(query, holder)` in `services/my-requests.ts` composes them with `REVIEWABLE_REQUEST_STATUSES` and `RELEASED_REQUEST_STATUSES` from `collection-scope.ts`.
- **Owner predicate.** The controller reads `ownRequestorId(ctx.state)` as `my-request-status-summary.ts` does (403 when the scope is not `own`); the service joins `csrm_assessment_requests_requestor_lnk as o` on `o.csrm_assessment_request_id = r.id` and `o.idambox_user_id = requestorId`. No query value reaches the owner check.
- **Read path.** Count and page ids in SQL (owner + holder + status + `q` as `(LOWER(r.request_number) LIKE … OR LOWER(r.title) LIKE …)` with the queue's `literalContains` and `ESCAPE '!'`), order by the sort's column with the id tiebreak, then hydrate the page with `REQUEST_RELATIONSHIP_POPULATE` (`relationship-scope.ts`) and project each document with `projectRequestLifecycle(document, ctx.state)`.
- **Item.** `MyRequestItem = { documentId, requestNumber, title, requestStatus, submittedDate, dueDate, updatedAt, daysSinceSubmission, holder, stage: { key, label }, nextAction: { summary, href? } | null, returned: { reason: string | null; at: string } | null, questionnaire: { documentId, answered, total } | null }`. `holder` is the lifecycle's `holderFor(currentKey)` (equal to the SQL by test); `stage` is `{ key: currentKey, label: currentLabel }`; `returned` is set for a `draft` with `revertedAt`; `questionnaire` is set only when the relationship projection marks the questionnaire available to the viewer, with the counts from the questionnaire scope's existing progress projection (export it from `questionnaire-scope.ts` if it is module-private). No assessment field is projected.
- **Design note 9.** In both catalogue copies, remove `my_requests` from note 9's list of reserved `/api/v1` request aliases served through the core routes and append: `Phase 11 serves GET /api/v1/my_requests as reserved, under the Requestor's My Requests Function, owner-scoped by the policy; it lists the caller's own requests with their lifecycle holder.` Edit one copy and copy the file over the other.
- **Matrix row.** Mirrors the status summary's row: `expect: everyIdentity(200)`, `ownedRecordTotal: ownedByRequestorsOnly`, `mustNotDisclose` listing every other actor's request ids, and a `seeAlso` naming the new integration test.
