## Phase Goal

**As a** Security Analyst, **I want to** tell the AI what to add, change or remove in a questionnaire and to have it propose follow-up questions without touching answered ones, **so that** the question list keeps up with new information while I stay in control.

This plan's slice: the run record holds questionnaire proposal runs and the AI reads exactly the right context for them: the request, the marked notes and files, and the questionnaire with its answered questions fixed, with the instruction in its own slot.

<objective>
Extend Phase 12's run record and context builder for the two operations (D-14, D-17, D-19, D-20): the run operations, per-operation envelope parsing and the append of decision events v2; the context summary's Phase 15 version with its questionnaire and instruction sections, carried by the run read, the specification and the web parser; the pure questionnaire part with its allowed sets and bounds; the loader for both operations (answers only for a submitted batch, the proposal history, marked notes and opted-in files); and the non-empty `analystInstruction` slot.

Purpose: QUES-12 criterion 1 (the proposal uses the request, the marked notes and the answered questions as fixed context) and QUES-11 criteria 3 and 4 (the run records the instruction; the instruction travels in its own slot, never mixed with Requestor text).
Output: one new module, four extended Phase 12 modules, the run read contract change, and their tests.

Edits Strapi source? Yes. Changes the specification? Yes (the run read). Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Per-operation parsing.** `parseRunProposalFor(operation, value)` and `parseRunDecisionsFor(operation, value)` dispatch: `questionnaire-proposals` and `question-rewrite` use `parseQuestionnaireProposal` and `parseQuestionnaireDecisionEvents` (15-02); the Phase 12 operations keep `parseRunProposal` and `parseRunDecisions` (v1). `appendAiRunDecisions(strapi, runId, events)` loads the run's `operation` and validates both the stored log and the appended events through `parseRunDecisionsFor`; a v1 event on a questionnaire run, or a v2 event on a Phase 12 run, is refused with `AiRunRecordError` and nothing is written.
- **Summary version.** `ContextSummaryV4` (the number 15-01 recorded) = Phase 14's version plus `questionnaire: { scope, questionsOffered, answered, answerContent, openItemsListed, rejectedItemsListed, rejectedItemsTotal, removedListed } | null` and `instruction: { source: "analyst" | "plain-language-preset" | "default-task" } | null`. `buildAssessmentContext` always emits it; generation and draft runs carry `questionnaire: null`; generation carries `instruction` (`analyst` or `default-task`), the draft `null`. `parseContextSummary` accepts every earlier version and projects them with both new keys null.
- **Run read.** `AiRun.operation` enum gains the two operations; `AiRunContextSummary.schemaVersion` gains the new value; `AiRunContextSummary` gains required nullable `questionnaire` (`AiRunContextQuestionnaire`, closed) and `instruction` (`AiRunContextInstruction`, closed). `AiRun.instruction` (12-10) already carries the text.
- **Questionnaire part** (`buildQuestionnaireProposalContext(input)`, pure). Input: `scope`, `targetQuestionDocumentId` (rewrite), the questions in display order (active and removed, each with `documentId`, `questionKey`, section `{ key, title, order }`, `order`, `questionText`, `helpText`, `answerType`, `choices`, `required`, `visibility`, `removed`, `answered`, and `answerLabel` only when answer content is included), `answerContent` (`included` or `withheld`), `openItems` (proposed texts and kinds), `rejectedItems` (proposed text, reason, decided-at), `instructionSource`. Output: the `referenceData` sections (questions as `Q1…Qn` in display order with `answered="yes"` or `"no"`, section titles, answer types, choice labels, required flag and visibility as `Qn equals {label}`; already proposed as `P1…`; rejected by the analyst as `X1…` with their reasons, the 100 most recent first; removed by the analyst as `R1…`), the `answers` `RequestorDataSection` (submitted answers only, by `Qn`), the allowed sets (`ProposalAllowedSets` plus `refs: Map<"Qn", documentId>`, `answeredRefs`, `removedDocumentIds`, `controllerChoiceLabels: Map<"Qn", label[]>`, `sourceRefs` = request fields, `note-{n}`, `file-{n}`, answered `Qn` and `instruction`) and the summary section. Rewrite scope: the target and its section in full, other active question texts only, no answers, no lists. No names, ids, dates or record numbers in any rendered text (Phase 12 D-04).
- **Bounds** (`QUESTIONNAIRE_CONTEXT_BOUNDS`): `activeQuestions: 150`, `openItemsListed: 200`, `rejectedItemsListed: 100` (ranked, with the total in the summary, never silent), `removedListed: 200`; any other excess throws `AssessmentContextTooLargeError`, and the prompt still meets `CONTEXT_BOUNDS.questionnairePromptCharacters`.
- **Loader.** `buildAssessmentContextFor(strapi, { operation, requestId, questionnaireId, targetQuestionId?, instruction, instructionSource })` for the two operations reads the questionnaire with its questions, the answered flag from `isAnsweredValue`, answer content only when every active visible question holds a submitted envelope (`projectQuestions`' submitted-batch rule), and the questionnaire's completed runs of the two operations (at most 101, Document Service filtered by `questionnaire.documentId`, `operation $in`, `status: "completed"`, fields `documentId`, `operation`, `proposal`, `decisions`) to derive open and rejected items through the fold, skipping damaged runs; it includes the request part, the selected systems and assets and the Risk Type library for `questionnaire-proposals` only, and the marked notes (13-16) and opted-in file text (Phase 14) for both.
- **Slot.** `renderAnalystInstructionSlot(instruction: SlotInstruction | null)` returns the empty string for null and `promptDataTag("analystInstruction", instruction)` otherwise; the tag name is a code constant.
