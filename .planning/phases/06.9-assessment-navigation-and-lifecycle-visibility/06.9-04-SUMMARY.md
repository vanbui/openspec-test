# Phase 06.9 Plan 04: GAP-1 Closure, Every Offered Status Filters Summary

**Every status the two Analyst list filters offer now returns a filtered or empty list instead of the error state. The server accepts the complete vocabularies but never widens what a queue reads: a request status outside the selected queue is answered with an empty page and a total of 0 before any record is read. `closed` is accepted inside the analyst assessment scope. The Released queue's records now parse. The contract, generated client and typecheck carry and enforce the vocabularies.**

GAP-1 in `06.9-VERIFICATION.md` found that 06.9 D-1 was only half wired. The filters listed all seven request statuses and all four assessment statuses, but the published contract and Strapi accepted only the per-queue sets. So choosing, for example, Approved under "Requires my attention" returned HTTP 400, and the list rendered "We couldn’t load assessment requests". Two `as never` casts on the list calls hid the mismatch from typecheck.

Executing the plan's browser proof exposed a second gap on the same path. The Released queue's response item was published, and parsed by the closed client schema, with only the four reviewable statuses. So any populated Released queue rendered the error state too. That is fixed here as a recorded deviation.

## Accomplishments

- **Server intersection:** `collection-scope.ts` validates `filters[requestStatus]` against all seven datamodel statuses. The three action queues read only the four reviewable statuses and the Released queue only approved and closed. No queue reads a draft.
  - `buildAnalystReviewCollectionQuery` returns a discriminated result.
  - A status outside the queue gets `kind: "outside-queue"`, carrying pagination and no query. The controller answers an empty page from it.
  - Anything that is not exactly one known status is still 400: unknown, wrong-case, empty, repeated, or an operator object.
- **Closed assessments:** `ASSESSMENT_STATUSES` is the four-value datamodel vocabulary, so `status=closed` is accepted on the analyst list. The owner list keeps its released-owner predicate.
- **Contract:**
  - `specification.json` publishes the seven-value `filters[requestStatus]` enum on `GET /v1/assessment_requests`, and the four-value `status` enum on `GET /v1/risk_assessments` and `GET /v1/my_risk_assessments`. Each carries a description of its scope semantics.
  - `AssessmentRequestQueueItem.requestStatus` publishes the six statuses a queue returns.
  - `schema.d.ts` is regenerated, and `api:check` is clean.
- **Parser:** `assessmentRequestQueueItemSchema` accepts approved and closed, matching the published item. A populated Released queue now lists its requests.
- **Typecheck enforcement:**
  - The three list calls in `assessment-service.ts` no longer cast, and `collectionParams` returns the generated query-parameter type.
  - Proven: restoring the pre-fix generated client makes typecheck fail with TS2322 on both call sites.
- **Tests that select values:**
  - **Unit:** a builder matrix (4 queues x 7 statuses), with rejection and validation-order checks; a four-status assessment builder test for both scopes.
  - **Mounted:** a dedicated queue-status fixture covering every queue x status combination, including drafts owned by both Requestors, plus a closed-assessment test.
  - **Contract:** the published filter enums equal the content-type enums, the queue item publishes every status a queue reads, and the generated unions match.
  - **Web:** every rendered option flows through navigation, the parser and the service to a published value; route content renders the shared empty-filter state for a 200 empty page; the Released queue parses and lists approved and closed requests.
  - **Browser:** Approved under "Requires my attention" and Closed on the assessment list show the empty-filter state, and the same status in its own queue lists its record.

## Decisions Made

- **Intersection with no query.** The outside-queue result has no `dataQuery` or `countQuery` property, so the controller cannot issue one. The unit matrix asserts both properties are absent. Validation of pagination, the other filters and the sort still runs first, so a malformed request with an outside-queue status is 400, not 200.
- **Closed is in scope.** Recorded in `assessment-scope.ts` beside the vocabulary.
- **Datamodel as the source of the vocabularies in tests.** The unit and contract tests read the enums from the frozen content-type `schema.json` files. The published and served vocabularies are therefore checked against the datamodel, not restated. No content-type file changed.
- **Dedicated, non-memoized fixtures** for the mounted tests (the 06.8 lesson). The closed-assessment test is the last test in its file because a closed assessment changes the totals that the earlier status-summary assertion sums.
- **Precise queue item vocabulary.** The response item publishes six statuses, not seven, because a review queue never returns a draft. Its closed parser matches exactly.

## Deviations from Plan

1. **[Rule 1/3: bug blocking the gap's truth] The Released queue's response item rejected the records it returns.**
   - **Found during:** Task 3's targeted Playwright run. The new test's non-vacuity check chose Approved in the Released queue and got the error state.
   - **Issue:** `AssessmentRequestQueueItem.requestStatus` (`specification.json`) and `assessmentRequestQueueItemSchema` (`assessment-schema.ts`) allowed only the four reviewable statuses. The Released queue (06.8 D-12) returns approved and closed requests, so any populated Released queue, with or without a status filter, failed the closed parse and rendered "We couldn’t load assessment requests". This predates 06.9. The 06.8 and 06.9 filter tests only checked option labels, so it was never exercised.
   - **Fix:** RED in `e14891e` (web parse and route tests, and a contract assertion), then GREEN in `47ec90e`. The item publishes every status a queue reads (all but draft), the client is regenerated, and the closed parser is widened to match. No server code and no content-type changed.
   - **Verification:** the full suites and the targeted Playwright run above, including the in-queue record check.
2. **A third cast removed and the owner enum widened.** The orchestrator named two `as never` casts. The owner-collection call (`listMyReleasedAssessments`) used the same `collectionParams` helper and the same server validator. Widening only the analyst enum would have left `GET /v1/my_risk_assessments` published narrower than the server. That endpoint's enum was widened with a description of its released-only intersection, and its cast was removed. A mounted test proves the owner scope is unchanged. This was recorded in the plan's scope findings before execution.
3. **RED test order adjusted before the first RED commit.** The first run of the builder matrix failed on the new `kind` field rather than on the gap. The loop was reordered so RED failed on the gap's reason: a valid status rejected with `AssessmentRequestQueryError`. No assertion changed.
4. **One docs commit.** The plan, this summary, the verification update and the roadmap entry are committed together, as the orchestrator directed, rather than in a separate plan commit.
5. **STATE.md not touched.** The orchestrator owns it, so the executor's state-update steps were skipped.

**Total deviations:** 5. Item 1 is a correctness fix without which GAP-1's truth ("any status, in any queue, returns a filtered or empty list") could not hold for the Released queue. Item 2 is a small, contract-consistent extension of G-4. None reduces scope.

## Issues Encountered

- **An existing coupling, noted and not changed.** `projectAssessmentStatusSummary` counts every assessment in `total` but has buckets only for draft, in-review and approved. So `total` exceeds the bucket sum once a closed assessment exists. No product flow closes an assessment today. The existing mounted assertion `total == draft + inReview + approved` holds only because no closed assessment exists when it runs, which is why the new closed-assessment test runs last.
- **Line endings.** The working tree is CRLF with an LF index (`core.autocrlf=true`). The generator and appended test blocks wrote LF; git normalises on commit. After `api:check` the generated file showed as modified with no content diff, and it was restored with `git checkout --`.
- **Unrelated working-tree changes left alone.** Three `.planning` files for 06.7 and 06.8 were already modified before this plan started (timestamps 19:20 local). They were not staged or altered.
- **Concurrent load.** Another checkout outside this repository was running its own Playwright suite and dev servers during this plan. No process used this repository's ports or `apps/strapi/dist`. Every run here passed without retries.
