<interfaces>
Canonical served operation contract from `CSRM_ASSESSMENT_REQUEST_OPERATIONS`:
- `GET:/api/csrm-assessment-requests`
- `POST:/api/csrm-assessment-requests`
- `GET:/api/csrm-assessment-requests/{id}`
- `PUT:/api/csrm-assessment-requests/{id}`
- `DELETE:/api/csrm-assessment-requests/{id}`

Existing grant resolution contract:
- `loadEffectiveGrants` combines the implicit Requestor Role with explicitly assigned Roles.
- `hasOperation` grants an operation only through a FunctionAPI whose `url` exactly equals the route operation.
- `hasExplicitAnalystOperation` recognizes only explicit `Security Analyst` and `Security Analyst Agent` Roles carrying the exact operation.
- The DELETE route already supplies `CSRM_ASSESSMENT_REQUEST_OPERATIONS.delete` and `requireRequestOwnership: true`; once Requestor lacks the DELETE FunctionAPI, the policy denies before ownership can grant access.

Required catalogue split:
- Keep `function.risk_assessment_requests.core_api` API-only and assign it to Requestor, Security Analyst, and Security Analyst Agent with only the four canonical GET/POST/GET-item/PUT FunctionAPIs.
- Create `function.risk_assessment_requests.delete_api` as a second API-only Function with no `menuPath`, assign it only to `role.security_analyst` and `role.security_analyst_agent`, and attach one FunctionAPI named `function.risk_assessment_requests.delete_api.api.01` for `DELETE:/api/csrm-assessment-requests/{id}`.
- Keep Role `functionIds`, Function `roleIds`, Function `functionApiIds`, and FunctionAPI `functionId` reciprocal and seedable.
</interfaces>
