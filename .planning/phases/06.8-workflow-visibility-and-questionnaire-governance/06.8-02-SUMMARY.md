# Phase 06.8 Plan 02: Withdrawn Review on Edit Summary

An accepted analyst edit to an assessment that was already reviewed and release-ready now
stores `assessmentStatus` `draft`. The release operation therefore refuses it with the
existing 409, because `validateReleaseReadiness` reports `assessmentStatus` outstanding —
a derived "not release-ready" label would have left that gate passable. The reviewer of
record is never cleared, so the assessment persists `draft` together with a non-null
`reviewedBy`, which is unreachable for an assessment that was never reviewed and is the
durable evidence that a completed review was withdrawn by a later edit.

`transitionForAcceptedEdit` is now an explicit table over four accepted combinations and
throws the existing 409 for everything else. The trigger is deliberately narrow: only an
`in-review` assessment on an `under-review` request that was release-ready before the edit
regresses. An edit to an incomplete assessment behaves exactly as it did before this plan,
and the `draft`-on-`under-review` branch is the fresh-review pass that returns a regressed
assessment to `in-review`, so nothing can be stranded in a state it cannot leave. The
request lifecycle never regresses; `requestStatus` stays `under-review` in every accepted
branch.

The supersession of the Phase 4 state precedent is recorded in a comment above the
function, naming D-04 and D-13, so a future reader does not read it as an accidental
regression. Per D-16 the transition is audited by the edit record itself and prompts for no
free-text reason.

The analyst who caused the withdrawal is now told so in words: a drafted assessment that
still carries a reviewer renders a non-dismissible notice naming the superseded reviewer,
stating that the assessment returned to drafted and that saving it again records a fresh
review. The release affordance was already gated on `in-review`, so the regression
withdraws it with no change, and the notice adds no control that could release or re-review
without a real save.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - Bug] The shared mounted release-readiness helper left the assessment in `draft`**

- **Found during:** Task 2, on the first integration run after the transition change.
- **Issue:** `completeMountedReleaseReadiness` patches the assessment metadata and then
  every Risk in list order. The contextual Risk created earlier in the suite already had a
  control implementation, so it was already complete. Once the generated Risk was patched,
  the assessment was release-ready, and the helper's final Risk PATCH was itself an
  accepted edit to a release-ready assessment. Under the new table that edit correctly
  stored `draft`, so the pre-existing release test failed with
  `RELEASE_SECOND_WRITE_FAILURE_NOT_OBSERVED (409 !== 500)` and, in cascade,
  `OWNER_NEW_RELEASE_MISSING`.
- **Fix:** The helper now reads the assessment after completing the Risks and, when it
  observes the regression, takes the fresh-review pass with one further accepted edit,
  asserting that the status returns to `in-review`. It checks the actual stored status
  rather than assuming an edit parity, so it is deterministic. The helper's contract —
  "in-review and release-ready" — is restored, and no release assertion was weakened.
- **Files modified:** `apps/strapi/tests/assessment-workflow.integration.test.ts`
- **Commit:** `6aa2b4e`

### Plan corrections

**2. The plan's `<automated>` verify commands are not runnable from the repository root**

The plan gives `node --test … apps/strapi/.tmp/tests-dist/tests/<file>.js` from the
repository root. The unit file runs correctly that way, but the integration file boots
Strapi and resolves its API directory relative to the current working directory, so from
the root it failed with `ENOENT … C:\bproton\interns\csrm\src\api\csrm-assessment\routes\csrm-assessment.ts`
— the path with `apps/strapi` missing. The workspace's own `test` script runs from
`apps/strapi`, so the commands were run from there. This is the same class of defect as the
plan 01 gate, and the substantive check was unaffected once run from the right directory.

**3. The plan's mounted case needed its own aggregate**

The plan said to reuse the existing completion helper rather than write a second one, which
the new case does. It did not say which assessment to use, and the sequence ends in a real
release, so it could not consume `generatedAssessmentId`, which the concurrency release
test owns. The new case therefore generates its own draft from the unused
`jobTargets.completed` questionnaire. That questionnaire carries no mappable answer, so the
draft has no Risk; the case creates one minimal Risk through the existing contextual Risk
route and then hands the aggregate to `completeMountedReleaseReadiness`. No second
completion helper was written.

**4. The mutation reload was widened; the mutation response projection was not**

The plan said to widen "the mutation reload" to the release relation set. Only the
in-transaction reload that feeds the transition was widened, which is the reload that
computes readiness and the one the acceptance criterion is about. The separate response
reload in `updateAssessment` still uses `assessmentMutationPopulate`, deliberately, because
widening it would have added Risks and the requestor to the PATCH response body and changed
a published contract this plan is not allowed to change. `assessmentReleasePopulate` was
moved above `assessmentMutationPopulate` so the single constant is declared before both
uses.

### Deliberate non-changes

`transitionForAcceptedEdit` still accepts `draft` on a `risk-assessment-drafted` request
regardless of whether a reviewer is present, as it did before. Adding a reviewer check
there would have turned a previously accepted combination into a 409, which is a behaviour
change the plan did not ask for. The reviewer rule is expressed instead as "stamp the
acting analyst only when no reviewer exists yet", which keeps the documented outcome for
both shapes.

No Function grant, catalogue entry, contract operation, or generated client change was
needed or made. Plan 01 had already published the entire Phase 06.8 operation surface, and
D-13 adds no operation: it changes the stored result of an existing accepted edit.
