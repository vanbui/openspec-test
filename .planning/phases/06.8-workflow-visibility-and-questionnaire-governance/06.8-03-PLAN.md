<objective>
**As a** Security Analyst, **I want to** return a released or submitted questionnaire to analyst
review with a recorded reason, **so that** I can correct its questions without ever changing a
Requestor's questionnaire behind their back and without losing the record of what I did.

Purpose: D-15 collapses D-03 and D-06 into exactly one explicit transition. This plan builds that
one operation on the server, including the analyst-review gate that plan 04's question mutations
reuse, and the answer-state handling D-06's re-submission rule depends on.
Output: one mounted operation, one reusable gate, and mounted proof across all three actors.

Layering note: this plan is server-only because the web questionnaire feature files are owned by
plan 05, which lands the analyst controls for release, return-to-review and question editing in one
pass. The tracer below is still end-to-end — it drives the real mounted HTTP route through the
authorization policy, the locked transaction, and the SQLite data layer, and reads the result back
out of the database.
</objective>

## Locked decisions this plan implements

| Decision | How this plan honours it |
| --- | --- |
| D-15 | One explicit Analyst-only return-to-analyst-review transition. Question add, edit and delete are gated on the questionnaire being in analyst review; no edit ever causes an implicit backward transition. |
| D-03 | Only a human Security Analyst may perform it, enforced by the narrow Function grant published in plan 01 and by the policy's human-analyst operation set. |
| D-06 | After the return, the surviving valid answers keep their values as drafts, so after re-release the Requestor completes what changed and explicitly re-submits. |
| D-16 | A mandatory free-text reason is required, because this is one of the three standalone backward-transition actions. |
| D-02 | The transition moves only to the immediately preceding editable state, and the release history survives in the append-only log even though the current release facts are cleared. |
| D-14 | Clearing `releasedAt` and `releasedBy` is what makes the questionnaire analyst-only again; the gate keeps reading those fields and never the log. |

In `questionnaire-governance-workflow.ts` add `assertQuestionnaireInAnalystReview(questionnaire, request)`
and export it, because plan 04's three question mutations reuse it as their precondition. It throws
409 unless the release timestamp is absent, the owning request status is `submitted` or
`questionnaire-in-progress`, and the request has no linked assessment. Absence of the release
timestamp is the definition of "in analyst review" — the gate reads the authoritative fact and never
the event log.

Add and export `returnAnswersToDraft(definition, answers, now)`. It maps every envelope whose state
is submitted to a draft envelope carrying the same value and a fresh `updatedAt` with no
`submittedAt`, and leaves every other envelope untouched. Do not reuse `buildDraftAnswerBatch`: that
helper deliberately throws unless the whole active batch is submitted, which is correct for the
06.1 reversal operation and wrong here, because a released-but-unsubmitted questionnaire must also be
returnable. Leave `buildDraftAnswerBatch` and every existing reversal path unchanged.

Add and export `returnQuestionnaireToAnalystReview(input)`. It parses the mandatory reason with the
shared `parseRevertReason`, mapping its error to a 400 with the governance error class, so the
reason vocabulary and the 500-character bound stay identical to the two existing reversal
operations. It then runs inside the serialized locked transaction: reload the questionnaire with its
questions and its request populated, including whether the request has an assessment; call
`assertAnalystGovernanceActor` and `assertQuestionnaireInAnalystReview` inverted — that is, refuse
when the questionnaire is *already* in analyst review with 409, since there is nothing to return —
and refuse when the request has advanced past the questionnaire stage or already has an assessment,
which is what confines the move to the immediately preceding editable state; parse the question
definition and persist the answers `returnAnswersToDraft` produces; and finally perform one
questionnaire update that sets the release timestamp and the released-by relation to null and writes
the log value `appendGovernanceEvent` returns for a `returned-to-review` event carrying the reason.
Everything in one transaction: the cleared release facts, the draft answers and the appended event
must be atomic, so an interrupted return can never leave a questionnaire released with drafted
answers. Per D-02 the append is the only write to the log, so the prior release entry survives the
clearing of the current release facts and no later record ever deletes an earlier one; and per D-02
the refusal above is what confines the move to the immediately preceding editable state.

Add `returnToReview: "POST:/api/v1/questionnaires/{questionnaireId}/return_to_review"` to
`CSRM_QUESTIONNAIRE_OPERATIONS`, mount the route above the `/v1/questionnaires/:questionnaireId`
catch-all with a resource-scoped policy config and no Requestor release gate flag, and add a thin
controller handler that resolves the questionnaire id and the acting identity, passes the request
body through, and maps the governance error class through the existing `safeError` helper.

Extend the mounted integration test with one case that drives the whole path: release the fixture
questionnaire as the analyst, POST the return route with a reason, assert 200, and assert through a
database reload that the release timestamp and released-by relation are null, that the log has two
entries whose kinds are `released` then `returned-to-review` in that order with the reason on the
second, and that the owning Requestor's GET of the questionnaire is 403 again.
