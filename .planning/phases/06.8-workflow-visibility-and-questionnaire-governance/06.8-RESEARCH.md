# Phase 06.8: Workflow Visibility and Questionnaire Governance - Research

**Researched:** 2026-09-20
**Domain:** Server-authoritative workflow-state derivation, append-only audit/revision modelling under a frozen relational schema, and a shared actor-aware request hub (Next.js App Router + Strapi 5)
**Confidence:** MEDIUM — the codebase evidence is HIGH confidence (all claims below were read directly from source this session); the resolution of several D-01/D-02/D-04 ambiguities is a reasoned recommendation that needs a discuss-phase-style confirmation before the planner locks it in.

## Summary

Phase 06.8 is not a new vertical slice; it is a governance and visibility layer over three already-built aggregates (`CsrmAssessmentRequest`, `CsrmQuestionnaire`, `CsrmQuestion`, `CsrmAssessment`). The single hardest problem — and the one the roadmap already flags as a known contract gap — is that **the frozen schemas have no persisted concept of "questionnaire released to Requestor" and no persisted concept of a growing audit/revision history.** Today, a generated questionnaire is immediately visible and answerable by its owning Requestor the instant `generateQuestionnaire` completes — there is no release gate anywhere in the authorization policy, the routes, or the schema. The only audit precedent in the codebase (Phase 06.1's `revertReason`/`revertedAt`/`revertedBy`) is explicitly documented as "latest fact only, not a history" — insufficient for D-02's "later records are never silently deleted" and D-09's "dated timeline."

The recommended minimal-footprint path is two additive, optional attributes on the existing frozen-adjacent `CsrmQuestionnaire` content type (schema.json addition, requires a new `docs/contract-gaps/` record before implementation, following the exact Phase 06.1 precedent), plus **zero schema changes** for everything else: the D-01 stepper, the D-11 dashboard cards, and the D-12 review-queue filters are all derivable from data that already exists. D-08's answer-revalidation rule is a direct reuse of the existing pure function `isQuestionnaireValueValid`. D-07's "deleted question stays in audit history" rule requires *not* reusing the existing hard-delete pattern that questionnaire regeneration uses today, and instead extending the already-versioned `options` JSON envelope on `CsrmQuestion` with a soft-delete marker — which needs **no schema.json change at all**, because it only changes what the envelope's own JSON contents mean, exactly the way `answer.state`/`schemaVersion` already work.

**Primary recommendation:** Add one new optional JSON attribute `governanceLog` to `CsrmQuestionnaire` (an append-only, schema-versioned array of dated event envelopes — release, return-to-review, question-edited, question-deleted, question-added, answer-cleared, each carrying actor + reason + timestamp) under a single new contract-gap record. Derive "is released" from the log's most recent release-class event rather than adding a redundant boolean, consistent with the codebase's established pattern of deriving state instead of storing it. Extend `CsrmQuestion.options` (already a JSON envelope, already versioned) with a soft-delete marker instead of hard-deleting rows. Build the D-01 stepper, D-11 cards, and D-12 filters as pure derivations over existing `requestStatus`/`assessmentStatus`/answer-envelope data — no new fields needed there.

### Pattern 1: Derive, don't duplicate, workflow status
**What:** Every "is this record in state X" question is answered by a pure function over already-persisted fields, never by a newly stored redundant flag.
**When to use:** D-01 stepper step, D-05/D-06 "released" gate (recommended derivation), D-04 "reviewed vs drafted" display state.
**Example (existing precedent to imitate):**
```typescript
// Source: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-scope.ts:195-199
export function questionnaireState(document: RecordValue): QuestionnaireStatus {
  const questions = safeActiveQuestions(questionsOf(document)) ?? [];
  if (questions.length > 0 && questions.every((question) => isSubmittedAnswer(question.answer))) return "submitted";
  return questions.some((question) => hasValue(question.answer)) ? "draft" : "not-started";
}
```

### Pattern 2: Schema-versioned JSON envelope for compatible extension
**What:** A frozen relational schema's existing `json` attribute can grow new *envelope* fields (with a `schemaVersion` bump and a closed parser) without touching `schema.json` at all.
**When to use:** D-07's soft-delete marker on `CsrmQuestion.options`; any other per-question metadata this phase needs.
**Example (existing precedent to imitate):**
```typescript
// Source: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-definition.ts:110-119
exactKeys(options, ["schemaVersion", "questionKey", "section", "order", "required", "visibility", "choices"]);
if (options.schemaVersion !== 1 /* ... */) throw new QuestionnaireDefinitionError();
// D-07 extension: bump to schemaVersion 2 (or add an optional "deleted"/"deletedAt" key guarded by a
// backward-compatible parser branch) so existing questionnaires with schemaVersion 1 options remain valid.
```

### Pattern 3: Serialized, row-locked, transactional workflow mutation
**What:** Every workflow-state-changing mutation acquires a per-document in-process mutation queue AND a `SELECT ... FOR UPDATE` row lock inside a `db.transaction`, then re-validates authoritative state before writing.
**When to use:** The new release/return-to-review/edit-question/delete-question operations must follow this exact shape.
**Example:**
```typescript
// Source: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-workflow.ts:200-207, 353-381
async function runQuestionnaireMutation<T>(input: WorkflowInput, work: () => Promise<T>): Promise<T> {
  if (input.actor !== "requestor") throw new QuestionnaireWorkflowError(403, "CSRM questionnaire mutation is denied.");
  return serializeQuestionnaireMutation(input.questionnaireDocumentId, () =>
    input.strapi.db.transaction(async ({ trx }) => {
      await lockQuestionnaire(input.strapi, input.questionnaireDocumentId, trx);
      return work();
    }));
}
```
(New analyst-only mutations need an analogous `runAnalystQuestionnaireMutation` guard — the existing guard is hard-coded to `actor === "requestor"` and cannot be reused unmodified.)

### Anti-Patterns to Avoid
- **Hard-deleting `CsrmQuestion` rows for analyst-initiated deletes:** the existing regeneration code path does this (`questionnaire-generation-workflow.ts:35`), but D-07 explicitly forbids it for edits/deletes made after generation. Use the soft-delete envelope marker instead.
- **Gating questionnaire release only in the web layer:** AGENTS.md: "Navigation visibility is not authorization." The release gate must live in `csrm-authorization.ts` / the workflow service, not just in which link the UI renders.
- **Treating `assessmentStatus: "in-review"` as equivalent to "release-ready reviewed":** the codebase enters `in-review` on the *first* accepted edit (`assessment-workflow.ts:142-154`) and deliberately preserves it across later edits ("later edits preserve the original reviewer and states" — STATE.md Phase 04). Re-deriving a stricter "reviewed" label from `validateReleaseReadiness(...).ready` (already computed live on every read) avoids contradicting this precedent — see Open Questions.
- **Inventing a new content type for audit/revision history:** explicitly forbidden by the roadmap's known-gap note and AGENTS.md ("Document contract/model gaps rather than inventing competing entities").

## Common Pitfalls

### Pitfall 1: Assuming "released" already exists somewhere
**What goes wrong:** A planner instinctively assumes there's already an existing status value or flag gating Requestor questionnaire visibility, because assessments already have a release concept (`isReleased`, `releaseAssessment`).
**Why it happens:** The assessment release pattern is well established and easy to pattern-match onto questionnaires.
**How to avoid:** Grep confirms `requireQuestionnaireOwnership`/`requireQuestionnaireCollectionScope` in `csrm-authorization.ts` never check any release-like fact (verified lines 268-292); the questionnaire routes (`routes/csrm-questionnaire.ts`) mount GET/PATCH/POST for a Requestor as soon as they own the request, generation status notwithstanding. Treat "questionnaire release" as 100% new server-side work.
**Warning signs:** A plan task that says "wire up the existing release flag" for questionnaires — there isn't one.

### Pitfall 2: Copying the regeneration hard-delete pattern for analyst question deletion
**What goes wrong:** `persistGeneratedQuestionnaire` deletes old `CsrmQuestion` rows outright when regenerating (`questionnaire-generation-workflow.ts:35`). A plan that reuses this helper for "analyst deletes a question" will silently violate D-07.
**Why it happens:** It's the only existing "remove a question" code path in the repo.
**How to avoid:** Build a distinct soft-delete operation that flips a marker inside `options` JSON and leaves the row (and its `answer`) intact; only regeneration (replacing an *unanswered* questionnaire wholesale) may still hard-delete, because D-07 only concerns questions removed from an in-flight governance edit, not a full regeneration of an unanswered questionnaire.
**Warning signs:** Any new code that calls `strapi.documents("api::csrm-question.csrm-question").delete(...)` outside the existing regeneration path.

### Pitfall 3: Conflating `assessmentStatus: "in-review"` with the D-01 "Assessment reviewed" step
**What goes wrong:** Mapping "Assessment reviewed" to `assessmentStatus === "in-review"` directly would make the stepper flip to "reviewed" on the very first, possibly trivial, analyst edit — and then D-04's "editing a reviewed assessment returns it to drafted" would force reintroducing a status regression that STATE.md explicitly says the team decided *against* ("Stamp reviewedBy and draft-to-review transitions only on the first accepted edit; later edits preserve the original reviewer and states" — Phase 04).
**Why it happens:** `in-review` sounds like "reviewed."
**How to avoid:** Map "Assessment reviewed" to `assessmentStatus === "in-review" AND validateReleaseReadiness(assessment).ready === true` (already computed live on every read via `validateReleaseReadiness`/`projectReleaseReadiness` in `assessment-workflow.ts:219-266,268-305`). Under this mapping, D-04's "editing... returns it to drafted" needs **no new backend transition at all** — an edit that leaves any required field incomplete naturally recomputes to "not ready," which the stepper displays as "drafted," while `assessmentStatus` in the database is untouched. See Open Questions for the alternative reading and why it's rejected.
**Warning signs:** A migration/task description that says "add a status transition that moves `assessmentStatus` back to `draft`."

### Pitfall 4: Widening `csrm-authorization.ts`'s `requireQuestionnaireOwnership`/`requireQuestionnaireCollectionScope` generically instead of adding a narrow new grant
**What goes wrong:** Bolting release-gate logic onto the existing shared ownership check risks affecting every other questionnaire route (answers, submit, revert) that must NOT be release-gated the same way (an Analyst must still see an unreleased questionnaire; a Requestor must not).
**Why it happens:** It looks like the natural place since it already resolves `questionnaireActor`.
**How to avoid:** Follow the Phase 06.1 precedent exactly: a new, narrow, API-only Function/config flag (e.g. `requireQuestionnaireReleased` for Requestor-facing GET/PATCH/POST routes) checked only where it matters, leaving analyst routes and the existing ownership check untouched.
**Warning signs:** A diff that touches `requireQuestionnaireOwnership`'s core branch rather than adding a new branch/config key.

### Pitfall 5: Forgetting the E2E harness starts its own Strapi
**What goes wrong:** Running `pnpm --prefix apps/web test:e2e` while a `pnpm dev`/`strapi develop` process is already running collides on the shared `apps/strapi/dist` build directory and fails with a confusing 405, not an auth error (documented directly in `apps/web/playwright.config.ts:6-20`).
**Why it happens:** Developers habitually leave `pnpm dev` running.
**How to avoid:** Stop all dev servers before invoking the E2E suite; the config already isolates ports, SQLite file, and Next build dir per invocation.
**Warning signs:** A GREEN run reports 405s that look like an authorization bug.

## Code Examples

### Reusable answer-revalidation for D-08
```typescript
// Source: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-definition.ts:185-205 (read this session)
export function isQuestionnaireValueValid(question: QuestionnaireDefinitionQuestion, value: unknown): value is QuestionnaireValue {
  if (value === null) return true;
  switch (question.answerType) {
    case "Text":
    case "Long text":
      return typeof value === "string" && value.length <= 65_535;
    case "Boolean":
      return typeof value === "boolean";
    case "Single select":
      return typeof value === "string" && Boolean(question.choices?.some((choice) => choice.value === value));
    case "Multi select":
      return Array.isArray(value)
        && value.length <= 1_000
        && value.every((entry) => typeof entry === "string" && question.choices?.some((choice) => choice.value === entry));
    case "Date":
      if (typeof value !== "string" || !/^\d{4}-\d{2}-\d{2}$/.test(value)) return false;
      return new Date(`${value}T00:00:00.000Z`).toISOString().slice(0, 10) === value;
    case "File upload":
      return false;
  }
}
```
Use: after an analyst edits a question's `answerType`/`choices`/`required`, re-run this against the question's current `answer.value`. If it returns `false`, clear the answer (set to `null` / mark not-submitted) and record a D-08 plain-language explanation entry in the governance log for that question.

## Open Questions

1. **Does D-04's "editing a reviewed, unreleased assessment returns it to drafted" require an actual `assessmentStatus` write-back, or is it satisfied by re-deriving the stepper label from live readiness?**
   - What we know: `assessmentStatus` currently enters `"in-review"` on the first accepted edit and is deliberately preserved across all subsequent edits (`assessment-workflow.ts:142-154`; STATE.md Phase 04: "later edits preserve the original reviewer and states"). `validateReleaseReadiness`/`projectReleaseReadiness` are already recomputed live on every read and would naturally show "not ready" the moment a required field becomes incomplete.
   - What's unclear: whether "drafted" in D-04 means the literal `draft` enum value (a real regression, contradicting the documented precedent) or a UI label for "not currently release-ready."
   - Recommendation: adopt the derived-label reading (Assumption A1) unless the operator explicitly wants the stored regression; confirm during plan-checking or a discuss-phase follow-up before committing to a `transitionForAcceptedEdit` change.

2. **Should the questionnaire "released" fact be a dedicated field pair or derived from the governance log?**
   - What we know: the codebase's own stated design principle for `CsrmQuestionnaire` is "adds audit facts only and does not introduce a competing questionnaire status field" (Phase 06.1 contract gap). A dedicated `releasedAt`/`releasedBy` pair would be the more literal continuation of that same file's *own* precedent (which did add dedicated fields, just not a status field); a log-derived boolean is more consistent with the *general* house style of deriving rather than storing.
   - What's unclear: which the operator/architect prefers for this specific case, since both are defensible readings of "don't add a competing status field."
   - Recommendation: default to log-derived (Assumption A2), but this is the single most consequential wording choice in the upcoming contract-gap record — surface it explicitly for confirmation before the contract-gap record is written.

3. **Is "Only a Security Analyst may return a released questionnaire to analyst review" (D-03) an explicit, standalone "recall" action, or purely a side effect of D-06's "an Analyst edit to a submitted questionnaire returns it to analyst review"?**
   - What we know: D-06 describes edit-triggers-return-to-review as automatic; D-03 is stated as a standalone rule restricting *who* may perform "return a released questionnaire to analyst review." Since D-05 already restricts question editing to Analysts only, D-03 may just be reiterating D-05's actor restriction for this specific transition, not describing a second, explicit "recall without editing" operation.
   - What's unclear: whether the plan needs a distinct `POST /v1/questionnaires/{id}/return_to_review` operation (with its own mandatory reason per D-02) separate from "edit a question," or whether editing a question is the *only* trigger.
   - Recommendation: treat D-03 as confirming the actor restriction on the edit-triggered transition described in D-06 (no separate recall-without-editing endpoint) unless CONTEXT.md discussion surfaces a concrete "recall released questionnaire with no edit" scenario; this keeps the new-Function surface area minimal and matches the "Claude's Discretion" note that layout/composition (not new workflow primitives) is left open.

4. **Does D-02's "mandatory reason" apply to every backward transition, including the D-04 assessment reviewed→drafted case?**
   - What we know: D-02 states the general rule; D-04 does not mention a reason. The existing request/questionnaire revert-to-draft operations both require a mandatory reason (`parseRevertReason`).
   - What's unclear: if Recommendation A1 is adopted (D-04 is a pure derived-label change with no stored transition), there is no explicit "action" for an Analyst to take and hence no reason to collect — the reason requirement becomes moot for D-04 specifically.
   - Recommendation: if A1 is confirmed, D-02's mandatory-reason clause applies only to the explicit revert/return-to-review actions (request revert, questionnaire revert, questionnaire return-to-review), not to D-04's assessment case.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Requestor bypassing the release gate by guessing the questionnaire GET/PATCH/POST route before release | Elevation of Privilege | Server-side release check inside the authorization policy (or workflow service, defense-in-depth) — never rely on the UI not linking to it. |
| Analyst "Security Analyst Agent" (automation role) gaining question-edit/release/return-to-review grants it should not have (per the existing precedent that the automation agent must NOT be able to revert submitted work) | Elevation of Privilege | Follow the Phase 06.1 precedent exactly: `function.questionnaire.revert_to_draft_api` is granted to `role.security_analyst` and `role.requestor` only, explicitly excluding `role.security_analyst_agent`. | Governance log tampering / silent history rewrite | Tampering | Append-only write pattern: the workflow service only ever appends to `governanceLog` inside the same transaction as the state change it documents; no update path may remove or edit prior entries. Validate on read with a closed schema so a malformed/truncated array fails safe (same posture as `parseQuestionnaireDefinition`). |
| Question/answer disclosure via the "audit history" surface bypassing normal ownership scoping | Information Disclosure | Route the revision-timeline projection through the exact same `requireQuestionnaireOwnership`/`requireQuestionnaireCollectionScope` checks as every other questionnaire read; do not add a separate unscoped "history" endpoint. |
