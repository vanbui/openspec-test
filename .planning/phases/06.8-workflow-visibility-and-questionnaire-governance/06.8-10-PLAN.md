## Harness rules this plan must follow

- The Playwright harness starts its **own** `strapi develop` with its own ports, its own SQLite file
  and its own Next build directory. Every manually running dev server must be stopped first. A
  collision surfaces as a method-not-allowed response that reads like an authorization bug and is not
  one; `playwright.config.ts` documents this and the recovery.
- A run rewrites `apps/web/next-env.d.ts` and `apps/web/tsconfig.json` to point at its throwaway
  build directory. Restore both after the run so the change does not travel into a commit.
- The phase gate is the **full** suite. Running only the specs this phase adds is the exact mistake
  Phase 06.6 recorded.
- Browsers must be present; the headless shell is installed alongside the browser.

Create `questionnaire-governance-workflow.spec.ts` as the phase's dual-actor journey. Reuse the
sign-in helper, the actor-switching pattern and the answering helpers from the existing questionnaire
spec rather than writing new ones; import or copy them in the same style the existing specs use.

First leg — the Requestor cannot reach an unreleased questionnaire. Sign in as the Requestor and open
their requests list and dashboard. Assert the deliberately unreleased fixture's questionnaire does not
appear in My Questionnaires, does not appear in the dashboard counts, and that its request's hub
renders no questionnaire summary at all. Then navigate directly to that questionnaire's URL in a
separate browser context and assert the screen reports that the questionnaire cannot be displayed or
is not found, and that no question text from the fixture appears anywhere in the page. This is the
criterion-3 denial, and it must be proved by direct navigation, because an assertion that a link is
missing proves only that navigation visibility works.

Second leg — the Analyst governs. Sign in as the Security Analyst, open the same questionnaire from
the analyst review surface, and assert: the questions are readable; the lifecycle stepper on the
request names the generated step as current in words; the governance panel offers release and offers
no return control; and the revision timeline renders its empty state. Add one question, edit an
existing question's choices, and delete a third; after each, assert the panel reflects the change and
the timeline gains a dated entry naming the change. Then release the questionnaire and assert the
timeline gains the release entry and the stepper's current step moves to the released step.

Third leg — the Requestor answers and submits. Switch to the Requestor, open the questionnaire, assert
the deleted question is absent and the added question is present and outstanding, answer every active
question, submit, and assert the stepper's current step moves to the submitted step on the request
hub.

Fourth leg — the Analyst returns, corrects, and re-releases. Switch to the Analyst, return the
questionnaire to analyst review through the confirmation dialog, and assert: the dialog refuses to
confirm with an empty reason; a reason is required and accepted; after confirming, the timeline shows
the dated return entry with the reason; and the Requestor's access is gone, proved again by direct
navigation in a separate context. Then edit a question so an existing answer no longer validates,
assert the cleared answer is reported in plain language naming the question, re-release, and switch
back to the Requestor to assert the cleared answer is empty, the summary-depth timeline states in
plain words what requires their attention, they can complete it, and they can re-submit.

Wrap the screen-level assertions of each leg in the width loop over 1440 and 375, reusing the
overflow helper, and assert at 375px that the governance panel, the stepper, the hub and the timeline
are all reachable by keyboard in document order with a visible focus indicator. Name each assertion
with the criterion it proves so a failure report identifies the criterion at risk rather than only a
selector.
