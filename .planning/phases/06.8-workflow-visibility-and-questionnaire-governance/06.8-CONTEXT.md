# Phase 06.8: Workflow Visibility and Questionnaire Governance - Context

**Gathered:** 2026-09-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the Assessment Request the shared, actor-aware operational hub. Phase 06.8 adds accessible request and assessment lifecycle visibility, Requestor request summaries, Analyst questionnaire review/edit/release controls, auditable questionnaire revisions, and an actionable-versus-released Analyst request queue. Strapi remains the production API and authorization boundary.

</domain>

<decisions>
## Implementation Decisions

### Lifecycle transitions and audit history
- **D-01:** The visible request lifecycle is `Draft → Submitted → Questionnaire generated (analyst-only) → Questionnaire released → Questionnaire submitted → Assessment drafted → Assessment reviewed → Assessment released`. The stepper is read-only, names the current state in text, and differentiates completed, current, and future steps without colour alone. — **Reversibility:** costly — state vocabulary is a published API/UI contract.
- **D-02:** A backward transition may move only to the immediately preceding editable state. It requires an Analyst action, mandatory reason, and visible audit record; later records are never silently deleted. — **Reversibility:** one-way — audit and workflow persistence shape must preserve historical facts.
- **D-03:** Only a Security Analyst may return a released questionnaire to analyst review.
- **D-04:** Editing a reviewed, unreleased assessment returns it to drafted and requires a fresh review before release. — **Reversibility:** costly — it controls the existing review and release gate.

### Questionnaire editing, release, and resubmission
- **D-05:** AI generation produces an analyst-only questionnaire. Analysts can view, edit, add, and delete questions; Requestors see a questionnaire only after an explicit Analyst release.
- **D-06:** An Analyst edit to a submitted questionnaire returns it to analyst review. After explicit re-release, the Requestor must complete newly required questions and explicitly re-submit; unchanged valid answers remain.
- **D-07:** A deleted question and its submitted answer remain in audit history but are excluded from the active questionnaire and from later assessment input. — **Reversibility:** one-way — it retains evidence needed for an auditable risk workflow.
- **D-08:** Preserve an answer only when it still validates against the revised question definition; clear affected answers with a plain-language explanation on re-release.
- **D-09:** Both actors see a dated questionnaire-revision timeline. Analysts can inspect detailed question/answer changes; Requestors see a plain-language summary of what requires review.

### Request hub, dashboard, and queue
- **D-10:** Beneath the request lifecycle stepper, show a compact operational summary and next required action; then concise, permission-scoped summaries for the questionnaire, assessment, risks, controls, information systems, and information assets. Each summary links to its existing authoritative detail screen rather than embedding a duplicate editor.
- **D-11:** The Requestor dashboard adds lifecycle-state cards for “My assessment requests”; each count links to the existing owner-scoped My Requests list filtered to that state.
- **D-12:** `/app/review/requests` defaults to “Requires my attention” and has explicit “Awaiting Requestor”, “Generation in progress”, and “Released” filters. Released work is visible but does not dilute the default action queue.

### Resolved during planning (locked)

Research surfaced four genuine ambiguities in D-02 through D-06. They are resolved
here so the planner treats them as settled rather than reopening them.

- **D-13 (resolves D-04):** editing a reviewed, unreleased assessment performs a real
  state transition back to drafted — not a derived "not release-ready" label. D-04
  requires *a fresh review before release*, and release readiness only measures field
  completeness, so a derived label would let a reviewed-then-edited assessment be
  released with no second review, defeating the gate. This knowingly supersedes the
  Phase 4 precedent that later edits preserve the original reviewer and states; that
  precedent is why D-04 is rated costly. The superseded review fact is retained in
  history, never deleted, per D-02. — **Reversibility:** costly.
- **D-14 (resolves the release-fact question):** the questionnaire release fact is
  persisted as dedicated audit-fact fields (released-at and released-by, named to match
  the existing revert-audit convention), and those fields — not a scan of the governance
  log — are the authoritative release gate. Rationale: the gate is an access-control
  decision, and access control must read an explicit validated field rather than derive
  itself from parsing a mutable JSON array, where a malformed or truncated log failing
  safe would deny every read. This follows the Phase 06.1 precedent most literally: that
  record added dedicated audit-fact fields and only forbade a competing *status* field,
  which released-at/released-by are not. The governance log carries the narrative
  history, including re-releases, for the D-09 timeline. — **Reversibility:** costly.
- **D-15 (resolves D-03 against D-05/D-06):** there is exactly one explicit,
  Analyst-only return-to-analyst-review transition, it requires a mandatory reason, and
  it is audited. Question edit, add, and delete are permitted only while the
  questionnaire is in analyst review. To change a released or submitted questionnaire an
  Analyst therefore returns it to review first, edits, then re-releases. No edit ever
  causes an implicit backward transition, because an implicit transition could not carry
  the reason and audit record D-02 requires. This covers D-03 (released) and D-06
  (submitted) with one operation and no hidden state changes. — **Reversibility:** costly.
- **D-16 (resolves D-02 mandatory-reason scope):** the mandatory reason applies to the
  three explicit standalone backward-transition actions — request revert to draft,
  questionnaire revert to draft, and questionnaire return to analyst review — where the
  reason is the only evidence of intent. The D-13 assessment transition is triggered by
  an edit rather than a standalone action, and is audited by the edit record itself
  (actor, timestamp, and the fact that a prior review was superseded); it does not prompt
  for separate free-text. Prompting for a reason on every field edit would be
  disproportionate without adding evidence the diff does not already carry.

### the agent's Discretion
- The planner may choose exact layout/composition patterns, provided they reuse existing feature-oriented typed services, semantic tokens, shared state primitives, and server-enforced record permissions.

</decisions>

### Established Patterns
- Production web calls flow through typed service modules and Server Actions; pages and arbitrary UI components do not issue raw fetches.
- Requestor “My” routes are owner-scoped even for Security Analysts; review queues are distinct explicitly authorized surfaces.
- Related records have three presentation states: absent is stated, protected/unavailable is not disclosed, and available is linked.
- AI output is advisory; explicit Analyst review and release remain mandatory.

### Integration Points
- Assessment Request detail, questionnaire detail/review, assessment detail, Requestor dashboard, and `/app/review/requests`.
- Strapi content types, exact catalogue-backed workflow operations, OpenAPI contract, typed client schemas/services/actions, and actor-specific E2E coverage.

<specifics>
## Specific Ideas

- The lifecycle stepper explains current state; it must not become a second workflow-control surface.
- One shared request-detail structure serves Requestors and Analysts, with record-level authorization governing actions and related-record visibility.

</specifics>
