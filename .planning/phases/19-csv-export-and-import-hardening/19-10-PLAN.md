## Phase Goal

**As a** Security Analyst or risk manager, **I want to** export any list I can see and to import spreadsheets without fighting the format, **so that** CSRM fits the Excel work around it.

This plan's slice: the released Risk Assessment leaves CSRM as a file, through one record-read check. Jane exports her own released assessment; anyone else gets the not-found refusal; the analyst exports it once released; the assessment lists export too.

<objective>
Gather the released-assessment read into one module (D-14) and switch the three released reads and the My risk assessments list to it with no behaviour change; serve the released-assessment export for both actors (D-03 group 2, D-15, D-21) through the fixed-table pipeline; serve the Risk assessments and My risk assessments exports (D-03 group 1, D-04); publish, grant, inventory and prove every grant and refusal (D-02, D-13, D-16, D-38). Proves ROADMAP criterion 2 in the API.

Purpose: one record-read check that Phase 17 widens to participants, 17.1 to `closed` requests and 19.1 composes for notification readability, so exports, the print report and My risk assessments follow with no export change (G-12, G-13; orchestrator constraint).
Output: the predicate module, three served operations and their proofs.

Edits Strapi source? Yes. Changes the specification? Yes. Runs Playwright? No.

Scope note: 19 files at four tasks. The predicate, the reads it replaces and the export that calls it change together so the one place is proven by the same suite run; the remaining files are the contract chain shared by the three operations.
</objective>

## Recorded planning decisions

- **The module (`released-assessment-read.ts`).** `type AssessmentViewer = { kind: "requestor"; documentId: string } | { kind: "analyst" }`. `RELEASED_ASSESSMENT_FILTERS` (frozen): `assessmentStatus` `approved`, `approvalDate`, `assessmentDate` and `approvedBy.documentId` not null, `assessmentRequest.requestStatus` `approved` (today's `releasedAssessmentQuery` facts, unchanged). `readableAssessmentFilters(viewer)`: requestor → `{ assessmentRequest: { requestor: { documentId: { $eq: viewer.documentId } } } }`; analyst → `{}`. `isReadableReleasedAssessment(document, viewer)`: the in-memory twin of both filters (today's `isReleasedAssessmentForOwner` plus the release facts). `findReadableReleasedAssessment({ documents, viewer, documentId, populate })`: one `findOne` with both filters merged, then the in-memory check; returns the document or null. - **The analyst detail says whether it is released.** `projectAnalystAssessmentDetail` gains `released: boolean` from `isReadableReleasedAssessment(document, { kind: "analyst" })`, published as a required property of the analyst assessment detail schema in the specification and parsed by the web's `assessment-schema.ts` in the same commit (the 06.9 lesson), so the analyst page's Export and Print report (plan 19-12) and its report route follow the one module, including 17.1's widening, with no web copy of the rule.
