## Phase Goal

**As a** Security Analyst, **I want to** have a data-driven dashboard, reports, and alerts covering my review queues, high and critical risks, and overdue treatments, **so that** I can prioritise analyst work from live workload signals.

<objective>
Serve the two alert operations end to end, and seed the deterministic data every browser proof relies on:

1. **Server.** Stateless alerts derived on read (D-01, D-10). The list is a knex `UNION ALL` of one branch per kind with an outer order, count and page. The summary groups the same branches by kind and urgency, so the totals always agree (D-12).
2. **Contract and client.** The closed OpenAPI components, the regenerated client, closed Zod parsers and the parity guard registration (D-08).
3. **Fixture.** A dedicated Phase 7 seed (D-23), re-anchored on every boot so its overdue, due-soon and review-due conditions hold whatever the date.

Purpose: alerts are the core of DASH-01's "overdue treatments, due dates and alerts" and of DASH-02. Plans 05, 06 and 08 build on this repository, its projection and its client.

Output:
- the alert query parser, repository, controller and routes;
- the published contract and regenerated client;
- the web alert schema and service;
- the seed fixture wired into bootstrap;
- tests at every seam.
</objective>

## Recorded planning decisions

- **Governing dates follow the UI-SPEC §3.2 map.** `critical-residual-risk-untreated` is governed by the Risk's `identifiedDate` ("Identified"), not the research table's target date, and `ineffective-control` by the Control Implementation's `reviewDate` ("Last reviewed"). This is the plan choice the UI-SPEC asked the planner to make.
- **`kind` is repeatable** (1-8 unique values). The dashboard's "Treatments due" widget can then read both treatment kinds in alert order from one bounded page (plan 08). The Alerts screen still sends one kind at a time.
- **Integer enums declare `minimum`.** Page size is `enum [5, 10, 25, 50]` with `minimum: 5`, because the parity guard synthesises `Math.max(minimum, 1)` for integers and would otherwise send 1.
- **String fields use no `pattern`.** The guard substitutes a fixed identifier, and the Zod schemas do not pin the alert id's format.
- **The Control Implementation `source.title`** is the server-joined `"{controlNumber} {controlName}"`, built in the projection, not in SQL, so no dialect-specific concatenation is needed. `source.identifier` is the parent Risk's `riskNumber`, which is the link text in UI-SPEC §3.2. `link` points at the parent Risk.
- **Seed fixture size.** The fixture adds exactly five Risks. The Risk Register journey asserts that its page-1 total equals its distinct rendered rows at the default page size of 25, and the fresh E2E database holds about six other Risks when that spec runs.
- **Seed request statuses.** Fixture requests use `under-review` or `questionnaire-in-progress` (never `submitted`, so no spec can start generation on them), plus one `approved` request for the released assessment. All are owned by Jane.
- **The seed never creates a Control.** `administration-workflow.spec.ts` asserts exactly "2,646 results" on the Controls list, so the fixture's Control Implementations reference existing library Controls by stable `controlNumber`. It adds one dedicated Information System, "Phase 7 exposure platform". No spec asserts a count of Information Systems.
