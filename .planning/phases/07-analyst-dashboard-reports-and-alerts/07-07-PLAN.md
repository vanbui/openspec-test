## Recorded planning decisions

- **The index lives in a route group, `reports/(report-index)/`.** Its `loading.tsx` and `error.tsx` then wrap the index only, and never wrap `/app/reports/[reportKey]`. Next prefetches a dynamic route "from the layout to the first loading boundary", so a boundary at `reports/loading.tsx` would flash the index skeleton on every client navigation into a report from outside the index.
- **`generateMetadata` resolves the capability first.** It returns "Reports | IdamBox CSRM" for a non-analyst whatever the key, and for an unknown key. Otherwise it returns the key's metadata title. A document title must never reveal whether a key is valid to someone who may not read reports.
- **Report detail headers for denied actors** use the index header ("Reports" and its §7.1 description), so the header also discloses nothing.
- **The detail `loading.tsx` cannot know the key.** It renders the breadcrumb root, a title skeleton and the section skeletons. The page itself renders the real header and wraps the data read in a `Suspense` fallback, which renders the key-specific skeleton.
- **`error.tsx` uses Next 16.3's `retry` prop** (see plan 05).
- **The Reports navigation item lands here**, with its route (see plan 05).

## Hard rules (carried forward)

- **Styling.** Semantic tokens only, with values from the direction document. Status and severity are never shown by colour alone.
- **States.** Five states through the shared primitives.
- **Accessibility and layout.** WCAG 2.2 AA from 375px to 1440px, with only the labelled cross-tab region scrolling horizontally.
- **Services and authorization.** Typed services only. The capability check precedes every read.
- **E2E rules.** Helpers assert the shell, never the URL, and browser tests never assert global totals.
- **Attribution and staging.** Zero AI or tool attribution. Explicit-path staging.
