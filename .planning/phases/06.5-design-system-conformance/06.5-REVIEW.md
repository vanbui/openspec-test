# Phase 06.5: Code Review Report

**Reviewed:** 2026-09-10T09:30:09Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

The scoped implementation keeps populated reads on the existing typed services and does not introduce a raw UI fetch or AI-release path. However, the fixture switch can bypass per-route authorization when enabled, and the browser matrix contains a dashboard permission assertion that cannot pass against the rendered recovery action. The documentation authority guard is also materially easier to evade than its stated contract.

## Critical Issues

### CR-01: E2E fixture switch bypasses route-level authorization when enabled

**File:** `C:/bproton/interns/csrm/apps/web/src/lib/testing/e2e-ui-state.ts:12-17`

**Issue:** The resolver activates solely from `CSRM_E2E_UI_STATE_HARNESS=1`; it has no test-runtime restriction. Several routes then select fixture output before their protected service call: assessments at `app/(app)/app/review/assessments/page.tsx:12-15` and questionnaires at `app/(app)/app/review/questionnaires/page.tsx:13-21`. The shared layout only requires `assessment-request:read`, so a requestor who has that base capability can receive a review-route fixture without the normal `listAnalystAssessments` / `listQuestionnairesForReview` Strapi authorization check. `server-only` stops client bundling, not an accidentally enabled production/development deployment flag. This violates the project requirement that authorization be enforced server-side.

**Fix:** Make the harness impossible to enable outside an explicitly isolated test runtime, and run the route's normal server-side capability guard before accepting any fixture. For example, pass a test-only capability-checked context into the resolver, or have each route authorize first and only then branch into non-populated presentation. Add an integration test with a Requestor session proving `__e2eState` cannot render a reviewer or administration fixture.

### CR-02: Dashboard permission cells in the state matrix are guaranteed to fail

**File:** `C:/bproton/interns/csrm/apps/web/e2e/design-system-conformance.spec.ts:54-59`

**Issue:** `expectStateMeaning` requires exactly one recovery link matching `a[href*="/app/"]` for every permission state. The dashboard permission UI instead renders only `href="/sign-in"` in `requestor-dashboard.tsx:234-241`. Therefore the dashboard's two permission cells always fail at line 57, irrespective of server data or styling. The phase summary confirms the browser suite never reached Playwright results, so this contradiction was not caught by execution.

**Fix:** Assert a route-specific accessible recovery action rather than hard-coding an `/app/` URL for every state. For the dashboard permission state, assert the visible “Return to sign in” link and `/sign-in`; retain the restricted-record assertions separately.

## Warnings

### WR-01: Documentation authority guard misses ordinary token/hexadecimal table rows

**File:** `C:/bproton/interns/csrm/apps/web/scripts/verify-design-spec-authority.mjs:43-45`

**Issue:** The duplicate detector only matches a hexadecimal value wrapped in parentheses immediately after a token (for example `` `--color-x` (`#abcdef`) ``). A conventional Markdown row such as ``| `--color-x` | `#abcdef` |``—or a three/eight-digit CSS hex—passes even though it recreates the prohibited competing token/value authority. The only negative test at `verify-design-spec-authority.test.mjs:41-54` uses the same narrow parenthesized representation, so it does not protect the documented rule.

**Fix:** Parse table cells (or use a deliberately broad, tested pattern) and reject any color-section row containing a semantic token plus a valid CSS hexadecimal literal. Add fixtures for bare, backticked, 3-digit, 6-digit, and 8-digit hexadecimal values.

### WR-02: The “ordinary server” test does not prove authorized content is retained

**File:** `C:/bproton/interns/csrm/apps/web/e2e/design-system-conformance.spec.ts:87-102`

**Issue:** The separately spawned Next server receives neither the isolated Strapi origin/token nor an assertion that a real authorized dashboard projection rendered. After visiting the fixture URL, the test only checks that the marker is absent and the static “Dashboard” heading exists. A server whose typed request fails and renders the ordinary error state satisfies both assertions, so the test does not substantiate its claimed proof that the query cannot override authorized content.

**Fix:** Supply the same known isolated Strapi configuration and development identity to the spawned server, then assert a known populated, authorized element (or intercept and assert the typed service request succeeds) before verifying that no fixture marker appears.
