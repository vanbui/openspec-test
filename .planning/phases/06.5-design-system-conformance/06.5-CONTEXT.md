# Phase 06.5 Context: Design System Conformance

This phase closes a documentation defect, not a visual one. The product already
implements its design system faithfully; three documents describe that system and
disagree, and an audit consequently measured the product against a superseded
baseline and reported a failure that does not exist.

The decisions below are locked. They were established by reading the design
document and by measuring the running application, not by inference.

## The correction that defines this phase

`.planning/APP-UI-REVIEW.md` originally reported that no rendered element matched
the type contract — "0 of 179" on the Risk Register. That measurement used
`01-UI-SPEC.md:78-85`, which contracts four size+weight pairs and two weights.

`docs/design/csrm-design-direction.md` is the real design system. It is named in
the `globals.css` header comment, runs to 360 lines, and carries computed contrast
ratios for every colour pairing. Its §3.10 contracts nine type tokens with weights
400/500/600; its component guidance adds nav items at 13px/500.

Measured against it, on the running app at 1440px:

| Route | Conformance |
|---|---:|
| `/app` | 88% (42/48) |
| `/app/requests` | 97% (63/65) |
| `/app/risks` | 99% (138/140) |
| `/app/review/assessments` | 90% (52/58) |
| `/app/review/questionnaires` | 96% (44/46) |
| `/app/admin/controls` | 99% (236/238) |

Do not re-run a sweeping typography migration. It is not warranted.

## D-01 — One source of truth for the design system

`docs/design/csrm-design-direction.md` is authoritative for colour, type, spacing,
radii, motion, and component guidance.

`01-UI-SPEC.md` and `06-UI-SPEC.md` are amended to **defer** to it — remove their
restated values and reference the document instead. Do not delete the specs and do
not rewrite their success criteria; only the sections that restate design values
change. Specifically:

- `01-UI-SPEC.md` §Typography (lines ~76-89) restates a four-pair ramp that no
  longer matches anything. Replace the table with a pointer to §3.10.
- `01-UI-SPEC.md` §Color and semantic tokens (lines ~90-101) restates hex values.
  Replace with a pointer to §3.1-3.7.
- `01-UI-SPEC.md:109` states 40px/44px sidebar rows. The design document specifies
  36px. Replace with a pointer, and note the withdrawal in the amendment.
- `01-UI-SPEC.md:78` forbids all-caps. This is the stale rule — see D-02.
- `06-UI-SPEC.md:80` already agrees with the design document; make its reference
  explicit rather than descriptive.

Record each amendment inline so the history of the change is legible to whoever
reads the spec next.

## D-02 — Uppercase micro-labels are kept

An earlier decision on 2026-09-10 settled the all-caps conflict as sentence case
everywhere. **That decision is reversed.** It was taken without the design document
in view.

`csrm-design-direction.md` §2 takes the uppercase micro-label deliberately as a
brand signature set in Inter, and §3.10 specifies it at 11px/500/+0.05em tracking.
Its named uses are table headers, KPI captions, eyebrows, and sidebar section
labels. `06-UI-SPEC.md:80` agrees.

Navigation items and form field labels stay sentence case — which is already how
they render, so no change is needed there.

## D-03 — `DataTable` uppercase headers are a real bug; make them render

`data-table.tsx` carries `uppercase` on its header cells at both call sites
(around lines 117 and 289), and headers render **sentence case** in the browser.
Verified: `/app/risks` renders "Risk number"; `assessment-list.tsx`'s own `<table>`
renders "ASSESSMENT".

The specified treatment is uppercase, so the fix is to make it render, not to
remove it.

**Cause confirmed** — measured on `/app/risks` at 1440px, no need to re-diagnose:

- The `<th>` computes exactly what §3.10 specifies: `text-transform: uppercase`,
  11px, weight 500, `letter-spacing: 0.55px` (0.05em). The token application is
  correct.
- The `<button>` inside it computes `text-transform: none`.
- A bare `<button>` injected into that same `<th>` at runtime also computes
  `none`, which proves a stylesheet rule targets `button` generally rather than
  anything specific to this element. That is the Tailwind preflight
  (modern-normalize) `button, select { text-transform: none }` reset.
- Every column in the Risk Register is sortable, so every header goes through the
  button branch — which is why the whole table renders sentence case.

**The wider concern is not borne out.** The button correctly inherits font size,
weight, letter-spacing and family; preflight sets `font: inherit`, so only
`text-transform` is reset. Do not go looking for other dropped inherited styles.

**Fix:** restore the transform on the sortable header button — `uppercase` on the
button, or `text-transform: inherit`. Prefer whichever keeps the treatment defined
once in `data-table.tsx` rather than duplicated at both header call sites.

## D-04 — The residual type drift, in full

These are the only off-contract pairs measured across six routes. Fix exactly
these; do not sweep further.

All four were located in the running application; the DOM paths below are measured,
not inferred.

| Pair | Count | Element | Fix |
|---|---|---|---|
| `12/600` | 1 per route | `aside.sidebar > nav > div > p.px-3.text-xs` — the "Administration" section label | `--text-micro` 11/500. It is already correctly uppercase; only size and weight are wrong. |
| `11/400` | 1 per route | `aside.sidebar > div.shell-footer > form.role-switcher > p` — the dev-fixture note | `--text-caption` 12/400 |
| `14/600` | 4 | `/app` only — `ul.grid > li > span.font-semibold.tabular-nums`, the dashboard KPI counts | `14/500`, not the 30/600 display token. §3.10 reserves display for hero KPI values; these are inline counts in a compact list, and §3.10's own rule is "emphasis inside rows: 500 weight, never bold-700". 14/500 is conformant and preserves the current visual. |
| `12/700` | 4 | `assessment-list.tsx` ad hoc `<thead>` | `--text-micro` 11/500, resolved by D-05 |

Two notes on judgement. The `11/400` element is inside the development-only role
switcher and never ships, so it is cosmetic — fix it, but do not spend design
thinking on it. The `14/600` counts are the only case where the nearest design
token would change the visual; the reasoning for choosing 14/500 over 30/600 is
recorded above and should not be silently re-decided during execution.

## D-05 — Both ad hoc assessment headers take the shared micro token; the DataTable migration moves to 06.6

`assessment-list.tsx` renders its own `<table>` headers and is the source of the
off-contract `12/700` weight. **In this phase only its header type classes change**,
onto the same micro treatment `DataTable` uses (11px/500/uppercase/0.05em), and the
treatment is extracted so the two tables and `DataTable` cannot drift apart again.

Both `<thead>` elements are in scope — the assessment-requests table and the
risk-assessments-for-review table. Fixing one and not the other leaves the
divergence half-open.

**The migration onto `DataTable` is deferred to Phase 06.6**, assessed and moved
deliberately rather than dropped:

- `assessment-list.tsx` holds three list renderings, two of them raw `<table>`s,
  not the single table the phase was scoped around.
- `DataTable` requires nine props including pagination and density state that these
  lists wire differently from `risk-register.tsx`.
- Two structural assertions in `assessment-review-workflow.test.tsx` (lines ~120-121)
  bind to the current testids and responsive classes and would need rewriting.
- 06.6 owns "one layout per record type" and will rewrite these surfaces regardless,
  so migrating here means doing the work twice.

Do not change list-versus-card choices on any surface in this phase.

## D-06 — `color-scheme` is declared

`:root` computes `color-scheme: normal` and there is no `meta[name=color-scheme]`,
so UA-painted chrome — scrollbars, select popups, autofill — follows the operating
system while the light-first app does not. Declare `color-scheme: light`.

The app is deliberately light-only: `01-UI-SPEC.md:97` records that the dark
sidebar is "a deliberate BProton-led anchor, not dark mode". Do not add a dark
theme.

## Out of scope

- Any change to the cool neutral scale, Inter, or the accent colour. A warm
  palette, serif display face, and mono family were proposed and withdrawn; the
  design document had already rejected all three, chiefly because risk severity is
  carried by warm hues and loses distinctness on a warm canvas.
- Record-link treatment, list-versus-card layout, the shared state primitives, the
  Risk Register sticky identifier, and anchor-as-disabled pagination. All are real
  and all belong to 06.6.
- The Strapi datamodel. Content-type schemas are frozen.

## Verification

Every criterion is checked on the running application at 375px and 1440px, not
inferred from source. Conformance is asserted by reading the design document's
token set, not a hard-coded list, so the check cannot drift from the contract the
way this review did.
