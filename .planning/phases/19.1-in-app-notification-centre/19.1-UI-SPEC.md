# Phase 19.1 — UI Design Contract

> Visual and interaction contract for the in-app notification centre (NOTIFY-01). It covers:
> - the header control with its unread count, its place in the header and the 375px fit (D-24, D-25);
> - the `Bell` clash with the Alerts item (D-24);
> - the notification item and the server's sentence for each kind and part (D-11, D-16, D-17);
> - the panel, a popover from 768px and a full-screen sheet below (D-26);
> - the Notifications page with its All and Unread views (D-27);
> - marks, Undo, rollback and refusal copy (D-19 to D-23, D-29).
>
> It adds no colour, type size, weight, family, radius, shadow or duration. Three patterns the direction does not name yet are proposed as CSRM extensions X-33 to X-35. The only values they combine in new ways are existing §3.9 steps and the §4 Dialogs confirm width.

## Voice, formats and shared copy rules

Phase 11's and Phase 13's rules apply unchanged. In addition:

- **Terms:** `Notifications`, `Mark as read`, `Mark as unread`, `Mark all as read`, `View all notifications`, `All`, `Unread` (D-31). A notification is never called an "alert", a "message" or a "note", and copy never says "inbox", "feed" or "activity".
- **Counts:** written-out plurals with `tabular-nums`: `1 unread`, `3 unread`, `{n} notification` or `{n} notifications`.
- **Addressing:** "you" appears in a sentence addressed to its recipient, as Phase 13 allows.

## 1. The header control (D-24, D-25; X-33)

**Surface:** the shell header, on every route inside the shell, Home included (D-28).

### 1.1 Anatomy and behaviour

| Part | Contract |
|---|---|
| Gate | Renders only for a viewer who holds `notification:read` (D-37). Without it the header is exactly Phase 11 §3's |
| Position | In the right-hand group, after the search control and before the role tag (or the account menu in OIDC mode), 8px from each. DOM order: `Menu` (below 1024px), the header title (from 768px), `Search`, `Notifications`, then the role tag or account menu. The skip link's next Tab stop is still `Menu` |
| Shape | An icon-only outline circle (§4 Buttons) with a 16px `Bell`: the icon-button size from 768px, the touch-target size below. While the panel is open it has the `--color-bg-inset` fill (X-33) |
| Count capsule | X-33: ink, at the circle's top end corner. It shows `1` to `99`, then `99+` above that. A zero, a failed read and a refused read show no capsule: never a `0`, a dash or an error (Phase 11 §1.3) |
| Accessible name | Visually hidden text: `Notifications`, then `, {n} unread` when the count is above zero, with the exact count even above 99 (`Notifications, 120 unread`). With no count it is `Notifications`. The capsule is `aria-hidden`. `aria-haspopup="dialog"`, `aria-expanded`, and `aria-controls` while open. The name is not a live region (Phase 11 §1.3) |
| Shortcut | None (UI-D2) |
| Prefetch | Pointer enter or focus starts loading the panel's code (Phase 11 §4.7's pattern, §4.6) |

### 1.2 When the count is read (Orchestrator Confirmation; research Pattern 7)

The count is read at five points:
- with each server render of the layout (a full load, a router refresh, or a Server Action of the person's that revalidates), from the layout's unawaited promise in a Suspense boundary with no fallback;
- from each mark's returned exact count (§6);
- when the panel opens, together with its list;
- **once after each client navigation the person makes**;
- after Phase 13's silent note read (13 §9.2) resolves, through a client-side signal.

It is never read on a timer and never polled. The navigation and note re-reads follow the person's own action, so they are not an automatic refresh under §6 do-not 9. X-33 writes this rule into the direction. Each value carries the server's `asOf`, and only a later value replaces the shown count (research Pitfall 9). A failed re-read hides the capsule.

### 1.3 Viewports and the 375px fit

| Viewport | Header |
|---|---|
| 1440, 1024 | `[Cyber Risk Manager] … [Search ⌘K] [(bell) 3] [SECURITY ANALYST]` |
| 768 | `[Menu] [Cyber Risk Manager] … [Search Ctrl K] [(bell) 3] [ROLE]` |
| 375 | `[(menu)] … [(search)] [(bell) 3] [SECONDARY REQUESTOR]` |
| 320 | The same, with the role tag truncated with an ellipsis (Phase 11 §3's rule below 375px, unchanged) |

Today the phone `Menu` control is an outline pill with its label (about 85px wide), so a fourth header control cannot fit at 375px. X-33 therefore makes every header control below 768px an icon-only circle at the touch-target size, with its label visually hidden and its accessible name unchanged (`Menu`, `Search`), and sets the header's gap to 8px below 768px (UI-D4). The arithmetic for the longest development role, as the Secondary Requestor:
- **Available width:** 375 − 2 × 16 (`--spacing-gutter-xs`) = 343px.
- **Used width:** `Menu` 44 + 8 + `Search` 44 + 8 + `Notifications` 44 + 8 + the role tag = 333px. The role tag is about 177px: 19 characters at 11px with IBM Plex Mono's 0.6em advance plus 0.14em tracking, plus 20px of padding and a 2px border.
- **Spare:** 10px.

The capsule's 4px overhang lies over the gap and takes no layout width. In OIDC mode the account menu is a 44px circle, so the row is shorter.

## 2. The icon clash with Alerts (D-24)

**Decision (UI-D1):** `Bell` belongs to Notifications, because people look for a bell in the header to find what waits for them. The Security Analyst sidebar's `Alerts` item (Phase 11 §1.1, row 6) changes from `Bell` to `AlarmClock`. An Alert is a derived due or overdue signal, so a clock fits it. `AlarmClock` is not used elsewhere, and it does not reuse an urgency icon (`CalendarX2`, `CalendarClock`, `Flag`) or a severity shape. After this change an Alert and a Notification never share a symbol. The planner places the one-line change in `navigation.ts` and its navigation unit test (see "Notes carried").

## 3. The notification item (X-34)

### 3.1 Anatomy

| Part | Contract |
|---|---|
| Kind icon | 16px, `--color-text-secondary`, `aria-hidden` (§3.3) |
| Sentence | The server's sentence, verbatim (§3.2), in `--text-body` and `--color-text-primary`: 500 while unread and 400 once read. It is never composed or edited by the web. It wraps anywhere. In the panel it clamps to three lines with the full text in the DOM; on the page it is shown whole |
| Meta line | `--text-caption`, `--color-text-secondary`, 4px below the sentence: the time (§3.4). While unread, the time is followed by ` · ` and the X-17 single-item marker (`New`) |
| Link | The sentence and meta line are one block link (§4 Record links, block links) to the destination (D-17), with a trailing 16px `ChevronRight` in `--color-text-muted`. Its accessible name is its content, with visually hidden `, ` separators. It opens in a new tab like any link |
| Mark control | Only on the page (§5.3); the panel has none (UI-D11) |
| Frame | Padding 12px by 16px, with 12px between the icon and the text. Items are divided by 1px `--color-border-default` hairlines; hover is `--color-bg-hover`. Every item is at least the touch-target height |
| Read state | Follows the stored state at once, including optimistic changes (X-34; UI-D14) |

### 3.2 Sentences (D-16; the server's wording module)

A sentence is a lead clause, a colon, and then the record as `{identifier} · {name}` (X-4), with no closing full stop (UI-D5). A **person is named** only where the recipient's own read of the record shows that person (D-16). Otherwise the sentence **names the part**. When the `facts` envelope fails its parser, or the person cannot be resolved and the part is unknown, the sentence falls back to the **record level** (D-09). In that case a `note-added` notification opens the request page without the anchor.

| Kind | Recipient part | Named | Part-named | Record-level |
|---|---|---|---|---|
| `request-assigned` | `security-analyst` | `{Assigner} assigned you a request: {request number} · {request title}` | `A Security Analyst assigned you a request: …` | `Request assigned to you: …` |
| `questionnaire-released` | `requestor` | Never named (UI-D6) | `A Security Analyst released a questionnaire for you to answer: {questionnaire number} · {questionnaire title}` | `Questionnaire ready for you to answer: …` |
| `questionnaire-submitted` | `security-analyst` | `{Requestor} submitted answers to a questionnaire: {questionnaire number} · {questionnaire title}` | `The Requestor submitted answers to a questionnaire: …` | `Questionnaire answers submitted: …` |
| `assessment-released` | `requestor` | Never named (UI-D6) | `A Security Analyst released a risk assessment: {assessment number} · {request title}` | `Risk assessment released: …` |
| `note-added` | `requestor` | `{Author} added a note to a request: {request number} · {request title}` | `A Security Analyst added a note to a request: …` | `New note on a request: …` |
| `note-added` | `security-analyst` | `{Author} added a note to a request: …` | `The Requestor added a note to a request: …` | `New note on a request: …` |

Further rules:
- **Assessment naming:** an assessment has no title, so it is named by its number and its request's title (D-16).
- **Release and close (Phase 17.1):** `assessment-released` stays one kind (Orchestrator Confirmation). The wording module therefore chooses its lead clause from the request's status when the notification is read. Phase 17.1 adds the `closed` lead, proposed as `A Security Analyst released a risk assessment and closed its request: …`, with its record-level form `Risk assessment released and request closed: …`. Phase 17.1 confirms the wording. This phase builds only the selection point.
- **Requesting analysts:** a requesting analyst receives requestor-part sentences, unchanged (D-08).

### 3.3 Icons per kind

| Kind | Icon | Matches |
|---|---|---|
| `request-assigned` | `UserRoundCheck` | Phase 13's `Assigned to me` |
| `questionnaire-released` | `ClipboardList` | The Requestor's `My questionnaires` |
| `questionnaire-submitted` | `ClipboardCheck` | The analyst's `Questionnaires` |
| `assessment-released` | `ShieldCheck` | `My risk assessments` |
| `note-added` | `MessageSquareText` | Notes (X-17's `MessageSquareDot` stays the unread-count mark) |

Later phases add a row here for each kind they add (D-12).

### 3.4 Times

Times use X-3's absolute instant through `LocalInstant` in a `<time dateTime>`: `1 Oct 2026, 3:47 pm`. No relative times are used (UI-D8). Items are not grouped by day (UI-D9).

## 4. The panel (D-26; X-35)

### 4.1 Frame per width

| Width | Contract |
|---|---|
| From 768px | A non-modal popover anchored below the control's end edge with an 8px offset. It is 480px wide (§4 Dialogs confirm width), bounded by the viewport less the page gutter. Its list scrolls within the viewport height less the header height and 48px. Surface, border, `--radius-lg` and `--shadow-overlay` follow §4 for popovers. The breakpoint is chosen when the panel opens; if the width crosses 768px while it is open, it closes |
| Below 768px | A full-screen modal sheet with a title row and `Close`, like X-13's phone form. The footer is pinned at the bottom |

### 4.2 Contents, in order

1. **Title row:** an h2 `Notifications` in `--text-heading-sm`. Below 768px, an icon-only `Close` circle at the touch-target size follows it.
2. **Status row,** 16px padding:
   - while any notification is unread: the figure link `{n} unread` (X-10; `--text-caption` at 500 with the record-link treatment; accessible name `{n} unread notifications`) opens `/app/notifications?view=unread`, and the ghost small pill `Mark all as read` sits at the row's end (touch-target height below 768px);
   - when nothing is unread: `No unread notifications` in `--text-caption` and `--color-text-secondary`, and no button.
3. **List:** a `ul` named `Latest notifications` holding the latest 10 notifications, read and unread, newest first (UI-D10), as §3 items. It has 4px padding so no focus ring is clipped.
4. **Footer,** above a hairline: `View all notifications`, an outline pill link to `/app/notifications` (full width at the touch-target height below 768px). It is hidden while the person has no notifications at all.

### 4.3 States

| State | Contract |
|---|---|
| Loading | Nothing for 300ms, then four skeleton items mirroring §3.1: an icon block, a sentence block at about 75% width, and a meta block at about 30% width, at the item height. The list has `aria-busy` |
| First use | No notification at all: the compact shared state `No notifications yet`, with `You’ll be told here when a request, questionnaire or risk assessment needs you.` It has no action, and the footer is hidden (UI-D22) |
| All read | Status row `No unread notifications`, with the recent items listed as read |
| Error | `We couldn’t load notifications` with a ghost small `Try again` that re-reads the list and the count. The header capsule is hidden, as for any failed read |
| Refused (403) | The control is not rendered without the capability; a 403 here shows the error state's copy with `Refresh page` (family T, T7) |

### 4.4 Focus and keyboard

- **Open:** `Enter` or `Space` on the control opens the panel, and focus moves to its title (`tabindex="-1"`).
- **Tab order:** the unread figure, `Mark all as read`, each item, then `View all notifications` (below 768px, `Close` comes first).
- **Escape:** closes the panel and returns focus to the control.
- **From 768px:** moving focus out of the popover or clicking outside it closes it. Below 768px, focus is trapped in the sheet.
- **After `Mark all as read`:** the button leaves, so focus moves to the panel title (UI-D13).

### 4.5 Opening an item (D-19; research Pattern 8; Phase 11 §4.6)

- **Activation:** activating an item applies its read state and the count change at once, closes the panel and navigates. The mark is sent without blocking the navigation.
- **Guard:** when the guard is blocking (a Requestor with unsaved answers), Phase 10's leave dialog opens above the panel:
  - `Keep answering` returns focus to the item, which stays unread;
  - `Leave questionnaire` opens the item.
- **New tabs:** a modifier click or middle click opens a new tab and marks the item read, and the panel stays open. "Open in new tab" from the context menu leaves the item unread, an accepted limitation (UI-D24).
- **Focus after navigating:** focus returns to the header control, which persists, and the router announces the page title. A `note-added` destination focuses its note instead (Phase 13 §8.2).

### 4.6 Loading on demand (D-32)

The panel's code loads through `next/dynamic`, prefetched on pointer enter or focus of the control (Phase 11 §4.7). If the control is activated before the code arrives, the frame opens with the §4.3 skeleton. If the code cannot load, the frame shows the error state, and `Try again` loads it again. `performance.spec.ts` budgets hold.

## 5. The Notifications page (D-27)

### 5.1 Route and frame

| Part | Contract |
|---|---|
| Route | `/app/notifications`. It is not a sidebar item; the header control and the panel's footer are its entries |
| Heading and route title | `Notifications`; `Notifications \| IdamBox CSRM` (Phase 11 §2.1 pattern, `page-headings.ts`) |
| Description | `Updates on the requests, questionnaires and risk assessments you work on. Open one to go to its record.` |
| Header action | `Mark all as read`, an outline pill, shown while any notification is unread and absent otherwise (UI-D17); full width below 768px (§4 Page header) |
| Width | `--spacing-container-max` (UI-D15) |
| Gate | `notification:read`; otherwise the shared permission state, with `Notifications` as its area |

### 5.2 View control

A `SegmentedControl` named by the visible label `Show`, with `All` (the default) and `Unread`. It is a closed URL filter: `view=unread`, or no parameter for All. Choosing a view resets to page 1. Unknown or invalid `view`, `page` and `size` values fall back to the defaults, and a page beyond the last shows the last page. While the next view loads, the current list stays at the §5 pending opacity, with a skeleton after 300ms.

### 5.3 List, marks and pagination

| Width | Contract |
|---|---|
| From 768px | One `--color-bg-surface` card (§4 Cards, no hover) holding a `ul` named after the view (`All notifications`, `Unread notifications`) of §3 items. Each row ends with its mark control: a ghost small pill, `Mark as read` or `Mark as unread`, described by the item's sentence (`aria-describedby`), 16px from the end edge and vertically centred |
| Below 768px | One §4 card per notification, 12px apart, at 16px padding. The block link comes first, then the mark control as a full-width ghost pill at the touch-target height above a hairline. The sentence is shown whole |
| Pagination | The shared list pagination with its total and `Rows per page` (10, 25 or 50; default 25), newest first. In the Unread view the total equals the header count (one predicate, D-14) |
| Density | One comfortable density with no toggle (UI-D15) |

**Unread view:** an item marked read stays in place, shown as read, until the view is next loaded. Its own toggle therefore reverses the mark in place (X-34). `Mark all as read` likewise leaves the items in place, shown as read.

### 5.4 States

| State | Contract |
|---|---|
| Loading (`loading.tsx`) | The real heading and `Show`, then a list card of eight skeleton items mirroring §5.3 (the mark pill as a 32px block), after 300ms, following the existing route loading files |
| First use (All, none at all) | `No notifications yet` · `You’ll be told here when a request, questionnaire or risk assessment needs you.` · primary pill `Go to Home` (UI-D22) |
| Cleared (Unread, none unread) | `No unread notifications` · `Notifications you’ve read stay in All.` No action (§4 Empty states, cleared) |
| Error (`error.tsx`) | `We couldn’t load notifications` · `Try again` |
| Permission | The shared permission state for `Notifications` |

## 6. Marks, Undo and refusals (D-19 to D-23, D-29)

### 6.1 Behaviour

| Action | Feedback | On failure |
|---|---|---|
| Open (§4.5) | The item shows as read and the count drops at once | The item and count revert, and a T5 toast appears |
| `Mark as read`, `Mark as unread` (page) | The item and count change at once; the button's label swaps, and the button is at pending opacity with `aria-busy` until the server answers. A polite status reads `Marked as read` or `Marked as unread`. No toast (UI-D18) | The item reverts (§5 rollback), and a T1 or T2 toast appears |
| `Mark all as read` (panel, page) | Every unread item shown and the count change at once. Then an X-14 toast: `Marked {n} notification as read` or `Marked {n} notifications as read`, with `Undo`. When the server changed none, there is no toast (UI-D18). Focus moves to the panel title or the page `h1` (UI-D13) | Everything reverts, and a T3 toast appears |
| `Undo` | Marks unread exactly the notifications that action marked, by its read time (Orchestrator Confirmation). Confirms with `Marked {n} notification as unread` or `Marked {n} notifications as unread` | A T4 toast appears |

No mark revalidates the page. Each mark returns the exact unread count, and the header adopts it under §1.2's `asOf` rule. No GET marks anything, and a destination page never marks its notification (D-23).

### 6.2 Refusal copy (new family T, added to Phase 10 §10.2 and `refusal-copy.ts`)

| Code | When | Toast (danger unless noted; danger toasts persist until dismissed) |
|---|---|---|
| T1 | Mark as read failed | `We couldn’t mark this notification as read` · `Try again in a moment.` · `Try again` |
| T2 | Mark as unread failed | `We couldn’t mark this notification as unread` · `Try again in a moment.` · `Try again` |
| T3 | Mark all as read failed | `We couldn’t mark your notifications as read` · `Try again in a moment.` · `Try again` |
| T4 | Undo failed | `We couldn’t undo that` · `Your notifications are still marked as read.` · `Try again` |
| T5 | The mark sent on opening failed | `We couldn’t mark a notification as read` · `{identifier} · {name} is still unread in your notifications.` (the record fields of D-16) · no action |
| T6 | 404 on a page mark: the notification is no longer visible (D-15) | Info: `This notification is no longer available` · `You can no longer open its record, so it has left your notifications.` The item leaves the list and the count is re-read. On opening, a 404 is silent, because the destination page explains (UI-D19) |
| T7 | 403 | `You don’t have access to notifications` · `Refresh the page to see what you can open.` · `Refresh page` |

A 400 or an unexpected failure uses T1 to T4 by action. Service-unavailable copy stays Phase 10's.

## Decisions recorded

These were made without asking (auto mode), following the locked context, `AGENTS.md`, the glossary and the direction.

| # | Decision | Reason |
|---|---|---|
| UI-D1 | Notifications take `Bell`; the `Alerts` sidebar item takes `AlarmClock` (§2). | The bell is where people look for what waits for them. An Alert is time-based. No urgency or severity icon is reused. |
| UI-D2 | The control is icon-only at every width, with no visible label, shortcut or tooltip. | A labelled pill does not fit the header beside `Search` and the role tag. No new shortcut means no conflict with `Ctrl+K`. A tooltip would put meaning behind hover (do-not 11). |
| UI-D3 | The capsule caps at `99+`; the name always carries the exact count from hidden text. | The capsule needs a bounded width. D-24 asks for the exact count in the name. |
| UI-D4 | Below 768px `Menu` becomes an icon-only circle and the header gap is 8px (X-33). | §1.3: without it the 375px row is about 382px for 343px. Names are unchanged, so existing locators hold. |
| UI-D5 | A sentence is `{lead}: {identifier} · {name}`, with no closing full stop. | It names the record by number and title (criterion 2) at the end, where a long title clamps. Titles may end in punctuation. |
| UI-D6 | The release kinds name the part (`A Security Analyst`), never the releaser. | Research A5: the Requestor's questionnaire read does not show the releaser. One rule for both release kinds is safe from leaks. |
| UI-D7 | The record's number and title fields are not shown again in the item; the web uses them only in T5. | The sentence already carries them, and repeating them in the item adds noise. |
| UI-D8 | Times are absolute (X-3), never relative. | Relative times would need a timer to stay true (do-not 9) and a new format. |
| UI-D9 | No day grouping. | Groups split across pages and add headings to a ten-item panel. Each item shows its time. |
| UI-D10 | The panel lists the latest 10, read and unread together. | It shows recent context and the all-read state in one list. The page holds the rest. |
| UI-D11 | The panel has no per-item mark. | One Tab stop per item; per-item marks live on the page (D-27). |
| UI-D12 | The panel is 480px wide from 768px. | It uses the direction's confirm-dialog width, the narrowest §4 overlay width that fits a two-line sentence with a long title. |
| UI-D13 | After `Mark all as read`, focus moves to the panel title or the page `h1`. | The button leaves when nothing is unread, and focus must not be lost (2.4.3). |
| UI-D14 | An unread marker follows the read state at once, unlike X-17. Items in the Unread view stay in place until reload. | Reading a notification is explicit, so the marker must reflect it. Staying in place lets the toggle and Undo reverse without the list jumping. |
| UI-D15 | The page is container width, with one comfortable density and no toggle. | It is a feed of sentences, a reading page rather than a data table (D-29 invited the argument). |
| UI-D16 | Views use the `Show` segmented control (`All` default, `Unread`) in the URL. Pages are 10, 25 or 50 rows, default 25. | Two options suit a segmented control (§4 Forms), and URL state survives reloads. |
| UI-D17 | `Mark all as read` is hidden, not disabled, when nothing is unread. | There is nothing to do, and the status row already says `No unread notifications`. |
| UI-D18 | Single marks confirm in place with a polite status and no toast. `Mark all as read` uses the Undo toast, and shows no toast when nothing changed. | A single toggle reverses itself (D-29). An empty Undo would mislead. |
| UI-D19 | A 404 on opening is silent; a 404 on a page mark removes the item with T6. | On opening, the destination's not-found state already explains. On the page, the item must leave visibly. |
| UI-D20 | The count is re-read once after each navigation and after Phase 13's silent note read, never on a timer. X-33 records this reading of do-not 9. | Orchestrator Confirmation; research Pitfall 8. |
| UI-D21 | `assessment-released` chooses its lead clause from the request's status at read time. Phase 17.1's `closed` wording is proposed in §3.2. | Orchestrator Confirmation: one kind serves release and close. |
| UI-D22 | Page first use offers `Go to Home`. The panel's first use has no action and no footer. | Home lists the work itself (D-28). A popover with a call to action and nothing to show would compete with the page. |
| UI-D23 | Refusal copy is a new family T. | It is the next free letter after Phase 19's S. |
| UI-D24 | A context-menu "Open in new tab" leaves the notification unread. | It cannot be detected (research Pattern 8). The person can mark it on the page. |
