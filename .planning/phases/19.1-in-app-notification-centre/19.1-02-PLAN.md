## Phase Goal

**As a** Requestor, a risk owner or a Security Analyst, **I want to** be told in the app when work waits for me and to open it in one step, **so that** nothing waits unseen between the people in the flow.

This plan's slice: the approved entity exists and a notification can be stored and worded. The schema, the kind registry, the facts envelope, the read-time wording and destinations, and the one eligible-person predicate, proven by a mounted write and read and by unit tests at their seams.

## Recorded planning decisions

- **Registry shape.** `notification-kinds.ts` exports `NOTIFICATION_UID = "api::csrm-notification.csrm-notification"`, `NOTIFICATION_KINDS` and `NOTIFICATION_PARTS` (`as const`), `type NotificationKind`, `type NotificationPart`, `type NotificationKindSpec = { kind; parts: readonly NotificationPart[]; subject: "request" | "questionnaire" | "assessment"; recipients: "new-assignee" | "requestor" | "assigned-analyst" | "note-other-part"; analystReadOperation: string | null; namesActor: Readonly<Record<NotificationPart, boolean>>; usesNoteAnchor: boolean }`, a `KIND_SPECS` object `satisfies Record<NotificationKind, NotificationKindSpec>` read only through a `Map` (`notificationKindSpec(value: unknown): NotificationKindSpec | null`), `isNotificationKind`, `isNotificationPart`. Rows: `request-assigned` (parts `security-analyst`; subject `request`; recipients `new-assignee`; analyst read `CSRM_ASSESSMENT_REQUEST_OPERATIONS.findOne`; names the actor); `questionnaire-released` (`requestor`; `questionnaire`; `requestor`; null; never names); `questionnaire-submitted` (`security-analyst`; `questionnaire`; `assigned-analyst`; `CSRM_QUESTIONNAIRE_OPERATIONS.findOne`; names the actor); `assessment-released` (`requestor`; `assessment`; `requestor`; null; never names); `note-added` (`requestor` and `security-analyst`; `request`; `note-other-part`; `CSRM_REQUEST_NOTE_OPERATIONS.list`; names the actor; note anchor). Plan 19.1-03's service implements the four recipient rules; Phase 17 adds its own rows and rules (for example the participants of `response-requested`). Confirm each analyst read against the first service call of its destination page (`/app/review/requests/[documentId]`, `/app/review/questionnaires/[documentId]`) and record any change in the summary (research A3).
- **Acting and reversal reads (D-12, D-20, D-21).** `NOTIFICATION_ACTING_READS` keyed by act: `submit-questionnaire` → kinds `questionnaire-released`, subject `questionnaire`; `persist-assessment-draft` → kinds `questionnaire-submitted`, subject `questionnaire`. `NOTIFICATION_REVERSAL_READS` keyed by reversal: `change-assignee` → part `security-analyst`, every kind, subject `request`, recipient the former assignee; `return-questionnaire-to-review` → kinds `questionnaire-released` and `questionnaire-submitted`, subject `questionnaire`, any recipient; `revert-answers-to-draft` → kinds `questionnaire-submitted`, subject `questionnaire`, any recipient. Both `as const satisfies`; plan 19.1-03's repository reads them.
- **Envelope.** `notification-facts.ts`: `NOTIFICATION_FACTS_SCHEMA_VERSION = 1`; `buildNotificationFacts(kind, { actorDocumentId, note? })` returning `{ schemaVersion: 1, actorDocumentId }` or, for `note-added`, with `noteDocumentId` and `noteSequence`; it throws `NotificationFactsError` for a missing or malformed value, so a write can never store a bad envelope. `parseNotificationFacts(kind, value)` returns the typed envelope or null when the value is not an object, the version differs, a key is unknown or missing, an id is not a 1 to 255 character string, or the sequence is not a positive safe integer.
- **Projection.** `notification-projection.ts` exports `type NotificationRow = { documentId; kind; recipientPart; facts; notifiedAt: Date; readAt: Date | null; request: { documentId; requestNumber; title; requestStatus }; questionnaire: { documentId; questionnaireNumber; title } | null; assessment: { documentId; assessmentNumber } | null }`, `notificationSentence(row, people)`, `notificationDestination(row, facts)` and `projectNotification(row, people)` returning `{ documentId, kind, notifiedAt, readAt, sentence, recordNumber, recordTitle, destination }` (ISO strings for times) or null for an unknown kind or part. `people` is a `ReadonlyMap<string, Person>` from 13-03's `resolvePeople`. The record is `{identifier} · {name}` with the middle dot U+00B7 between single spaces (X-4); `questionnaire-released` and `questionnaire-submitted` name the questionnaire by its number and title, `assessment-released` the assessment by its number and its request's title, the other kinds the request by number and title. `assessmentReleasedLead(requestStatus)` is a closed map whose only entry in this phase is the release lead; any other status reads the release lead too, and Phase 17.1 adds `closed`. Destinations use `encodeURIComponent` on every id.
- **Sentences** (19.1-UI-SPEC §3.2, verbatim, `{record}` = `{identifier} · {name}`, no closing full stop):
  - `request-assigned`/`security-analyst`: `{Assigner} assigned you a request: {record}` · `A Security Analyst assigned you a request: {record}` · `Request assigned to you: {record}`.
  - `questionnaire-released`/`requestor`: `A Security Analyst released a questionnaire for you to answer: {record}` · record level `Questionnaire ready for you to answer: {record}`.
  - `questionnaire-submitted`/`security-analyst`: `{Requestor} submitted answers to a questionnaire: {record}` · `The Requestor submitted answers to a questionnaire: {record}` · `Questionnaire answers submitted: {record}`.
  - `assessment-released`/`requestor`: `A Security Analyst released a risk assessment: {record}` · record level `Risk assessment released: {record}`.
  - `note-added`/`requestor`: `{Author} added a note to a request: {record}` · `A Security Analyst added a note to a request: {record}` · `New note on a request: {record}`.
  - `note-added`/`security-analyst`: `{Author} added a note to a request: {record}` · `The Requestor added a note to a request: {record}` · `New note on a request: {record}`.
  A kind that names the actor uses the person's `displayName` when `people` resolves the envelope's `actorDocumentId`, the part-named form when it does not, and the record-level form when the envelope fails its parser.
- **Destinations (D-17).** `requestor`: `questionnaire-released` → `/app/questionnaires/{questionnaireId}`; `assessment-released` → `/app/assessments/{assessmentId}`; `note-added` → `/app/requests/{requestId}#note-{noteDocumentId}`. `security-analyst`: `request-assigned` → `/app/review/requests/{requestId}`; `questionnaire-submitted` → `/app/review/questionnaires/{questionnaireId}`; `note-added` → `/app/review/requests/{requestId}#note-{noteDocumentId}`. On a failed envelope, `note-added` drops the anchor.
- **Harness.** `CsrmFixtureUid` gains `"api::csrm-notification.csrm-notification"`; the harness gains `getNotifications(userDocumentId): Promise<Record<string, unknown>[]>` (Document Service `findMany` filtered by the recipient's documentId, populating the request, questionnaire and assessment, newest first). Failure injection reuses the existing `withDocumentWriteFailure(uid, "create", failAt, action)`, so no second injector is added (research suggested `withNotificationCreateFailure`).
