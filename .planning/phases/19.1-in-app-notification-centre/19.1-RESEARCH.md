# Phase 19.1: In-app notification centre - Research

**Researched:** 2026-10-01
**Domain:** Strapi 5 transactional writes and SQL read predicates (SQLite in development and tests, PostgreSQL by construction), Next.js 16 App Router refresh semantics, header and panel UI on shadcn/Radix
**Confidence:** HIGH for the transaction, SQL and Next.js mechanics (read in the installed sources this session); MEDIUM for PostgreSQL behaviour (no PostgreSQL run exists: R-08-37); LOW only where tagged `[ASSUMED]`.

## Summary

Every open research question has an answer in the installed sources.

1. **Notification writes join the event's transaction.** Strapi 5.51.0 keeps the open transaction in an `AsyncLocalStorage` context. Every Document Service method is wrapped in `strapi.db.transaction(...)`, and when a transaction is already open that call reuses it and its commit and rollback do nothing. So `strapi.documents(NOTIFICATION_UID).create(...)`, called inside `strapi.db.transaction(async ({ trx }) => …)`, joins it, relation links included. A thrown error rolls back the event and the notification together. The per-document promise-tail queues (`serializeGovernanceMutation`, `serializeAssessmentMutation`, Phase 13's `withRequestLock`) only order work inside the process, and need nothing new. Two traps remain:
   - **Raw knex.** `strapi.db.connection` ignores the ALS context. On SQLite, whose knex pool is `max: 1`, a raw query inside a transaction waits about 60 s for the pool and then fails (13-RESEARCH Pitfall 1).
   - **`updateMany` with a relation filter.** `strapi.db.query(uid).updateMany({ where: <relation filter> })` is broken in 5.51.0: it builds an `UPDATE` with no data and throws (fixed upstream in strapi/strapi#26909, not in the installed version).

2. **Counts.** The exact-count question is settled by one knex repository in the shape of `request-status-summary.ts` and `review-queue-repository.ts`:
   - **Base relation:** `csrm_notifications` joined to its recipient link (indexed) and to its request, bounded by `notified_at <= asOf`, then filtered by a per-part readability predicate. The predicate composes the record reads' own rules: the questionnaire release fact, Phase 19's released-assessment predicate as an SQL twin beside it, and the request requestor link. The caller's analyst standing is a set of booleans per kind, computed once from the grants the policy already loaded.
   - **One predicate, four uses:** the page, the total, the unread figure and "Mark all as read" all use it. "Mark all as read" is one `UPDATE … WHERE id IN (<predicate>) RETURNING id` inside a transaction (verified on the bundled SQLite 3.51.3).
   - **Oracle:** an integration test compares the repository with a semantic oracle that calls the record predicates themselves, so the totals stay exact and any drift is caught.

3. **The header count.** It cannot refresh on client navigation by itself: layouts do not re-render, and that is documented. It does refresh on a full load, a router refresh, and any Server Action that revalidates or calls `refresh()`. The installed source shows why: an action request carries no `RSC` header, so the server renders the whole tree from the root layout, which settles Phase 11's assumption A2. The recommendation is a small client store in the trigger:
   - seeded from the layout's unawaited promise;
   - updated by every notification action's returned exact count;
   - each value carries the server `asOf`, and the newer one wins;
   - re-read through a summary Server Action after each client navigation, which is event-driven, not polling (orchestrator to confirm against do-not 9).

**Primary recommendation:**
- **Strapi:** write notifications only through `strapi.documents(...).create` inside the event's transaction. Read and bulk-mark through one knex repository whose every query inside a transaction calls `.transacting(trx)`.
- **Web:** keep the count in a client store reconciled by `asOf`, and open a notification through `Link`'s `onNavigate` with Phase 10's guard, firing the mark as the navigation proceeds.

### Writing notifications (decision 18; 17 D-56)

- **D-05:** A notification is one fact per recipient per event, written in the same transaction as the event it reports, through one notification service the workflows call (for example `notify({ kind, subject, actor, facts })` resolving its recipients inside the transaction). The workflows call it explicitly; no Strapi lifecycle hook writes notifications, because recipients depend on the workflow's actor and state, and hooks would fire for seeds and imports too. If writing the notification fails, the event's transaction fails with it, so no event lacks its notification and no notification describes an event that did not happen. Research confirms that the document service joins the workflow's `strapi.db.transaction` for these writes. **Reversibility:** costly - every event hook relies on the transactional contract.
- **D-06:** Who is never told.
  - **The person who acted**, the **service identity** (an IdamBox User holding the Security Analyst Agent role) and an **inactive user**: the service skips them through D-07's predicate, checked at the moment of the event.
  - **Nobody, for "the assigned analyst" while the request is unassigned:** the queue's unassigned pool (Phase 13 D-14) is the team's channel, and nothing fans out to every analyst.
  - **Nobody for AI or job events:** AI runs, job completions and the service identity's acts create no notification in this phase ("AI proposals ready" is deferred, as Phases 15 and 16 recorded).
- **D-07:** The eligible-person predicate moves forward from Phase 17 D-16 into this phase, because 19.1 executes first and needs it for recipients: one shared module (for example `apps/backend/src/csrm/people/eligible-person.ts`) answering "an active IdamBox User who does not hold the Security Analyst Agent role". Phase 13's assignee eligibility (its D-06) composes it with the human analyst role, and Phase 17 reuses it, unchanged, for risk owners, control owners and the people search. If Phase 13's plans have already built an equivalent check inside its assignee eligibility, this phase factors it out rather than writing a second one.
- **D-08:** Each notification records the part its recipient was told in, `recipientPart`, a closed vocabulary that reuses Phase 13's `authorPart` values: `requestor` and `security-analyst` now. Phase 17 adds its participant parts (for example `risk-owner`) and Phase 17.1 `executive-approver`, extending it as they extend the kinds. The part chooses the readability predicate (D-13) and the destination (D-17). An analyst who raised a request is told about it as its Requestor and sent to the Requestor's pages, where that work waits, as Phase 11 reads an analyst's own requests "from the Requestor's side" (11 D-03) and Phase 13 files a requesting analyst's notes in the Requestor's part (13 D-07, D-23). **Reversibility:** costly - a stored vocabulary that readability and destinations read.
- **D-09:** The `facts` envelope is versioned and holds only identifiers and numbers: the acting person's id, a note's id and per-request sequence, and later a round number or the id of a decision or contest point. It never holds a title, a name or Requestor text. A closed parser per kind reads it and fails safe (the 06.8 posture): readability never reads the envelope, and a notification whose envelope cannot be parsed is still listed, worded at the record level and sent to the record's page rather than an anchor.
- **D-10:** No backfill and no seed. Notifications start when this phase is deployed: assignments, notes, releases and submissions made earlier notify nobody. The development seed creates none (they would be fabricated events), so a fresh development database shows the centre's first-use empty state until someone acts.

### The first kinds (decision 18; G-19; 17 D-57)

- **D-11:** The kinds in this phase, a closed vocabulary in code (one registry module) and in the contract:

  | Kind | Event | Recipient and part | Subject relations | Destination (D-17) | Read by acting (D-20) | Read by reversal (D-21) |
  |---|---|---|---|---|---|---|
  | `request-assigned` | Someone else assigns or reassigns a request to an analyst (Phase 13 D-05, D-12); never picking it up oneself | The new assignee, `security-analyst` | request | The analyst request page | — | A later assignment change that takes the request away from them (reassign, unassign or Undo) |
  | `questionnaire-released` | A questionnaire is released or released again (06.8) | The Requestor, `requestor` | request, questionnaire | The Requestor's questionnaire page | The recipient submits that questionnaire | The questionnaire returned to analyst review |
  | `questionnaire-submitted` | The Requestor submits the answers | The assigned analyst, `security-analyst` | request, questionnaire | The analyst questionnaire page | The recipient starts the assessment draft from it | The answers returned to draft (06.1, by either party), or the questionnaire returned to analyst review |
  | `assessment-released` | v1 release (Phase 17.1 replaces it with released and closed for new events) | The Requestor, `requestor` (Phase 17 adds every participant once the gate is open) | request, assessment | The Requestor's released assessment page | — | — (a released record is immutable, decision 9) |
  | `note-added` | A note is posted (Phase 13) | The other part: the Requestor for an analyst's note (`requestor`), the assigned analyst for a note in the Requestor's part (`security-analyst`) | request; note id and sequence in `facts` | The request page for that part, at the note (`#note-{id}`, Phase 13 UI-SPEC) | The recipient's note read state passes the note (D-22) | — (notes are append-only) |

  The assignment operation writes `request-assigned` inside its own compare-and-set transaction (Phase 13 D-05, D-09), rather than the centre reading the assignment history afterwards (Phase 13 D-12's wording), so D-05's rule holds. A note posted by an analyst who is not the assignee still notifies the Requestor; a colleague's analyst note does not notify the assignee, matching Phase 13's unread rule (notes in one's own part are never new to one). Files posted with a note ride on its `note-added` (Phase 14 D-17); there is no file kind. **Reversibility:** costly - published kind values.
- **D-12:** How later phases extend the centre, without a schema change (Phase 12's run `operation` precedent):
  - **One registry** holds each kind's parts, subject relations, readability, wording, destination, and its acting and reversal reads. A later phase adds rows there, extends the contract's kind and part enums, and extends the web's closed parser in the same plan.
  - **Phase 17** adds `response-requested` (to each participant asked) and `response-submitted` (to the assigned analyst), its participant parts, and every participant as a recipient of `assessment-released` once the gate is open. **Phase 17.1** adds acceptance requested, executive approval requested, decision recorded and voided, round recalled, and released and closed. **Phase 17.2** adds contest point raised and answered, and assessment returned (NOTIFY-04). **Phase 20** adds its reminders and escalations (NOTIFY-02, G-16, G-18). Sub-records (a round, a decision, a contest point) travel as ids in `facts`; the optional `risk` relation serves risk-scoped kinds.
  - **A kind is never removed** once notifications of it exist: when Phase 17.1 replaces `assessment-released` with released and closed for new events, earlier `assessment-released` notifications stay readable and worded.

### Readability (decision 18; G-12; 17 D-58)

- **D-13:** Nobody is told about a record they may not read. A notification is listed and counted only while its recipient may read its subject, decided when the list and the count are read, never from a stored copy of access, by the record reads' own predicates for the part it was told in:
  - **`requestor`:** the request's `requestor` is the recipient, and the subject is readable to them by its record rule: the questionnaire released (its dedicated release fact, 06.8, as `requireQuestionnaireReleasedForRequestor` gates it today); the assessment by Phase 19's one released-assessment predicate (19 D-14), which Phase 17 widens to participants and Phase 17.1 to `closed` in its one place, so this phase's readability follows with no change of its own; notes by Phase 13's notes predicate (`canUseRequestNotes`).
  - **`security-analyst`:** the recipient currently holds the human Security Analyst grant for the subject's read, as the policy decides it for the record read (any request, questionnaire or notes thread), and the subject exists.
  - **The subject gone:** a notification whose request, questionnaire or assessment no longer exists is not shown or counted.

  In this phase that hides, for example, the Requestor's `questionnaire-released` while the questionnaire is back in analyst review (06.8 clears its release fact), and every analyst-part notification of someone who no longer holds the Security Analyst role. From Phase 17, a former owner's notifications disappear with their read (17 D-22). **Reversibility:** costly - every list, count and mark reads it.
- **D-14:** Counts stay exact. The list total, the unread summary and the count that "Mark all as read" clears are the same predicate. The recommendation is SQL predicates in a repository, with exact totals checked against a semantic oracle (the Phase 7 D-21 and D-30 pattern): `recipient = caller`, then per part the joins above, with the caller's analyst standing computed once per request from the grants the policy already loaded. A bounded in-memory filter is the alternative; research chooses, provided counts stay exact at any volume and the totals equal the lists.
- **D-15:** A notification the caller cannot see is, for them, missing: marking it by id is 404, exactly as another person's notification is (D-03 item 3).

### Wording and destination (17 D-59)

- **D-16:** The server words each notification for its recipient when it is read, as `request-lifecycle.ts` words next actions today (Phase 11 D-27): one plain-text sentence that names the record by its number and title, plus the record's number and title as separate fields the web lays out ("{identifier} · {name}", X-4). An assessment, which has no title, is named by its number and its request's title. Titles are never stored, so a renamed request reads correctly and nothing is copied out of the record's own access rules. A sentence names a person (resolved from `facts` at read time) only where the recipient's own read of the record already shows that person, such as a note's author or, for an analyst, who assigned them; otherwise it names the part ("A Security Analyst released …"). The UI-SPEC writes the sentences; the web formats what it is given and never composes wording.
- **D-17:** The destination is the page the recipient's part opens, built by the server at read time: Requestor pages for the `requestor` part (`/app/requests/{id}`, `/app/questionnaires/{id}`, `/app/assessments/{id}`), analyst pages for the `security-analyst` part (`/app/review/requests/{id}`, `/app/review/questionnaires/{id}`), with the note anchor for `note-added`. This refines Phase 17 D-59's "actor class" to the part (D-08), so a requesting analyst lands where their Requestor work waits. The web's closed parser accepts a destination only as an in-app path of a known shape, so a server fault can never produce an outside link.

### Read state (17 D-60)

- **D-18:** Read state is per notification and per person: `readAt` on the recipient's own row (one reader per row, so no separate read-state table, unlike notes). Marking is idempotent; marking read again keeps the first read time; marking unread clears it.
- **D-19:** A notification is read when the person:
  - **opens it** from the panel or the page. Opening goes through Phase 10's navigation guard and its programmatic entry point (Phase 11 D-51), and reads the notification only when the navigation goes ahead, so a Requestor with unsaved answers who chooses "Keep answering" keeps it unread;
  - **marks it read**, one at a time;
  - **chooses "Mark all as read"**, which reads exactly the notifications the unread count counts, created up to the `asOf` of the view the person saw, so one that arrives later stays unread. It confirms with an Undo toast (X-14), whose Undo marks exactly those notifications unread again.

  A person can also **mark one unread** again. This and Undo are this phase's additions to Phase 17 D-60, from G-4's rule that reversible actions offer Undo.
- **D-20:** Acting on the work reads the actor's own unread notifications of that kind about that record, in the act's transaction (D-11's "Read by acting" column): submitting a questionnaire reads its `questionnaire-released`; starting the assessment draft from a questionnaire reads the actor's `questionnaire-submitted`. A colleague's act never reads someone else's notification; only a reversal does (D-21).
- **D-21:** Reversing the event reads the recipient's unread notification about it, in the reversing transaction, because the work no longer waits for them (D-11's "Read by reversal" column): an assignment taken away, or undone straight after it was made, leaves the former assignee nothing unread; answers returned to draft read the assigned analyst's `questionnaire-submitted`; a questionnaire returned to analyst review reads the Requestor's `questionnaire-released` (and the analyst's `questionnaire-submitted` when the answers had been submitted). The notification stays in the person's history as read, so a later release, with its own new notification, never brings the old one back unread. This is a refinement of Phase 17 D-60.
- **D-22:** A `note-added` notification is read when the person's note read state passes its note (Phase 13 D-24, with its sequence confirmation). Phase 13's "mark read through note N" operation reads, in its own transaction, the person's unread `note-added` notifications for that request whose note sequence is at most N. This refines Phase 17 D-60's "derived at read time": the observable rule is the same, and the count stays one predicate instead of a join to the read-state table. Reading a notification never moves the note read state, so the thread's "New" markers keep Phase 13's rule.
- **D-23:** No GET has a side effect: the list and the summary never mark anything, and every read is an explicit write (a mark, an act or a reversal). A test proves the reads leave `readAt` unchanged.

### Channels and retention (17 D-62, D-63)

- **D-33:** The centre is channel-neutral: a notification records that something waits for a person, and holds no channel or delivery field. Phase 20 adds its reminder kinds through the same service and its email delivery facts in its own entity or a dated amendment to this phase's record, without changing `CsrmNotification` (ROADMAP Phase 20: "Reminder delivery facts join Phase 19.1's notification record or get their own; the plan decides"). No email is sent here; the capture provider and the email plugin are Phase 20's (decision 18, G-7, G-18).
- **D-34:** Notifications are never deleted and never edited except for `readAt`, and they follow the request record's retention. A request deleted through the analyst-only core delete (possible only before it holds a note or an assessment: Phase 13 D-21, Phase 16's confirmation) takes its notifications out of every list (D-13), and nothing purges them. A shorter retention for read notifications is a candidate Admin setting in Phase 22.

### Roles, grants and catalogue (17 D-64)

- **D-35:** One new API-only Function (name by research, for example `function.notifications.notifications_api`) holds the three FunctionAPIs, in both catalogue copies, byte-identical. It is granted to `role.requestor` (the birthright every person holds) and `role.security_analyst`, and never to `role.security_analyst_agent`. A catalogue design note records it and amends note 6 for notifications. It is not in `HUMAN_ANALYST_ONLY_OPERATIONS`, because Requestors use it. No new IdamBox Role.
- **D-36:** The policy, for every notification operation:

### Pattern 1: The notification write joins the event's transaction (D-05)

**What:** Strapi 5 binds the open transaction to an `AsyncLocalStorage` store. `Database#transaction` reuses it when one exists, and only the outermost call commits or rolls back:

```js
// Source: apps/backend/node_modules/@strapi/database/dist/index.js:60-71 (verbatim excerpt, read this session)
    async transaction(cb) {
        const notNestedTransaction = !transactionContext.transactionCtx.get();
        const trx = notNestedTransaction ? await this.connection.transaction() : transactionContext.transactionCtx.get();
        async function commit() {
            if (notNestedTransaction) {
                await transactionContext.transactionCtx.commit(trx);
            }
        }
        async function rollback() {
            if (notNestedTransaction) {
                await transactionContext.transactionCtx.rollback(trx);
            }
        }
```

Every Document Service method is wrapped in that call:

```js
// Source: node_modules/.pnpm/@strapi+core@5.51.0_…/node_modules/@strapi/core/dist/services/document-service/common.js:3-5 (verbatim)
const wrapInTransaction = (fn)=>{
    return (...args)=>strapi.db.transaction?.(()=>fn(...args));
};
```
The repository wires `findMany`, `findFirst`, `findOne`, `delete`, `create`, `clone`, `update` and `count` through it (`document-service/repository.js:566-573`). The query builder's `execute` also attaches the ALS transaction (`@strapi/database/dist/query/query-builder.js:539-542`: `const transaction = transactionContext.transactionCtx.get(); if (transaction) { qb.transacting(transaction); }`). The entity manager's relation attach on `create` opens a nested `strapi.db.transaction()` (`entity-manager/index.js:217`), which reuses the outer one. [VERIFIED: the four files above, read this session]

**Consequences:**
- `strapi.documents(NOTIFICATION_UID).create({ data: { recipient, assessmentRequest, … } })` called inside `strapi.db.transaction(async ({ trx }) => …)` writes the row and its link rows in the event's transaction.
- A throw from `notify`, or from any later event write, rolls back both together. This is the same mechanism that already makes `submitQuestionnaire` roll back every answer (`questionnaire-workflow.integration.test.ts:356`, "mounted production submission rolls back every answer when its second update fails").
- **Guard:** `notify` should refuse to run outside a transaction, using `strapi.db.inTransaction()` (`index.js:57-59`: `return !!transactionContext.transactionCtx.get();`), so a future caller cannot write a notification without its event.
- **Per-document queues:**
  - the existing promise-tail maps (`questionnaire-governance-workflow.ts:150-165`, `questionnaire-workflow.ts:179-193`, `assessment-workflow.ts:379-396`, Phase 13's `withRequestLock`) order work inside the process per document;
  - `notify` adds an insert into another table, so the queues need no change;
  - `notify` must never call `withRequestLock` (13-03: never nested for one request). It runs inside whichever lock the event already holds.

**Where `notify` runs, by event:**
| Event | Transaction it joins | Lock held | Notes |
|---|---|---|---|
| `request-assigned` | Phase 13 `changeRequestAssignee` (`withRequestLock`) | request row | Write after the compare-and-set update; skip on the no-op (same target) |
| `questionnaire-released` | `releaseQuestionnaire` via `runGovernanceMutation` (`questionnaire-governance-workflow.ts:344-379`) | questionnaire row | Also on "released again" after a return to review |
| `questionnaire-submitted` | `submitQuestionnaire` via `runQuestionnaireMutation` (`questionnaire-workflow.ts:322-338`) | questionnaire row | Recipient is the assignee: see Pattern 2's race |
| `assessment-released` | `releaseAssessment` (`assessment-workflow.ts:509-549`) | assessment row | Requestor only in this phase; Phase 17 adds participants |
| `note-added` | Phase 13 `addRequestNote` (`withRequestLock`) | request row | Facts carry the note's `documentId` and `sequence` |

**The draft "act" (D-20):**
- `generateAssessment` only enqueues a job (`assessment-workflow.ts:843-853`), and the draft is persisted later, inside `persistAssessmentDraft`'s transaction (`assessment-workflow.ts:740-801`), for `initiatingAnalystDocumentId`.
- Reading the actor's `questionnaire-submitted` in that transaction means the notification is read exactly when the draft exists, and a failed job leaves it unread.
- That is a read, not a job event, so it does not breach D-06.

**What:** the kind's recipient function reads the request through the Document Service: `requestor`, and Phase 13's `assignedAnalyst` for "the assigned analyst". It reads each candidate's `accountStatus` and role names in the same transaction, and drops:

**Part (D-08):**
- the request's `requestor` is told in the `requestor` part, even when that person is an analyst;
- the assignee is told in the `security-analyst` part;
- `note-added` goes to the part opposite the note's `authorPart`.

**The PostgreSQL race (not reachable on SQLite):**
- `submitQuestionnaire` locks only the questionnaire row. Phase 13's reassignment locks only the request row.
- On PostgreSQL, a submit can read assignee A while a reassignment to B commits, then notify A after the reassignment's reversal read has run. A is left with an unread notification about work that is no longer theirs, and B is never told.
- **Remedy:** before reading the assignee, the "assigned analyst" recipient function takes the request row lock (`queryBuilder(REQUEST_UID).select(['id']).where({ documentId }).forUpdate().transacting(trx)`, the same shape as `lockAssessmentRequest`, `assessment-workflow.ts:715-722`).
- **Lock order:** questionnaire row, then request row. That order already exists: `submitQuestionnaire` updates the request status after locking the questionnaire, and assignment never touches a questionnaire, so no cycle forms.
- On SQLite, knex's single connection serialises every transaction, and knex skips `forUpdate` for SQLite.
- Record the construct in R-08-37 (no PostgreSQL run exists).

### Pattern 3: One readability predicate, in SQL, with an oracle (D-13, D-14, D-15)

**What:** the repository builds a base relation and a readability filter, and every read uses both:

- **Base:**
  - `csrm_notifications n` INNER JOIN its recipient link, `rl.idambox_user_id = :callerId`, where `:callerId` is the numeric id the policy resolved (as `countOwnedRequestsByStatus` uses `requestorId`);
  - INNER JOIN its request link and `csrm_assessment_requests r`, so "subject gone" means not listed;
  - LEFT JOIN the questionnaire and assessment links and rows;
  - `n.notified_at <= :asOf`, where `:asOf` is a `Date` taken once at the start of the read.
- **Readable:** an OR of the per-part, per-kind branches below. A branch that matches nothing hides the row, so an unknown kind or part fails closed.

| Part | Kind | Predicate (all must hold) | Source rule it composes |
|---|---|---|---|
| `requestor` | any | `r`'s requestor link names `:callerId` | request ownership (`requireRequestOwnership`) |
| `requestor` | `questionnaire-released` | questionnaire row exists, `q.released_at IS NOT NULL`, and the questionnaire's own request's requestor is `:callerId` | `requireQuestionnaireReleasedForRequestor` (`csrm-authorization.ts:379-391`, the release fact) |
| `requestor` | `assessment-released` | Phase 19's released-assessment predicate for `:callerId`, as its SQL twin | 19 D-14 / 19-RESEARCH Pattern 3 |
| `requestor` | `note-added` | the requestor branch above (the requestor always passes `canUseRequestNotes`) | 13-05 `canUseRequestNotes` |
| `security-analyst` | `kind IN (:analystKinds)` | the subject row exists (the questionnaire for `questionnaire-submitted`) | policy: `hasHumanAnalystOperation(explicitRoles, registry[kind].analystReadOperation)` |

**Analyst standing:**
- **Computed once:** the policy computes `analystKinds`, the kinds whose analyst read the caller holds through the human role, from the `grants.explicitRoles` that `loadEffectiveGrants` already returned (`csrm-authorization.ts:161-184`), and passes it on `ctx.state.csrmAuthorization`.
- **A parameter, not a join:** the list is always the caller's own, so the analyst part reduces to a bound list. Nothing is per row.
- **Operations per kind:**
  - `request-assigned`: the request read the analyst page uses (`CSRM_ASSESSMENT_REQUEST_OPERATIONS.findOne` = `"GET:/api/csrm-assessment-requests/{id}"`, `apps/backend/src/api/csrm-assessment-request/operations.ts`);
  - `questionnaire-submitted`: `CSRM_QUESTIONNAIRE_OPERATIONS.findOne` = `"GET:/api/v1/questionnaires/{questionnaireId}"` (`apps/backend/src/api/csrm-questionnaire/operations.ts`);
  - `note-added`: 13-05's notes list, `"GET:/api/v1/assessment_requests/{requestId}/notes"` (planned).
  - The registry fixes these; which read anchors each kind is `[ASSUMED]` until the planner confirms it against the destination page's first call.

**Composing, not restating:**
- **The repository's SQL twins:** the questionnaire and request rules are one-line facts (`released_at IS NOT NULL`, the requestor link).
- **The assessment predicate's SQL twin:** Phase 19 gathers the released-assessment predicate into one module in Document Service form (19-RESEARCH Pattern 3). 19.1 adds an SQL twin beside it, in the same module and under the same constants. The analyst queue already has the knex shape of "released means the complete triple" (`review-queue-repository.ts:99-111`); the Requestor form adds `r.request_status = 'approved'` and the requestor link (`assessment-scope.ts:159-189`, quoted in 19-RESEARCH).
- **Drift guard:** one oracle integration test seeds a matrix of states and asserts, for each caller, that the repository's ids, order, total and unread equal those of a semantic oracle. The oracle loads every one of the caller's notifications through the Document Service and filters them with the record predicates themselves: the policy's release rule, Phase 19's `findReadableReleasedAssessment` or its successor, and `canUseRequestNotes`. This is the Phase 7 D-21 and D-30 pattern. When Phase 17 widens the predicate to participants and 17.1 widens it to `closed`, the twin must follow, and the oracle fails if it does not.

**Exactness rules:**
- **One builder:** the page query, `COUNT(DISTINCT n.id)`, the unread count and the bulk-mark subquery are built from one function, so totals equal lists by construction.
- **Totals in one statement:** compute the total and the unread figure together (`COUNT(*)` and `SUM(CASE WHEN n.read_at IS NULL THEN 1 ELSE 0 END)`), so they share a snapshot. On PostgreSQL both come back as strings or bigints, so parse them with a `wholeCount` helper like `request-status-summary.ts:55-62`.
- **Order:** `n.notified_at DESC, n.id DESC`, which is stable.
- **Pages:** a closed size set (10, 25 or 50, proposed); an out-of-range page is 400 or an empty page, the planner's choice in line with the existing list conventions.
- **`asOf` bound:** every read uses `n.notified_at <= :asOf`, and the response returns that `asOf`. A notification committed during the read cannot skew one figure against another.

**Hidden means missing (D-15):**
- the mark-by-id path selects the requested ids through the same predicate, inside the transaction;
- if fewer ids come back than were sent, the whole call is 404 and nothing changes;
- another person's id fails the recipient join, so it gets the same 404.

**Indexes:**
- Strapi gives every link table an index on each FK column and a unique index on the pair, with `ON DELETE CASCADE` foreign keys (`@strapi/database/dist/metadata/relations.js:376-420`). So the recipient join is indexed, and deleting a request or user removes the link, which hides the notification.
- A schema.json cannot declare an index on `notified_at` or `read_at` `[ASSUMED]`, and D-01 keeps `database/migrations/` empty.
- Per-person volumes (hundreds to low thousands, never deleted per D-34) sort cheaply after the indexed recipient join. Record a volume residual and leave any index migration to Phase 22's retention work.

**Link table and column names:**
- **Rule:** the table is `{collectionName}_{attribute_in_snake}_lnk`, its columns are `{singular_snake}_id` and the target's `{singular_snake}_id`, and the target column for users is `idambox_user_id`. Existing tables confirm it: `csrm_questionnaires_assessment_request_lnk` with `csrm_questionnaire_id` and `csrm_assessment_request_id` (`review-queue-repository.ts:72-74`), and `csrm_assessment_requests_requestor_lnk` with `csrm_assessment_request_id` and `idambox_user_id` (`request-status-summary.ts:73-75`). [VERIFIED: both files, read this session]
- **Proposed for the new type:** `csrm_notifications_recipient_lnk`, `csrm_notifications_assessment_request_lnk`, `csrm_notifications_questionnaire_lnk`, `csrm_notifications_assessment_lnk` and `csrm_notifications_risk_lnk`. ### Pattern 4: Every `readAt` change is an explicit write (D-18 to D-23)

**Rule:** do not use `strapi.db.query(uid).updateMany` with a relation in `where` on 5.51.0.

**Why:**
- `entity-manager/index.js:352` builds `createQueryBuilder(uid).where(where).update(dataToUpdate)`;
- with a relation in `where` the builder adds joins, so `shouldUseSubQuery()` is true (`query-builder.js:251-256`);
- `runSubQuery()` then returns `connection[originalType]().whereIn('id', nestedSubQuery)` (`query-builder.js:263`), an `UPDATE` without its data. In knex 3.0.1, `knex('t').update().whereIn(...)` throws `Cannot convert undefined or null to object` (probed this session);
- upstream fixed it in strapi/strapi#26909 ("`runSubQuery()` now passing `state.data` into the outer UPDATE"), after 5.51.0.

[VERIFIED: source read and probe] [CITED: github.com/strapi/strapi/pull/26909]

**The write paths, all in the repository, all in a transaction, every raw query `.transacting(trx)`:**
| Path | SQL shape | Bound |
|---|---|---|
| Mark by ids (1 to 50, read or unread) | select the readable ids among the request, 404 if any is missing; then `UPDATE csrm_notifications SET read_at = :now WHERE id IN (:ids) AND read_at IS NULL` (read), or `SET read_at = NULL WHERE id IN (:ids)` (unread) | Marking read again keeps the first time (D-18) |
| Mark all, up to `asOf` | `UPDATE csrm_notifications SET read_at = :markedAt WHERE id IN (<readable predicate> AND n.read_at IS NULL AND n.notified_at <= :asOf) RETURNING id` | Exactly the unread count's rows (D-19) |
| Undo of mark all | `SET read_at = NULL` on the caller's readable rows changed by that call (Open Question 2) | Only rows still holding that read |
| Acting read (D-20) | recipient = actor, `kind = :kind`, subject link = `:subject`, `read_at IS NULL` | In the act's transaction |
| Reversal read (D-21) | `kind = :kind`, subject link = `:subject`, `read_at IS NULL`, any recipient (former assignee for assignment) | In the reversing transaction |
| Note read (D-22) | candidates: recipient = reader, `kind = 'note-added'`, request link = `:request`, unread; at most the 500 notes a request may hold (13-05's `NOTES_PER_REQUEST_MAX`, planned); parse `facts.sequence` in code; update the ids whose sequence ≤ N | Dialect-neutral: no JSON SQL on SQLite TEXT vs PostgreSQL jsonb |

Both `RETURNING` and an `UPDATE … WHERE id IN (SELECT … FROM same_table …)` run on the bundled SQLite: `update t set r=? where id in (select id from t where r is null) returning id` returned both rows. knex compiles `.returning('id')` for better-sqlite3. [VERIFIED: probe this session] PostgreSQL supports both; whether the repository's statements run there is `[ASSUMED]` until R-08-37's run.

**Dates:**
- **Bind `Date` objects, never ISO strings,** in every raw comparison and update.
- **Why:** Strapi's datetime field turns values into a `Date` (`fields/datetime.js` `toDB` → `parseDateTimeOrTimestamp`), and knex's better-sqlite3 dialect binds a `Date` as `binding.valueOf()`, epoch milliseconds (`knex/lib/dialects/better-sqlite3/index.js:54-61`). So SQLite stores datetimes as integers. An ISO-string binding there compares text against integers and silently returns wrong rows.
- **On PostgreSQL,** the `pg` driver serialises a `Date` itself.

[VERIFIED: source read]

**No GET side effect (D-23):** the list and summary controllers call only read functions. An integration test snapshots `read_at` for the caller's rows before and after both GETs.

### Pattern 7: When the header count refreshes (D-25)

**Settled from the installed Next.js 16.3.6:**

- **Client navigation does not re-render the layout.** "On navigation, layouts preserve state, remain interactive, and do not rerender." [CITED: apps/csrm/node_modules/next/dist/docs/01-app/01-getting-started/03-layouts-and-pages.md:43] And: "shared layouts won't automatically be refetched on every navigation, only the page segment that changes." [CITED: …/03-api-reference/05-config/01-next-config-js/staleTimes.md:35]
- **A full load or `router.refresh()` re-renders the route, layouts included.** "Refresh the current route. Making a new request to the server, re-fetching data requests, and re-rendering Server Components." [CITED: …/04-functions/use-router.md:46]
- **A Server Action that calls `revalidatePath`, `updateTag` or `refresh()`, or that sets cookies, re-renders the current route in the same response.** [CITED: …/02-guides/server-actions.md, "A single response carries data and UI"] That re-render includes the `(app)` layout:
  1. the client's action fetch sends `Accept`, `Next-Action` and `Next-Router-State-Tree`, but no `RSC` header (`client/components/router-reducer/reducers/server-action-reducer.js:51-55`);
  2. the server parses a router state only for RSC requests (`server/app-render/app-render.js:205-206`: `shouldProvideFlightRouterState = isRSCRequest && …`);
  3. with no router state, `renderComponentsOnThisLevel = !flightRouterState || …` (`walk-tree-with-flight-router-state.js:58-61`) is true at the root, so the whole tree renders from the root layout.

  [VERIFIED: source read this session] This settles Phase 11's assumption A2 as true. Keep 11-13's browser proof as the empirical check.
- **An action that does none of those** "carries only its return value, and the current route is not re-rendered." [CITED: server-actions.md:74]
- **Actions are dispatched one at a time per client** (server-actions.md:28).
- **A navigation dispatched while an action is pending discards that action's router state but not its result:**
  - the navigation marks the pending action `discarded` (`client/components/app-router-instance.js:147-150`);
  - the reducer still calls `resolve(actionResult)` for the caller (`server-action-reducer.js:263`);
  - a discarded action that revalidated triggers a refresh afterwards (`app-router-instance.js:82-88`).

  [VERIFIED: source read]

**Refresh points:**
| Trigger | Refreshes the count? | How |
|---|---|---|
| Full load or reload | Yes | The layout's unawaited summary promise (`force-dynamic` is already set in `(app)/layout.tsx`) |
| `router.refresh()` | Yes | Same |
| Any Server Action of the person's that revalidates (submit, release, assign, note posted, …) | Yes | The layout re-renders in the action response, so a new promise reaches the trigger |
| A notification mark (one, all, Undo, open) | Yes | The action returns the exact unread count and `asOf`; the store adopts it, and no revalidation is needed |
| Opening the panel | Yes | The list action returns the items, the unread figure and `asOf` |
| Client navigation (Link, back, forward) | **No, unless added** | Recommended: one summary Server Action after each pathname change |
| Phase 13's silent note read (`markRequestNotesReadAction`, no revalidation, UI-D15) | **No, unless added** | Recommended: the notes component signals the trigger store to re-read, client side only, since published shapes do not change (D-03) |

**Recommended store (in the trigger):**
- **Value:** `{ unread: number | null, asOf: string }`.
- **Seeding:** from `use(layoutPromise)` inside `<Suspense fallback={null}>`. A new promise from a later layout render reseeds it.
- **Reconciling:** every value carries the server's `asOf`, and the store adopts an incoming value only when its `asOf` is later.
  - Summary and list reads take `asOf` before counting.
  - Mark responses take it after the update.
  - So a summary read that started before a mark committed can never overwrite that mark's result, whatever order they arrive in.
- **Optimistic changes:** open, mark and "Mark all as read" apply an overlay immediately and roll back on failure, with a danger toast (X-14's failure path).
- **Failure:** `null` (a failed or refused read) shows no badge (D-24).
- **Navigation re-read:** fires on a `usePathname()` change, skipping the first render, single-flight. A failed re-read sets `null`.
- **Cost:** one summary aggregate per client navigation. Because actions are sequential, the person's next action may wait one round trip. Record the cost.

**Do-not 9:** the direction says "**Do not** auto-advance, auto-rotate, or auto-refresh visible content without a user-visible control." (`docs/design/csrm-design-direction.md:497`). The navigation re-read has no timer and runs only after the person navigates. Reading that as compliant is `[ASSUMED]`, so the orchestrator or the UI-SPEC confirms it (Open Question 1).

### Pattern 8: Opening a notification in one step (D-19, D-23)

**Phase 10's guard contract (10-08-PLAN):**
- Next's `Link` calls `onClick`, then `onNavigate`. `onNavigate` receives only an object with `preventDefault()`.
- When the guard is not blocking, `guardLink` does nothing and the link navigates.
- When it is blocking, it prevents the navigation and opens the dialog. "Leave questionnaire" runs `onLeave`, then `router.push(href)`.
- Modifier-key and middle clicks do not fire `onNavigate`.

**So each item is one `<Link href={destination}>`:**
- **`onClick`:** records the trigger element. On a Ctrl, Meta or Shift click, the browser opens a new tab or window; fire the mark only.
- **`onAuxClick`:** for button 1 (middle click), fire the mark only.
- **`onNavigate`:**
  - if `guard.blocking`, call `guard.guardLink(e, { href, trigger, onLeave: open })`;
  - otherwise call `open()` directly.
- **`open()`:**
  1. apply the optimistic read to the item and the store;
  2. close the phone sheet (Phase 11 D-14's rule);
  3. dispatch `markNotificationsAction({ ids: [id], read: true })` without awaiting it.

  The navigation proceeds at once, and the action's result still resolves (Pattern 7) and reconciles the store.

**Keyboard and edge cases:**
- Enter on the link is a click, so the same path runs.
- "Keep answering" leaves the notification unread (D-19).
- "Open in new tab" from the context menu cannot be detected, so it stays unread. Record that as an accepted limitation.
- The destination page never marks anything (D-23 and the deferred "reading by visiting").

**Rejected alternative: a Server Action that marks and then `redirect()`s.** It is one round trip, and its full-tree response would refresh the badge. But the user sees no `loading.tsx` while the destination renders inside the POST, and the guard's push would have to change. Use the fire-and-navigate path.

### Anti-Patterns to Avoid
- **Lifecycle hooks for notifications.** They fire for seeds and imports, and have no actor (D-05).
- **Raw `strapi.db.connection` inside a transaction without `.transacting(trx)`.** On SQLite it deadlocks on the single pooled connection (Pitfall 1).
- **`strapi.db.query(uid).updateMany` with a relation `where`.** It is broken in 5.51.0 (Pattern 4).
- **Restating the release rule in a second place without an oracle.** Phase 17's widening would silently diverge.
- **Storing titles, names or a destination string.** That stale-copies access-controlled text (D-09, D-16).
- **A Route Handler that proxies notification reads for the client.** That is a frontend API facade (AGENTS.md); use Server Actions.
- **Marking on GET, or on destination page render.** This breaks D-23.
- **Rendering a "0" badge, or an error badge.** D-24 says a failed or zero count shows nothing.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic notification with its event | Outbox, after-commit hooks, a second transaction | Document Service create inside the event's `db.transaction` (ALS) | Already atomic; failure rolls both back (Pattern 1) |
| Per-request serialisation | A new lock | Phase 13's `withRequestLock`, the existing per-document queues and row locks | One lock module (13-03) |
| Closed payload checks | Ad hoc `if` chains | The existing `assertPayload` and closed-parser conventions (D-03), and zod on the web | Contract parity guard expects closed parsers |
| Popover, sheet, focus trap, Escape, focus return | Custom overlay | shadcn `popover.tsx` and `sheet.tsx` (Radix) | Keyboard and ARIA handled (WCAG 2.1.1, 2.4.3) |
| Undo toast, failure toast | Custom toast | `sonner.tsx` with X-14 | Direction pattern already recorded |
| Pagination and views | Custom pager | `pagination.tsx`, `tabs.tsx` or the existing segmented control, plus closed URL parsing | Matches existing lists |
| People names | A join to users in the list SQL | 13-03's `resolvePeople` (bounded `findMany`, `PERSON_FIELDS`) | One projection of people (D-04 of Phase 13) |
| Counting | In-memory filter of all rows | One SQL predicate with the oracle | Exact at any volume (D-14) |

**Key insight:** nearly every hard part, from atomicity and locks to overlays, toasts and the people projection, already exists in this repository or its planned Phases 10 to 13. The new code is the registry, the SQL predicate with its oracle, and the store.

## Common Pitfalls

### Pitfall 1: A raw knex query inside a transaction hangs on SQLite
**What goes wrong:** a test hangs for about 60 seconds, then fails with a pool timeout.
**Why it happens:** knex's sqlite3 dialect pools one connection (`poolDefaults() { return defaults({ min: 1, max: 1 }, super.poolDefaults()); }`, `knex/lib/dialects/sqlite3/index.js:215-217`), and `config/database.ts` sets `acquireConnectionTimeout` to `env.int('DATABASE_CONNECTION_TIMEOUT', 60000)`. A raw `strapi.db.connection` query does not join the ALS transaction, so it waits for the connection the transaction holds. [VERIFIED: source read]
**How to avoid:** inside any transaction, every repository function takes `trx` and calls `.transacting(trx)`, or uses the Document Service or `strapi.db.query`.
**Warning signs:** the same symptom 13-RESEARCH Pitfall 1 records.

### Pitfall 2: `updateMany` with a relation filter throws
**What goes wrong:** `Cannot convert undefined or null to object`.
**Why it happens:** see Pattern 4. Upstream's fix (strapi/strapi#26909) is not in 5.51.0.
**How to avoid:** use raw `UPDATE … WHERE id IN (subquery)` in the repository, or an `updateMany` with `where: { id: { $in: ids } }` only.

### Pitfall 3: ISO strings compared with SQLite datetimes
**What goes wrong:** `notified_at <= '2026-…'` matches nothing, or everything.
**Why it happens:** Strapi stores datetimes on SQLite as epoch-millisecond integers through knex's `Date` binding.
**How to avoid:** always bind `Date` objects, and parse `asOf` from the request into a `Date` before use.

### Pitfall 4: Totals that disagree with the list
**What goes wrong:** the badge says 3 and the Unread view shows 2.
**Why it happens:** separate predicates, or separate statements across a concurrent insert.
**How to avoid:** use one builder and one aggregate statement, every read bounded by `notified_at <= asOf`, and the oracle test.

### Pitfall 5: A notification leaks a title through the count or the 404
**What goes wrong:** Maya learns that Jane has a notification about record X.
**Why it happens:** a recipient filter is missing on one path, or an error message echoes an id or title.
**How to avoid:** the recipient join is on every query; mark-by-id answers one actor-neutral 404; the matrix's `FIXTURE_TITLE_PATTERN` and `LEAK_PATTERN` (`authorization-matrix.ts:86-90`) apply to the new rows.

### Pitfall 6: The service identity is admitted through the birthright
**What goes wrong:** the matrix's serviceAgent row shows 200.
**Why it happens:** `loadEffectiveGrants` gives every active user the Requestor roles.
**How to avoid:** the explicit agent-role refusal (Pattern 5), with matrix rows for all three operations.

### Pitfall 7: The PostgreSQL assignee race
See Pattern 2. Lock the request row before reading the assignee, in that order. Record the construct in R-08-37.

### Pitfall 8: A stale badge after a client navigation or a silent note read
**What goes wrong:** Jane reads the new note in the thread, but the bell still says 1.
**Why it happens:** the layout does not re-render, and 13-05's `markRequestNotesReadAction` does not revalidate (UI-D15).
**How to avoid:** the navigation re-read, and a client-side "may have changed" signal that the notes component sends after its mark-read resolves (Pattern 7).

### Pitfall 9: The mark result lost to a navigation
**What goes wrong:** the badge jumps back after opening.
**Why it happens:** a summary read that started before the mark committed arrives after the mark's result.
**How to avoid:** the `asOf` rule; only a value with a later `asOf` replaces the store's.

### Pitfall 10: A reversal that misses the right rows
**What goes wrong:** after a return to analyst review and a re-release, Jane sees two unread notifications.
**Why it happens:** the reversal read was not in the return-to-review transaction, or it filtered by recipient when it should read any recipient's rows on that subject.
**How to avoid:** D-21's rows in the registry, tested by the "released again shows exactly one new" integration case (`<specifics>`).

### Pitfall 11: Generated Strapi types and the content-type freeze
**What goes wrong:** `apps/backend/types/generated/*.d.ts` change after a Strapi boot (they are already modified in the working tree), or the freeze check lists extra schema files.
**How to avoid:** never stage the generated types. The freeze check lists exactly `apps/backend/src/api/csrm-notification/content-types/csrm-notification/schema.json`.

### Pitfall 12: Header DOM order and the 375px fit
**What goes wrong:** `app-shell.spec.ts`, `design-contract.spec.ts` and `accessibility.spec.ts` fail.
**Why it happens:** the header's order becomes Menu, the header title, Search, Notifications, then the role tag or account menu (D-24), and the longest development role must still fit at 375px.
**How to avoid:** name these specs in the plan that changes the header (D-40).

## Code Examples

### The write, inside an existing workflow transaction
```ts
// Pattern for apps/backend/src/api/csrm-notification/services/notification-service.ts (proposed).
// Relies on: strapi.db.inTransaction() (@strapi/database/dist/index.js:57-59) and the
// Document Service joining the ALS transaction (document-service/common.js:3-5).
export async function notify(strapi: NotifyStrapi, event: NotificationEvent): Promise<number> {
  if (!strapi.db.inTransaction()) {
    throw new NotificationServiceError("A notification is written only inside its event's transaction.");
  }
  const kind = notificationKind(event.kind);                 // closed registry; unknown kind throws
  const candidates = await kind.recipients(strapi, event);   // Document Service reads join the transaction
  let written = 0;
  for (const candidate of candidates) {
    if (candidate.user.documentId === event.actorDocumentId) continue;   // never the person who acted
    if (!isEligiblePerson(candidate.user)) continue;                     // active, not the agent role
    await strapi.documents(NOTIFICATION_UID).create({
      data: {
        recipient: candidate.user.documentId,
        recipientPart: candidate.part,
        kind: event.kind,
        assessmentRequest: event.requestDocumentId,
        ...(event.questionnaireDocumentId ? { questionnaire: event.questionnaireDocumentId } : {}),
        ...(event.assessmentDocumentId ? { assessment: event.assessmentDocumentId } : {}),
        facts: kind.facts(event),                            // { schemaVersion: 1, … } ids and numbers only
        notifiedAt: event.at.toISOString(),
      },
    });
    written += 1;
  }
  return written;
}
```
Relation connect by `documentId` string is the existing create shape: `assessmentRequest: String(target.request.documentId)` in `persistAssessmentDraft` (`assessment-workflow.ts:753-765`). [VERIFIED: read this session]

## Open Questions

1. **Should the badge re-read on client navigation?**
   - **What we know:** without it the count is stale between server renders (Pattern 7). With it, one summary aggregate runs per navigation, with no timer.
   - **What's unclear:** whether do-not 9 ("auto-refresh visible content without a user-visible control") covers a navigation-triggered refresh.
   - **Recommendation:** adopt it, and have the orchestrator or the UI-SPEC confirm.
2. **How does Undo identify what "Mark all as read" changed?**
   - **What we know:** D-03 proposes returning the ids, but the mark call accepts at most 50 ids, while a bulk mark can change more.
   - **Options:**
     - (a) Return `markedAt` (the single `read_at` the bulk write used) and add an Undo form `{ read: false, markedAt }` that clears the caller's rows still holding exactly that time. It is exact in practice: SQLite stores integer milliseconds, and the same person cannot issue two marks in the same millisecond, because Server Actions are sequential per client.
     - (b) Return the ids and accept up to the number changed in a dedicated Undo form.
   - **Recommendation:** (a), which keeps payloads small. The planner records the choice in the contract-gap record.
3. **What does an assignment change read for the former assignee?**
   - **What we know:** D-21 says it "leaves the former assignee nothing unread", while D-11's table reads only `request-assigned`.
   - **What's unclear:** whether the former assignee's `questionnaire-submitted` and analyst-part `note-added` on that request are also read.
   - **Recommendation:** read all of the former assignee's unread `security-analyst`-part notifications on that request, because the work no longer waits for them. Confirm in the record.
4. **What is the shared service-identity refusal set called?**
   - **What we know:** Phase 19 (planned) adds `EXPORT_OPERATIONS` with the agent refusal; 19.1 and 17 need the same refusal.
   - **Recommendation:** the orchestrator asks Phase 19's planner to name it generically from the start (for example `SERVICE_IDENTITY_REFUSED_OPERATIONS`), so 19.1 only adds members. Otherwise 19.1 renames it and amends Phase 19's record.
5. **Where does `note-added` keep the note sequence?**
   - **What we know:** `facts` holds it, and D-22's read parses at most 500 candidates in code.
   - **What's unclear:** what to do with an unparseable envelope in that read.
   - **Recommendation:** read it along with the others. It is about the thread the person has just viewed, and D-09 fails safe at the record level.

### Known Threat Patterns for Strapi 5 and Next.js 16

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| IDOR on mark-by-id (another person's id) | Tampering / Information disclosure | Recipient join in the same predicate; whole call 404, persistence deep-equal |
