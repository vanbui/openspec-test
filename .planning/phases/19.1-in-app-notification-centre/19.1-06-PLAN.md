## Phase Goal

**As a** Requestor, a risk owner or a Security Analyst, **I want to** be told in the app when work waits for me and to open it in one step, **so that** nothing waits unseen between the people in the flow.

This plan's slice: the questionnaire and assessment workflow tells each side when work arrives and clears it when they act or the work is taken back.

## Recorded planning decisions

- **Release.** In `releaseQuestionnaire`, inside its governance mutation's transaction after the release facts and the governance log are written: `notify(strapi, { kind: "questionnaire-released", actorDocumentId: analyst, requestDocumentId, questionnaireDocumentId, at })`. Releasing again after a return writes a new notification; the earlier one stays read.
- **Return to analyst review.** In `returnQuestionnaireToAnalystReview`, inside its transaction after `releasedAt` is cleared: `readNotificationsOnReversal(trx, { reversal: "return-questionnaire-to-review", subjectDocumentId: questionnaireDocumentId, now })`.
- **Submit.** In `submitQuestionnaire`, inside its transaction after every answer is stamped and the request status updated: `notify(strapi, { kind: "questionnaire-submitted", actorDocumentId: requestor, requestDocumentId, questionnaireDocumentId, at })` (its assigned-analyst rule locks the request row; lock order questionnaire row, then request row, which the request status update already uses), then `readNotificationsOnActing(trx, { act: "submit-questionnaire", recipientId: requestorId, subjectDocumentId: questionnaireDocumentId, now })`.
- **Revert to draft.** In `revertQuestionnaireToDraft` (06.1, either party), inside its transaction after the answers return to draft: `readNotificationsOnReversal(trx, { reversal: "revert-answers-to-draft", subjectDocumentId: questionnaireDocumentId, now })`.
- **Assessment release.** In the v1 `releaseAssessment`, inside its transaction after the release triple is written: `notify(strapi, { kind: "assessment-released", actorDocumentId: analyst, requestDocumentId, assessmentDocumentId, at })`. Phase 17 adds participants as recipients and Phase 17.1 reuses the kind for release and close.
- **Draft act.** In `persistAssessmentDraft`, inside its transaction after the assessment is created: `readNotificationsOnActing(trx, { act: "persist-assessment-draft", recipientId: <the job's initiating analyst's numeric id>, subjectDocumentId: questionnaireDocumentId, now })`. The enqueue writes nothing, and a failed job reads nothing.
- **Tests.** `notification-events.integration.test.ts` drives the release, return, submit, revert, assessment release and draft operations over HTTP with the deterministic providers, reading results through `GET /api/v1/notifications` per person; atomicity uses `withDocumentWriteFailure(NOTIFICATION_UID, "create", 1, …)` and the existing workflow failure injectors (`withQuestionUpdateFailure`, `withDocumentWriteFailure` on the workflow's own uid).
