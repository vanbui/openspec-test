## Phase Goal

**As a** Requestor, a risk owner or a Security Analyst, **I want to** be told in the app when work waits for me and to open it in one step, **so that** nothing waits unseen between the people in the flow.

This plan's slice: notifications are written to the right people inside an event's transaction, and each person's list, count and marks are exact and limited to what they may read now.

<objective>
Build the notification service (`notify`, D-05 to D-08) and the repository whose one SQL readability predicate feeds the list, the total, the unread count and "Mark all as read" (D-13 to D-15), with every `readAt` write: marks, Mark all as read bounded by `asOf`, Undo by the single read time, and the acting, reversal and note reads (D-18 to D-22). Prove readability against a semantic oracle (D-14) and record the PostgreSQL constructs in R-08-37.

Purpose: the operations (19.1-04) and the event hooks (19.1-05, 19.1-06) only call these two modules.
Output: two services, the SQL twin beside Phase 19's predicate, the oracle test, service tests, harness helpers and the residual-risk entry.

Edits Strapi source? Yes (dev servers stopped). Changes the specification? No. Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Service.** `notification-service.ts` exports `type NotificationEvent = { kind: NotificationKind; actorDocumentId: string; requestDocumentId: string; questionnaireDocumentId?: string; assessmentDocumentId?: string; assigneeDocumentId?: string; note?: { documentId: string; sequence: number; authorPart: NotificationPart }; at: Date }`, `NotificationServiceError`, and `notify(strapi, event): Promise<number>`. It throws `NotificationServiceError` when `strapi.db.inTransaction()` is false, for an unknown kind, and for an event missing the relation its kind's subject needs. Recipient rules by the registry's `recipients`: `new-assignee` (the event's `assigneeDocumentId`, part `security-analyst`); `requestor` (the request's requestor, part `requestor`); `assigned-analyst` (take the request row lock with the `lockAssessmentRequest` shape, `queryBuilder(REQUEST_UID).select(["id"]).where({ documentId }).forUpdate().transacting(trx)`, then read the request's `assignedAnalyst`; none when unassigned; part `security-analyst`); `note-other-part` (author part `security-analyst` → the requestor in part `requestor`; author part `requestor` → the assigned analyst after the row lock, part `security-analyst`). Candidates are loaded through the Document Service with `accountStatus` and role names; the actor and every candidate failing `isEligiblePerson` are dropped; duplicates collapse to one. Each write is `strapi.documents(NOTIFICATION_UID).create` with relations by documentId, `facts` from `buildNotificationFacts`, and `notifiedAt` from `event.at`. `notify` never calls `withRequestLock` (it runs inside whichever lock the event holds) and never runs for an AI run or a job event (D-06).
- **Repository.** `notification-repository.ts` takes `connection` (`strapi.db.connection`) for reads outside a transaction and `trx` for everything inside one; every raw query inside a transaction calls `.transacting(trx)`. `type NotificationReadScope = { recipientId: number; analystKinds: readonly NotificationKind[]; asOf: Date }`. `readableNotifications(connection, scope)` builds the base (`csrm_notifications n`, inner join of the recipient link on `idambox_user_id = recipientId`, inner join of the request link and `csrm_assessment_requests r`, left joins of the questionnaire and assessment links and rows, `n.notified_at <= asOf` bound as a `Date`) and the readable OR: `requestor` part with `questionnaire-released` (questionnaire row present, `q.released_at` not null, the request's requestor link names the caller), `assessment-released` (`whereReleasedAssessmentReadable` on `a` and `r` for the caller), `note-added` (the request's requestor link names the caller); `security-analyst` part with `n.kind` in `scope.analystKinds` (an empty list matches nothing) and, for `questionnaire-submitted`, the questionnaire row present. `listNotificationsPage(connection, scope, { view, page, pageSize })` returns `{ rows: NotificationRow[], total, unread, pageCount }` with order `n.notified_at DESC, n.id DESC`, and `total` and `unread` from one aggregate statement (`COUNT(*)`, `SUM(CASE WHEN n.read_at IS NULL THEN 1 ELSE 0 END)`) parsed by a `wholeCount` helper like `request-status-summary.ts`; in the `unread` view `total` equals `unread`. `countNotifications(connection, scope)` returns `{ total, unread }` from the same statement. Rows map SQLite integer and PostgreSQL `Date` times to `Date`, and parse `facts` from text when needed.
- **Writes.** `markNotificationsById(trx, scope, documentIds, read, now)`: select the readable rows among the ids; if fewer come back than were sent, throw `NotificationNotVisibleError` before any write; then `UPDATE csrm_notifications SET read_at = now WHERE id IN (…) AND read_at IS NULL` for read, `SET read_at = NULL WHERE id IN (…)` for unread; return the number changed. `markAllNotificationsRead(trx, scope, markedAt)` runs one `UPDATE … SET read_at = markedAt WHERE id IN (readable AND unread) RETURNING id` with `scope.asOf` the view's `asOf`. `undoMarkAllNotifications(trx, scope, markedAt)` sets `read_at = NULL` on the caller's readable rows whose `read_at` equals `markedAt`. `readNotificationsOnActing(trx, { act, recipientId, subjectDocumentId, now })` and `readNotificationsOnReversal(trx, { reversal, subjectDocumentId, formerAssigneeId?, now })` read the kinds `NOTIFICATION_ACTING_READS` and `NOTIFICATION_REVERSAL_READS` name, by subject link and `read_at IS NULL` (the change-assignee reversal also by recipient and part). `readNoteNotificationsThrough(trx, { readerId, requestDocumentId, throughSequence, now })` selects the reader's unread `note-added` rows for the request (at most `NOTES_PER_REQUEST_MAX`), parses each envelope in code, and updates the ids whose `noteSequence` is at most N, including any whose envelope fails to parse (research Open Question 5). Every time is bound as a `Date`.
- **SQL twin.** `released-assessment-read.ts` (Phase 19's module holding `findReadableReleasedAssessment`) gains `whereReleasedAssessmentReadable(builder, { assessmentAlias, requestAlias, viewerId })`, placed beside Phase 19's predicate and documented as its twin: `{a}.assessment_status = 'approved'`, `{a}.approval_date` not null, an approver link exists, `{r}.request_status = 'approved'`, and the request's requestor link names the viewer. Its comment says Phase 17 widens "readable" and Phase 17.1 widens "released" in both forms together, and the oracle test fails if they diverge.
- **Harness.** Add `removeRoleFromUser(userDocumentId, roleName)` and `restoreRolesOfUser(userDocumentId)` if no equivalent exists, and `deleteRequestDirectly(requestDocumentId)` for the deleted-subject case. Reuse `withDocumentWriteFailure` for injected notification create failures.
