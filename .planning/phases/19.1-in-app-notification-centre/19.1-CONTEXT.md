<domain>
## Phase Boundary

Tell people in the app when work waits for them, and let them open it in one step. One notification service writes a notification for each person an event concerns, in the same transaction as the event; a header control shows the unread count; a panel lists the latest notifications; a Notifications page lists them all. Nobody is told about a record they may not read, at any time: readability is decided when the list and the count are read. The phase builds the centre with the five events that exist before Phase 17 (assignment, questionnaire released, questionnaire submitted, assessment released, new note), so Phases 17, 17.1, 17.2 and 20 add their kinds through the same service with no schema change. It delivers NOTIFY-01 (moved from Phase 17 by G-19).

### In scope
- The `CsrmNotification` entity, its per-person read state and its closed kind and part vocabularies, through one contract-gap record and its approval checkpoint (D-01, D-08, D-09, D-11, D-12).
- The notification service and its event hooks in the assignment, notes, questionnaire and assessment workflows, including the reads that acting on the work and reversing an event cause (D-05 to D-07, D-19 to D-22).
- Readability, wording and destinations decided at read time (D-13 to D-17).
- Three operations (list, unread summary, mark read or unread), with exact grants for every human user, the service identity refused, and the caller as the only scope (D-03, D-35 to D-37).
- The header control, the panel (popover from 768px, sheet below) and the Notifications page with all and unread views (D-24 to D-32).
- The tests, including a Playwright spec for the centre's flows and negative cases at 1440px and 375px (D-39, D-40).

### Out of scope
- Phase 17's `response-requested` and `response-submitted` kinds, the participant parts and the widened assessment readability: Phase 17 adds them through this phase's service and predicates (`<seams>`).
- Phase 17.1's, 17.2's and Phase 20's kinds (G-18), Phase 20's email delivery and reminders (NOTIFY-02), and the notification retention setting (Phase 22).
- Real-time push, polling, digests or coalescing, notification preferences (NOTIFY-03), team fan-out, and a notification widget on Home (D-28). See `<deferred>`.
- Any change to an existing content type, request status, questionnaire or assessment status, or published response shape (D-01, D-03).
- Keycloak, and live AI generation in any automated suite.

## Implementation Decisions

### Scope and contract boundary

- **D-01:** The only content-type change is one new type, `CsrmNotification`, in a new API folder (`apps/backend/src/api/csrm-notification/`), through `docs/contract-gaps/phase-19.1-notifications.md` and its approval checkpoint before any schema file changes (`<contract_gaps>`). Names are proposals in JDL style; the record fixes them.

  | Attribute | Type | Meaning |
  |---|---|---|
  | `recipient` | many-to-one `IdamBoxUser`, required | The one person told |
  | `recipientPart` | string, closed vocabulary | The part they were told in (D-08) |
  | `kind` | string, closed vocabulary | What happened (D-11, D-12) |
  | `assessmentRequest` | many-to-one `CsrmAssessmentRequest`, always set | The request the event belongs to |
  | `questionnaire`, `assessment` | many-to-one, optional | Set where the kind has one |
  | `risk` | many-to-one `CsrmRisk`, optional | Unused by this phase's kinds; there for the risk-scoped kinds of Phases 17.1 and 20 (D-12) |
  | `facts` | json, versioned envelope | Identifiers and numbers only (D-09) |
  | `notifiedAt` | datetime, server-owned | The event's own time |
  | `readAt` | datetime, optional | Absent means unread (D-18) |

  Every relation is unidirectional, so no existing content type gains an attribute. `draftAndPublish` is off, and the type gets no Strapi core router: it is reachable only through D-03's operations, and the inventory and the matrix prove that no core route exists. No JDL entity covers notifications (catalogue design note 6), so none competes with one, and decision 18 is the domain decision behind it. **Reversibility:** one-way - a new table holding who was told what and their personal read state; undoing it needs a data migration, and Phases 17, 17.1, 17.2 and 20 write through it.
- **D-02:** Every new endpoint follows the established chain (Phase 12 D-02, Phase 13 D-02, Phase 17 D-02): exact Role → Function → FunctionAPI grants in both catalogue copies, byte-identical; record-level checks in Strapi against the resolved IdamBox User (`ctx.state` after the identity middlewares), never branching on the auth mode; the operations and schemas in `docs/references/specification.json`, then `api:generate` and a clean `api:check`; closed parsers registered in the contract parity guard; a row per route in the authorisation matrix for its six callers; `docs/references/served-operations.json` regenerated with the dev servers stopped. The server shape and its web parser change in the same plan (the 06.9 lesson).
- **D-03:** The API changes are these, and no others. Paths and names are proposals; research fixes them.
  1. **List:** `GET /api/v1/notifications`, the caller's own notifications, newest first, paginated with an exact total, with a closed view filter (all or unread). Each item carries what D-16 and D-17 give: its id, kind, time, read state, the server's sentence, the record's number and title, and the destination. The response's meta carries the unread total and the server time of the read (`asOf`, used by "Mark all as read").
  2. **Unread summary:** `GET /api/v1/notifications/summary`, the caller's exact unread count and `asOf`.
  3. **Mark:** `POST /api/v1/notifications/read`, either 1 to 50 notification ids with `read: true` or `read: false`, or "all, up to `asOf`" (D-19). It returns how many changed, the ids "Mark all as read" changed (for Undo) and the new exact unread count. An id that is not the caller's, or that the caller cannot see (D-15), makes the whole call 404. Payloads are closed (`assertPayload`): unknown keys, both forms at once, malformed or too many ids, or an `asOf` after the server's time are 400.

  Existing operations change behaviour but not shape: the assignment and note operations (Phase 13), questionnaire release, return to analyst review, submit and revert to draft, assessment draft generation and v1 assessment release write or read notifications in their own transactions (D-11, D-20 to D-22). No published response shape changes, and no new conflict reason is needed. **Reversibility:** costly - published operations, a closed kind vocabulary and payloads.
- **D-04:** This phase adopts Phase 17's D-56 to D-63 as its own decisions, renumbered, and refines them where today's code, Phases 11 and 13, or the execution order require it. "Adopted from Phase 17", after the deferred ideas, maps each one and states each refinement with its reason.

### Writing notifications (decision 18; 17 D-56)

- **D-05:** A notification is one fact per recipient per event, written in the same transaction as the event it reports, through one notification service the workflows call (for example `notify({ kind, subject, actor, facts })` resolving its recipients inside the transaction). The workflows call it explicitly; no Strapi lifecycle hook writes notifications, because recipients depend on the workflow's actor and state, and hooks would fire for seeds and imports too. If writing the notification fails, the event's transaction fails with it, so no event lacks its notification and no notification describes an event that did not happen. Research confirms that the document service joins the workflow's `strapi.db.transaction` for these writes. **Reversibility:** costly - every event hook relies on the transactional contract.
- **D-06:** Who is never told.
  - **The person who acted**, the **service identity** (an IdamBox User holding the Security Analyst Agent role) and an **inactive user**: the service skips them through D-07's predicate, checked at the moment of the event.
  - **Nobody, for "the assigned analyst" while the request is unassigned:** the queue's unassigned pool (Phase 13 D-14) is the team's channel, and nothing fans out to every analyst.
  - **Nobody for AI or job events:** AI runs, job completions and the service identity's acts create no notification in this phase ("AI proposals ready" is deferred, as Phases 15 and 16 recorded).
- **D-07:** The eligible-person predicate moves forward from Phase 17 D-16 into this phase, because 19.1 executes first and needs it for recipients: one shared module (for example `apps/backend/src/csrm/people/eligible-person.ts`) answering "an active IdamBox User who does not hold the Security Analyst Agent role". Phase 13's assignee eligibility (its D-06) composes it with the human analyst role, and Phase 17 reuses it, unchanged, for risk owners, control owners and the people search. If Phase 13's plans have already built an equivalent check inside its assignee eligibility, this phase factors it out rather than writing a second one.
- **D-08:** Each notification records the part its recipient was told in, `recipientPart`, a closed vocabulary that reuses Phase 13's `authorPart` values: `requestor` and `security-analyst` now. Phase 17 adds its participant parts (for example `risk-owner`) and Phase 17.1 `executive-approver`, extending it as they extend the kinds. The part chooses the readability predicate (D-13) and the destination (D-17). An analyst who raised a request is told about it as its Requestor and sent to the Requestor's pages, where that work waits, as Phase 11 reads an analyst's own requests "from the Requestor's side" (11 D-03) and Phase 13 files a requesting analyst's notes in the Requestor's part (13 D-07, D-23). **Reversibility:** costly - a stored vocabulary that readability and destinations read.
- **D-09:** The `facts` envelope is versioned and holds only identifiers and numbers: the acting person's id, a note's id and per-request sequence, and later a round number or the id of a decision or contest point. It never holds a title, a name or Requestor text. A closed parser per kind reads it and fails safe (the 06.8 posture): readability never reads the envelope, and a notification whose envelope cannot be parsed is still listed, worded at the record level and sent to the record's page rather than an anchor.
- **D-10:** No backfill and no seed. Notifications start when this phase is deployed: assignments, notes, releases and submissions made earlier notify nobody. The development seed creates none (they would be fabricated events), so a fresh development database shows the centre's first-use empty state until someone acts.

### The first kinds (decision 18; G-19; 17 D-57)

- **D-11:** The kinds in this phase, a closed vocabulary in code (one registry module) and in the contract:

  | Kind | Event | Recipient and part | Subject relations | Destination (D-17) | Read by acting (D-20) | Read by reversal (D-21) |
  |---|---|---|---|---|---|---|
  | `request-assigned` | Someone else assigns or reassigns a request to an analyst (Phase 13 D-05, D-12); never picking it up oneself | The new assignee, `security-analyst` | request | The analyst request page | — | A later assignment change that takes the request away from them (reassign, unassign or Undo) |
  | `questionnaire-released` | A questionnaire is released or released again (06.8) | The Requestor, `requestor` | request, questionnaire | The Requestor's questionnaire page | The recipient submits that questionnaire | The questionnaire returned to analyst review |
  | `questionnaire-submitted` | The Requestor submits the answers | The assigned analyst, `security-analyst` | request, questionnaire | The analyst questionnaire page | The recipient starts the assessment draft from it | The answers returned to draft (06.1, by either party), or the questionnaire returned to analyst review |
  | `assessment-released` | v1 release (Phase 17.1 replaces it with released and closed for new events) | The Requestor, `requestor` (Phase 17 adds every participant once the gate is open) | request, assessment | The Requestor's released assessment page | — | — (a released record is immutable, decision 9) |
  | `note-added` | A note is posted (Phase 13) | The other part: the Requestor for an analyst's note (`requestor`), the assigned analyst for a note in the Requestor's part (`security-analyst`) | request; note id and sequence in `facts` | The request page for that part, at the note (`#note-{id}`, Phase 13 UI-SPEC) | The recipient's note read state passes the note (D-22) | — (notes are append-only) |

  The assignment operation writes `request-assigned` inside its own compare-and-set transaction (Phase 13 D-05, D-09), rather than the centre reading the assignment history afterwards (Phase 13 D-12's wording), so D-05's rule holds. A note posted by an analyst who is not the assignee still notifies the Requestor; a colleague's analyst note does not notify the assignee, matching Phase 13's unread rule (notes in one's own part are never new to one). Files posted with a note ride on its `note-added` (Phase 14 D-17); there is no file kind. **Reversibility:** costly - published kind values.
- **D-12:** How later phases extend the centre, without a schema change (Phase 12's run `operation` precedent):
  - **One registry** holds each kind's parts, subject relations, readability, wording, destination, and its acting and reversal reads. A later phase adds rows there, extends the contract's kind and part enums, and extends the web's closed parser in the same plan.
  - **Phase 17** adds `response-requested` (to each participant asked) and `response-submitted` (to the assigned analyst), its participant parts, and every participant as a recipient of `assessment-released` once the gate is open. **Phase 17.1** adds acceptance requested, executive approval requested, decision recorded and voided, round recalled, and released and closed. **Phase 17.2** adds contest point raised and answered, and assessment returned (NOTIFY-04). **Phase 20** adds its reminders and escalations (NOTIFY-02, G-16, G-18). Sub-records (a round, a decision, a contest point) travel as ids in `facts`; the optional `risk` relation serves risk-scoped kinds.
  - **A kind is never removed** once notifications of it exist: when Phase 17.1 replaces `assessment-released` with released and closed for new events, earlier `assessment-released` notifications stay readable and worded.

### Readability (decision 18; G-12; 17 D-58)

- **D-13:** Nobody is told about a record they may not read. A notification is listed and counted only while its recipient may read its subject, decided when the list and the count are read, never from a stored copy of access, by the record reads' own predicates for the part it was told in:
  - **`requestor`:** the request's `requestor` is the recipient, and the subject is readable to them by its record rule: the questionnaire released (its dedicated release fact, 06.8, as `requireQuestionnaireReleasedForRequestor` gates it today); the assessment by Phase 19's one released-assessment predicate (19 D-14), which Phase 17 widens to participants and Phase 17.1 to `closed` in its one place, so this phase's readability follows with no change of its own; notes by Phase 13's notes predicate (`canUseRequestNotes`).
  - **`security-analyst`:** the recipient currently holds the human Security Analyst grant for the subject's read, as the policy decides it for the record read (any request, questionnaire or notes thread), and the subject exists.
  - **The subject gone:** a notification whose request, questionnaire or assessment no longer exists is not shown or counted.

  In this phase that hides, for example, the Requestor's `questionnaire-released` while the questionnaire is back in analyst review (06.8 clears its release fact), and every analyst-part notification of someone who no longer holds the Security Analyst role. From Phase 17, a former owner's notifications disappear with their read (17 D-22). **Reversibility:** costly - every list, count and mark reads it.
- **D-14:** Counts stay exact. The list total, the unread summary and the count that "Mark all as read" clears are the same predicate. The recommendation is SQL predicates in a repository, with exact totals checked against a semantic oracle (the Phase 7 D-21 and D-30 pattern): `recipient = caller`, then per part the joins above, with the caller's analyst standing computed once per request from the grants the policy already loaded. A bounded in-memory filter is the alternative; research chooses, provided counts stay exact at any volume and the totals equal the lists.
- **D-15:** A notification the caller cannot see is, for them, missing: marking it by id is 404, exactly as another person's notification is (D-03 item 3).

### Wording and destination (17 D-59)

- **D-16:** The server words each notification for its recipient when it is read, as `request-lifecycle.ts` words next actions today (Phase 11 D-27): one plain-text sentence that names the record by its number and title, plus the record's number and title as separate fields the web lays out ("{identifier} · {name}", X-4). An assessment, which has no title, is named by its number and its request's title. Titles are never stored, so a renamed request reads correctly and nothing is copied out of the record's own access rules. A sentence names a person (resolved from `facts` at read time) only where the recipient's own read of the record already shows that person, such as a note's author or, for an analyst, who assigned them; otherwise it names the part ("A Security Analyst released …"). The UI-SPEC writes the sentences; the web formats what it is given and never composes wording.
- **D-17:** The destination is the page the recipient's part opens, built by the server at read time: Requestor pages for the `requestor` part (`/app/requests/{id}`, `/app/questionnaires/{id}`, `/app/assessments/{id}`), analyst pages for the `security-analyst` part (`/app/review/requests/{id}`, `/app/review/questionnaires/{id}`), with the note anchor for `note-added`. This refines Phase 17 D-59's "actor class" to the part (D-08), so a requesting analyst lands where their Requestor work waits. The web's closed parser accepts a destination only as an in-app path of a known shape, so a server fault can never produce an outside link.

### Read state (17 D-60)

- **D-18:** Read state is per notification and per person: `readAt` on the recipient's own row (one reader per row, so no separate read-state table, unlike notes). Marking is idempotent; marking read again keeps the first read time; marking unread clears it.
- **D-19:** A notification is read when the person:
  - **opens it** from the panel or the page. Opening goes through Phase 10's navigation guard and its programmatic entry point (Phase 11 D-51), and reads the notification only when the navigation goes ahead, so a Requestor with unsaved answers who chooses "Keep answering" keeps it unread;
  - **marks it read**, one at a time;
  - **chooses "Mark all as read"**, which reads exactly the notifications the unread count counts, created up to the `asOf` of the view the person saw, so one that arrives later stays unread. It confirms with an Undo toast (X-14), whose Undo marks exactly those notifications unread again.

  A person can also **mark one unread** again. This and Undo are this phase's additions to Phase 17 D-60, from G-4's rule that reversible actions offer Undo.
- **D-20:** Acting on the work reads the actor's own unread notifications of that kind about that record, in the act's transaction (D-11's "Read by acting" column): submitting a questionnaire reads its `questionnaire-released`; starting the assessment draft from a questionnaire reads the actor's `questionnaire-submitted`. A colleague's act never reads someone else's notification; only a reversal does (D-21).
- **D-21:** Reversing the event reads the recipient's unread notification about it, in the reversing transaction, because the work no longer waits for them (D-11's "Read by reversal" column): an assignment taken away, or undone straight after it was made, leaves the former assignee nothing unread; answers returned to draft read the assigned analyst's `questionnaire-submitted`; a questionnaire returned to analyst review reads the Requestor's `questionnaire-released` (and the analyst's `questionnaire-submitted` when the answers had been submitted). The notification stays in the person's history as read, so a later release, with its own new notification, never brings the old one back unread. This is a refinement of Phase 17 D-60.
- **D-22:** A `note-added` notification is read when the person's note read state passes its note (Phase 13 D-24, with its sequence confirmation). Phase 13's "mark read through note N" operation reads, in its own transaction, the person's unread `note-added` notifications for that request whose note sequence is at most N. This refines Phase 17 D-60's "derived at read time": the observable rule is the same, and the count stays one predicate instead of a join to the read-state table. Reading a notification never moves the note read state, so the thread's "New" markers keep Phase 13's rule.
- **D-23:** No GET has a side effect: the list and the summary never mark anything, and every read is an explicit write (a mark, an act or a reversal). A test proves the reads leave `readAt` unchanged.

### The centre in the app (17 D-61, D-72, D-73)

- **D-24:** The header control fills the place Phase 11 left (11 D-13: "the notification centre in the header").
  - **Position:** in the header's right-hand group, after quick find's Search control and before the role tag (or the account menu in OIDC mode), so the DOM order is Menu, the header title, Search, Notifications, then the role tag or account menu, and the skip link's next Tab stop is still Menu (Phase 11 UI-SPEC §3).
  - **Shape:** an icon button (a circle at the touch-target size below 768px) whose visible count is the exact unread count, in ink, never a status hue (X-17's rule that unread is personal). Zero, a failed read and a refused read show no count, never a 0, a dash or an error (Phase 11 D-11).
  - **Name:** the accessible name is its content, "Notifications" then the count and its meaning ("Notifications, 3 unread"), with `aria-haspopup` and `aria-expanded`. The count is not a live region (Phase 11's rule).
  - **Gate:** it renders only for a viewer holding `notification:read` (D-37). Navigation visibility is not authorisation.
  - **Icon:** a bell is the convention, but the analyst sidebar's Alerts item uses `Bell` today (Phase 11 UI-SPEC §1.1). The UI-SPEC settles the clash, so an Alert (derived, Phase 7) and a Notification (an event for one person) never share a symbol.
- **D-25:** The count stays exact without polling (the direction's do-not 9; Phase 11 D-11). It is read once per server render of the layout, started without awaiting and rendered in a Suspense boundary with no fallback, so no page waits for it. It refreshes on a full load, a router refresh, and every Server Action of the person's that revalidates, including each mark, and whenever the panel opens, because opening re-reads the latest notifications and the count together. Optimistic changes (D-29) reconcile with the count each mark returns. Layouts do not re-render on client navigation (Next's partial rendering), so research confirms each refresh point, and whether the count should also refresh on navigation without polling.
- **D-26:** The panel. Activating the control opens the latest notifications (a bounded number, newest first, unread marked with X-17): from 768px a popover anchored to the control; below 768px a full-screen sheet (X-13's phone sheet, with a visible title row and Close). Each item is one link to its destination that opens the record in one step (D-17, D-19), so it also opens in a new tab. The panel carries "Mark all as read", the unread figure, and "View all notifications" to the page. Its code loads on demand (`next/dynamic` from the trigger, prefetched on pointer enter or focus, as quick find does in Phase 11 D-52); its list shows a skeleton after 300ms; it has a first-use empty state, an all-read state, and an error state with "Try again". Escape closes it and returns focus to the control; the sheet closes only once the navigation guard lets a navigation go ahead (Phase 11 D-14's rule for the drawer).
- **D-27:** The Notifications page at `/app/notifications`, heading and label "Notifications" and route title "Notifications | IdamBox CSRM" (Phase 11 D-09, with `page-headings.ts`). It has All and Unread views as a closed URL filter, pagination with its total and rows per page, "Mark all as read", and per-item "Mark as read" or "Mark as unread". It has empty states for first use, for an Unread view with nothing unread, and for errors, and loading and error boundaries; below 768px it renders cards. It is gated by `notification:read` and shows the shared permission state otherwise. It is not a sidebar item: the header control is its entry on every page and width, and the panel links to it.
- **D-28:** Home gains no notifications widget. The header control is on Home at every width, which answers the brief's "important notifications" (`docs/CSRM-PROJECT-BRIEF.md` §10) that Phase 11 deferred to the centre (its deferred ideas). Home keeps listing the work itself (Needs your action, Phase 11 D-19), and a second list of the same events would compete with it and with Phase 13's new-notes row.
- **D-29:** The G-4 bar:
  - a keyboard path for every action: the control, each item, "Mark all as read", the view filter, pagination and the per-item marks are buttons or links in DOM order, and Escape closes the panel;
  - optimistic feedback with rollback: opening, marking and "Mark all as read" update the item and the count at once, and roll back with a danger toast that says why (X-14's failure path);
  - one Undo toast, for "Mark all as read". Marking one item confirms in place, because its own toggle reverses it. There are no confirmation dialogs: nothing here is governance-significant;
  - skeletons after 300ms in the panel and on the page;
  - empty states that say what to do next;
  - one comfortable density, because the list is a feed of sentences, not a dense data table (the UI-SPEC may argue otherwise);
  - motion from the direction (popover 180ms in and 120ms out; sheet 260ms), with fades only under reduced motion;
  - phone layouts as a sheet and cards;
  - every figure opens its records: the badge opens the panel, the panel's unread figure opens the Unread view, and the Unread view's total equals the badge.

## Authorisation Model and Negative Cases

Keycloak authenticates. Strapi enforces Role → Function → FunctionAPI, then the record-level rule, against the resolved IdamBox User in `ctx.state`, identically under the development identity bridge and a Keycloak-verified user, never branching on the auth mode (POST-DEMO-BRIEF §2). Navigation visibility is not authorisation: every control the UI hides is also refused by Strapi.

**Grants** (D-35 to D-37): one API-only Function held by `role.requestor` and `role.security_analyst`, never the agent's role; the service identity refused by the policy whatever it holds; every operation scoped to the caller; readability applied by the service (D-13).

**Positive cases:**
- every active human user (a Requestor, a Security Analyst, an analyst who raised a request, and from Phase 17 a risk owner) lists, counts, opens and marks their own notifications;
- each person is told only about records they may read now, in the part they were told in.

**Negative cases** (each proven in the API by a Strapi integration test or a matrix row, and in the UI by Vitest or Playwright):

| Case | API outcome | UI outcome |
|---|---|---|
| Maya (an unrelated Requestor) lists notifications or reads the summary while Jane has unread ones | 200 with only Maya's own; none of Jane's is listed or counted, and no title of Jane's appears in any response | Maya's badge, panel and page show nothing of Jane's |
| Maya, Bob or anyone else marks one of Jane's notifications read or unread | 404 for the whole call, persistence unchanged | No such control |
| "Mark all as read" by Maya | Changes only Maya's own | Not applicable |
| A notification whose subject its recipient can no longer read (the questionnaire returned to analyst review; the recipient no longer a Security Analyst; the subject deleted) | Not listed or counted; marking it by id is 404 | It leaves the panel, the page and the badge |
| The service identity calls list, summary or mark | 403, its birthright included | Not applicable (no web session) |
| An event whose recipient would be the actor, the service identity or an inactive user | No notification written | Nothing to show |
| An event for "the assigned analyst" on an unassigned request | No notification written | The queue's unassigned pool shows the work |
| A request naming a recipient, an unknown parameter, a view outside the closed vocabulary, a page size outside the closed set, malformed or more than 50 ids, both mark forms at once, or an `asOf` in the future | 400, nothing written | Not applicable |
| A GET of the list or the summary | Never changes `readAt` | Not applicable |
| A route for the content type outside D-03 | None exists (the inventory and the matrix prove it) | Not applicable |
| A Requestor receives an analyst-part kind, or a sentence names a person the recipient's own read does not show | Never (tested) | Not applicable |
| A destination outside the app's own paths | Never served; the web's parser refuses one | No link rendered |
| No identity, or no token | The matrix conventions: 403, or the token family's status | The sign-in path |
| A viewer without `notification:read` | The policy's 403 by grant | No header control; the page shows the permission state |

**Phase 17's seventh matrix caller** (`riskOwner`, 17 D-75) states its outcome on this phase's rows: 200 for its own notifications, 404 for Jane's ids. Phase 17 proves its participant readability through the same predicates.

## Specific Ideas

- **The scenario in words.** Jane raises a request; Bob picks it up and assigns it to the second analyst, who, on her next page, sees "1" on the header control, opens the panel, and reads "Bob Doe assigned RAR-… · {title} to you"; one click opens the analyst request page and the count clears. Bob, who acted, has nothing new. The second analyst releases the questionnaire; Jane's bell shows "1": "The questionnaire for RAR-… is ready for you to answer", which opens her questionnaire page. She answers and submits, which reads that notification, and the second analyst, as assignee, is told the answers arrived. Jane adds a note; the assignee is told, and opening it lands at the note in the thread. The analyst replies; Jane is told. When the assessment is released, Jane is told and opens the released view. Maya, signed in throughout, sees only her own notifications, and the API refuses her any of Jane's.
- **Access going away.** If the analyst returns the questionnaire to analyst review before Jane answers, Jane's notification leaves her panel, her page and her count, and is marked read, so when the questionnaire is released again Jane sees exactly one new notification.
- **A requesting analyst.** When Bob raises a request of his own and a colleague releases its questionnaire, Bob is told as its Requestor and the notification opens the Requestor's questionnaire page.
- **Development database.** The new table, the grants and the capability reach the operator's development database only when the orchestrator restarts Strapi; tests use their own databases. Nothing is backfilled, so the centre starts empty.

## Orchestrator Confirmations (2026-10-01, post-demo Stage 2)

The research raised four questions. Each is settled as follows and binds the UI-SPEC and the plans:

- **Badge refresh:** the header count is re-read once after each client navigation the person makes, with no timer and no polling. It is not an automatic refresh in the sense of the direction's do-not rule 9, because it follows the person's own action. The UI-SPEC states this rule. A Server Action that revalidates re-renders the layout after the person's own marks.
- **Undo for "Mark all as read":** the operation returns the single read time it wrote, and Undo clears exactly the notifications marked at that time, not a list of ids. The contract-gap record documents this.
- **Reassignment (D-21):** the former assignee's analyst-side notifications on that request are all marked read, not only the assignment notification.
- **The service-identity refusal set:** Phase 19 names its set generically, `SERVICE_IDENTITY_REFUSED_OPERATIONS`, and this phase and Phase 17 add members to it. 19-CONTEXT records this.
- **`assessment-released` stays one kind (D-12):** Phase 17.1 reuses it for release and close, worded at read time from the request's `closed` status, rather than replacing it. Build the wording to allow that.
- **Implementation findings bind the plans (19.1-RESEARCH):** notification writes go through the Document Service so they join the event's transaction; bulk marks use raw SQL because of Strapi 5.51.0's `updateMany` bug on relation filters; and one SQL readability check feeds the list, the total, the unread count and "Mark all as read", with an oracle test.
