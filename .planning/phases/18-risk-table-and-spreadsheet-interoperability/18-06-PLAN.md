## Phase Goal

**As a** Security Analyst, **I want** an assessment's risks in a table I can edit, copy and paste like Excel or a SharePoint list, **so that** reviewing and updating many risks takes minutes rather than a long scroll.

This plan's slice: the organisation's 5 × 5 scales hold on every write, the rating derives and can be overridden with a reason, a stale single edit is refused instead of overwriting, and the analyst read carries what the table needs in one call.

## Recorded planning decisions

- **Parser.** In `assessment-workflow.ts`, `RISK_WRITABLE_FIELDS` and `projectAnalystRiskDetail`'s `RISK_DETAIL_FIELDS` gain `inherentRatingOverrideReason` and `residualRatingOverrideReason` (twin lists). `parseWritableRiskFields` keeps its shape checks (text, null, enum types) and adds: the two reasons are string or null. A new `validateWritableRiskFields(fields, current): RiskCellError[]` runs `resolveRatingWrite` for each stage the fields carry and returns every cell error (the bulk core's collecting form, 18-07); `parseWritableRiskFields` throws the first of them as `AssessmentWorkflowError(400, message, reason)` with `reason` the cell reason (`SCALE_VALUE_INVALID`, `RATING_SCALE_VALUES_REQUIRED`, `RATING_OVERRIDE_REASON_REQUIRED`).
- **Inner functions.** `createRiskWithinMutation` resolves both stages against an empty current and writes the result; `updateRiskWithinMutation` re-reads the risk inside the transaction (as today), then, before `resolveRelations`, runs `compareCellBases({ current: authoritativeRisk, bases })` when `bases` is given and throws `AssessmentWorkflowError(409, "CSRM Risk changed since it was read.", "RISK_CHANGES_CONFLICT")` carrying `conflicts` enriched by `latestFieldChangeAuthors`; then resolves both stages with the current values, writes the result, and returns `{ ...record, changed, overridesCleared: { stage, reason }[] }`. An override cleared by a changed input appears in the history row's `changes` as the reason field going to null. `createRiskWithinMutation` takes an optional `generateRiskNumber` passed to `createWithRiskNumber` (research Answer 4's test seam).
- **Who changed it.** `latestFieldChangeAuthors(strapi, { riskDocumentIds, fields }, trx)` reads the history rows of those risks newest first (on the transaction) and returns, per risk and field, the latest row whose `changes` names the field: `{ changedBy: { documentId, displayName } | null, changedAt }`. It is narrative only: no gate reads it.
- **PATCH.** The risk controller's update accepts `{ data, bases? }`; `bases` keys must be in `data`; the 409 body is `RiskChangesConflictErrorResponse` with `conflicts` (`riskId` is the path's risk). The spec's `assessment-workflow/update-risk` request gains optional `bases` and the 409 response.
- **Scale publication.** `RISK_SCALE_DESCRIPTIONS` copies the approved record's `## Default Scale Descriptions` verbatim (likelihood: one text per level; consequence: `{ financial, operational, regulatoryLegal, reputational, privacy, safety }` per level); `publishedRiskScale()` returns the record's `## The Published Scale` shape. Phase 22 replaces the source behind the same function (17.1 D-58).
- **Read additions.** Analyst detail: top-level `riskScale` (spec `RiskScale`); each risk `controlImplementations` = `(document.controlImplementations ?? []).map(projectControlImplementationSummary)` narrowed to `{ documentId, controlNumber, title, status }` (spec `RiskControlSummary`), plus both reasons. Participant risk item and `RequestorReleasedAssessmentDetail`'s successor (17-07's `ParticipantAssessmentDetail` risk item) and the released analyst projection gain both reasons. AI values awaiting confirmation stay excluded (17 D-26). The web parsers in `assessment-schema.ts` mirror every addition.
- **Readiness and fingerprint.** In 17.1's submission readiness, the per-risk requirement key `ratingsFollowScale`, label `Ratings follow the scale`, outstanding for an unreleased active risk when `ratingsFollowScale(values).follows` is false, destination the risk's cell (`risks?cell={riskNumber}.{field}` for the first offending field). In `decision-fingerprint.ts`, the decision scope's allowlist gains both reasons under the next version number; comparison of a stored act uses the version it was stored with (17.1 D-37's rule).
