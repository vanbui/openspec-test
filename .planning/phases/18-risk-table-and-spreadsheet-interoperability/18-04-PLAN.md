## Phase Goal

**As a** Security Analyst, **I want** an assessment's risks in a table I can edit, copy and paste like Excel or a SharePoint list, **so that** reviewing and updating many risks takes minutes rather than a long scroll.

This plan's slice: the approved storage exists, the body limit is explicit, every refusal has its closed code, and the analyst read tells the table whether it may edit and why not.

## Recorded planning decisions

- **Schemas.** Exactly 18-01's attributes. `csrm-saved-view/schema.json`: `"collectionName": "csrm_saved_views"`, info `singularName` `csrm-saved-view`, `pluralName` `csrm-saved-views`, `displayName` `CSRM Saved View`, `options.draftAndPublish: false`; `owner` `{ "type": "relation", "relation": "manyToOne", "target": "api::idambox-user.idambox-user" }`; `viewKey` string required maxLength 64; `name` string required maxLength 80; `visibility` string required maxLength 16; `definition` json required. The folder holds only `content-types/csrm-saved-view/schema.json` (18-10 adds routes and services). `csrm-risk/schema.json` gains only the two `text` attributes with `maxLength: 500`.
- **Body limit.** In `strapi::body`'s config add `jsonLimit: '1mb'` beside `formLimit`, with a comment: `D-13 (Phase 18): one bulk save is at most 1,000 rows and 1,000,000 bytes; raising this widens every JSON route.`
- **Reasons.** Append 18-01's new reasons to `CONFLICT_REASONS` in both lists with a comment naming Phase 18. Spec: add them to the `reason` enum of `AssessmentWorkflowErrorResponse` and of the risk update's conflict schema; new components `RiskCellReason` (enum of the 14 cell reasons), `RiskCellConflict` `{ riskId, field, base, current, changedBy: { documentId, displayName } | null, changedAt: string(date-time) | null }`, `RiskChangesConflictErrorResponse` (`error.status` 409, `error.details.reason` `RISK_CHANGES_CONFLICT`, `error.details.conflicts` 1 to 5,000 items) and `RiskChangesInvalidErrorResponse` (`error.status` 400, `error.details.reason` `RISK_CHANGES_INVALID`, `error.details.cells` 1 to 5,000 items of `{ riskId?, newRowKey?, field, reason: RiskCellReason }`), all `additionalProperties: false`.
- **Mode.** `assessmentEditability({ assessment, actor }): { editable: true } | { editable: false; reason; roundNumber: number | null }` returns the guard's first refusal in 17.1 D-23's order (`ASSESSMENT_NOT_MUTABLE`, `RESPONSE_ROUND_OPEN`, `ACCEPTANCE_ROUND_OPEN`, `ACTOR_IS_RISK_OWNER`, `ACTOR_IS_EXECUTIVE_APPROVER`), with the open round's number for the two round reasons. `assertAssessmentEditable` throws its `AssessmentWorkflowError` from that result, so the two cannot diverge (its 400 for a blank actor stays). The analyst detail controller computes it for the requesting analyst and `projectAnalystAssessmentDetail` emits `riskTableMode: { editable, reason, roundNumber }` (`reason` and `roundNumber` null when editable). Spec component `RiskTableMode`, required on `AnalystAssessmentDetail`; the web parser in `assessment-schema.ts` mirrors it.
