# Phase 06.1: Requestor and Analyst Revert-to-Draft for Requests and Questionnaires - Research

**Researched:** 2026-09-03
**Domain:** Authoritative Strapi workflow reversal, audit facts, and typed Next.js mutation flows
**Confidence:** HIGH

## User Constraints

### Locked Decisions

- A Request may be reverted only from `submitted` — before any questionnaire work exists. Reverting clears `submittedDate` and returns `requestStatus` to `draft`.
- A Questionnaire may be reverted only while the parent request is `questionnaire-in-progress` and no assessment draft exists. Reverting flips every submitted answer envelope back to `state: "draft"`; answer values are preserved.
- Both actors (owning Requestor, authorised Security Analyst) may revert; Strapi remains authoritative for record-level authorization.
- A short reason is mandatory and persisted, along with the reverting identity and timestamp, on `CsrmAssessmentRequest` and `CsrmQuestionnaire`. The data-model additions must be justified in a `docs/contract-gaps/` record before the schema changes, per the project brief.

### Non-negotiable project constraints

- Produce the plan only; do not include Keycloak or OIDC work.
- Keep Strapi as the production API boundary. Web pages must use typed `openapi-fetch` services and Server Actions; no raw page fetches or frontend API facade.
- Preserve JDL terminology; server-side Role → Function → FunctionAPI and record authorization are authoritative.
- Add a justification record in `docs/contract-gaps/` before the minimal optional Strapi schema additions.
- Register every changed Strapi route in the Role/Function/FunctionAPI catalogue, add it to `docs/references/specification.json`, and regenerate `apps/web/src/lib/api/generated/schema.d.ts`.
- Use strict TypeScript, semantic design tokens, WCAG 2.2 AA patterns, responsive 375–1440px behavior, and automated tests.

## Summary

The current request workflow makes `requestStatus` and `submittedDate` server-owned on ordinary request updates. The current questionnaire has no persisted status: `questionnaireState` derives `"submitted"` only when every active answer envelope is submitted, and answer mutation rejects any batch containing a submitted envelope. Reversal therefore must be an explicit protected workflow operation, not a widened generic update or a synthetic questionnaire status.

The smallest compatible audit extension is three optional attributes on each aggregate: `revertReason` (text), `revertedAt` (datetime), and `revertedBy` (many-to-one IdamBox user relation). These express the required most-recent reversal fact without invalidating existing records. Because these fields cannot represent an unbounded history, the contract-gap record must explicitly define the supported audit semantics and must precede both schema edits.

**Primary recommendation:** Add `POST` reversal operations for each aggregate, authorize the route with the existing resource policy, lock and re-read the authoritative aggregate inside a transaction, then write the workflow reversal and audit fact together. For questionnaires, replace every active submitted answer with a draft envelope retaining its exact `value` and a fresh server-owned `updatedAt`, omitting `submittedAt`.

## Existing Contract Findings

### Request reversal implications

The authoritative request vocabulary is exactly `"draft"`, `"submitted"`, `"questionnaire-in-progress"`, `"risk-assessment-drafted"`, `"under-review"`, `"approved"`, and `"closed"`. [VERIFIED: apps/strapi/src/api/csrm-assessment-request/content-types/csrm-assessment-request/schema.json:77-91]

> `"draft", "submitted", "questionnaire-in-progress", "risk-assessment-drafted", "under-review", "approved", "closed"`

`prepareRequestorUpdate` currently requires the persisted request to be draft before any Requestor update and only creates submission by writing `requestStatus: "submitted"` and a server timestamp. [VERIFIED: apps/strapi/src/api/csrm-assessment-request/services/request-workflow.ts:58-73]

> `if (persisted.requestStatus !== "draft") throw new AssessmentRequestWorkflowError();`
>
> `return { ...writable, requestStatus: "submitted", submittedDate: submittedAt.toISOString() };`

Use a distinct request reversal service rather than weakening `prepareRequestorUpdate`. It must allow only the exact persisted `submitted` status, require no attached questionnaire or assessment, set `requestStatus: "draft"`, set `submittedDate: null`, and write the audit fields in the same transaction. The UI must then reuse the existing draft edit/submit flow rather than implementing a second form.

### Questionnaire reversal implications and recommended envelope algorithm

The questionnaire answer envelope accepts only `"draft"` or `"submitted"`. A submitted envelope has the additional `submittedAt` property; a draft envelope must not contain it. [VERIFIED: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-workflow.ts:51-64]

> `const allowed = value.state === "submitted" ? ["schemaVersion", "value", "state", "updatedAt", "submittedAt"] : ["schemaVersion", "value", "state", "updatedAt"];`

Current drafts are deliberately blocked after submission by `assertMutableAnswerBatch`. [VERIFIED: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-workflow.ts:102-105]

> `if (Object.values(answers).some((answer) => isRecord(answer) && answer.state === "submitted")) {`
>
> `throw new QuestionnaireWorkflowError(409, "CSRM questionnaire has already been submitted.");`

The questionnaire state is derived, not stored: it is submitted when every active question has a submitted envelope. [VERIFIED: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-scope.ts:177-181]

> `if (questions.length > 0 && questions.every((question) => isSubmittedAnswer(question.answer))) return "submitted";`

**Recommended reversal algorithm:** within the existing serialized questionnaire mutation and database transaction, lock the questionnaire, re-load its questions plus parent request and assessment relation, and fail with 409 unless (a) the derived questionnaire state is submitted, (b) parent `requestStatus` is exactly `"questionnaire-in-progress"`, and (c) the parent `assessment` relation is absent. Parse the current definition and for every active answer envelope require the current closed submitted shape, then persist:

```ts
{
  schemaVersion: 1,
  value: submitted.value,
  state: "draft",
  updatedAt: now.toISOString(),
}
```

The algorithm intentionally removes `submittedAt`, preserves the typed `value` exactly, and therefore makes `assertMutableAnswerBatch` pass on the next draft save. It must update the questionnaire audit fields in the same transaction. It must not change the parent request status: existing `nextRequestStatusAfterDraft` explicitly accepts `"questionnaire-in-progress"` and leaves it unchanged. [VERIFIED: apps/strapi/src/api/csrm-questionnaire/services/questionnaire-workflow.ts:95-100]

> `if (status === "questionnaire-in-progress") return status;`

The request assessment relation is the authoritative no-draft guard; the existing assessment-draft workflow already treats a present relation as an existing assessment and fails closed on incompatible request state. [VERIFIED: apps/strapi/src/api/csrm-assessment/services/assessment-workflow.ts:524-541]

> `const existingAssessmentId = relationDocumentId(request.assessment);`
>
> `if (existingAssessmentId) {`

## Minimal Data-model Extension

### Required ordering

1. Create `docs/contract-gaps/phase-06.1-revert-audit-facts.md` first. It must justify why the frozen JDL lacks a reversible-workflow audit fact, record that only the most recent reversal is persisted, identify the fields below as optional compatibility additions, and state that a complete event history is deferred to a future explicit model decision.
2. Only after that record exists, add the attributes to the two Strapi `schema.json` files.
3. Update contract, catalogue, bootstrap copy, generated web types, backend projections, and tests together.

### Recommended fields

Add the same optional attributes to `CsrmAssessmentRequest` and `CsrmQuestionnaire`:

| Attribute | Strapi type | Meaning | Why minimal |
|---|---|---|---|
| `revertReason` | `text` | Required per-operation reason written by the server. | One scalar records the stated reason without a new audit entity. |
| `revertedAt` | `datetime` | Server-generated timestamp of the latest successful reversal. | One scalar provides time without a status-history model. |
| `revertedBy` | `manyToOne` to `api::idambox-user.idambox-user` | Acting Requestor or authorised Security Analyst. | Reuses the established IdamBox identity relation pattern. |

All attributes must remain optional in schemas and OpenAPI create/update documents so existing records remain valid. The JDL currently defines request `submittedDate` and `requestStatus`, but contains no corresponding revert-audit properties; it defines only questionnaire number, title, and description. [VERIFIED: docs/references/idambox-datamodel.jdl:65-80 and 158-162]

> `submittedDate Instant,`
>
> `requestStatus CsrmRequestStatus required`
>
> `entity CsrmQuestionnaire { questionnaireNumber String unique, title String required, description TextBlob }`

Use a shared closed mutation body `{ reason: string }`, trimmed and non-empty. A maximum of 1,000 characters is a recommended bounded interpretation of “short”; it needs confirmation in the planning decision if the team has a different operational limit. [ASSUMED]

## Common Pitfalls

### Treating questionnaire state as a database field

**What goes wrong:** A new questionnaire status creates a competing lifecycle source and diverges from current answer-envelope derived state.

**Avoidance:** Change all active submitted envelopes to draft and continue using `questionnaireState`; do not add a questionnaire status field.

### Converting only some envelopes or retaining `submittedAt`

**What goes wrong:** Mixed batches remain non-mutable or misprojected as submitted; an extra `submittedAt` violates the closed draft envelope shape.

**Avoidance:** Reparse the definition, require a complete submitted batch, transform every active submitted envelope, and omit `submittedAt`.

### Checking eligibility before the transaction only

**What goes wrong:** A concurrent assessment-draft creation or another reversal can invalidate a stale decision.

**Avoidance:** Preserve the existing serializer/row-lock model and re-read authoritative request, questionnaire, question, and assessment relation state after locking.

### Relying on hidden buttons for authorization

**What goes wrong:** A forged request could operate on another Requestor’s record or bypass capability grants.

**Avoidance:** Register exact FunctionAPI grants and attach the existing resource authorization policy to each route; retain server-side owner checks.

### Exposing analyst draft answers after reversal

**What goes wrong:** Reversed answers are drafts again and must not be visible in the analyst review projection.

**Avoidance:** Reuse `projectQuestions` and test that analyst detail returns the safe awaiting-submission state after reversal.

### Updating only one contract surface

**What goes wrong:** Runtime route, catalogue, OpenAPI, bootstrap catalogue, and generated web type drift breaks capability enforcement or typed calls.

**Avoidance:** Treat all of them as one atomic contract task and run the existing contract/catalogue and generated-schema checks.

## Open Questions

1. **Does “audit trail” require every historical revert rather than the latest revert fact?**
   - What we know: Scope explicitly requires reason, identity, and timestamp persisted on each named aggregate, and insists on minimal optional schema additions.
   - What is unclear: Whether later reversals must retain earlier events.
   - Recommendation: Lock the phase to most-recent reversal facts, document the limitation before schema edits, and defer immutable event history to a separately justified model extension.

2. **What maximum reason length is required?**
   - What we know: The reason must be short and mandatory.
   - What is unclear: Exact business maximum.
   - Recommendation: Use the shared 1–1,000-character closed schema unless the product owner specifies another bound.
