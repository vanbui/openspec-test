## Top 3 Priority Fixes

1. **AI-generated content has no durable provenance or labeling at the point of review** — When an analyst clicks "Review generated questionnaire" (`apps/web/src/features/assessments/questionnaire-generation-job.tsx:195`), they land on `QuestionnaireReview` (`apps/web/src/features/questionnaires/questionnaire-review.tsx`), which renders only `title`, `questionnaireNumber`, and (once submitted) a "Submitted" badge — there is no "AI-generated" badge, provider name, or generation date anywhere on this page. The only place `providerName`/`providerVersion` is shown is the transient completed-job card (`questionnaire-generation-job.tsx:178`), which disappears once the analyst navigates away or reloads. `QuestionnaireSummary` and `questionnaire-service.ts` do not project `generatedBy`/`generatedDate` at all, even though those fields exist on the Strapi content type (per `06.2-01-SUMMARY.md`). **User impact:** an analyst reviewing a questionnaire days later, or via the questionnaire list, cannot tell it was AI-generated versus manually authored, undermining the trust/provenance requirement this phase explicitly targets. **Fix:** project `generatedBy`/`generatedDate`/provider fields through `questionnaire-service.ts` into `QuestionnaireSummary`, and render a persistent "AI-generated · {provider} · {date}" badge/line on `QuestionnaireReview` and in the questionnaire list, not only on the transient job card.

2. **Third weight (`font-medium`, 500) violates the declared two-weight typography contract** — The app-shell contract mandates exactly two weights (400/600). `font-medium` appears extensively across this feature's files (e.g. `questionnaire-generation-job.tsx:178-179`, `assessment-detail.tsx:60,66`, `revert-audit-summary.tsx:43`) alongside `font-semibold`. **User impact:** inconsistent visual weight hierarchy undermines the "label vs. body" distinction the type ramp is meant to enforce, and any future design audit will keep flagging this drift. **Fix:** replace `font-medium` usages in this feature area with `font-semibold` (Label role) or plain body weight, matching the declared 400/600 ramp.

3. **`text-xs` used outside the declared four-size type ramp** — `text-xs` (12px) appears repeatedly (e.g. `revert-audit-summary.tsx:43`, `assessment-detail.tsx` `DetailValue` label at line 60) but the spec's ramp is 14/16/20/28px only. **User impact:** an extra, smaller-than-spec size erodes legibility and the ramp's internal consistency, particularly for metadata labels that are already dense. **Fix:** raise these labels to `text-sm` (14px, the Label role) or fold them into the existing Label typography token rather than introducing a fifth size.

## Detailed Findings

### Pillar 1: Copywriting (3/4)
- Positive: state copy is consistent and specific — `statusCopy` object (`questionnaire-generation-job.tsx:35-40`) gives distinct, plain-language messages per status; the replacement confirmation dialog explicitly states "This replaces the existing questionnaire only when it has no Requestor answers. Answered questionnaires are protected." (`questionnaire-generation-job.tsx:184`), which is good high-stakes copy.
- Gap: the failed-state `AlertDescription` renders `job.failureMessage` directly from the server (`questionnaire-generation-job.tsx:177`) with no client-side normalization or fallback copy. If the backend ever returns an internal error string, it will render unfiltered to the analyst. There's no evidence in the reviewed files of message allow-listing on the client.
- Minor: "Attempt {job.attempt}" badge (`questionnaire-generation-job.tsx:182`) exposes an internal retry counter to the user with no explanation of what "Attempt" means in context — acceptable for an analyst-facing tool but slightly jargon-y.

### Pillar 2: Visuals (2/4)
- The generation lifecycle card has a reasonable focal point (one primary CTA — Generate/Replace) and clear iconography (`Sparkles`, `LoaderCircle`, `CheckCircle2`, `AlertCircle`, `Clock3`) that differentiates states.
- Icon-only decorative icons are correctly `aria-hidden` throughout.
- Major gap: there is no persistent visual signal (badge, icon, colored strip) that content on the questionnaire-review screen originated from AI generation versus manual entry — see Top Fix #1. This is a visual-hierarchy and trust-signaling miss specific to this phase's stated purpose (AI-generated content).
- The failed/timeout/completed states are visually differentiated only by icon + border, all using the same `border-border` gray box for queued/running/timeout (`questionnaire-generation-job.tsx:179,186`) — acceptable, but a running (in-progress) state and a timeout (stalled) state look nearly identical apart from the icon, making it easy to miss that generation has stalled.

### Pillar 3: Color (3/4)
- No hardcoded hex/rgb values found in the audited files (`grep` for `#[0-9a-fA-F]` and `rgb(` returned nothing).
- No direct `text-primary`/`bg-primary`/`border-primary` usage in the reviewed generation/review files — components rely on shadcn `Button`/`Badge`/`Alert` variants, which is correct token discipline.
- `ConfirmDialog`'s `confirmVariant="destructive"` is used for the "Replace unanswered questionnaire" action (`questionnaire-generation-job.tsx:184,193`), which is appropriate given this is a data-loss-adjacent action, but it means the button color for "confirm regeneration" is identical to genuinely destructive delete actions elsewhere in the app (e.g. `AnalystQuestionnaireRevert` in `assessment-detail.tsx:92`). This dilutes the destructive-red signal's rarity value if regeneration (a recoverable, re-runnable action) is styled identically to irreversible deletion.
- Success badge on submitted state uses semantic `border-success-border bg-success-subtle text-success` tokens (`questionnaire-review.tsx:66`) — correct token usage.

### Pillar 4: Typography (2/4)
- `text-xs`, `text-sm`, `text-base`, `text-lg`, `text-xl` all appear across `apps/web/src/features/assessments` and `apps/web/src/features/questionnaires` — five distinct sizes against the app's declared four-size ramp (14/16/20/28px), and `text-lg`/`text-xl` don't map cleanly onto the declared 20px Heading / 28px Display roles either.
- `font-medium` (weight 500) appears dozens of times alongside `font-semibold` — a third weight beyond the declared 400/600 pair. See Top Fix #2/#3 for concrete file references.
- The generation card headline `<h2 className="font-semibold leading-none">Questionnaire generation</h2>` (`questionnaire-generation-job.tsx:182`) correctly matches the Heading role's 600 weight, but doesn't declare an explicit size class, inheriting from `CardHeader`/`CardTitle` defaults rather than the token scale directly — hard to verify against the 20px contract without checking the shadcn Card primitive.

### Pillar 5: Spacing (3/4)
- No arbitrary bracket spacing (`[Npx]`/`[Nrem]`) found in the audited generation/review/dialog files.
- `gap-x-3` (12px) is used in the completed/running state rows (`questionnaire-generation-job.tsx:178-179`) — 12px is not one of the declared 4/8/16/24/32/48/64 tokens; it's a valid Tailwind default but off the app's own declared scale.
- `p-4` (16px) and `gap-3`/`space-y-4` are otherwise consistent with the md (16px) and sm/lg tokens.
- Card padding, button sizing, and dialog layout all rely on shadcn primitives rather than hand-rolled spacing, which is a good consistency signal.

### Pillar 6: Experience Design (2/4)
- Strong state coverage: queued/running/completed/failed statuses, a bounded 30-second client poll with graceful "Check again" recovery (`questionnaire-generation-job.tsx:82-113,161-167`), stale-job-ID protection against overwriting a newer job with a late response (`activeJobIdRef` checks at lines 96, 109), and an explicit acknowledgement-gated confirmation before destructive-adjacent regeneration (`ConfirmDialog` at line 184).
- `aria-live="polite"` status announcements (`questionnaire-generation-job.tsx:183`) and `role="alert"` on the form-error `Alert` (line 185) show accessibility-conscious state handling.
- Gap: as detailed in Top Fix #1, generated content carries no durable AI-provenance signal beyond the transient job card — this is the central "trust and provenance" requirement called out for this phase and it is not met once the user leaves the generation screen.
- Gap: the "review the generated questionnaire before use" instruction (`questionnaire-generation-job.tsx:178`) is good guidance but is not reinforced on the destination review page itself — there's no "unreviewed AI content" indicator on `QuestionnaireReview` distinguishing a freshly generated, not-yet-submitted questionnaire from one already vetted by a Requestor.
- Positive: the regeneration guard correctly prevents overwriting answered Requestor work (per `06.2-02-SUMMARY.md`), and the UI surfaces this via the explicit confirmation dialog description.
