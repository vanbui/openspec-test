## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01 — Vendor-agnostic by design: scope to the OpenAI-compatible wire protocol.** Standardize the integration surface on the OpenAI Chat Completions wire format (shared by OpenAI, Azure OpenAI, Groq, Together, Fireworks, Mistral, DeepSeek, vLLM, Ollama, LM Studio, TGI, llama.cpp server). Native Anthropic Claude is out of direct reach; a customer wanting it points `baseURL` at their own translating gateway.

**D-02 — One dependency (`openai` npm package), used as a thin HTTP client; direct calls, no mandatory gateway.** Config-driven HTTP client pointed at a configurable `baseURL`, no mandatory proxy. API key is genuinely optional/blank-able in config (some self-hosted servers reject an `Authorization` header entirely). No TLS-verification-skip option in app code — trusting a custom CA is a deployment/OS-level concern (`NODE_EXTRA_CA_CERTS`).

**D-03 — Fully independent per-operation provider configuration.** `config/ai.ts` carries two complete, independent `{baseURL, apiKey, model}` triples — one for assessment-draft generation, one for questionnaire generation.

**D-04 — Provider-selection switch, safe default, and forced test hermeticity.** `CSRM_AI_PROVIDER=deterministic|openai-compatible` selects the provider at runtime, read once at module load (not scattered `process.env` checks), injected into the workflow. Default to `deterministic` when unset. Test setup must force `CSRM_AI_PROVIDER=deterministic` explicitly, overriding whatever a developer's local `.env` says.

**D-05 — Config surface and boot-time validation.** `config/ai.ts` follows the existing `config/*.ts` / `env()` convention. Holds: the D-04 switch, the two D-03 provider triples, an operator-supplied `providerLabel` (D-06), a structured-output-mode toggle (D-07, default on), an explicit request timeout (~60s), and a max-output-tokens cap. At boot, when the real provider is selected, validate required fields (`baseURL`, model names) are present and fail fast with a clear startup error if not. Do not ping the endpoint live at boot.

**D-06 — Durable provenance fields, and a contract-gap doc that supersedes the Phase 8 deferral.** Add `providerName` (operator-supplied friendly label from config, defaulting to `"openai-compatible"` when unset — not a hardcoded vendor name, not the raw `baseURL` host) and `providerVersion` (the exact model ID string) to both `CsrmQuestionnaire` and `CsrmAssessment`. Both written in the same transaction as `generatedDate`/`generatedBy`. File `docs/contract-gaps/phase-06.7-*.md` explicitly stating this supersedes the Phase 8 deferral in `phase-04-deterministic-draft-jobs.md` and `phase-06.2-questionnaire-generation-provenance.md`.

**D-07 — Structured output is a quality aid, not the trust boundary; toggleable per deployment.** Request `response_format` to shape the response, but `parseAssessmentDraftProposal`/`parseQuestionnaireGenerationProposal` remain the unconditional validation gate. Make structured-output-mode an optional config flag (default on) so a deployment against a backend that errors on unrecognized `response_format` can disable it and fall back to prompt-only JSON.

**D-08 — Prompt-injection guardrails are layered, with the schema parser as the real backstop.** System prompt frames Requestor-authored fields as quoted, untrusted data. The closed-vocabulary schema parser is the actual backstop. The model has no tool/function access beyond producing the one JSON proposal.

**D-09 — Error taxonomy: generic analyst-facing message, differentiated internal codes.** Analyst-facing message stays generic and safe. Internal `failure.code` values: `PROVIDER_AUTH_ERROR`, `PROVIDER_RATE_LIMITED`, `PROVIDER_TIMEOUT`, `PROVIDER_OUTPUT_INVALID`.

**D-10 — Explicit latency, token, and context-size bounds; fail loudly, never truncate silently.** ~60s request timeout maps to `PROVIDER_TIMEOUT`. Explicit max-output-tokens cap sized to the parser's own bounds (≤50 risks, ≤10,000 questions). If assembled context exceeds the configured model's window, fail the call loudly rather than silently trimming. Context sizing per deployment is an operator responsibility.

**D-11 — Job registry and restart behavior are unchanged; no new durability, no instance-wide concurrency cap.** The in-memory, TTL-bounded job registries are unchanged. No new "orphaned job → failed" logic. No instance-wide concurrency cap.

## Summary

This phase substitutes a real, vendor-agnostic AI backend behind two already-frozen provider interfaces (`AssessmentDraftProvider`, `QuestionnaireGenerationProvider`) without touching their call sites' shape. The codebase already has an exact seam for this: both interfaces are single-method (`generate(context): Promise<Proposal>`), both have an existing closed-shape parser that is the real trust boundary, and both existing job registries already support typed, taxonomy-coded failures (`AssessmentDraftJobFailure`, `QuestionnaireGenerationJobFailure`) that a provider `generate()` can throw and have surfaced safely. Implementing this phase is almost entirely about (1) writing two new provider modules that wrap the `openai` npm package as a thin OpenAI Chat Completions client, mapping SDK-level errors onto the D-09 taxonomy; (2) a new `config/ai.ts` following the existing `env()` convention, validated at Strapi's `register()` boot phase; (3) a provider-selection module read once at import time; (4) two additive optional string fields on the `CsrmAssessment`/`CsrmQuestionnaire` schemas, written alongside existing `generatedDate`/`generatedBy`, requiring only a `schema.json` edit (this repo has no manual-migration convention — SQLite dev/prod both rely on Strapi's own schema sync; the `database/migrations/` directory is an empty placeholder); and (5) forcing `CSRM_AI_PROVIDER=deterministic` inside the one file that actually boots a real Strapi instance for tests, `tests/helpers/strapi-http-harness.ts`.

The `openai` npm package (verified 7.15.0, published 2026-09-10, officially maintained by OpenAI, 29.5M weekly downloads) declares `engines.node >= 22.0.0`, which is stricter than this repo's own `apps/strapi/package.json` engines range (`>=20.0.0 <=26.x.x`); the actual dev/CI runtime is Node 24.19.0 per STATE.md so this is not a blocker today, but it is a real latent incompatibility worth a note in the plan. A second, more consequential SDK gotcha: `openai-node`'s constructor throws at construction time if `apiKey` is left `undefined` and `OPENAI_API_KEY` is unset — even when a custom `baseURL` is supplied — so D-02's "genuinely optional/blank-able" key requires the new provider code to always pass `apiKey: config.apiKey ?? ""` explicitly, never omit the field. A third real-world finding: self-hosted OpenAI-compatible backends are inconsistent about `response_format` — some (older llama.cpp builds, some vLLM versions) reject it outright, but Ollama's `/v1/chat/completions` endpoint is documented to **silently ignore** `response_format: json_schema` and return unconstrained text, which the closed parser will correctly reject as malformed rather than erroring at the HTTP layer. This validates D-07's "parser as unconditional gate" design and should be called out explicitly as a pitfall, since it means "structured-output-mode is on" is not itself proof that output will be schema-shaped.

**Primary recommendation:** Add exactly one dependency (`openai`), write two new provider modules (one per operation) plus one shared OpenAI-compatible client/error-mapping helper under a new `src/csrm/` module, replace the two direct `deterministicXProvider` imports in `assessment-workflow.ts` and `questionnaire-generation-workflow.ts` with a provider-selection module read once at import time, add `config/ai.ts` validated in `register()`, add two optional string fields to both content-type `schema.json` files with a new contract-gap doc, and force `CSRM_AI_PROVIDER=deterministic` at the top of `tests/helpers/strapi-http-harness.ts` alongside the other test-only env overrides already there.

### Pattern 2: OpenAI-compatible provider adapter (D-01, D-02, D-07)

**What:** One adapter per operation implementing the existing `AssessmentDraftProvider`/`QuestionnaireGenerationProvider` interface (`{ name, version, generate(context) }`), internally building a prompt from the context, calling the shared OpenAI-compatible client, and returning the raw parsed JSON (the existing `parseXProposal` call already happens at the workflow call site, so the adapter itself should return a *plain unvalidated object*, matching how the deterministic provider's `generate()` result is passed through `parseAssessmentDraftProposal(...)` at the call site — see call site above).

**Client construction — exact SDK shape verified this session** [CITED: github.com/openai/openai-node README, fetched 2026-09-14; GitHub issue openai/openai-node#1464, fetched 2026-09-14]:
```typescript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: config.baseURL,
  // MUST always pass an explicit string, never leave apiKey undefined:
  // openai-node throws "The OPENAI_API_KEY environment variable is
  // missing or empty..." at construction time if apiKey is omitted and
  // OPENAI_API_KEY is unset in the environment -- even with a custom
  // baseURL set. Confirmed via openai/openai-node#1464 ("Library throws
  // error if apiKey isn't provided, even for custom base URLs").
  apiKey: config.apiKey ?? "",
  timeout: config.requestTimeoutMs, // D-10: ~60s
  maxRetries: 0, // the job registry's own retry (D-11) is the retry mechanism; do not double-retry inside the SDK
});
```

**Chat completion call with optional structured output (D-07):**
```typescript
const response = await client.chat.completions.create({
  model: config.model,
  messages: [
    { role: "system", content: systemPromptFramingUntrustedInput }, // D-08
    { role: "user", content: renderedContext },
  ],
  // D-10: explicit cap, never rely on SDK/provider defaults.
  // NOTE: "max_tokens" is the field understood by the Chat Completions
  // endpoint that essentially every OpenAI-compatible self-hosted server
  // mirrors (vLLM, Ollama, llama.cpp, LM Studio, TGI). OpenAI's own newer
  // reasoning models (o1/o3) prefer "max_completion_tokens" instead, but
  // self-hosted OpenAI-compatible backends generally do NOT recognize
  // "max_completion_tokens" -- sending the wrong field name for a given
  // target model/backend combination is a documented pain point. [CITED:
  // OpenAI community/docs search results, 2026-09-14; the exact field
  // name is a target-model property, not a library-wide constant, so the
  // plan should make this configurable or document it as an operator/
  // deployment concern rather than a fixed choice in code.]
  max_tokens: config.maxOutputTokens,
  ...(config.structuredOutputMode ? {
    response_format: {
      type: "json_schema",
      json_schema: { name: "assessment_draft_proposal", strict: true, schema: /* JSON Schema mirroring the existing parser's shape */ {} },
    },
  } : {}),
});
const rawText = response.choices[0]?.message?.content;
if (!rawText) throw new AssessmentDraftJobFailure("PROVIDER_OUTPUT_INVALID", "Draft assistance produced no usable output.");
let parsedJson: unknown;
try { parsedJson = JSON.parse(rawText); }
catch { throw new AssessmentDraftJobFailure("PROVIDER_OUTPUT_INVALID", "Draft assistance produced malformed output."); }
return parsedJson; // caller applies parseAssessmentDraftProposal() as the real gate (D-07)
```
[ASSUMED: the `response_format.json_schema` object shape (`{type: "json_schema", json_schema: {name, strict, schema}}`) is the documented OpenAI Chat Completions structured-output shape as of the SDK's current major version; not independently exercised against a live endpoint this session — verify against the installed `openai@7.15.0` TypeScript types (`ChatCompletionCreateParams`) during implementation, since minor SDK versions have changed this shape before (the SDK also ships a higher-level `client.chat.completions.parse()` + `zodResponseFormat()` helper which this phase should NOT use, since D-07 keeps validation in the existing hand-rolled parser rather than adopting Zod).]

**Error-mapping table (D-09) — verified error class names from official source** [CITED: github.com/openai/openai-node README "Error handling" section, fetched 2026-09-14]:
| SDK error / condition | D-09 code |
|---|---|
| `OpenAI.AuthenticationError` (HTTP 401) | `PROVIDER_AUTH_ERROR` |
| `OpenAI.PermissionDeniedError` (HTTP 403) — bad/missing key scoped wrong | `PROVIDER_AUTH_ERROR` |
| `OpenAI.RateLimitError` (HTTP 429) | `PROVIDER_RATE_LIMITED` |
| `OpenAI.APIConnectionTimeoutError` (request exceeded `timeout`) | `PROVIDER_TIMEOUT` |
| Any other `OpenAI.APIError` (400/404/409/422/5xx), a caught network `APIConnectionError`, or a backend that ignores `response_format` and returns free text / non-JSON / schema-invalid JSON | `PROVIDER_OUTPUT_INVALID` (falls through to the existing parser or to a JSON.parse failure) |

**Known real-world pitfall validating D-07's design** [CITED: web search of `vllm-project/vllm`, `ollama/ollama`, `ggml-org/llama.cpp` issue trackers, 2026-09-14]: self-hosted OpenAI-compatible backends are inconsistent about `response_format`. Ollama's `/v1/chat/completions` compatibility layer is documented to **silently ignore** the OpenAI-style `json_schema` response format rather than erroring, returning ordinary unconstrained text. vLLM and llama.cpp have had open issues/partial support for `response_format: json_schema` across versions. This means "structured-output-mode is on" does not guarantee schema-shaped output even when the call itself succeeds with HTTP 200 — the existing closed-shape parser catching this as `PROVIDER_OUTPUT_INVALID` (via `JSON.parse` failure or the parser's own rejection) is the correct and only reliable backstop, exactly as D-07 designed it.

### Anti-Patterns to Avoid
- **Letting the SDK's own key-presence check gate boot, instead of D-05's explicit validation:** the SDK throws lazily at client-construction time (inside the provider adapter, on first `generate()` call), not at Strapi boot. Boot-time validation (D-05) must be a separate, explicit check in `register()`, not "let the first Generate click surface the SDK's error."
- **Omitting `apiKey` from the `OpenAI` constructor call when it is blank** — causes a hard throw even for a self-hosted `baseURL` that needs no key (see Pattern 2, confirmed via `openai/openai-node#1464`). Always pass `apiKey: config.apiKey ?? ""`.
- **Using `client.chat.completions.parse()` + `zodResponseFormat()`:** this is the SDK's own higher-level structured-output helper, but it requires a Zod schema and effectively becomes a second, competing validation layer against D-07's mandate that the existing hand-rolled parser remains the unconditional gate. Use the lower-level `client.chat.completions.create()` and pass a plain JSON Schema object as `response_format.json_schema.schema` instead.
- **Retrying inside the SDK (`maxRetries` > 0) on top of the job registry's own retry (D-11):** the existing registry model is "failed job → analyst-initiated retry via `retry()`". Doubling retry logic inside the SDK obscures which attempt is which and risks masking rate-limit or auth failures behind silent internal retries; set `maxRetries: 0` and let the existing job-level retry own this.
- **Sharing one `{baseURL, apiKey, model}` triple across both operations "to keep config simple":** explicitly rejected by D-03; must be two fully independent triples even if a given deployment happens to point both at the same values.

## Common Pitfalls

### Pitfall 1: `apiKey` omission throws even for keyless self-hosted backends
**What goes wrong:** Constructing `new OpenAI({ baseURL: ... })` without an explicit `apiKey` throws `"The OPENAI_API_KEY environment variable is missing or empty..."` at construction time, even when `baseURL` points at a self-hosted server that doesn't need a key.
**Why it happens:** The SDK's own constructor validates `apiKey` presence independent of whether `baseURL` is the default OpenAI endpoint. [CITED: `openai/openai-node#1464`, fetched 2026-09-14]
**How to avoid:** Always pass `apiKey: config.apiKey ?? ""` explicitly; never conditionally omit the key.
**Warning signs:** Strapi boot or first Generate click throws an `OPENAI_API_KEY environment variable is missing` error even though `config/ai.ts`'s `baseURL`/`model` boot validation (D-05) passed.

### Pitfall 2: Self-hosted `response_format` support is inconsistent and can fail silently, not loudly
**What goes wrong:** With structured-output-mode on (D-07 default), some self-hosted OpenAI-compatible backends (documented: Ollama's `/v1/chat/completions` layer) silently ignore `response_format` and return free-form text instead of erroring — the call succeeds at the HTTP layer but the content isn't JSON-schema-shaped.
**Why it happens:** `response_format: json_schema` support varies by backend and version; it is not guaranteed by "OpenAI-compatible" branding. [CITED: `ollama/ollama` issue #10001, `vllm-project/vllm` issues #7656/#3148/#19097, `ggml-org/llama.cpp` issue #11847, all found via web search 2026-09-14]
**How to avoid:** Never treat "the call returned 200" as proof of schema conformance — always route the raw text through the existing closed-shape parser (D-07's design already does this correctly) and map a `JSON.parse` failure or parser rejection to `PROVIDER_OUTPUT_INVALID`.
**Warning signs:** High `PROVIDER_OUTPUT_INVALID` rates specifically against one self-hosted backend but not others — a signal to recommend that deployment disable `structuredOutputMode` (D-07's toggle) rather than a code bug.

### Pitfall 3: `max_tokens` vs. `max_completion_tokens` field-name mismatch across models/backends
**What goes wrong:** OpenAI's own newer reasoning models prefer/require `max_completion_tokens`; the classic `max_tokens` field is what essentially all self-hosted OpenAI-compatible servers actually implement. Sending the wrong one for a given target can either be rejected (400) or silently ignored depending on the backend's strictness.
**Why it happens:** The Chat Completions field name diverged between OpenAI's hosted API evolution and what third-party/self-hosted OpenAI-compatible servers actually mirror. [CITED: OpenAI community discussions, found via web search 2026-09-14 — not an official single-page spec citation, treat as MEDIUM confidence]
**How to avoid:** Use `max_tokens` as the default (it is the field the vendor-agnostic self-hosted target set overwhelmingly implements per D-01's own list — vLLM/Ollama/LM Studio/TGI/llama.cpp), and document in `config/ai.ts`'s comments (or a short operator note) that a deployment targeting an OpenAI reasoning model may need a code change or a translating gateway (already anticipated by D-01/D-02's gateway escape hatch).
**Warning signs:** A deployment against an OpenAI o-series model silently produces truncated or unbounded output despite the configured cap.

### Pitfall 4: Node engine mismatch between `openai`'s `engines.node >=22.0.0` and this repo's `>=20.0.0` floor
**What goes wrong:** A contributor or CI runner on Node 20 or 21 could install and (depending on npm's `engine-strict` setting, which this repo does not set) run `openai@7.15.0` with undefined behavior.
**Why it happens:** `openai` bumped its minimum Node requirement in a recent major/minor version; this repo's `package.json` engines floor predates this dependency.
**How to avoid:** Either bump `apps/strapi/package.json`'s `engines.node` floor to `>=22.0.0`, or explicitly accept the risk in the plan given the actual dev/CI machine already runs Node 24.19.0.
**Warning signs:** Cryptic SDK errors on an older Node runtime that don't reproduce on the primary dev machine.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Prompt injection via Requestor-authored free text (`businessPurpose`, `thirdPartyDetails`, submitted questionnaire answers) reaching the AI prompt | Tampering / Elevation of Privilege | D-08's layered guardrails: system prompt frames the fields as quoted untrusted data; the closed-vocabulary schema parser is the real backstop (a successful injection can only select a valid-but-wrong enum value, caught by mandatory human review); the model has no tool/function access beyond producing the one JSON proposal. |
| Provider-diagnostic leakage to the analyst-facing UI (stack traces, backend hostnames, raw SDK error messages) | Information Disclosure | D-09's generic analyst-facing message + differentiated internal `failure.code`; already enforced by both registries' `safeFailure()` functions, which only recognize the typed `AssessmentDraftJobFailure`/`QuestionnaireGenerationJobFailure` classes and otherwise fall back to a fully generic message — confirmed by the existing unit test asserting `JSON.stringify(failed).includes("secret")` is false. |
| Secrets (API keys) leaking into client bundles or logs | Information Disclosure | All provider config lives in `config/ai.ts` / server-side `env()` values, never passed to `apps/web` (constraint, unchanged architecture — `apps/web` has no access to Strapi's `config/` directory or environment). |
| SSRF-adjacent risk: an operator-configured `baseURL` pointing at an unintended internal host | Tampering | Out of scope for this phase's app code per D-02 (operator-controlled config, not user-controlled input) — `baseURL` is a deployment-time config value set by the operator, never derived from any Requestor/analyst-supplied input at runtime. |
