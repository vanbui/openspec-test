# Phase 06.7: Real AI Provider Integration for Questionnaire and Assessment Generation - Context

**Gathered:** 2026-09-14
**Status:** Ready for planning
**Source:** Operator-supplied plan-phase orchestrator context, derived from a Socratic grilling session (mattpocock-skills:grilling) covering vendor/SDK architecture, provenance persistence, job durability, guardrails, and ops posture. The operator explicitly rejected a single-vendor SDK in round 2 and required a vendor-agnostic, self-hostable integration; the decisions below reflect the corrected direction.

<domain>
## Phase Boundary

Substitute a real AI provider behind the two existing provider interfaces —
`AssessmentDraftProvider` (Phase 4) and `QuestionnaireGenerationProvider`
(Phase 06.2) — so both generation operations call a real model instead of the
deterministic stand-ins, while human review and release stay mandatory.

Scope is limited to these two already-implemented operations. The phase does
not build an agent framework, RAG memory, a LoRA refresh loop, or any other
capability described in `docs/AgenticAIResearch.docx` (a separate, broader
internship research brief) — that broader track informs a later phase
(Phase 8; advances INT-01/02/04), not this one. It does not touch the UI or
job-lifecycle contracts (routes, polling shape, job states) established in
Phase 4 and 06.2. It does not add durable job-queue infrastructure — that
also stays with Phase 8.

Advances INT-03.

</domain>

<decisions>
## Implementation Decisions

### D-01 — Vendor-agnostic by design: scope to the OpenAI-compatible wire protocol

The operator explicitly does not want to be locked into one AI vendor or
model, and must be able to point the app at a self-hosted LLM if a customer
prefers that. OpenAI, Azure OpenAI, Groq, Together, Fireworks, Mistral,
DeepSeek, and effectively every self-hosted runtime (vLLM, Ollama, LM
Studio, TGI, llama.cpp server) already implement the same OpenAI Chat
Completions wire format — same request/response shape, different `baseURL`
and key. Standardize the integration surface on that protocol. Native
Anthropic Claude (a different wire format) is out of direct reach for this
phase; a customer wanting it can point `baseURL` at their own translating
gateway (see D-02) — CSRM code never needs to know a gateway is there.

### D-02 — One dependency (`openai` npm package), used as a thin HTTP client; direct calls, no mandatory gateway

`apps/strapi` currently has almost no dependencies beyond Strapi core — no
schema library, no HTTP client, everything else hand-rolled. Add exactly one
new dependency, the official `openai` npm package, used purely as a
config-driven HTTP client (not a framework) pointed at a configurable
`baseURL`. This is a concrete, justified dependency (correct retry/timeout/
streaming/structured-output-request handling for a real external network
protocol) rather than framework creep — everything downstream of the raw
response is still the existing hand-rolled closed-shape parser (D-07).

Calls go directly to the configured endpoint — no mandatory gateway/proxy.
A customer wanting a vendor this phase doesn't reach directly (Claude,
Bedrock, Vertex) can still get there by pointing `baseURL` at their own
OpenAI-compatible gateway; that's ordinary config, not a CSRM feature.

Self-hosted auth/network specifics: API key is genuinely optional/blank-able
in config (some self-hosted servers reject an `Authorization` header
entirely). No TLS-verification-skip option in app code — trusting a custom
CA for a self-hosted deployment is a deployment/OS-level concern
(`NODE_EXTRA_CA_CERTS`), not something CSRM code ships.

### D-03 — Fully independent per-operation provider configuration

`config/ai.ts` carries two complete, independent configuration triples —
`{baseURL, apiKey, model}` for assessment-draft generation and the same
three for questionnaire generation — not one shared endpoint with just a
different model name per operation. This lets a deployment put
assessment-draft generation on a strong SaaS model while routing
questionnaire generation to a cheaper self-hosted model (or vice versa)
without any code change either way.

### D-04 — Provider-selection switch, safe default, and forced test hermeticity

`CSRM_AI_PROVIDER=deterministic|openai-compatible` selects the provider at
runtime, read once at module load (not scattered `process.env` checks) and
injected into the workflow. Default to `deterministic` when unset, so a
missing/misconfigured env var fails safe rather than silently attempting a
live call with no key — this default-safe behavior is also the operational
kill-switch (flip the var, restart, you're back to deterministic; no
separate runtime toggle needed for this phase).

Test setup must force `CSRM_AI_PROVIDER=deterministic` explicitly,
overriding whatever a developer's local `.env` says — the default-when-unset
rule alone protects CI but not a local `npm test` run against a `.env` a
developer set up for manual testing against a real/self-hosted model. This
is what makes "deterministic providers still selectable for tests and
offline runs" (roadmap success criterion 1) an actual guarantee rather than
an accident of what's unset.

### D-05 — Config surface and boot-time validation

`config/ai.ts` follows the existing `config/*.ts` / `env()` convention used
elsewhere in `apps/strapi/config/`. It holds: the D-04 switch, the two D-03
provider triples, an operator-supplied `providerLabel` (D-06), a
structured-output-mode toggle (D-07, default on), an explicit request
timeout (~60s), and a max-output-tokens cap.

At boot, when the real provider is selected, validate required fields
(`baseURL`, model names) are present and fail fast with a clear startup
error if not — cheap, catches typos immediately. Do not ping the endpoint
live at boot: a self-hosted box can be legitimately unreachable at startup
(still warming up) without that being a real misconfiguration; the
`PROVIDER_*` failure taxonomy (D-09) already handles a genuinely-unreachable
endpoint at call time.

### D-06 — Durable provenance fields, and a contract-gap doc that supersedes the Phase 8 deferral

Roadmap success criterion 3 requires provider name, version, timestamp, and
initiating analyst to be persisted for every generated questionnaire and
assessment draft. Today provider name/version live only in the volatile,
TTL-bounded job registry — `docs/contract-gaps/phase-04-deterministic-draft-jobs.md`
and `docs/contract-gaps/phase-06.2-questionnaire-generation-provenance.md`
both explicitly say durable provider provenance is a Phase 8 responsibility.
This phase's own success criterion overrides that deferral for this narrow
addition.

Add two new fields to both `CsrmQuestionnaire` and `CsrmAssessment`:
- `providerName` — an operator-supplied friendly label from config (D-05),
  defaulting to `"openai-compatible"` when unset. Not a hardcoded vendor
  name (there is no fixed vendor per D-01) and not the raw `baseURL` host
  (avoids leaking internal hostnames into a field the UI may display).
  Lets an auditor actually distinguish "generated by our self-hosted Llama
  box" from "generated by OpenAI's cloud."
- `providerVersion` — the exact model ID string configured/returned (e.g.
  `gpt-5`, `llama-3.1-70b-instruct`) — self-documenting, no separate version
  bookkeeping.

Both are written in the same transaction as the existing
`generatedDate`/`generatedBy`. File a new `docs/contract-gaps/phase-06.7-*.md`
record that explicitly states this addition supersedes the Phase 8
deferral in the two documents above, per the project's convention of
justifying data-model additions in a contract-gap record before the schema
change.

### D-07 — Structured output is a quality aid, not the trust boundary; toggleable per deployment

Request the provider's native structured-output/tool-calling mode
(`response_format`) to shape the response, but the existing closed-shape
parsers (`parseAssessmentDraftProposal`, `parseQuestionnaireGenerationProposal`)
remain the unconditional validation gate regardless of what the provider
claims to have honored — untouched by this phase.

Not every OpenAI-compatible self-hosted runtime handles an unrecognized
`response_format` field gracefully; a minimal one could error outright.
Make structured-output-mode request an optional config flag (default on)
so a deployment against such a backend can disable it and fall back to
prompt-only JSON, with the same parser as the enforcement point either way.

### D-08 — Prompt-injection guardrails are layered, with the schema parser as the real backstop

Requestor-authored free text reaches the prompt in both operations
(`businessPurpose`/`thirdPartyDetails` for questionnaire generation;
submitted questionnaire answers for assessment-draft generation) — the
classic injection surface. Containment:

1. The system prompt frames every Requestor-authored field explicitly as
   quoted, untrusted data to analyze — never as instructions.
2. The closed-vocabulary schema parser (D-07) is the actual backstop: even a
   successful injection can only select a valid-but-wrong value from the
   fixed vocabulary (e.g. a wrong rating), which mandatory human review
   already exists to catch.
3. The model is given no tool/function access beyond producing the one JSON
   proposal — no escalation path even under a successful injection.

### D-09 — Error taxonomy: generic analyst-facing message, differentiated internal codes

Real provider calls introduce failure modes the deterministic providers
never had. Keep the analyst-facing message generic and safe in every case
(existing pattern, no provider diagnostics leak to the UI), but
differentiate the internal `failure.code` taxonomy so logs (and a later
Phase 8 audit trail) can distinguish transient-and-retryable from
never-succeeds-without-operator-action:

- `PROVIDER_AUTH_ERROR` — bad/missing key or config
- `PROVIDER_RATE_LIMITED`
- `PROVIDER_TIMEOUT`
- `PROVIDER_OUTPUT_INVALID` — malformed/schema-invalid output despite
  structured-output mode

### D-10 — Explicit latency, token, and context-size bounds; fail loudly, never truncate silently

Set an explicit request timeout (~60s) that maps to `PROVIDER_TIMEOUT` on
expiry, and an explicit max-output-tokens cap sized to the parser's own
existing bounds (≤50 risks, ≤10,000 questions) — don't rely on SDK/provider
defaults.

Self-hosted models may have much smaller context windows than SaaS frontier
models. If assembled context (all questionnaire answers plus risk
types/controls, or the free-text business fields) exceeds the configured
model's window, fail the call loudly with a clear error rather than
silently trimming — dropping unknown risk-relevant content to fit a budget
risks a confidently-wrong output, which is worse than an honest failure.
Context sizing per deployment is documented as an operator responsibility,
not mitigated in app code.

### D-11 — Job registry and restart behavior are unchanged; no new durability, no instance-wide concurrency cap

The in-memory, TTL-bounded job registry (`assessment-draft-registry.ts`,
`questionnaire-generation-registry.ts`) is unchanged by this phase — no
durable job queue. A restart mid-job means the job record is simply gone (a
plain in-memory `Map`, wiped on restart); a subsequent poll for that
`jobId` returns `404 Not Found`, matching what
`phase-04-deterministic-draft-jobs.md` already documents. No new "orphaned
job → failed" logic is added — the existing single-flight re-entry rule
(re-click Generate → no active job, no committed record → a fresh job
queues cleanly) already gives a working recovery path.

Nothing bounds how many different questionnaires'/requests' jobs can be
`running` simultaneously instance-wide (only per-record single-flight is
enforced today). No instance-wide concurrency cap is added for this phase;
rely on `PROVIDER_RATE_LIMITED` (D-09) and analyst-initiated retry — this is
a small-headcount internal tool, and a semaphore/queue is real complexity
for a problem not yet observed in practice.

### D-12 — Development verification target (operator decision, 2026-09-15)

Live development verification uses a local OpenAI-compatible runtime only:
Ollama at `http://127.0.0.1:11434/v1`, model `qwen3.5:9b`, blank API key, for
both operation triples. Request and questionnaire content never leaves the
machine; no external SaaS endpoint is approved for development. The non-secret
`CSRM_AI_*` values live in the gitignored `apps/strapi/.env`, and must not be
set to `openai-compatible` while an E2E run is in progress, because the isolated
harness reads that file. Automated suites remain hermetic (D-04).

### D-13 — Optional reasoning control for thinking models (found in pre-execution probe, 2026-09-15)

A probe of the D-12 target showed that `qwen3.5:9b` is a reasoning model: with
default settings it spent its whole output budget in a separate `reasoning`
field, returned empty `content`, and took 62 seconds for a one-line answer.
With `reasoning_effort: "none"` it returned schema-valid JSON in about 5 seconds.

Add one optional, vendor-neutral setting, `CSRM_AI_REASONING_EFFORT` (config key
`reasoningEffort`, default empty). When empty, the request carries no
`reasoning_effort` field at all, so endpoints that do not recognise it are
unaffected; when set, its value is passed through verbatim. Empty `content` with
a populated `reasoning` field is still `PROVIDER_OUTPUT_INVALID` — reasoning text
is never parsed as the proposal. The development `.env` sets it to `none` and
raises `CSRM_AI_REQUEST_TIMEOUT_MS` for local hardware; the code defaults are
unchanged.

### D-14 — Questionnaire generation uses a model-friendly wire shape mapped server-side (found in live verification, 2026-09-15)

Live verification against the D-12 target showed the plan 01 request schema could
never produce a valid questionnaire from a real model: it described each question's
`options` only as `{type: "object"}`, so the model invented its own shape
(`answerType: "single-choice"`, `options: { options: [...] }`) and every generation
failed the definition parser with `PROVIDER_OUTPUT_INVALID`. The question content
itself was specific and useful; only the structure was wrong. The unit tests had not
caught this because their endpoint double returned hand-written definitions.

The model now returns a simpler shape in which every field is required, so the
schema stays valid under `strict: true` for any compatible endpoint: per question
`questionText`, `answerType` restricted to Text, Long text, Boolean, Single select,
Multi select and Date, `sectionTitle`, `required`, and `choices` as a string array
that is empty unless the answer type is a select. The adapter deterministically
builds the stored definition from it: server-assigned `questionKey` values, section
keys and orders by first appearance, per-section question order, and `{value, label}`
choices only for select types. File upload is excluded because no upload contract
exists and a required upload question would block completion; conditional
visibility is not generated. The unchanged closed parser still validates the built
definition and remains the unconditional gate (D-07): a select with no choices or
with duplicate choices is rejected, never repaired.

</decisions>

<constraints>
## Constraints

- Provider substitution happens entirely behind the existing
  `AssessmentDraftProvider` and `QuestionnaireGenerationProvider`
  interfaces. No UI or job-lifecycle rework — routes, polling shape, and job
  states from Phase 4/06.2 are unchanged.
- Deterministic providers remain selectable and are the test/offline
  default (D-04); automated journeys must stay hermetic.
- No secrets in client code. All provider config (keys, `baseURL`s, models)
  lives server-side in Strapi config (D-05), never shipped to `apps/web`.
- AI output is never auto-released: assessment release remains an explicit
  analyst-only action; generated questionnaires remain drafts until the
  Requestor submits them. Unchanged by this phase.
- Any new durable field (D-06) is justified by a `docs/contract-gaps/`
  record before the schema change, per the project's established
  convention (Phases 06.1, 06.2, 06.3 all did this).
- Minimal dependency footprint: exactly one new backend dependency
  (`openai`, D-02), consistent with `apps/strapi`'s existing near-zero
  dependency posture.
- `UI hint: no` per ROADMAP.md — this phase is not expected to touch
  `apps/web` beyond whatever the existing job-status projection already
  surfaces (provider name/version becoming visible where provenance is
  already displayed, if anywhere, is incidental, not a new UI surface).

</constraints>

<acceptance>
## Acceptance Criteria

The roadmap's four success criteria for Phase 06.7 are the acceptance
criteria and are not restated here. In addition:

- `CSRM_AI_PROVIDER` unset (or any value other than `openai-compatible`)
  behaves identically to `deterministic` — proven by a test, not just by
  code inspection.
- Test/CI runs never reach a live network call regardless of local `.env`
  contents (D-04) — proven by test setup explicitly forcing the
  deterministic provider.
- The new `docs/contract-gaps/phase-06.7-*.md` record exists and explicitly
  states it supersedes the Phase 8 deferral in the Phase 4 and 06.2
  contract-gap docs (D-06).
- A missing required AI config field (when `CSRM_AI_PROVIDER=openai-compatible`)
  fails Strapi boot with a clear error, not a runtime surprise on first
  Generate click (D-05).
- Each of the four `PROVIDER_*` failure codes (D-09) is reachable by a test
  (mocked provider responses), and the analyst-facing message stays generic
  in all four cases.

</acceptance>
