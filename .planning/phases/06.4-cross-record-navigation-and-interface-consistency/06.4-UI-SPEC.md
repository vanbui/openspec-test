# Phase 06.4 — UI Design Contract

This phase preserves the established CSRM visual direction. It changes record-to-record wayfinding, readiness clarity, and the consistent placement of an existing reversal action; it does not introduce a new visual language, colour role, primitive, or overlay treatment.

## Binding Inputs

- Locked decisions D-01 through D-07 in `06.4-CONTEXT.md` govern this contract.
- The Phase 06.4 roadmap scope decisions and five success criteria are the acceptance bar.
- `docs/design/csrm-design-direction.md` remains authoritative: semantic tokens only, 1px structural borders, no in-page shadows, skeletons for content loading, risk/status never colour-only, and the existing overlay shadow only for the confirmation dialog.
- Where the locked context leaves an implementation choice open, this contract chooses the smallest extension of the current patterns. The related-record capability result must distinguish `absent` from `unavailable`; this is necessary to satisfy D-02 without leaking a protected record's identity.

## Interaction and Placement Contract

### Detail-surface focal points

The relationship area remains secondary to the page identity and workflow state. Within that established hierarchy, the authorised assessment relationship tile is the request-detail relationship anchor; in assessment editing, the readiness summary precedes the complete requirement set; and on questionnaire surfaces, the linked assessment-request identifier is subordinate page metadata. These placements clarify the workflow without adding a new emphasis treatment.

### 1. Record-opening links in assessment lists

Applies only to `assessment-list.tsx` (card and table variants) and `released-assessment.tsx`. Remove the trailing row/card-level `Open {assessmentNumber}` control and its empty Actions column. No other list is changed by this phase.

| Context | Contract |
|---------|----------|
| Table | The Assessment identifier is the single record-opening link in the Assessment column. Keep its tabular numerals; use 13px table text at 500 and the semantic link treatment: `text-text-link`, visible 1px underline in the resting state, underline offset 4px, and focus-visible ring. The title/summary remains plain text. The `<tr>` gains `bg-surface-hover` on pointer hover, 80ms standard transition, but never becomes a button or a tab stop. |
| Mobile assessment card | The assessment identifier is the single link, placed in the existing top metadata line before the status. It uses the same always-visible underline/link colour treatment and 44px minimum target height through its containing metadata row. Summary remains plain text. |
| Released-assessment card | The assessment number becomes the single link in the card header metadata line, before the rating. It receives the same resting underline and focus treatment. The summary remains non-interactive. The whole card receives only the existing border/`bg-surface-hover` hover response; it is not a nested link and has no second keyboard target. |
| Keyboard and pointer | Exactly one keyboard target opens each record: the identifier link. Row/card hover is decorative orientation feedback only. Do not add row `onClick`, `role=link`, `tabIndex`, or a click handler; this avoids duplicate navigation and preserves predictable link semantics. |
| Link affordance at rest | Link colour plus a persistent text-decoration are both required; hover may strengthen the underline but must not be the first indication of interactivity. The focus ring remains the global 2px semantic focus treatment and must be visible against the hovered surface. |

### 2. Related records on request and questionnaire detail

Related navigation is capability-checked and record-scoped before it reaches the presentation. A link must never be emitted based solely on an identifier in a broader payload, and the destination remains server-authorised.

| Surface | Existing and authorised | Absent | Exists but actor is not authorised |
|---------|------------------------|--------|-----------------------------------|
| Request detail — questionnaire | In the existing relationship card, show the questionnaire title or questionnaire number as a standard text link, with the same always-visible underline treatment. Supporting copy states its workflow state when present. | Show a neutral, non-link `Alert` in the relationship card: heading `No questionnaire is linked`; body `A questionnaire will appear here when one is created for this request.` Do not render an empty account, a placeholder identifier, or a disabled link. | Do not render a relation row, title, identifier, href, or generic empty-state language. Show the existing request content without this related-record affordance. This state is intentionally visually silent so protected record existence is not disclosed. |
| Request detail — assessment tile | Render the tile only for an authorised assessment. The assessment identifier is the single link and the single keyboard target, exactly as in section 1; the tile surface extends that link's hit area by an overlay rather than becoming a link itself. Wrapping the whole tile in one anchor would absorb all four counts into the link's accessible name and would contradict the rule section 1 sets for every other record surface in this phase. | Do not render an assessment tile. Existing request status/workflow content remains in place; no `0` tile and no empty account is shown. | Do not render the tile, its counts, assessment number, or explanatory access text. This is distinct from absence because no absence message is shown. |
| Questionnaire detail and questionnaire review | Render `Assessment request {requestNumber}` as a standard text link directly below the page header metadata and before reversal/audit content. Use the request number as the link target; title may be supporting plain text if already projected. | Show neutral supporting text: `No assessment request is linked to this questionnaire.` No href, button, disabled treatment, or fabricated identifier. This is an integrity/ordinary-content state, not an account empty state. | Omit the related-request line entirely, including its number/title and any unavailable label, to avoid revealing protected record information. |

The authorised link uses a 44px minimum hit area by applying vertical padding inside its block/row while preserving the text-link visual. It remains the only keyboard target for its relation row. If the typed projection cannot express the three states above without exposing data, treat that as the D-07 response-contract work: carry an explicit safe relationship availability state and register the changed parser in the parity inventory. Do not infer unauthorised from `null`.

### 3. Assessment contextual-Risk tile

| Aspect | Contract |
|--------|----------|
| Placement | In the request-detail relationship column, immediately after/alongside the questionnaire relationship content, under the same `Questionnaire and draft` relationship heading or its successor. It is a linked card/tile only when the assessment is authorised. |
| Heading | Micro-label `CONTEXTUAL RISKS`, followed by the linked assessment identifier/title. Add visible supporting text `Open risk assessment` only when required to make the linked-tile action unambiguous; it is not an additional target. |
| Counts | Show exactly four fixed, ordered measures: Low, Moderate, High, Critical. Reuse the existing `RiskRatingBadge` component (`apps/web/src/components/csrm/risk-rating-badge.tsx`) for each rating rather than introducing a second severity vocabulary: it already carries the per-rating lucide icon, the text label and the semantic risk tokens, and it is already used on the released-assessment surface this phase edits. Pair each badge with a tabular numeric count. `aria-label` states the full category and count, for example `Critical contextual risks: 0`. Colour is reinforcement only; the rating is named in text by the badge. |
| Zero state | Render every rating even when its count is zero. Use the same icon, label, and tabular `0`; do not hide, replace with a dash, or collapse a zero category. This makes a complete all-zero tally legible and comparable. |
| Layout, 375–767px | Tile is full-width. Rating measures form a 2-by-2 grid with 8px gaps; label and count stay together and never truncate. The tile's linked hit area is at least 44px high and its contents wrap rather than horizontally scroll. |
| Layout, 768–1439px | Tile remains full-width in its relationship column. Measures use one four-column row when the available column is at least 560px; otherwise retain the 2-by-2 grid. Never reduce labels to icons alone. |
| At 1440px | Within the existing two-column request layout, retain the compact four-measure row where it fits. Do not stretch the tile into a dashboard KPI strip or add charts. |
| Hover/focus/loading | The tile surface may use the existing card affordance: semantic border strengthening and `translateY(-1px)` at 120ms expo, driven by hover on the surface. Focus is the visible semantic focus ring on the identifier link, and the ring must remain visible against the hovered surface. On a known-layout load, use a skeleton matching the heading and 2-by-2/4-column count grid after the existing 300ms threshold. Do not use a content spinner. |

Counts are server-computed and bounded using the established rating-summary projection shape. Client components render the supplied four-count object; they do not fetch individual Risks or calculate counts locally.

### 4. Complete release-readiness requirement set

The readiness panel always displays the complete, current release requirement set. It is not a list that appears only when requirements are missing and then shrinks as work is completed.

| Aspect | Contract |
|--------|----------|
| Heading and summary | Keep `Release readiness` with supporting text that release is rechecked on request. Place an explicit text summary first: `All release requirements are met` or `{n} of {total} release requirements met`. Use tabular numerals for the counts. |
| Requirement grouping | Render one ordered group for assessment-level requirements and one named group for each contextual Risk. A Risk group heading is its stable Risk number (for example `Risk RSK-001`), never an array index. Requirement labels use the existing domain labels such as `Risk owner`, `Residual rating`, and `At least one mitigation control`. |
| State treatment | Every requirement row starts with an icon and an explicit state word: `Met` with `CheckCircle2`, or `Outstanding` with `AlertCircle`. State text and icon remain present in all themes and at every viewport; semantic success/warning colour is supportive only. Met rows use normal surface/text hierarchy; outstanding rows may use the warning semantic foreground/subtle surface but retain the same border and legible text. |
| Destination | A requirement with a valid edit destination is a text link to its specific assessment/Risk section. An outstanding risk-scoped requirement links to the named Risk's unique anchor, not a shared `#identified-risks` anchor. A met item does not require a link; when it has one, it must follow the same text-link affordance without adding a second button. |
| Missing Risk | The assessment-level `At least one Risk` requirement is shown as `Outstanding` when none exists and links to the Identified Risks section. Once Risks exist, it is shown as `Met`. |
| Specific risk identity | Validator paths may use an index internally, but the client presentation must map each risk-scoped requirement to the current Risk number supplied in the authoritative response/projection. The visible requirement is `Risk RSK-001 — Risk owner — Outstanding`, never `risks[3]` and never only `Risk owner`. |
| Ready state | Do not replace the full set with a single success sentence. Retain all rows marked `Met`, then show the release action in its normal position. |
| Responsive, 375–767px | The panel is a single column. Assessment and Risk groups stack, each row wraps label and status naturally, and the icon stays aligned to the first line. Do not place state in a narrow right-aligned-only column. Long risk numbers/statements break/wrap; no horizontal scrolling. |
| Responsive, 768–1440px | In the existing editor grid, retain the readiness panel as the side panel at `xl` when available; otherwise stack it below assessment details. Within each row, use a two-column layout only when label and state remain readable; state may align to the end but must wrap beneath at narrower widths. Never make the panel exceed the available column or truncate a record name. |
| Live updates | On refresh after a save, replace the complete set atomically and announce the summary through the existing polite live region. Do not use a spinner in place of the requirement set; use a layout-matched skeleton only for initial known-layout loading. |

If the current `releaseReadiness` response only carries missing paths, extend its safe projection to carry the complete requirement state and stable Risk identity. This is a response/projection change, not a data-model change. It must update the published contract, generated declaration, client parser, and D-07 parity inventory together.

### 5. Standard `Return to draft` control and confirmation

Applies to `assessment-detail.tsx`, `questionnaire-detail.tsx`, `questionnaire-review.tsx`, and `request-form.tsx`.

| Aspect | Contract |
|--------|----------|
| Treatment | Use the shared `Button` component with the standard primary/default treatment, label exactly `Return to draft`, and the same `ConfirmDialog` trigger pattern in all four locations. Do not use outline, raw styled `<button>`, a link, or a secondary button variant. Confirmation remains destructive because the workflow reversal is consequential. |
| Position | Place it immediately after the page header/relationship metadata and before audit summary, forms, questionnaire renderer, draft-generation controls, or other workflow actions. It occupies the same first action position on both Questionnaire surfaces and both Request-detail surfaces. Preserve 16px separation below the control before following content. |
| Availability | Show only when the already-authorised reversal state permits it. Do not use a disabled control to explain access or state. |
| Confirmation | Retain the existing 480px confirmation dialog, semantic scrim, border, radius, focus trap, and the single permitted overlay shadow. Title/description and explicit destructive confirmation label stay record-specific (`Return request to draft` / `Return questionnaire to draft`). |
| Reason field | The labelled `Reason` field occupies the full usable content width of the dialog: the form group is `w-full`, and the textarea is `w-full` with no ancestor max-width narrower than the dialog's content box. At 375px it fills the dialog width inside the 16px viewport inset; at desktop it fills the 480px dialog content width. Keep the 500-character counter/help text under the field and existing invalid-state icon/text behaviour. |
| Dialog responsiveness | Dialog width remains `min(480px, calc(100vw - 32px))`; header, reason group, error message, and footer share the same content width. Footer actions wrap/stack if necessary rather than squeezing the reason field. |

| Role | Size | Weight | Line Height | Phase use |

## Implementation Boundaries and Verification

- Keep data access in the existing typed service/action layer. Related-record visibility is decided by the existing capability adapter and server-authorised projection, never by JSX data presence.
- D-07 applies to any changed relationship, rating-summary, or release-readiness projection: update the published contract and generated declaration, register its parser in `contractResponseParsers`/`responseParserModule`, and preserve deliberate-narrowing documentation.
- Do not introduce a datamodel change. If a schema change appears necessary, stop and record the contract gap before implementation.
- Add/extend automated component tests for: persistent record-link affordance and sole tab stop; removed Open controls; authorised/absent/unauthorised relation rendering; each named rating including zero; full met/unmet readiness set with a specific Risk number; shared primary reversal treatment/position; and full-width reason field at narrow and wide viewports.
- Browser verification must check 375px and 1440px for the tile, complete readiness list, and reversal dialog; confirm the dialog remains the only surface using the overlay shadow.

## Review Amendments

Two corrections were applied to this contract after it was drafted, both in the
direction of the consistency this phase exists to deliver:

1. **The contextual-Risk tile is not itself a link.** The draft made the whole
   tile one anchor. Section 1 of this same contract rules that a record surface
   has exactly one keyboard target — the identifier — and that the surrounding
   surface is decorative. A tile-wide anchor would also absorb all four counts
   into the link's accessible name. The identifier is the link; the surface
   extends its hit area.
2. **Rating counts reuse `RiskRatingBadge`.** The draft invented a glyph
   vocabulary (`○ ◆ ▲ ⯃`) for the four ratings. The product already has
   `RiskRatingBadge`, carrying the per-rating lucide icon, the text label and the
   semantic risk tokens, in use on six surfaces including the released-assessment
   screen this phase edits. `⯃` (U+2BC3) is also not reliably rendered. A phase
   about consistency must not introduce a second severity vocabulary.
