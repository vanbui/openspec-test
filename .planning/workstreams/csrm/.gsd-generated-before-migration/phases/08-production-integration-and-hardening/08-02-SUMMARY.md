## Accomplishments

- One server-only predicate, `resolveSessionRuntimeMode(env)`, decides the development session: `next dev` is unchanged, and a production build needs `CSRM_ENVIRONMENT=development`, `CSRM_DEV_IDENTITY=true` and a valid run attestation, with each gate proven to fail closed alone (T-08-R02, R03).
  - **Correction (phase code review, SR-01):** this held only for a production build started with `NODE_ENV=production`. The resolver read the runtime `NODE_ENV` and returned the session whenever it was `development`, so the same build started with `NODE_ENV=development` offered the development sign-in with no attestation and without either variable. The resolver now keys the `next dev` branch on the compiled `NODE_ENV`, and `production-hardening.spec.ts` proves that case refused (`08-REVIEW.md` SR-01).
- The session adapters, the sign-in page and the transport use only that resolver; `parseSessionRuntimeMode` is gone. Outside the attested runtime `current()` resolves no session and `signIn()` redirects to `/sign-in?returnTo=…` instead of throwing, so a production build never surfaces the framework error page from the application layout (T-08-R09); `setDevelopmentRole` still throws and no cookie is minted.
- The sign-in page renders the UI-SPEC §9.1 unavailable card (HTTP 200, no form, no button, own document title) when no session is available; the available card is byte-identical.
- The development role cookie is `Secure` exactly when the first `x-forwarded-proto` value is `https` (D-47); `httpOnly`, `SameSite=Lax`, `path=/` and the eight-hour lifetime are unchanged.
- The web `webServer` builds and starts a production server with `NODE_ENV=production`; the Strapi entry is byte-identical; a `desktop` project carries the device profile. `next.config.ts` points an isolated build at `tsconfig.e2e.json`, so a run no longer appends its dist directory to `tsconfig.json` (the 44 stale `.tmp/` entries are gone); `next-env.d.ts` is untracked and ignored; `typecheck` and `lint` run `next typegen && tsc --noEmit`.
- `expectSettled` replaces the `document.title` poll; every accessibility sweep destination names its exact title and level-one heading, and the shell test asserts the shell, not the URL.
- `production-hardening.spec.ts` proves the attested server offers the development sign-in and that the same build without the attestation shows the unavailable card, redirects `/app`, mints no cookie even for a posted sign-in, passes axe at 375 and 1440, and is killed cleanly (T-08-R19).
- The full suite passed 51/51 on the production build with a clean tree afterwards, and the harness timeouts are set from the measurements.

## Specs fixed for the production build (Task 4)

Both failed in the first full run (49 passed, 2 failed) and were fixed at their source in `1418f80`; neither assertion was loosened.

1. **`analyst-insights.spec.ts` "analyst dashboard shows what needs attention…"** — `allTextContents()` read the High and Critical widget's record links once, 56 ms after `goto('/app/review')` resolved, and saw none; the failure snapshot taken about 130 ms later shows the links. On the production build the streamed widget (React 19.2 batches server-rendered Suspense reveals) appears after the document's `load` event, which `next dev`'s slower load masked. The list is now awaited with `expect(links).not.toHaveCount(0)` before it is read; the `> 0` assertion is the same, retrying.
2. **`requestor-request-workflow.spec.ts` "Requestor completes an authorised assessment request journey"** — after "Save draft" on the edit form, `expect(getByText(editedDescription))` passed in 9 ms while the URL was still `/edit` (the edit form's textarea carries that text), so `Submit request` was clicked on the edit form's own trigger an instant before `router.push` replaced the page with the request detail; the dialog it opened unmounted with the form. The journey now waits for the detail route and its `Request actions` region and clicks inside that region.

The other one-shot collection reads in the suite (`.all()`, `.count()`, `allTextContents()`) each follow a retrying assertion on the same revealed content and passed in both full runs; they were left alone.

## Decisions Made

- **`expect.timeout` kept at 15 s** (D-46 allows lowering, and the plan's rule was to keep 15 s unless the slowest assertion allows 10 s with margin). The slowest measured assertion is 5.1 s and the slowest server-bound one 3.0 s, so 10 s would hold a two-fold margin; but the conformance spec still spawns an ordinary `next dev` server that compiles routes on demand, and a flake there costs a twelve-minute gate re-run for a fifteen-second faster failure. Recorded in the config comment.
- **Web `webServer` timeout 300 s**: the plan's formula (twice the measured 34 s, rounded up to the minute, never below 300 s) lands on the floor.
- **Explicit environment objects in the predicate tests**: both predicates take `env`, so the tests build the environment they hand in (real attestation files under `tmpdir()/csrm-playwright-e2e`, removed in `afterEach`) instead of writing `process.env`; the adapter, page and transport tests, whose subjects read `process.env`, use `vi.stubEnv` and `vi.unstubAllEnvs`.
- **A standalone `next build` pre-check** (33 s, under a hand-made attestation) ran before the first full run to confirm the build path leaves the tree clean, that `/sign-in` builds as a dynamic route, and that the Google Fonts fetch works through this host's proxy.
- **Targeted runs use `pnpm --filter @csrm/web exec vitest run <pattern>`**: the plan's `pnpm … test -- <pattern>` form forwards the `--` and runs the whole suite.
- **The Requestor request detail's document title** is the root default `IdamBox CSRM` because the route declares no metadata; the sweep asserts what the page renders and the gap is in `deferred-items.md` for plan 08-12.
- **INT-04 is not marked complete** in REQUIREMENTS.md, matching 08-01.
