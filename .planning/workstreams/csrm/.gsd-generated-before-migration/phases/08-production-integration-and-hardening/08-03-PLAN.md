## Recorded planning decisions

- **The inventory is an integration test against the mounted Strapi, not a source-parsing unit test** (planner's discretion within D-04; the research sketched a node:test unit inventory). Reason: the core routers resolve their routes only when Strapi loads (`createCoreRouter` returns a lazy `routes` getter that reads the content type from the running instance, and `csrm-assessment-request` wraps it), and the D-38 collision and the D-37 plugin routes are visible only in the mounted registries. The harness already boots one Strapi per test file; the extra file costs about a minute. The web side stays static and fast because it reads the checked-in JSON.
- **Sources of truth inside the running instance:** `strapi.apis[<name>].routes[<router>].routes` (method, path, handler, config.auth, config.policies for every application router), `strapi.plugins[<name>].routes['content-api'].routes` (plugin routes, recorded with plugin name only) and `strapi.server.api('content-api').listRoutes()` (the koa layers proving each path+method is mounted once and, for `/api/roles`, which layer is first). The harness gains `listMountedContentApiRoutes()` and `readUsersPermissionsAdvancedSettings()` to expose them without exposing the instance.
- **Write mode is an environment flag on the same test**: `SERVED_OPERATIONS_WRITE=1` makes the test overwrite `docs/references/served-operations.json` instead of asserting equality; the `served-operations:write` package script documents the invocation. Drift fails with `SERVED_OPERATIONS_DRIFT: run SERVED_OPERATIONS_WRITE=1 pnpm --filter @csrm/strapi served-operations:write`.
- **Task order captures the collision:** Task 1 writes the inventory on the current tree (with the `api::role.role` and users-permissions layers both present on `GET /api/roles` and the observed responder), commits it, then Task 2 changes the routers and regenerates, so the two commits are the D-38 before/after record.
- **File count accepted under D-49 (plan check, 2026-09-25):** the plan lists 22 files, above the 15-file guideline, because its edits are mechanical multi-site changes of one kind (seven routers set to `only: []`, the two catalogue copies, and the inventory's readers on both sides) and the executor runs with a large context; it is not split, and one owner per file per wave still holds.
