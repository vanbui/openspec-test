# Phase 06.4 Plan 02: Relationship availability and Risk tally Summary

Related records are now decided on the server and projected as bounded,
identity-safe summaries.

## Accomplishments

- A request carries its questionnaire and its assessment as three-state
  summaries. The request controller's `findOne` attaches them from a separate
  bounded read, leaving the core handler's own behaviour untouched.
- The assessment summary carries `Low`, `Moderate`, `High`, `Critical` and
  `total`, following the established rating-summary shape, counted from the
  assessment's own contextual Risks on the server.
- A questionnaire carries its assessment request the same way. It previously
  projected an object of `undefined` fields when no request was linked, which
  gave the browser no way to tell an absent relation from a protected one.

## Decisions worth carrying forward

**Residual rather than inherent rating.** The roadmap asks for "contextual Risk
counts at each rating", but the product shows inherent and residual side by side
in the Risk Register, so an unqualified count would be ambiguous. Residual is
what remains after the assessment's controls and so is the figure a reader of a
finished assessment is deciding on. The field is named `residualRiskCounts` so
the interface states which rating it counts.

**An in-review assessment is unavailable to its own Requestor.** This follows
the design contract, under which an unavailable relation renders nothing. It
does mean a Requestor sees no indication that their assessment is underway;
that is worth a look on the built screen before it is settled.

`unavailable` is modelled but not currently produced for the questionnaire's
request relation: anyone authorised to read a questionnaire is authorised to
read its request. It is declared so the contract can express it without a later
shape change.
