# Phase 06.4 Plan 09: Relationship navigation browser coverage Summary

The existing analyst workflow now verifies both currently published, authorised
related-record routes at 375px and 1440px without claiming coverage for the
blocked request relationship and release-readiness projections.

## Accomplishments

- Added an encoded document-ID path assertion for the existing review
  questionnaire link and the completed assessment link.
- At 375px and 1440px, the seeded analyst journey verifies each link is visible
  and its page has no horizontal overflow before following the authorised route.
- Each link is followed and checked against its exact actor-specific destination:
  `/app/review/questionnaires/[documentId]` or
  `/app/review/assessments/[documentId]`.

## Non-interactive Decision

Plans 06.4-04 and 06.4-06 are blocked because the published typed response
contracts do not declare their server projections. The current request-detail
interface therefore has neither the three-state relationship surface nor the
contextual-Risk tile required by Task 1. The E2E harness also has no safe
fixture or route for absent and identity-free unavailable relationship states.

No Requestor browser extension was added: its workflow creates and submits a
new request but does not produce a questionnaire or assessment relationship.
Adding test-only data mutation or inferring a relation from a broader payload
would violate the server-authoritative boundary. The existing analyst links
were the only viable related-record browser coverage and were added.

## Resolution

The blocker recorded above was the absent response contract, not missing
fixtures. Once the request relationship and readiness contracts were published
and Plans 06.4-04 and 06.4-06 completed, both states proved reachable from the
existing seed as the owning Requestor:

- `RAR-DEV-QUES-DRAFT-001` has a questionnaire and no assessment, giving the
  absent state.
- `RAR-DEV-QUES-001` has a questionnaire and an assessment still in review, so
  its own Requestor may not open it — the unavailable state, with no fixture
  work needed.
- `RAR-RELEASED-33SAEN` has no questionnaire and a released assessment, giving
  the named absence alongside a populated tally.

`apps/web/e2e/request-relationship-states.spec.ts` covers all three at 375px and
1440px, including that an unavailable assessment leaks no identifier and is
never presented as an absence. Six checks pass.

Records are opened by clicking a title rather than by a hardcoded document id:
the browser harness seeds its own database and Strapi generates fresh document
ids per seed, so only the seeded numbers and titles are stable. An earlier draft
of this coverage failed for exactly that reason.
