## Phase Goal

**As a** Security Analyst, **I want** an assessment's risks in a table I can edit, copy and paste like Excel or a SharePoint list, **so that** reviewing and updating many risks takes minutes rather than a long scroll.

This plan's slice: one save. Every unsaved change of the table, and later every imported row, reaches Strapi in one call that applies all or nothing, refuses stale cells per cell, honours the round locks and is recorded as one act.

## Recorded planning decisions

- **Operation and route.** `CSRM_RISK_TABLE_OPERATIONS.saveRiskChanges = "POST:/api/v1/risk_assessments/{assessmentId}/risk_changes"` in `csrm-assessment/operations.ts`; router `routes/risk-table.ts` (type `content-api`, no core router) mounting `POST /v1/risk_assessments/:assessmentId/risk_changes` → `api::csrm-assessment.risk-table.saveRiskChanges` with the existing CSRM policy chain (`global::csrm-app-enabled`, `global::csrm-authorization`); controller `controllers/risk-table.ts` with the `safeError(ctx, status, message, reason?, details?)` shape the risk controllers use.
- **Core (`saveRiskChanges(strapi, { assessmentDocumentId, actor, body, source, generateRiskNumber? })`).** `source` is `{ kind: "table" }` (this plan) or `{ kind: "import" }` (18-09); `batchId = crypto.randomUUID()`. Steps, every refusal before any write: (1) `parseRiskChangesBody` with `RISK_WRITABLE_FIELDS` and the control implementation's writable fields; (2) `withMutableAssessmentMutation({ strapi, assessmentDocumentId, analystDocumentId: actor, transition: "accepted-edit", appliesEdit: (r) => r.changed, mutate })`, which applies the guard once; (3) inside `mutate`, one read of every named risk with its assessment and control implementations on the transaction: any risk not of this assessment (or absent) throws 404 `CSRM Risk was not found.` for the whole batch; any withdrawn risk throws 409 `RISK_WITHDRAWN`; (4) creates beyond `MAX_ASSESSMENT_RISKS` minus the assessment's risks throw 409 `ASSESSMENT_RISK_LIMIT`; (5) `compareCellBases` per update and control update; any conflict throws 409 `RISK_CHANGES_CONFLICT` with `conflicts` enriched by `latestFieldChangeAuthors`; (6) `validateWritableRiskFields` per row with its current values, plus owner and approver eligibility, the exception-field rule, unknown relation ids (`RECORD_NOT_FOUND`) and duplicate controls (`CONTROL_ALREADY_ON_RISK`) collected for every cell; any error throws 400 `RISK_CHANGES_INVALID` with `cells`; (7) apply, sequentially (`for … of`, never `Promise.all`): each update through `updateRiskWithinMutation`, each create through `createRiskWithinMutation` (passing `generateRiskNumber`), then each control entry through `createControlImplementationWithinMutation` (status `Planned` unless set) or `updateControlImplementationWithinMutation`, all with `source: { kind: source.kind, batchId }`. Database errors are never caught and continued. Result `RiskChangesResult` `{ batchId, changed, updated: [{ riskId, fields }], created: [{ key, riskId, riskNumber }], controls: [{ riskId, controlImplementationId, controlNumber, created }], overridesCleared: [{ riskId, stage, reason }], risks: AnalystRiskDetail[] }` (the touched risks as the analyst projection projects them).
- **History.** `RISK_HISTORY_SOURCES` gains `table` and `import`; `HistorySource` gains `{ kind: "table"; batchId }` and `{ kind: "import"; batchId }`, passed through to `recordRiskHistory`'s `sourceKind` and `batchId` by the risk and control implementation inner functions.
- **Specification.** Path `/v1/risk_assessments/{assessmentId}/risk_changes` (`post`, operationId `risk-table/save-risk-changes`): request `RiskChangesRequest` (the 18-01 body, `additionalProperties: false`, bounds as `maxItems`), 200 `RiskChangesResponse` (`{ data: RiskChangesResult }`), 400 `RiskChangesInvalidErrorResponse` or `AssessmentWorkflowErrorResponse`, 401, 403, 404, 409 `RiskChangesConflictErrorResponse` or `AssessmentWorkflowErrorResponse`, 413.
- **Catalogue and grants.** Function `function.risk_table.changes_api` (API-only, `Save Risk Table Changes`, `role.security_analyst` only) with FunctionApi `.api.01` `POST /api/v1/risk_assessments/{assessmentId}/risk_changes`; one design note `Phase 18: the risk table's Functions are API-only and human-only (D-25).` in the docs copy, then copied byte-identically. The literal joins `HUMAN_ANALYST_ONLY_OPERATIONS` in `csrm-authorization.ts` and its matrix mirror. Matrix row for `POST:/api/v1/risk_assessments/{assessmentId}/risk_changes`: `analyst` allow (record rule: the analyst's assessment scope), `secondAnalyst` allow, `owner` (Jane) 403, `otherRequestor` (Maya) 403, `riskOwner` 403, `serviceAnalystAgent` 403, anonymous 401, with an empty body variant proving the grant check runs before parsing.
