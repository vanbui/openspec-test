## Phase Goal

**As a** risk owner, **I want to** contest anything in an assessment I am asked to accept and see each point answered, and as a Security Analyst I want to rework the whole assessment and resubmit it, **so that** acceptance rests on content both lines have challenged and agreed.

This plan's slice: the whole life of a contest point in the API: a participant raises it, everyone taking part reads and replies, a Security Analyst answers it, and its raiser resolves or withdraws it, with every refusal of D-19.

<objective>
Serve the eight point operations (D-02 items 1 to 5): raise (D-04, D-06), list and read one with its thread and comparison (D-05, D-14, D-16), reply (D-07), answer (D-08), resolve, withdraw and undo (D-09), with targets that leave the assessment (D-10) and every separation-of-duties refusal (D-19). Publish, grant and prove them (D-20, D-22). Contest writes use the serialisation queue and row lock alone (16-04's `withAssessmentLock`), never the mutable-assessment wrapper, because an answer is not a content edit (orchestrator constraint; D-08).

Purpose: COLLAB-04 criteria 1 to 3 and 5, ASSESS-26 criterion 2's answers and criterion 5's refusals, SC1, SC2 and SC5 in the API.
Output: one service, one controller, one route file, three Functions, eight matrix rows and the integration and static tests.

Edits Strapi source? Yes. Changes the specification? Yes. Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Module layout.** `apps/backend/src/api/csrm-contest-point/` gains `operations.ts` (`CSRM_CONTEST_OPERATIONS` with `raise`, `list`, `findOne`, `reply`, `answer`, `resolve`, `withdraw`, `undo`, the literals of 17.2-01), `routes/contest-points.ts` (a custom `content-api` route file in `apps/backend/src/api/csrm-assessment/routes/csrm-assessment.ts`'s form with `policies(operation, …)` and handlers `api::csrm-contest-point.contest-point.<action>`; never `createCoreRouter`), `controllers/contest-point.ts` (handlers `raise`, `list`, `findOne`, `reply`, `answer`, `resolve`, `withdraw`, `undo`; closed body and query parsers refusing unknown keys with 400), and `services/contest-points.ts`.
- **Viewer resolution** (`loadContestViewer`, inside the service). The service identity is refused by the policy (`SERVICE_IDENTITY_REFUSED_OPERATIONS`, `HUMAN_ANALYST_ONLY_OPERATIONS`) before the controller. A human Security Analyst reads through the analyst read; anyone else through 17-07's `findReadableAssessment` (404 when unreadable, so a former participant is 404); parts from `participationOf` plus `security-analyst` for a human analyst. The request's requestor who is an analyst acts in the `requestor` part (19.1 D-08). The facts feed 17.2-02's decision functions; the service never re-implements a rule.
- **Writes** (each in `withAssessmentLock(strapi, assessmentDocumentId, async ({ assessment, trx }) => …)`, never `withMutableAssessmentMutation`, never nested): load the open acceptance round with `loadOpenAcceptanceRound` in `trx`; load the point and its entries in `trx`; call the decision function; on refusal throw `ContestPointError(status, reason, details?)` so persistence stays deep-equal; on success append the entry with `sequence = last + 1` and `postedAt` from the transaction's clock, then write the point's `status` from `deriveContestPointStatus` through one function `writeCachedContestStatus` (the only point update in the code base).
- **Raise.** Body `{ roundNumber, target, reason, followsUpPointNumber? }`; `parseContestTarget` (400), `parseContestText(reason, 2_000)` (400); the raiser's participant projection built in `trx` through 17-07's projector over the locked assessment; `cutContestSnapshot` (`not-readable` → 404, `no-executive-approver` → 400); a `followsUpPointNumber` must name a point of the same assessment (404 otherwise); `number` is `max + 1` over the assessment's points under the lock; `raiserParts` from the viewer's parts; `status` `open`. 201 `{ data: ContestPointDetail }`.
- **Reads.** `GET …/contest_points` query: `status` (`open`, `answered`, `closed`, `all`; default `all`), `round` (integer ≥ 1), `riskId`, `target` (a `contestTargetKey`), `mine` (`true`), `page` (≥ 1), `pageSize` (1–100, default 25); order open, answered, then closed, each by number. Points are listed by assessment and resolved from their snapshot ids, never filtered through the control-implementation relation (research Pitfall 3). Response `{ data: ContestPointSummary[], meta: { pagination, counts: { open, answered, closed } } }`. `GET …/contest_points/{pointNumber}` query `entriesBefore` (sequence) and `entriesPageSize` (1–50, default 20): `{ data: ContestPointDetail }`.
  - `ContestPointSummary`: `number`, `status`, `target` (`{ kind, field, key, label, riskId, riskNumber, controlImplementationId, controlName }` from the snapshot), `leftAssessment`, `reason`, `raisedBy` (`{ name }`), `raiserParts`, `roundNumber`, `raisedAt`, `latestAnswer` (`{ outcome, byName, at }` or null), `replyCount`, `followsUpNumber`.
  - `ContestPointDetail`: the summary plus `snapshot` (fields and control implementations with typed values), `comparison` (`SnapshotComparison` from `compareSnapshot` against the participant-visible content now, built with 17-07's projector for every viewer; null when `leftAssessment` or when the target is masked as being prepared), `thread` (`{ entries: ContestEntryView[], earlierCount }`; `ContestEntryView`: `sequence`, `kind`, `authorName`, `authorParts`, `body`, `answerOutcome`, `viaUndo`, `postedAt`, `replacedAt` on an answer a later answer supersedes), and `viewerActs` (`reply`, `answer` with its offered `outcomes`, `resolve`, `withdraw`, `undo` with `until`, each `{ allowed, reason? }` from the decision functions).
  - `leftAssessment` is `(targetKind === "control-implementation" && controlImplementation === null) || the risk is withdrawn`, derived at read time; a withdrawn risk's reason, actor and time are never projected to anyone through this read.
- **Reply** `{ body, expectedSequence }` → 201 `{ data: ContestEntryView }`. **Answer** `{ outcome: "changed" | "kept", body, expectedSequence }` → 201; the viewer facts add `isRequestorOfRequest`, `isRiskOwnerOnAssessment`, `isExecutiveApproverOnAssessment` from the assessment's active risks; no risk history row, no review fact and no assessment status is written (D-08). **Resolve** and **withdraw** `{ expectedSequence, viaUndo? }` (`viaUndo` only on withdraw with `expectedSequence` 0, the raise's Undo) → 200 `{ data: ContestPointDetail }`. **Undo** `{ expectedSequence }` → 200.
- **Functions and sets** per 17.2-01: `function.contest_points.read_api` (`.api.01` list, `.api.02` read, `.api.03` reply; `.api.04` history is added by 17.2-08), `function.contest_points.raise_api` (`.api.01` raise, `.api.02` resolve, `.api.03` withdraw, `.api.04` undo; `.api.05` send back is added by 17.2-05), `function.contest_points.answer_api` (`.api.01`). Each read and raise literal joins `SERVICE_IDENTITY_REFUSED_OPERATIONS`; the answer literal joins `HUMAN_ANALYST_ONLY_OPERATIONS` and the matrix mirror. The design note names the three Functions and the absence of core routes.
- **Matrix** (`authorization-matrix.ts`). One row per route stating all seven callers; the `riskOwner` caller's fixture gains an open acceptance round (17.1 D-68's fixture) and a point it raised, so its read, reply, resolve and withdraw rows have a subject; a participant answering is refused by grant.
- **Static test** (`contest-points-static.unit.test.ts`): scan `apps/backend/src` and assert the only `.update(` on `api::csrm-contest-point.csrm-contest-point` is inside `writeCachedContestStatus` and sets only `status`; no `.update(` or `.delete(` on `api::csrm-contest-point.csrm-contest-entry`; no `.delete(` on a point; no `createCoreRouter`, `createCoreController` or `createCoreService` in the folder.
