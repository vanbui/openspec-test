## Remediation and re-verification (2026-09-03)

All three failed gaps and all five unverified behaviours above are now closed.
Every result below was produced by running the suites and driving the browser,
not by inspection.

### Gaps closed

| Gap | Resolution |
|---|---|
| Questionnaire reads omitted the audit facts | `projectQuestionnaire` now returns `revertReason`, `revertedAt`, and a bounded `revertedBy` of `{documentId, displayName}`. The same defect existed for requests and was not reported: `getRequest` populated only the two inventory relations, so the request screen could never show the facts either. Both reads now populate `revertedBy`, and the contract documents it. |
| Reversal reason declared in three web modules | Extracted to `apps/web/src/lib/schemas/revert-reason.ts`; the request schema, questionnaire action, and questionnaire service all consume it. |
| OpenAPI did not describe the trimmed contract | The documented request body carries the bounded reason, and the two request paths now document the `revertedBy` populate value and the two scalar audit fields. Generated declarations were regenerated from the contract, not hand-edited. |

### Defects found during browser verification

1. **A stale incremental build, misread as an authorization gap.** The first
   reversal attempts failed, and this record originally claimed the routes were
   missing from the development permission allowlist. That was wrong twice over:
   the failing status was 405, not 403, and that list names legacy public
   permissions to delete on boot rather than routes to grant. The real cause was
   a corrupted incremental Strapi build, whose dist clean had reported ENOTEMPTY;
   a clean rebuild resolved it. The incorrect permission edit has been reverted.
2. **The questionnaire renderer kept its read-only view after a reversal.** It
   seeded `submitted` from a prop with `useState`, which does not re-seed while
   the component stays mounted, so a reverted questionnaire rendered the
   submitted panel under a header that already read In progress. It now re-seeds
   when the server-owned mode changes.

### Test corrections

Three existing assertions were invalidated by the new grant and were corrected
rather than worked around: the catalogue parity test assumed every request
operation maps to the core or delete function; the harness read helpers did not
populate `revertedBy`; and one questionnaire denial case was labelled as a
non-owner when that identity owns the fixture, so its valid reason is refused
for state rather than ownership. Each denial case now asserts its exact expected
status so a refusal from the wrong guard fails the test.

### Further defects found by driving the analyst path

3. **The analyst reversal was unreachable.** The analyst request route passed an
   empty state whenever the request had no linked questionnaire, which suppressed
   the request context and the reversal action. A submitted request without a
   questionnaire is the only state a reversal is allowed from, so the action was
   hidden in exactly the case it exists for.
4. **A successful reversal was reported as a failure.** The response omitted the
   reverting identity because the update did not populate the relation, so the
   typed boundary rejected a 200 and told the person the reversal had failed
   while the record had already changed. An integration assertion now covers the
   response body, not only the persisted row.
5. **Automation could reopen submitted questionnaires.** Questionnaire reversal
   was granted through the shared questionnaire-details Functions, which the
   service analyst agent also holds. It now has its own API-only Function granted
   to the owning Requestor and human Security Analyst, matching request reversal.

That is fixture behaviour, not a reversal defect.

### End-to-end verification

The browser suite had never run on this machine: no Playwright browsers were
installed, so every spec failed instantly on `browserType.launch`. With the
pinned Chromium installed, the full suite is green — **16 of 16 passing**,
including the axe accessibility check, the six responsive breakpoints from 375px
to 1440px, assessment release, the Risk Register, and both reversal journeys.

Getting there exposed a further defect that neither the unit suites nor manual
browser checks had caught.

6. **Submitting from the edit screen stranded the person on a denial page.**
   Submitting is only offered from the edit route, and a submitted request may no
   longer be edited, so the action's own revalidation replaced the success state
   with that route's permission-denied screen. Whoever had just submitted was
   told they lack access. Submitting now navigates to the request itself.

   This path predates Phase 06.1 and was unreachable in a normal journey, since
   the only way in was to hold a draft and submit from the edit form rather than
   the detail page. Returning a request to draft creates the obvious route into
   it, which is how it surfaced.

Two failures were test mechanics rather than product faults, and both were
introduced by this phase's own work: the shared audit component changed the copy
the specs asserted, and the new reversal steps clicked client islands before
they had hydrated. Both are now deterministic rather than incidental.

The suite also surfaced a product gap worth keeping: the toast stack had no
close control, and hovering a toast pauses its dismiss timer, so a toast could
sit over a page's primary action indefinitely. The design direction already
requires warning and danger toasts to persist until dismissed, which is only
coherent with a dismiss affordance, so one was added.
