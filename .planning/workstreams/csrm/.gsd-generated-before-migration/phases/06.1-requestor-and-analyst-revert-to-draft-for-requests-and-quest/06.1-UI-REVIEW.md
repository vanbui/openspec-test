## Top 3 Priority Fixes

1. **Analyst revert paths give no success confirmation** — a Security Analyst who reverts a request or questionnaire sees the dialog simply close and the page re-render; there is no toast, no inline confirmation banner, nothing but the (easy to miss) appearance of the "Last returned to draft" panel. A failed silent no-op and a successful revert look identical for a beat. Fix: add `toast.success('Request returned to draft.')` / `toast.success('Questionnaire returned to draft.')` in `AnalystRequestRevert` (`apps/web/src/features/assessments/assessment-detail.tsx:92`), `QuestionnaireRevertControl` (`apps/web/src/features/questionnaires/questionnaire-detail.tsx:64`), and `AnalystQuestionnaireRevert` (`apps/web/src/features/questionnaires/questionnaire-review.tsx:91`), matching the pattern already used for the requestor path at `apps/web/src/features/requests/request-form.tsx:272`.

2. **Destructive-red button on a non-destructive, data-preserving action** — all four revert confirmations (`apps/web/src/features/assessments/assessment-detail.tsx:93`, `apps/web/src/features/questionnaires/questionnaire-detail.tsx:65`, `apps/web/src/features/questionnaires/questionnaire-review.tsx:92`, `apps/web/src/features/requests/request-form.tsx:278`) use `confirmVariant="destructive"`. The shell's own color contract reserves the destructive token for "confirmed destructive actions" (i.e., unrecoverable data loss), and this feature's own summaries stress the opposite — "preserving its values" / values are recoverable, and the record can be resubmitted. Rendering "Return to draft" in the same red as "Delete" or "Discard unsaved changes" teaches users to fear a routine, reversible workflow step and dilutes the signal value of red for genuinely destructive actions elsewhere in the app. Fix: introduce (or reuse) a neutral/warning `confirmVariant` for corrective-but-safe state transitions, or at minimum switch these four calls to `outline`/default with an amber/warning accent, leaving `destructive` for true data loss.

3. **12px `text-xs` used throughout revert-adjacent UI, outside the approved type ramp** — `DetailValue` labels (`apps/web/src/features/assessments/assessment-detail.tsx:53`), the `RevertAuditSummary` field labels (`apps/web/src/components/csrm/revert-audit-summary.tsx:43,56,62`), and the assessment relationship tile caption (`apps/web/src/features/requests/request-form.tsx:308`) all render at `text-xs`, a fifth size against the app's declared four-size/two-weight ramp (14/16/20/28, 400/600). This is a pre-existing pattern reused by this phase rather than a novel regression, but the phase had the opportunity to bring the "Reason / When / By" audit labels onto the approved Label size (14px/600) and didn't. Fix: replace `text-xs font-medium ...` with `text-sm font-semibold` (the Label role) on these audit and metadata labels, or formally add a documented "caption" size to the type ramp if 12px metadata labels are an intentional exception.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

**Strengths:**
- Both dialog descriptions make the consequence of reverting explicit and differentiated per aggregate: "This returns the request to draft and clears its submitted date." (`assessment-detail.tsx:93`, `request-form.tsx:278`) vs. "This returns the submitted answer batch to draft while preserving its values." (`questionnaire-detail.tsx:65`, `questionnaire-review.tsx:92`). This is good practice — it tells the user specifically what state changes and what's retained, rather than a generic "Are you sure?".
- Error fallbacks are plain-language and non-leaking: `'The request could not be reverted.'` / `'The questionnaire could not be reverted.'` (no stack traces, no API details).
- The reversal-reason field enforces a real reason (`revert-reason.ts:14`, `'Enter a reason for reverting this record.'`) rather than accepting an empty justification.

**Gaps:**
- Success feedback text exists in only one of four call sites (`'Request returned to draft.'`, `request-form.tsx:272`). The other three revert flows communicate success via silence + refresh only — see Top Fix #1.
- The `ConfirmDialog` reason field is labeled just "Reason" (`confirm-dialog.tsx:88`) with no field-level context tying it to the specific action ("Reason for returning this request to draft"); the dialog title carries that context but a screen-reader user tabbing directly to the textarea hears only "Reason."
- Confirm button labels ("Return request to draft" / "Return questionnaire to draft") are precise and differ appropriately from the shared trigger label "Return to draft" — good disambiguation between trigger and commit action.

### Pillar 2: Visuals (3/4)

- Each detail screen exposes exactly one revert affordance when eligible — no competing primary actions, consistent with a single focal action per view.
- Requestor and analyst views place the control differently: the requestor's `RequestWorkflowActions` renders "Return to draft" inline with the status badge in a `grid gap-3` (`request-form.tsx:278`), while the analyst's `AnalystRequestRevert` wraps the same button in its own `mb-4` div above the two-column detail grid (`assessment-detail.tsx:68,93`). Functionally fine, but the two actors get visually different weighting for the identical action, which is a minor hierarchy inconsistency worth normalizing if a component is ever extracted.
- Icon usage is compliant: the audit summary's `UndoDotIcon` and the alert `AlertCircle` icons are all `aria-hidden` and always paired with visible text (`revert-audit-summary.tsx:38`, `assessment-detail.tsx:43`) — no icon-only, unlabeled controls introduced by this phase.
- The `RevertAuditSummary` panel gets a comment-documented fix for long, unbroken reversal reasons that could overflow and scroll the page sideways (`revert-audit-summary.tsx:44-52`), showing deliberate attention to a real overflow case rather than an assumed one.

### Pillar 3: Color (2/4)

- No hardcoded hex/rgb values found in the audited feature files — tokens are consumed correctly at the class level.
- However, all four revert confirmations set `confirmVariant="destructive"` (see file:line list under Top Fix #2). The shell's color contract explicitly scopes the destructive token to "Confirmed destructive actions, destructive alert icon, and field-error indicator only," and defines the reusable `ConfirmDialog` destructive pattern for `Delete {record}` semantics — an unrecoverable action. Revert-to-draft is the deliberate opposite: it's designed to be corrective and values-preserving, and this phase's own copy says so. This is a repeated (4x), specific, and citable deviation from the declared token usage, and it's a UX signal problem, not just a token-purity nitpick: users learn to associate red with "returns to draft" the same way they associate it with "permanently delete."
- Note: this `destructive`-for-corrective-action pattern also appears elsewhere in the codebase (e.g., `administration-workspace.tsx:454`, `risk-detail-editor.tsx:197`), so this phase is following an established (if arguably wrong) local convention rather than inventing a new one. That context softens but does not remove the finding.

### Pillar 4: Typography (2/4)

- `text-sm` (14px, Label) and `text-base` (16px, Body) usage in the revert UI is on-ramp and correct.
- `text-xs` (12px) appears repeatedly in exactly the components this phase touches or introduced: `DetailValue` (`assessment-detail.tsx:53`), `RevertAuditSummary` field labels (`revert-audit-summary.tsx:43,56,62`), and `AssessmentRelationshipTile` (`request-form.tsx:308`). Per the app-wide type contract, only 14/16/20/28px sizes at 400/600 weight are approved; 12px is a fifth, undeclared size. This phase's new `RevertAuditSummary` component in particular had a clean opportunity to conform and used `text-xs` for all three of its field labels instead of the 14px/600 Label role.

### Pillar 5: Spacing (4/4)

- All spacing classes observed across the audited files (`p-4`, `gap-3`, `gap-4`, `gap-6`, `mb-1`, `mb-4`, `mb-6`, `mt-6`, `space-y-6`) map cleanly onto the declared 4px scale (16/12/16/24/4/16/24/24px).
- No arbitrary bracket spacing values (`[...px]`, `[...rem]`) found in the revert-related files.
- The one deliberate arbitrary-value usage found near this feature is `[overflow-wrap:anywhere]` in `revert-audit-summary.tsx:53,63`, which is a documented, justified layout-integrity fix (preventing sideways page scroll on long, unbroken reversal reasons) rather than an undisciplined spacing value — does not count against this pillar.

### Pillar 6: Experience Design (3/4)

- Loading, error, and permission-denied states are handled for both detail screens (`AssessmentDetailSkeleton` with `role="status"`, `SafeDetailState`/`SafeReviewState` with `role="alert"` on error/permission) — solid coverage carried over from the shell pattern.
- The reason-required confirmation flow in `ConfirmDialog` disables the confirm button while the reason is empty or over 500 chars, defers the invalid-state announcement until the field is touched (documented rationale at `confirm-dialog.tsx:40-46`), shows a live character counter, and disables both buttons while the request is pending — this is a well-built interaction, better than default confirm-dialog patterns.
- Analyst privacy boundary is preserved post-revert: `QuestionnaireReview`'s `awaiting-submission` state explicitly states "Draft answers remain private until the Requestor submits one complete answer batch" (`questionnaire-review.tsx:38`) rather than silently showing nothing, and the reverted questionnaire's audit facts (reason/when/by) remain visible to the analyst even though answer values do not.
- Gaps: (a) the missing success toast on three of four revert paths, covered under Top Fix #1; (b) revert-eligibility logic is computed two different ways for the same underlying rule — the requestor's own view gates on raw relation presence (`status === 'submitted' && !request.questionnaire && !request.assessment`, `request-form.tsx:277`) while the analyst view gates on relationship availability (`request.relationships?.assessment.availability !== 'available'`, `assessment-detail.tsz:68`). Both are documented as intentional in the SUMMARY ("a submitted request without a questionnaire remains ordinary analyst review content because it is the only reversible request case"), but two independently-computed eligibility checks for one business rule is a latent risk that the two actors could disagree about whether revert is available for the same record.
