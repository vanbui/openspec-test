## Recorded planning decisions

- **`treatment-facts.ts`.** `TREATMENT_PROGRESS_VALUES = ["Not Started", "In Progress", "Complete"] as const`. Facts types where every key is required (the module discipline of `treatment-due-state.ts`): `TreatmentApplicabilityFacts = { released: boolean; treatmentAction: string | null; withdrawnAt: string | Date | null }`; `TreatmentTrackingFacts = TreatmentApplicabilityFacts & { closureDate: string | null; treatmentProgress: string | null; treatmentStatus: string | null; treatmentResolveDate: string | null; targetDate: string | null }`. `isTreatmentApplicable(facts)`; `isTreatmentTracked(facts)` (applicable and `closureDate` null); `effectiveTreatmentProgress({ treatmentProgress, treatmentStatus })`; `governingTreatmentDate({ treatmentResolveDate, targetDate })`; `deriveTreatmentStatus(facts, today)`: not applicable → the stored `treatmentStatus` as is; closed → the stored status, or the effective progress when none is stored (D-15 leaves the recorded status); else Complete progress → `Complete`; governing date present and before `today` → `Overdue`; else the effective progress. `today` must pass `isUtcDate`, otherwise a `RangeError`.
- **`risk-people.ts`.** `RISK_PARTS = ["risk-owner", "executive-approver", "treatment-owner", "control-owner"] as const`; `RiskPeopleFacts = { riskOwner: string | null; executiveApprover: string | null; treatmentOwner: string | null; controlOwners: readonly string[] }` (documentIds). `riskPartsOf(viewerDocumentId, people)` returns the held parts in `RISK_PARTS` order. `TREATMENT_ACTS` and `ANALYST_ACTS` are the act vocabularies 20-01 records. `allowedRiskActs({ parts, isHumanAnalyst, state })`, where `state = { released, applicable, tracked, closed, complete, completedByViewerWithinUndo, reviewable, viewerIsReviewer }`, returns the acts D-13's table allows and the state permits: treatment owner and risk owner and any human analyst get `set-progress` (not complete), `add-note`, `complete` (not complete), `undo-completion` (complete and `completedByViewerWithinUndo`), `reopen-treatment` (complete), `add-evidence`, all only while tracked; the risk owner and a human analyst add the three change acts; the reviewer gets `review-decision` when reviewable; analyst acts come from `analystActWithholding`. `analystActWithholding({ raisedRequest, parts })` returns `own-request` when the analyst raised the request, `holds-part` when they hold `risk-owner`, `executive-approver` or `treatment-owner` (control-owner does not withhold; D-13 names three reasons), else null. `decideRiskAct(input)` returns `{ ok: true }` or `{ ok: false, status, reason? }` in the order: cannot read → 404; service identity → 403; a reader with no part who is not a human analyst → 403 `NOT_RISK_PERSON` (for `review-decision`: 403 `DECISION_NOT_PERMITTED`); a part the act table excludes → 403 `TREATMENT_ACT_NOT_PERMITTED`, or `TREATMENT_FIELD_NOT_PERMITTED` for the three change acts by a treatment owner; analyst acts: `OWN_REQUEST` (403) then `ACTOR_IS_RISK_OWNER`, `ACTOR_IS_EXECUTIVE_APPROVER`, `ACTOR_IS_TREATMENT_OWNER` (409, in that order); body invalid → 400 (the caller's reason, for example `TREATMENT_EVIDENCE_REQUIRED`); state → 409 in the order `RISK_NOT_RELEASED`, `TREATMENT_NOT_TRACKED`, `RISK_CLOSED` (analyst `reopen-risk` exempt; `RISK_NOT_CLOSED` for reopen of an open risk), `TREATMENT_COMPLETE`, `TREATMENT_NOT_COMPLETE`, `TREATMENT_CHANGED`. Readability itself is the caller's (20-05's repository); this module only orders the outcomes.
- **`decision-review.ts`.** `DECISION_REVIEW_STATES = ["not-applicable", "not-confirmed", "reviewer-missing", "overdue", "due", "due-soon", "later"] as const`. `decisionReviewDate({ decisionReviewDate, completingActReviewDate, isExempted, exemptionReviewDate, hasDecisionRows })` → `YYYY-MM-DD | null`: the column, else the completing act's date, else for a v1 exception (exempted, no decision rows) the UTC date of `exemptionReviewDate`, else null. `isDecisionReviewApplicable({ released, closureDate, treatmentAction, isExempted, reviewDate })`: released, open, (Accept or exempted) and a date. `decisionReviewers({ residualRating, riskOwner, executiveApprover, eligible })` → `{ required: "risk-owner" | "executive-approver", allowed: string[], missing: boolean }`, where `eligible(documentId)` is the caller's 19.1 `isEligiblePerson` answer; for Low and Moderate the allowed set is the risk owner plus a named eligible approver. `decisionReviewState(facts, today, leadDays)` in the state order above, `due-soon` from `reviewDate − leadDays` to the day before, `due` on the date. `nextDecisionReviewDate(today, residualRating)` adds 17.1's interval in months with `addUtcMonths`. `decisionReviewOpensOn(reviewDate, leadDays)`.
- **`reminder-policy.ts`.** `REMINDER_POLICY = { leadDays: 7, repeatDays: 7, decisionWaitingDays: 7, emailMaxAttempts: 3, emailLeaseMinutes: 15 } as const` with readers `reminderLeadDays()`, `reminderRepeatDays()`, `decisionWaitingThresholdDays()`, `reminderEmailMaxAttempts()`, `reminderEmailLeaseMinutes()`, and the comment that Phase 22 takes over this point (decision 1).
- **`reminder-rules.ts`.** `PERIODIC_REMINDER_KINDS` (`treatment-due-soon`, `treatment-overdue`, `treatment-overdue-escalated`, `decision-waiting`, `decision-review-due`, `assessment-review-due`) and `EVENT_NOTIFICATION_KINDS` (`treatment-assigned`, `decision-review-not-confirmed`). `ReminderCandidate = { kind; recipientDocumentId; part; reminderKey; periodKey; subject: { riskDocumentId?; assessmentDocumentId?; roundDocumentId? }; facts }`. Builders, each taking `today` (or `now` for instants) and the policy: `treatmentCandidates({ riskDocumentId, governingDate, tracked, complete, treatmentOwner, riskOwner, assignedAnalyst })`: `treatment-due-soon` when 0 ≤ days until the date ≤ lead, key `tds:{risk}:{recipient}:{date}`; when overdue by d ≥ 1 days, `treatment-overdue` with `n = floor((d − 1) / 7)`, key `tod:{risk}:{recipient}:{date}:{n}`, and `treatment-overdue-escalated` to the assigned analyst (part `security-analyst`) and the risk owner (`risk-owner`), key `toe:{risk}:{recipient}:{date}`. `decisionWaitingCandidates({ roundDocumentId, assessmentDocumentId, pending: [{ riskDocumentId, recipientDocumentId, part, pendingSince: Date }] }, now)`: per recipient the earliest `pendingSince`, whole days d; from d ≥ 8, `n = floor((d − 8) / 7)`, key `dw:{round}:{recipient}:{n}`. `decisionReviewCandidates({ riskDocumentId, reviewDate, state, reviewer, subjectKind })`: `lead` while due-soon, `due` on the date, `o{n}` with `n = floor(d / 7)` for d ≥ 7 days after it, key `drd:{risk}:{recipient}:{date}:{stage}`; none for `not-confirmed` or `reviewer-missing`. `assessmentReviewCandidates({ assessmentDocumentId, nextReviewDate, assignedAnalyst })`: `lead` within the lead before the date and `due` from the date, key `ard:{assessment}:{recipient}:{date}:{stage}`. `collapseOnePerPerson(candidates)`: one per recipient per subject and run, keeping the treatment reminder over the escalation for a risk owner who owns the treatment, and dropping a null recipient. Keys never exceed 255 characters.
- **`reminder-schedule.ts`.** `REMINDER_SCHEDULE_DEFAULT = "5 0 * * *"`, `REMINDER_TIME_ZONE = "Etc/UTC"`, `REMINDER_JOB_NAME = "csrmReminderRun"`, `readReminderSchedule(env)` → `{ enabled: false } | { enabled: true; rule: string }`, `ReminderScheduleError` naming `CSRM_REMINDER_SCHEDULE`.
- **`email-config.ts`.** `readEmailConfig(env, { appRoot })` → `{ mode: "capture" | "smtp" | "none"; captureDir; from; smtp: { host; port; secure; user?; password? } | null; webOrigin; available: boolean; unavailableReason: "not-configured" | null }`, reusing 14-03's double-key helper. Development defaults: capture at `join(appRoot, ".tmp/mail")`, `from` `CSRM <no-reply@csrm.localhost>`, `webOrigin` `http://localhost:3000`. `EmailConfigError` (naming the variable) for a provider other than `capture` or `smtp`, `capture` outside the double key, `smtp` without host or sender, a port outside 1 to 65,535, a capture directory inside `public/`, or a web origin that is not an origin (or not `https:` outside development). `emailPluginConfig(config)` → `{ provider: "nodemailer", providerOptions, settings: { defaultFrom } }` with research §R4 item 2's SMTP options and timeouts, or `{ jsonTransport: true }`.
- **`email-content.ts`.** `ReminderEmailInput = { kind: PeriodicReminderKind; recordNumber: string; date: string; days?: number; stage?: "lead" | "due" | "overdue"; relation?: "risk-owner" | "security-analyst"; link: string }` (closed). `buildReminderEmail(input)` → `{ subject, text }` with §14's subject and line 1 per kind, the record line, `Open it in CSRM (you’ll be asked to sign in):` and the link on its own line, then the footer verbatim, blank lines between; lines wrapped at 78 characters except the link. `formatEmailDate("2027-03-12")` → `12 Mar 2027`. `reminderLink(webOrigin, path)` joins and encodes.
