This plan's slice: the people who work on a treatment attach the files that show its progress or completion, screened and stored exactly as request attachments are, and nobody else can list, fetch or change them.

## Recorded planning decisions

- **Operations.** `CSRM_TREATMENT_EVIDENCE_OPERATIONS` per 20-01: `list`, `upload`, `download`, `setRemoval`. Routes in `routes/treatment-evidence.ts` (the core router file keeps `only: []`): `GET /v1/risks/:riskId/evidence`, `POST /v1/risks/:riskId/evidence` (multipart, `files` and optional `noteId`), `GET /v1/risks/:riskId/evidence/:evidenceId/content`, `PUT /v1/risks/:riskId/evidence/:evidenceId/removal` (`{ removed: boolean }`).
- **Readers and actors.** List and download: anyone `canReadRisk` with a part, and human analysts (participants without a part: 403 `NOT_RISK_PERSON`). Upload: the `add-evidence` act (treatment owner, risk owner, human analysts) while tracked; a closed risk → 409 `ATTACHMENTS_CLOSED`; before release 409 `RISK_NOT_RELEASED`; accepted 409 `TREATMENT_NOT_TRACKED`. Removal: the uploader or a human analyst; restore: the remover; both refused after closure with `ATTACHMENTS_CLOSED`. `noteId` must name a `progress-noted` history row on this risk, else 400.
- **Pipeline.** Each file goes through Phase 14's content check, allow-list and limits (counted per risk, the active count from `removedAt IS NULL`), storage port, scanner (the development double under the double key), quarantine on a blocked verdict, and the security events with the evidence's ids. `attachment-policy.ts` gains the evidence holder's limit and retention constant (seven years after the risk's `closureDate`, the same configuration point Phase 22 takes over); `rescan-scheduler.ts` rescans pending evidence beside pending attachments; `csrm-multipart-cleanup.ts` covers the evidence upload path if it is path-scoped.
- **Writes.** Upload and removal run inside `withReleasedRiskMutation` with `actorPart`, writing the row and `evidence-added` / `evidence-removed` / `evidence-restored` (`changes.fields: [{ field: "evidence", from, to: { documentId, label: fileName } }]`); `uploaderPart` is the uploader's first part or `security-analyst`.
- **Projection.** `TreatmentEvidence = { id, fileName, fileType, byteSize, uploadedBy: { documentId, displayName }, uploaderPart, uploadedAt, scanStatus, removedAt, removedBy, progressNoteId, canRemove, canRestore }`; list `{ data: TreatmentEvidence[], limits: { maxBytes, maxActive, active } }`. No AI field.
- **Contract.** Spec tag `treatment-evidence`, operationIds `treatment-evidence/list`, `/upload`, `/download`, `/set-removal`, components `TreatmentEvidence`, `TreatmentEvidenceListResponse`, `TreatmentEvidenceUploadResponse`, `TreatmentEvidenceRemovalRequest`; the download in Phase 19's file-response mode of the parity guard (19 D-19); errors reuse Phase 14's reasons and status codes (including its malware status). Catalogue `function.risk_register.treatment_evidence_api`, `.api.01` `List Treatment Evidence`, `.api.02` `Upload Treatment Evidence`, `.api.03` `Download Treatment Evidence`, `.api.04` `Remove or Restore Treatment Evidence`.
