**Known infrastructure facts.**
1. **Shared `dist`.** The orchestrator's dev Strapi (1337) and Next (3000) may run during planning. Everything that compiles Strapi shares `apps/backend/dist` and `apps/backend/.tmp/tests-dist`: the Strapi suite, a single Strapi file, `served-operations:write` and Playwright. All of these wait until the servers are stopped, and after wave 1 the plans run one at a time (D-33: waves 2 to 18 hold one plan each). A task executed while the servers run records those proofs as pending for the plan's end.
2. **SQLite serialises everything.** knex's SQLite pool is one connection, and `forUpdate` compiles to nothing (13-RESEARCH §E). The concurrent pick-up test proves the compare-and-set logic, not PostgreSQL locking. R-08-37 stays open.
3. **No raw knex in the lock.** A Strapi test that hangs for about 60 s and then fails with a pool timeout means a raw `strapi.db.connection` query ran inside `withRequestLock` without `.transacting(trx)`.
4. **Jobs are process-local** (R-08-36). No E2E relies on a job outliving a restart. The second-analyst journey follows a job inside one Strapi process.
5. **No live AI.** Every suite pins the deterministic provider. The marked-notes proofs assert the built context and the run summary, never model output.
6. **Windows vitest** can fail with `EPERM: rename`. Rerun that file alone before treating it as a real failure.
7. **Fixtures.** Each journey creates its own request through the UI or its own seed. The second analyst persona is seeded only behind `IDAMBOX_SEED_CSRM` and the development identity (D-31). The Strapi tests use 10-13's `second-analyst`.
8. **The base changes first.** Phases 10, 11 and 12 execute before Phase 13 and change the files this phase edits (queue, Homes, navigation, context builder, run record, conflict reasons). Re-run the plan check before executing.

## Sampling Rate

- **After every task commit:**
  - run the touched web test files by path;
  - run `typecheck` when types change, and `api:check` after any spec change;
  - run the touched Strapi files by path, dev servers stopped.
- **After every plan wave** (from wave 2 each wave is one plan):
  - run the full web suite, `typecheck`, `lint` and `api:check`;
  - run the full Strapi suite after every plan that edits Strapi: 13-03 to 13-08, 13-12 and 13-14 to 13-17 (13-13 edits no Strapi file). The task that closes each of these plans' Strapi change already runs it (13-03-02, 13-04-03, 13-05-02, 13-06-03, 13-08-02, 13-12-02, 13-14-01, 13-15-01, 13-16-02, 13-17-02); for 13-07, whose tasks run only the seed file, the wave sample runs it once;
  - run each plan's targeted Playwright specs once at its end: 13-07 (`app-shell`), 13-08 (`request-pick-up`), 13-09 (`request-pick-up`, `requestor-request-workflow`, `assessment-navigation-lifecycle`), 13-10 (`request-notes`, `requestor-request-workflow`), 13-11 (`request-notes`), 13-12 (`request-pick-up`, `request-notes`, `review-lists`), 13-13 (`navigation-and-home`, `quick-find`, `request-pick-up`), 13-14 (`analyst-insights`, `request-pick-up`), 13-15 (`requestor-request-workflow`, `review-lists`, `request-relationship-states`, `request-notes`, `request-pick-up`) and 13-18 (`request-notes`, `request-pick-up`, `performance`); each run ends with the clean-tree check. 13-01 to 13-06, 13-16 and 13-17 run no Playwright.

- **Max feedback latency:** 90 seconds for a task-level quick run. The tasks that close a Strapi change run the full Strapi suite (about 10–15 min), and the production-build E2E runs only at plan level.
