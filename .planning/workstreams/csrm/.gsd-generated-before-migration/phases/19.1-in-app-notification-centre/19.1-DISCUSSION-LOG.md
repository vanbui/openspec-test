## 2. The notification entity (decision 18; 17 D-56)

| Option | Description | Selected |
|--------|-------------|----------|
| One row per recipient and event: recipient, part, kind, request (always), questionnaire and assessment (optional), an optional risk relation for later kinds, a versioned identifiers-only facts envelope, the event time and `readAt`; unidirectional relations; no core router | Per-person read state in the row; later kinds need no schema change; no existing type changes | ✓ |
| The same without the risk relation | Phases 17.1 and 20 have risk-scoped kinds; their readability would need JSON extraction or a later schema change, which the ROADMAP rules out | |
| One row per event with a recipients list and a separate read-state table | Two tables and a join for every count (17-DISCUSSION-LOG area 19) | |
| Derived notifications computed on read | No stable read state; every source re-queried per page | |

**Choice:** `[auto] Entity: Q: "What does a notification hold?"` → one row per recipient and event, with a part and an optional risk relation (recommended default).
**Notes:**
- The risk relation follows Phase 12's run record, which carried an optional risk relation ahead of Phases 16 and 17.
- Unidirectional relations mean no attribute is added to the request, questionnaire, assessment or risk types.

## 3. Where notifications are written (17 D-56)

| Option | Description | Selected |
|--------|-------------|----------|
| Explicit calls to one notification service from each workflow, inside the event's own transaction; the event fails if the notification cannot be written | No event without its notification, and no notification without its event; recipients come from the workflow's actor and state | ✓ |
| Strapi lifecycle hooks on the affected types | Fire for seeds, imports and every write path; they know neither the actor nor the workflow's intent | |
| Written after commit, best effort | An event can commit with nobody told | |
| Derived from logs (the assignment log, the governance log) | Phase 13 D-12's wording; slower, and log parsing would drive a user-facing fact, against the 06.8 posture | |

**Choice:** `[auto] Writing: Q: "Where and when is a notification written?"` → explicit service calls in the event's transaction (recommended default).
**Notes:** Every event site in today's code is already one `strapi.db.transaction` with a row lock (questionnaire release, return to review, submit and revert; assessment release). Research confirms that document-service writes join it.
