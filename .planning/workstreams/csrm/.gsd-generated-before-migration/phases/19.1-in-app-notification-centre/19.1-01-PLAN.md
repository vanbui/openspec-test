- **Entity (D-01).** UID `api::csrm-notification.csrm-notification`, collection `csrm_notifications`, singular `csrm-notification`, plural `csrm-notifications`, display name `CSRM Notification`, `draftAndPublish: false`. Attributes: `recipient` (relation manyToOne `api::idambox-user.idambox-user`, unidirectional, set on every row by the service), `recipientPart` (string, required, max 32), `kind` (string, required, max 64), `assessmentRequest` (manyToOne `api::csrm-assessment-request.csrm-assessment-request`, set on every row), `questionnaire` (manyToOne `api::csrm-questionnaire.csrm-questionnaire`, optional), `assessment` (manyToOne `api::csrm-assessment.csrm-assessment`, optional), `risk` (manyToOne `api::csrm-risk.csrm-risk`, optional, unused by this phase's kinds), `facts` (json), `notifiedAt` (datetime, required), `readAt` (datetime, optional). The API folder holds the schema, a standalone router, a controller and services; it has no core router, controller or service factory.
- **Kinds (D-11) and parts (D-08).** Kinds: `request-assigned`, `questionnaire-released`, `questionnaire-submitted`, `assessment-released`, `note-added`. Parts: `requestor`, `security-analyst`. Both are strings in the schema and closed vocabularies in one registry module (`apps/backend/src/api/csrm-notification/notification-kinds.ts`) and in the specification enums; a later phase adds a registry row, an enum value and a web parser value in one plan, never a schema change (D-12). A kind is never removed once used; `assessment-released` serves Phase 17.1's release and close too, its lead clause chosen from the request status at read time (Orchestrator Confirmation).
- **Analyst read operation per kind (D-13; research A3, confirmed by 19.1-02 against each destination page's first call).** `request-assigned` → `CSRM_ASSESSMENT_REQUEST_OPERATIONS.findOne`; `questionnaire-submitted` → `CSRM_QUESTIONNAIRE_OPERATIONS.findOne`; `note-added` → `CSRM_REQUEST_NOTE_OPERATIONS.list` (13-05).
- **Facts envelope v1 (D-09).** `{ schemaVersion: 1, actorDocumentId }` for every kind, plus `noteDocumentId` and `noteSequence` (a positive safe integer) for `note-added`; ids are strings of 1 to 255 characters. Nothing else: no title, name or Requestor text. A closed parser per kind returns null on any deviation, and the read fails safe to the record-level sentence and the record page without an anchor.
- **Operations (D-03).** `GET /api/v1/notifications` (query keys `view` in `all` or `unread`, default `all`; `page`, a whole number from 1, default 1; `pageSize` in 10, 25 or 50, default 25; no other key), answering `{ data: Notification[], meta: { pagination: { page, pageSize, pageCount, total }, unread, asOf } }`; `GET /api/v1/notifications/summary` (no query key), answering `{ data: { unread, asOf } }`; `POST /api/v1/notifications/read` with exactly one closed body form: `{ data: { ids, read } }` (1 to 50 unique notification documentIds, `read` boolean), `{ data: { all: true, asOf } }`, or `{ data: { undo: true, markedAt } }`, answering `{ data: { changed, markedAt, unread, asOf } }` where `markedAt` is the single read time a `Mark all as read` wrote and null for the other forms. `Notification` is `{ documentId, kind, notifiedAt, readAt, sentence, recordNumber, recordTitle, destination }`. Errors: 400 for an unknown key, a recipient-naming key, a value outside a closed set, malformed, duplicate or more than 50 ids, two forms at once, or an `asOf` or `markedAt` later than the server's time; 403 by grant or for the service identity; 404 for the whole call when any id is not the caller's or not readable (D-15). Spec tag `notifications`; operationIds `notifications/list-notifications`, `notifications/get-notification-summary`, `notifications/mark-notifications`; components `NotificationKind`, `Notification`, `NotificationListMeta`, `NotificationListResponse`, `NotificationSummary`, `NotificationSummaryResponse`, `NotificationMarkRequest`, `NotificationMarkResult`, `NotificationMarkResponse`. No new conflict reason.
- **Undo (Orchestrator Confirmation).** `Mark all as read` writes one `readAt` value, returned as `markedAt`; Undo (`{ undo: true, markedAt }`) clears exactly the caller's readable notifications whose `readAt` equals it. This replaces D-03's "returns the ids" for Undo.
- **Reversal on reassignment (Orchestrator Confirmation).** An assignment change that takes a request away from an analyst reads all of that analyst's unread `security-analyst`-part notifications on that request.
- **Catalogue (D-35).** Function `function.notifications.notifications_api` ("Notifications API", API-only, no menuPath), `roleIds` `role.security_analyst` and `role.requestor` (never `role.security_analyst_agent`), FunctionApis `.api.01` `GET:/api/v1/notifications`, `.api.02` `GET:/api/v1/notifications/summary`, `.api.03` `POST:/api/v1/notifications/read`; one design note amending design note 6 for notifications. Not in `HUMAN_ANALYST_ONLY_OPERATIONS`.
- **Policy (D-36).** Route config `requireNotificationScope: true`; the three operations join Phase 19's `SERVICE_IDENTITY_REFUSED_OPERATIONS` (a holder of the Security Analyst Agent role is refused 403 whatever else it holds); the policy sets `csrmAuthorization.notificationRecipientId` (the resolved user's numeric id) and `csrmAuthorization.notificationAnalystKinds` (the kinds whose analyst read operation the caller holds through the human Security Analyst role).
- **Capability (D-37).** `notification:read`, anchored to `GET:/api/v1/notifications` and `GET:/api/v1/notifications/summary`, granted by the development map to every development role.
- **Bounds.** Ids per mark: 1 to 50. Page sizes: 10, 25, 50 (page default 25; the panel reads 10).
- **Plan order (D-41).** 01 records; 02 schema and pure modules; 03 the service and repository; 04 the three operations with the contract chain and the web service; 05 the Phase 13 event hooks; 06 the questionnaire and assessment event hooks; 07 the header room, capability and count; 08 the panel and opening; 09 the count kept exact, Mark all as read and Undo; 10 the page, the journeys and the full gate.
