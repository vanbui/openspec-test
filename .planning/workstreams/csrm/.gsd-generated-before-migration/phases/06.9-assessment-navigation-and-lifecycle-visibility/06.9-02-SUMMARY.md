# Phase 06.9 Plan 02: Shared Assessment Lifecycle and Request Navigation Summary

**Both assessment detail screens now open with a shared, actor-aware link to the originating request and a shared read-only four-step lifecycle stepper. The two Analyst list filters now list their complete status vocabularies with readable labels and the shared focus ring.**

Before this plan, neither assessment detail screen said where the assessment stood or how to reach the request behind it, and the Analyst filters showed a queue-dependent subset of statuses as raw enum text.

- **Lifecycle derivation:** `deriveAssessmentLifecycle` in `assessment-domain.ts` maps the four-value `assessmentStatus` enum to four ordered steps, each completed, current or future.
- **Stepper:** `AssessmentLifecycleStepper` renders that derivation read-only. It names the current state in text ("Current lifecycle state: In review"). Each step shows an icon plus a text label, and the current step is marked with `aria-current="step"`. It has no buttons or handlers.
- **Request link:** `AssessmentRequestLink` wraps `RecordLink`. Its destination comes from the served `actor`: Analysts go to `/app/review/requests/{documentId}` and Requestors to `/app/requests/{documentId}`.
- **Placement:** both callers render the link and then the stepper directly under their page header. Both sit inside the populated branch, so nothing the pages already showed was displaced.

## Accomplishments

- **Domain helpers:** `assessmentLifecycleStepKeys`, `deriveAssessmentLifecycle` and `assessmentRequestHref` are in the domain module; no lifecycle state is calculated in JSX.
- **One shared stepper and link, two callers:** `AssessmentEditor` and `ReleasedAssessmentDetailView` each import the same two components, and nothing else renders them.
- **Actor preserved:** the Requestor read now keeps the served `actor`. `getReleasedAssessment` returns `ReleasedAssessmentDetailForActor`, and `ReleasedAssessmentDetailView` accepts it.
- **Request-review filter (D-1):** lists all seven request statuses with `requestStatusPresentation` labels, independent of the queue.
- **Assessment list filter:** lists all four assessment statuses with `assessmentStatusPresentation` labels.
- **Shared select treatment (D-6):** both selects adopt `nativeSelectClassName`, which carries the `focus-visible` ring they were missing.
- **Tests:** stepper tests cover all four statuses, the ordered labels, icon plus text state and the absence of buttons in a narrow container. Editor and released-view tests assert the actor-correct link destination and the stepper heading. List tests assert the complete labelled vocabularies, queue independence and the focus-ring class.

## Decisions Made

- **Read-only stepper (D-4).** It explains state and is not a second workflow-control surface. Actions stay on their owning surfaces.
- **Destination from the served actor (D-3).** The link never inspects the pathname. Preserving `actor` in the released-detail transform was necessary for this, because the Requestor view previously received no discriminant.
- **Queue and status are orthogonal in the UI (D-1).** A queue choice changes which records return, not which status options the filter lists.

## Known Issue Found at Verification

The goal-backward verification on 2026-09-24 found that the widened filter options are not accepted by the API. The published contract and Strapi were not widened alongside the UI:

- **Request-review filter:** `filters[requestStatus]` accepts only the four reviewable statuses in the three action queues, and only `approved` and `closed` in the Released queue.
- **Assessment list filter:** `status` accepts `draft`, `in-review` and `approved`, but not `closed`.

Choosing one of the newly listed values therefore returns HTTP 400, and the list renders its error state. The unit and browser tests assert the listed labels but never select one, and the service's `as never` casts on these two list calls keep the generated parameter enums out of typecheck. This is recorded as GAP-1 in `06.9-VERIFICATION.md`.
