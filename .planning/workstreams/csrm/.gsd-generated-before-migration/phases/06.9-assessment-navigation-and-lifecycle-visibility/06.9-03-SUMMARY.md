# Phase 06.9 Plan 03: Dual-Actor Browser Proof and Record-Level Denial Summary

**A dedicated two-Requestor fixture and a new Playwright journey prove the phase in the browser: both actors see the shared lifecycle context and reach their actor-correct request page at 375px and 1440px, and a second Requestor who opens the owner's assessment by direct URL gets not-found with no owner fact on the page.**

The development seed had no released assessment owned by a Requestor, so the Requestor detail surface could not be exercised. `seed-assessment-navigation-lifecycle.ts` reconciles a dedicated, idempotent set of records:

- the primary Requestor's approved request `RAR-E2E-NAV-OWNER-001`, with its released assessment `ASM-E2E-NAV-OWNER-001`;
- an under-review request `RAR-E2E-NAV-ANALYST-001`, with the in-review assessment `ASM-E2E-NAV-ANALYST-001`, for the Analyst;
- an unrelated Requestor, Maya, who owns neither.

The seed runs only when `IDAMBOX_SEED_CSRM` is `true` and the development identity flags are set. It refuses to finish if the unrelated Requestor resolves to the owner.

## Accomplishments

- **Analyst journey:** opens `ASM-E2E-NAV-ANALYST-001` from the review list. Asserts:
  - the "Originating assessment request" link to `/app/review/requests/{id}`;
  - "Current lifecycle state: In review", with steps Completed, Current, Future, Future and `aria-current="step"` on the current one;
  - no button inside the stepper;
  - the request context and stepper appearing before the existing assessment content;
  - no overflow at 375px and 1440px;
  - the link is focusable, and following it opens the request page.
- **Requestor journey:** runs the same checks on the released assessment, with "Released" as the current state and a `/app/requests/{id}` destination. It also asserts that the page has no form and no save, add, edit, remove or release button.
- **Denial:** a Secondary Requestor in a separate browser context opens the owner's assessment URL directly. The spec asserts:

- **Accessibility:** a new `accessibility.spec.ts` test axe-scans the Analyst assessment editor and the Requestor released detail at 1440px and 375px.

## Decisions Made

- **Dedicated fixture:** new behaviour gets its own fixture rather than one another spec mutates, following the Phase 06.8 lesson about memoized fixtures causing false passes.
- **Not-found is the correct denial:** a permission notice would confirm to an unrelated Requestor that the assessment exists. Any future spec expecting a permission state on this path is asserting the wrong thing.
- **Shell-based sign-in assertion:** the helper waits for the Dashboard heading and the role in the banner.

## Deviations from Plan

1. **New development identity: Secondary Requestor.** The plan named only the seed and two specs, but a separate authenticated Requestor was required for the direct-URL denial. The identity was added to development sign-in, the role switcher, the session adapter and the development capabilities, with a grant identical to Requestor's. It is reachable only when the session runtime mode is development (`app/sign-in/page.tsx` calls `notFound()` otherwise), and its Strapi seed is gated on `IDAMBOX_SEED_CSRM` and `developmentIdentityEnabled()`.
2. **Harness rewrite committed, then restored.** The session's Playwright runs rewrote `apps/web/next-env.d.ts` to point at a throwaway `.tmp/ordinary-next-29000` build directory, and appended 14 `.tmp/` include entries, from seven harness build directories, to `apps/web/tsconfig.json`. `cd40d1c` carried both changes. `1fa032a` restored them, and the two files at HEAD are identical to their state before the run.

**Impact:** item 1 is necessary for the denial proof and stays development-only. Item 2 left no net change.

## Coverage Notes

- **Five-state coverage relies on existing tests.** The new spec adds populated and denial (not-found) browser coverage. The five states of the two touched list surfaces remain covered by the existing `design-contract.spec.ts` state fixtures at 1440px and 375px. The non-populated states of the two detail surfaces are covered by their component tests. No existing assertion was replaced.
- **Link focus is tested programmatically.** The spec checks it with `locator.focus()` and `toBeFocused()`. That proves the link is focusable, not where it sits in the Tab order.
- **The filter journey never selects a status value.** It asserts the listed labels only, which is why GAP-1 in `06.9-VERIFICATION.md` (listed filter values rejected by the API) was not observed at the gate.

## Issues Encountered

- **A URL assertion is not a sign-in assertion.** `toHaveURL(/\/app$/)` also matches `/sign-in?returnTo=/app`, so a click that never left the sign-in page passed, and the failure surfaced about fifty lines later as a misleading "element not found". The new helper asserts the shell. STATE.md records that two specs' helpers had this defect and that the Phase 06.9 one is fixed.
- **One transient failure in a partial run.** `accessibility.spec.ts:47` (the Phase 06.8 governed questionnaire) failed once in a two-spec partial run, with 76 violations led by a missing `<title>`, which is the signature of a scan starting mid-navigation. It passed in both full-suite runs.
- **Windows flake.** `request-workflow.test.tsx:48` intermittently fails with `EPERM: rename` in vitest's temp cache under concurrent disk load. It passes in isolation and in quiet full runs.
