# Phase 06.9 Plan 01: Originating Request Summary Contract Summary

**`GET /v1/risk_assessments/{assessmentId}` now carries a closed four-field summary of the originating Assessment Request for both actors. The Strapi projection, the published OpenAPI schema, the regenerated client and the strict Zod parser changed in one commit, with no content-type change.**

Before this plan, the assessment detail projection had no link to the request that produced it, so neither detail screen could offer a way back. The `assessmentRequest` oneToOne relation already existed on `CsrmAssessment`, so this plan added a projection and a contract declaration, not a datamodel change.

The detail query now populates that relation. The new `projectAssessmentRequestSummary` projector returns exactly `documentId`, `requestNumber`, `title` and `requestStatus`, and never the requestor, the questionnaire or any other relation field. It runs only after the authorisation decision has succeeded:

- **Requestor:** the owner-scoped released-assessment query, confirmed by `isReleasedAssessmentForOwner`.
- **Analyst:** the `assertAnalystAssessmentScope` check.

A Requestor who asks for another Requestor's assessment still receives 404, and the response body carries none of the other request's facts.

## Accomplishments

- **Projection:** `ASSESSMENT_DETAIL_QUERY` now populates `assessmentRequest`. `projectAssessmentDetail` adds the bounded summary, which both actor projectors inherit: `projectReleasedAssessmentDetail` and `projectAnalystAssessmentDetail`.
- **Contract:** `docs/references/specification.json` declares a reusable closed `AssessmentRequestSummary`, with `requestStatus` as the seven-value enum. `AssessmentDetail`, `AnalystAssessmentDetail` and `RequestorReleasedAssessmentDetail` reference it as a required property, and the web client was regenerated from the spec.
- **Parser:** `assessmentRequestSummarySchema` is a strict Zod object using `z.enum(requestStatuses)`, inserted into the shared detail shape. Both actor detail parsers stay closed.
- **Server coverage:** the owner and the Analyst each receive exactly the four fields. The owner's summary has exactly those keys. The Analyst detail key list includes `assessmentRequest`. A Requestor reading another Requestor's complete released assessment gets 404, and the body contains neither that request's title, number nor document ID.
- **Parser coverage:** an extra field inside the summary fails parsing for the released, Analyst and Requestor detail schemas.

## Decisions Made

- **Served, not inferred (D-2).** The link back to the request comes from a server projection that is made after authorisation. The client never reconstructs it from the route or from other records.
- **`requestStatus` is an enum, not an open string.** An open string would let the client render a confident label from an undefined presentation lookup, the same failure class as the Phase 06.8 questionnaire `state` field.
- **Malformed relation data fails the read.** It uses the existing 400 `AssessmentScopeError` convention of the neighbouring Risk relation check, rather than returning a partial object.

## Deviations from Plan

1. **Two planned files were not needed in this commit.**
   - `controllers/csrm-assessment.ts` needed no change, because both actor variants already spread `projectAssessmentDetail`.
   - `assessment-service.ts` consumed the new field through the regenerated types without change. It changed in plan 02, to carry the served `actor` through the Requestor read.
2. **Two component test fixtures were updated.** `assessment-editor.test.tsx` and `released-assessment.test.tsx` were not in the plan's file list, but the closed detail types now require `assessmentRequest`, so their fixtures had to carry it.
3. **The Strapi fixture builder is not fully independent.** Task 2 asked for a new builder that constructs its own two Requestors, two requests and linked assessments. Instead, `buildAssessmentDetailAccessFixture` wraps the memoized `seedAssessmentWorkflowFixtures()` and snapshots copies of the two requests. The denial proof itself is sound, and the phase's browser fixture (plan 03) is genuinely dedicated. This is recorded as a follow-up in `.planning/STATE.md`.
4. **The new assertions extend existing tests.** They were added to the existing mounted Requestor-read test and the Analyst metadata-route key list, rather than to separately named tests.

**Impact:** no scope change. Items 1 and 2 follow from how the existing projectors and closed types are composed. Item 3 is a test-isolation shortfall, not a coverage gap.
