# Phase 06.9 Research: Assessment Navigation and Lifecycle Visibility

## Scope and constraints

The phase is a presentation and projection change on the existing assessment read path. `assessmentRequest` already exists on `CsrmAssessment`; no Strapi content-type schema migration is required or permitted. The server remains the authorization boundary.

## Established implementation seams

- `apps/strapi/src/api/csrm-assessment/controllers/csrm-assessment.ts` returns the two actor-specific variants of `GET /v1/risk_assessments/{assessmentId}`.
- `apps/strapi/src/api/csrm-assessment/services/assessment-scope.ts` owns the bounded detail projection and its relation populate shape. Requestor access already loads a released assessment constrained by the related request's owner.
- `docs/references/specification.json` drives `apps/web/src/lib/api/generated/schema.d.ts` through `pnpm --prefix apps/web api:generate`.
- `apps/web/src/features/assessments/assessment-schema.ts` deliberately uses strict closed Zod objects and already discriminates assessment details by `actor`.
- `apps/web/src/features/assessments/assessment-domain.ts` is the correct non-JSX home for lifecycle derivation and human-readable assessment status presentation.
- `apps/web/src/features/requests/request-lifecycle-stepper.tsx` is the direct accessible visual precedent. `RecordLink` and `nativeSelectClassName` are existing shared primitives.

## Delivery approach

1. Change the server projection, OpenAPI response schema, generated web type, typed service mapping, and strict Zod parser in a single atomic contract plan. The relation is populated only after the existing assessment authorization decision has succeeded. The summary is closed to `documentId`, `requestNumber`, `title`, and `requestStatus`.
2. Build one `AssessmentLifecycleStepper`, driven by a domain derivation from the four assessment statuses. Compose that same component and an actor-derived `RecordLink` into both assessment detail callers without replacing their current fields, editor controls, or state handling. Correct the two touched native selects at the same time.
3. Add isolated unit fixtures and a new browser fixture. The browser fixture must contain two Requestors with distinct linked requests, so direct navigation by the non-owner proves that neither the assessment read nor its new request summary leaks data.

## Verification limits and handoff

The sandbox cannot launch test child processes. Plans therefore write complete unit and Playwright coverage but label execution as an external orchestration gate. Git writes are likewise owned by the orchestrator; plans contain no commit steps.

## Risks to guard

- A relation populated but not projected through every contract layer produces runtime parser failure or an invisible link.
- A client-only ownership check would expose another Requestor's request summary; denial must be proved at the HTTP/controller path and in a separate browser context.
- Two lifecycle components would drift; both callers must import the same feature component.
- Adding the top-of-page context must preserve existing loading, empty, populated, error, and permission-denied contracts.
