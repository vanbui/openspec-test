## Recorded planning decisions

- **Resolvers (`stage-facts.ts`).** `requestDocumentIdOfQuestionnaire(strapi, questionnaireDocumentId)` and `requestDocumentIdOfAssessment(strapi, assessmentDocumentId)` read the request link, which never changes after creation, so a read before the transaction is safe.
- **Questionnaire acts (acts 3 to 6).** In each, the existing in-process questionnaire tail stays outermost; inside its `strapi.db.transaction`, the act body (from the questionnaire row lock onward) runs as the `work` of `withStageRecording(strapi, { requestDocumentId, cause, actorDocumentId, at }, work)`, whose first statement is the request row lock: request lock, then questionnaire lock, in every act (Orchestrator Confirmation). `at` is the `Date` each act writes: `releasedAt` for `questionnaire-released`, the act's `now` for `questionnaire-returned-to-review`, the batch's submission instant for `answers-submitted`, `revertedAt` for `answers-returned-to-draft`. Read the clock once per act and pass that `Date` both to the write and to the recorder.
- **Round acts (acts 7 to 12).** Inside each act's existing transaction (already under `withRequestLock`), the writes run as `withStageRecording`'s `work`: `openResponseRound` (`response-round-opened`, `at` the round's `openedAt`, `round` the new round), `closeResponseRound` (`response-round-closed`, `closedAt`, the round), `submitFinalAssessment` (`final-assessment-submitted`, the acceptance round's `openedAt`, the new round), `closeAcceptanceRoundAndReopen` (`acceptance-round-recalled` when `outcome` is `recalled`, `acceptance-round-returned` when `returned`; `closedAt`; the round; `actorDocumentId` the recaller or the sending participant), `releaseAssessment` (`released-and-closed`, `approvalDate`, the completed acceptance round). The round is created before `after` is derived, so the new row carries it; where the round document id is only known inside `work`, pass a mutable holder the recorder reads after `work` returns (`roundDocumentId: () => string | null`), and extend `StageRecordingInput` to accept that form.
- **Coverage test.** For each key of `STAGE_CAUSE_ACTS` one case drives the act through the API with the harness identities (Jane, Bob, Riley, 17.1's executive approver persona where a decision needs one) and asserts exactly one new row with that cause, the act's instant, the acting user and the round; the test fails when a cause has no case (`assert.deepEqual(new Set(casesRun), new Set(STAGE_CAUSES))`). Rollback cases use `withDocumentWriteFailure` on the stage-transition UID for one questionnaire act and one round act (the act's facts deep-equal before and after, no row), and refusal cases (Maya on a release, a recall of a closed round) write no row.
- **Oracle test.** One request per path; after every step `latestRow.stage === deriveRequestStage(await loadStageFacts(...))`; for each round, the episode starting at its opening row ends at its closing row with `enteredAt` equal to `openedAt` and `closedAt`; the `released` row's `enteredAt` equals `approvalDate`; `gateSetAt !== null` exactly when the assessment has a round.
- **Guards.** `stage-history-guards.unit.test.ts` walks `apps/backend/src` source text: a file naming `api::csrm-stage-transition.csrm-stage-transition` and calling `.create(`, `.update(`, `.delete(`, `createMany`, `updateMany` or `deleteMany` must be `csrm/stage-history/stage-recorder.ts` or `bootstrap/seed-management-metrics.ts`; no file under `src/policies/` and no file whose name ends `-policy.ts`, `-guard.ts` or `readiness.ts` imports from `csrm/stage-history/` (D-05).
