## Phase Goal

**As a** risk manager or leader, **I want** trends, ageing, cycle times and a heat map, **so that** I can see whether risk and the assessment process are improving.

This plan's slice: the records every later Phase 21 plan builds on. The design direction gains six interface patterns, and two contract-gap records with nine dated amendments fix every stored shape, vocabulary, operation, parameter and rule. The pilot approves them before any code, schema or contract changes.

Attributes: `request` (manyToOne `api::csrm-assessment-request.csrm-assessment-request`, unidirectional, required in code), `stage` (string, required, maxLength 32; the closed vocabulary lives in code, Phase 16's `kind` precedent, so Phase 22's `manual-start` cause needs no schema change), `enteredAt` (datetime, required), `enteredBy` (manyToOne `api::idambox-user.idambox-user`, unidirectional; null only for a system act, of which this phase has none), `cause` (string, required, maxLength 64, closed in code), `round` (manyToOne `api::csrm-assessment-round.csrm-assessment-round`, unidirectional, optional), `sequence` (integer, required, min 1; per request, gap-free, assigned under the request row lock). Expected link tables `csrm_stage_transitions_request_lnk` (`csrm_stage_transition_id`, `csrm_assessment_request_id`), `csrm_stage_transitions_entered_by_lnk`, `csrm_stage_transitions_round_lnk`; 21-03's boot test records the executed names.
- **Stage vocabulary (D-06).** `REQUEST_STAGES` = `intake`, `questionnaire`, `drafting`, `response`, `rework`, `acceptance`, `returned-to-draft`, `released`; `OPEN_REQUEST_STAGES` = the first six. Derivation, first match wins (21-RESEARCH R1): `draft` → `returned-to-draft` when `revertedAt` is set, else no stage; released (`approved` or `closed`, 17.1 D-45) → `released`; with an assessment, Phase 17's `deriveAssessmentStage` (17-03, widened by 17.1) mapped `released-for-response` → `response`, `awaiting-acceptance` → `acceptance`, `with-security-analyst` → `rework`, otherwise `drafting`; submitted answers → `drafting`; a released questionnaire → `questionnaire`; otherwise `intake`.
- **Causes (D-07).** `STAGE_CAUSES` = `request-submitted`, `request-returned-to-draft`, `questionnaire-released`, `questionnaire-returned-to-review`, `answers-submitted`, `answers-returned-to-draft`, `response-round-opened`, `response-round-closed`, `final-assessment-submitted`, `acceptance-round-recalled`, `acceptance-round-returned`, `released-and-closed` (the twelve acts of 21-RESEARCH R2). Phase 22 amends `manual-start` into it (G-20).
- **Recorder (D-07; Orchestrator Confirmations).** `withStageRecording(strapi, { requestDocumentId, cause, actorDocumentId, at, roundDocumentId? }, work)` in `apps/backend/src/csrm/stage-history/stage-recorder.ts`: refuses outside a transaction; takes the request row lock in the act's transaction (19.1's in-transaction shape, never `withRequestLock`); derives the stage before the act, runs the act, derives it after; appends when `after` is a stage and differs from the request's latest row, or, with no row, from the stage before the act; `enteredAt` is the act's own instant (`at`), never the clock; `sequence` is the latest plus one. Submission (the request `PUT`) is wrapped in `withRequestLock`; the four questionnaire acts take the request row lock as the first statement of their transaction, so the lock order is request first everywhere. The `released` row is written at `approvalDate`.
- **Delete refusal (Orchestrator Confirmation).** The request controller's `delete(ctx)` refuses 409 `REQUEST_HAS_STAGE_HISTORY` when any row exists, beside `REQUEST_HAS_NOTES`, `REQUEST_HAS_ATTACHMENTS` and `REQUEST_HAS_ASSESSMENT`; a never-submitted draft has no rows and stays deletable.
- **Fixture exception (Orchestrator Confirmation; D-08, D-28).** `apps/backend/src/bootstrap/seed-management-metrics.ts` (`seedManagementMetrics`, `MANAGEMENT_METRICS_FIXTURE`), behind `IDAMBOX_SEED_CSRM` and the development identity, is the only writer besides the recorder: it creates and reconciles the `enteredAt` of its own requests' stage rows by `(request number, sequence)`, and the `occurredAt` of the `residual-reviewed`, `risk-closed` and `risk-reopened` history rows it creates, through the seed path only, never through any API.
- **Statistics (D-09 to D-12).** An episode runs from a row to the request's next row; a stage's sample is its episodes that ended in the period on requests whose status is reviewable or released, newest first under `THROUGHPUT_SAMPLE_CAP` (5,000) with `truncated`; the median keeps `medianDays`'s definition; the 90th percentile is nearest rank from `STAGE_PERCENTILE_MIN_SAMPLE` (10), otherwise null with the sample size. Time to release runs from the first `intake` row (else `submittedDate`, counted in `submissionFallbackCount`) to `approvalDate`. Ageing bands `0-2`, `3-5`, `6-10`, `over-10` working days (Monday to Friday over UTC dates), plus `not-recorded`; `AGEING_BAND_BOUNDS` and `WORKING_WEEKDAYS` in `insight-constants.ts`. Slowest items: `SLOWEST_ITEMS_LIMIT` (5) per stage.
- **Trend (D-13, D-14).** Month-end instants are `throughputMonths(today, period)[m].end`, exclusive; the as-at fold of 21-RESEARCH R6; `TREND_RISK_CAP` 5,000 and `TREND_HISTORY_ROW_CAP` 25,000 make the trend `Not available` beyond them; the current point is the register's live count.
- **Heat map (D-15, D-16).** One aggregate over the register's closed query; values read through 18 D-21's `readScaleValue`; withdrawn risks never count; `not-on-scale` counts per axis.
- **Operations and Functions (D-02, D-03; both catalogue copies; `role.security_analyst` only; never `role.security_analyst_agent` or `role.requestor`).** `CSRM_ANALYST_INSIGHT_OPERATIONS.listReportRecords` = `GET:/api/v1/reports/{reportKey}/records` under `function.reports.records_api` (`Report Records API`; `.api.01` `List Report Records`); `CSRM_RISK_OPERATIONS.heatMap` = `GET:/api/v1/risks/heat_map` under `function.risk_register.heat_map_api` (`Risk Heat Map API`; `.api.01` `Get Risk Heat Map`; `underlyingRead` the register list). Both literals join `HUMAN_ANALYST_ONLY_OPERATIONS` and `SERVICE_IDENTITY_REFUSED_OPERATIONS`. The analyst insight scope additionally requires Phase 12's run read (`GET:/api/v1/ai_runs/{runId}`) for the `ai-assistance` key on the report read, its records and its export, and for the dashboard's failed-runs row, which is omitted (never refused) without it. No new IdamBox Role; no new Requestor operation. One catalogue design note records the two Functions.
- **Report keys and parameters (D-03).** `REPORT_KEYS` appends `risk-trend` (period 6 or 12, default 12), `cycle-times` (default 6) and `ai-assistance` (default 6). Phase 20's filters (`assessmentType`, `division`, `businessUnit`) apply to every new key except `ai-assistance`.
- **Drill-downs (D-26; 21-RESEARCH R10).** `GET /api/v1/reports/{reportKey}/records`, closed parameters: `risk-trend` `point` (`YYYY-MM`, a complete month in the period) and `rating` (`Critical`, `High`, `Moderate`, `Low`, `not-rated`); `cycle-times` exactly one of `stage` (every stage but `released`) or `measure` (`response-rounds`, `days-to-response`, `acceptance-rounds` (releases with their acceptance-round counts; with `roundOutcome` `any`, `recalled` or `returned`, the acceptance rounds of that outcome instead), `contest-points`, `days-to-first-answer`, `days-to-decision`); `ai-assistance` `outcome` (`failed-or-interrupted` default, `failed`, `interrupted`, `completed`, `confirmed`, `edited`, `dismissed-or-rejected`, `lapsed`, `still-proposed`), `operation` (the run vocabulary), `provider` (exact, 1 to 64 of `[a-z0-9._-]`), `window` (`7d` default, `period`, or a `YYYY-MM` in the period); all `period`, the key's report filters, `page` and `pageSize` (5, 10, 25 default, 50). Response `ReportRecordsResponse { data: { kind: "trend-point" | "stage-episodes" | "round-measure" | "ai-runs", figure, rows }, meta: { pagination, scope: { asAt, period, filters } } }`; one service function returns `{ figure, rows }` for both the figure and its list.
- **List filters (D-03 items 5, 6; D-12, D-15, D-17).** Register: `inherentLikelihood`, `inherentConsequence`, `residualLikelihood`, `residualConsequence` (a served scale label or `not-on-scale`) and `exception` (`yes`), because Phase 20's plans add no exception filter (20-10); the web's `display=heat-map` is a web URL value never sent to Strapi. Review queue: `stage` (`OPEN_REQUEST_STAGES`), `ageBand` (`0-2`, `3-5`, `6-10`, `over-10`, `not-recorded`), sort key `inStage`, row projection `inStage: { stage, enteredAt, workingDays, calendarDays } | null` (spec `RequestInStage`), the same projection on `GET /api/v1/my_requests` rows (D-17).
- **Reasons (D-03 item 7).** 409 `REQUEST_HAS_STAGE_HISTORY`; 400 `REPORT_RECORDS_QUERY_INVALID` (the records parser); 400 `LIST_FILTER_INVALID` (an unknown `stage`, `ageBand`, position or `exception` value); 403 `INSIGHT_SCOPE_MISSING` (a human analyst lacking an underlying read). A key with no drill-down, or an unknown key, is 404.
- **Report additions (D-18 to D-20).** `risk-exposure`: `heatMap`, `exposedInformationAssets`, `riskTypes`, `acceptedReviews`; `treatment-performance`: `dueByTreatmentOwner`; `assessment-throughput`: `p90DaysToRelease` and the time-to-release sample note; `control-effectiveness`: released by default with an `underAssessment` section. Dashboard summary: `queueAgeing`, `failedAiRuns`, `reviewsDue`.
- **AI (record 2; D-21 to D-23).** A failed AI job is a run with status `failed` or `interrupted` started in the current UTC day or the six before; runs group by `(operation, jobId)` (a null `jobId` is its own group); "Completed on retry" is a `completed` run of the same group with a higher `attempt`, read whatever the window; an interrupted run is never recovered. A run's proposal outcome: `edited` when any decision event is `edited`; else `confirmed` when any is `accepted`; else `dismissed-or-rejected` when any is `dismissed` or a rejection; else `lapsed` when a later completed run of the same operation and target exists or the target assessment is released; else `still-proposed`; only completed runs have one. The edit share is the share of `aiProvenance` fields in state `edited` among those `accepted` or `edited`, over the newest `AI_FIELD_SAMPLE_CAP` (1,000) by `at`. The runs list projection allow-lists operation, target number and title, initiating analyst's display name, attempt, times, status, failure code and safe message, and never the instruction, context summary, proposal, decisions or any Requestor text (G-3).
