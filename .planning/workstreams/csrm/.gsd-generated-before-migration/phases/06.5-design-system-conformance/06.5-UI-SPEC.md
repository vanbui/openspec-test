## Executable State Boundary

The state matrix exists to verify presentation, not to simulate or weaken authorization.

1. Add a server-only typed resolver, called before each route invokes its normal data service. It recognizes only `populated`, `loading`, `empty`, `error`, and `permission` from the `__e2eState` query parameter.
2. The resolver may return a fixture state only when `CSRM_E2E_UI_STATE_HARNESS === '1'`; otherwise it returns no override and the route takes its ordinary production path. It must not be imported by client components, exposed as a public API, or enabled by a browser-controlled parameter alone.
3. Each fixture branch uses the route's real state component and safe, typed empty data. It must not construct records, disclose a record identifier/title, or bypass a typed service/Strapi authorization decision in the ordinary path.
4. Every route state root exposes `data-ui-state` with exactly its state name. `loading` additionally has an accessible busy status; `error` and `permission` expose distinguishable semantic roles as defined below. Test-only markers must not substitute for visible, accessible meaning.
5. A normal production 403 remains server-authoritative. Rendering a permission state does not grant access, reveal protected existence, or alter navigation authorization. Requestor ownership and analyst grants remain enforced by Strapi.
6. AI-related copy may describe generation as a suggestion, draft, or job awaiting review. It must never imply that AI released, approved, or can automatically release a Risk Assessment.

### State semantics and accessibility

| State | Required visible and semantic behavior |
|-------|----------------------------------------|
| Populated | `data-ui-state="populated"`; retain normal landmarks, controls, and data semantics. Tables have headers; sortable controls communicate state; badges retain icon plus text. |
| Loading | `data-ui-state="loading"`; use an `aria-busy="true"` region with a concise accessible loading label. Skeletons mirror final geometry after the direction document's delay; they are decorative and must not create duplicate announced content. |
| Empty | `data-ui-state="empty"`; use a heading plus supporting paragraph and at most one primary CTA. It is ordinary content, not an alert. A filtered-empty result states the filter outcome and offers Clear filters; it never pretends data do not exist. |
| Error | `data-ui-state="error"`; use a visible `role="alert"` error summary with icon, plain-language cause, and a keyboard-operable Retry control. Retain only safe page/filter context; do not expose stack traces, transport details, or protected data. |
| Permission | `data-ui-state="permission"`; use a visible `role="alert"` access-denied message that says the user cannot access this page or data. It must not distinguish absent from forbidden records, expose counts/identifiers, or provide an escalation claim unsupported by the product. |

## Copywriting Contract

Copy is route-specific only where the subject changes. It follows the document's empty-state anatomy: a concise heading, one or two lines of supporting context, then one plain-language CTA. Do not invent decorative or brand-led copy.

| Situation | Required copy constraint |
|-----------|--------------------------|
| Primary actions | Reuse the existing explicit action label for the route (for example create/new request or collection create/import). Use a verb plus domain noun; do not use vague “Continue” or “Learn more”. |
| First-use empty | Name the domain noun and say that no authorised items exist yet. Offer one route-native creation/import action only when the user is authorised for it. |
| Filtered empty | State that no matching authorised items were found for the current filters. The sole CTA is “Clear filters”. |
| Dashboard/widget empty | State the specific widget has no authorised activity. Do not add competing CTAs across widgets. |
| Error | State that the named page/list could not load, say that data were not changed, and offer “Retry”. Do not reveal implementation, API, role, record, or tenancy details. |
| Permission | State “You do not have access to this page or its data.” Do not name missing capabilities, roles, records, totals, or a potentially nonexistent collection. |
| AI status | Say “AI-generated draft” or “generation needs Security Analyst review” where applicable. Never call it approved, released, authoritative, or automatic. |
| Destructive confirmation | No new destructive action belongs to this state-harness phase. If an existing destructive confirmation is rendered, it keeps the explicit-noun confirmation, server-confirmed completion, and semantic danger treatment required by the design direction. |

## Interaction Constraints

- Loading uses skeletons for known dashboards, lists, tables, and workspaces. Blocking submits may use only the document-permitted inline indicator; never use a full-page spinner.
- Retry is keyboard reachable, has visible focus, repeats the same request without fabricating data, and leaves the user in the same route/query context. It must not be an optimistic mutation.
- State branches do not auto-refresh, auto-advance, or shift focus unexpectedly. On a user-triggered Retry, move focus only when needed to the newly rendered error summary or first meaningful recovered control.
- Status, risk severity, errors, and permission are never color-only: each has icon and text. Severity remains the document-defined ordered icon/label system, distinct from generic status.
- State fixtures do not add alternate navigation or controls. Navigation visibility remains capability-driven and is never treated as authorization.
