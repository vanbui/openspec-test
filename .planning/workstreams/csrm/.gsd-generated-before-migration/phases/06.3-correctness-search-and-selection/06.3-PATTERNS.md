## Pattern Assignments

### `apps/strapi/src/api/csrm-questionnaire/services/questionnaire-scope.ts` (service, CRUD/query-transform)

**Primary analog:** `apps/strapi/src/api/csrm-assessment/services/assessment-scope.ts` (tracked).

The current questionnaire builder already validates the closed flat query and builds one `filters` object, but validates `status` without composing it. Keep its current owner-scope composition and add the state predicate before using that same exact `filters` object for both count and data queries.

**Current validation/projection seam** — `apps/strapi/src/api/csrm-questionnaire/services/questionnaire-scope.ts:83-118`:

```ts
assertOnlyKeys(query, ["q", "status", "sort", "page", "pageSize"]);
// status is validated here
const filters: RecordValue = {
  ...(q ? { $or: [{ title: { $containsi: q } }, { questionnaireNumber: { $containsi: q } }] } : {}),
};
// owner scope is composed here
const countQuery = { filters };
return { countQuery, dataQuery: { filters, populate: { assessmentRequest: true, questions: true, revertedBy: true }, ... } };
```

**Status-filter composition pattern** — `apps/strapi/src/api/csrm-assessment/services/assessment-scope.ts:94-127`:

```ts
const predicates: RecordValue[] = [
  ...(q ? [{ $or: [{ assessmentNumber: { $containsi: q } }, { summary: { $containsi: q } }] }] : []),
  ...(query.status ? [{ assessmentStatus: { $eq: query.status } }] : []),
];
const filters = predicates.length === 1 ? predicates[0] : { $and: predicates };
const countQuery = { filters };
return { countQuery, dataQuery: { ...countQuery, populate: { ... }, sort, start, limit }, pagination };
```

For questionnaires, `state` is calculated from answers rather than a persisted field (`questionnaireState` at `questionnaire-scope.ts:188-192`). The plan must preserve truthful server-side filtering/count parity: select/filter in Strapi using a predicate that represents the actual state, or derive a bounded server-side candidate set before projection and calculate both data and total from the same state predicate. Do not add a browser-page filter.

## Shared Patterns

### Server-authoritative list filtering

**Sources:** `questionnaire-scope.ts:83-118`; `assessment-scope.ts:94-127`.

Validate only allowlisted query keys, form `filters` once from all validated predicates, then share that object between `countQuery` and `dataQuery`. Pagination/sort/populate belong only in `dataQuery`. All scope is enforced within Strapi, not inferred from a browser view.

### Typed client and failure boundary

**Sources:** `questionnaire-service.ts:108-119`; `assessment-service.ts:207-211`.

```ts
try {
  const { data, error, response } = await request(client);
  if (error || !data) return normalizeFailure(error, response.status);
  return { data: parse(data), error: null };
} catch (error) {
  return normalizeFailure(error);
}
```

Keep API calls in server-only typed services. Zod schema errors must remain distinguishable from transport errors where the established assessment transport already does so; do not move fetch/parsing to list components.

### Accessible filter control

**Source:** `request-table.tsx:145-171`.

Use an explicit Search submit and a visible Status label/select, semantic token classes, and a non-colour-only status presentation. Preserve `view` and query state in URLs, reset page only for filter/page-size/sort changes, and expose a server total with `role="status"`.
