# Phase 06.8: Workflow Visibility and Questionnaire Governance Verification Report

**Phase Goal:** As a Requestor or Security Analyst, I want the Assessment Request to be a shared,
actor-aware operational hub that shows exactly where the work stands and what is required next, and I
want questionnaire generation, editing, release, and revision to stay under explicit Analyst control
with an auditable history, so that both actors can act on the same record without guessing at
lifecycle state or losing evidence.

## Method

This is a re-verification of the single blocking gap the prior pass found (CR-02: the OpenAPI contract's
`QuestionnaireGovernanceResult` and `QuestionnaireReleaseResult` schemas were each an unsatisfiable
`allOf` of two `additionalProperties:false` branches, plus an independent `events`-shape mismatch). Per
the evidence-gate procedure, this pass gives the failed item full three-level verification and gives the
six previously-VERIFIED roadmap truths a regression check. The disclosed, matched-to-Phase-8 CR-04
deferral is unchanged and re-confirmed at the source line level, not merely re-asserted from the prior
report.

**What was independently re-verified in this session, not merely trusted from commit `aa976b5`'s
message or SUMMARY narrative:**

1. **Read the current `docs/references/specification.json` schemas directly** (not the diff, the live
   file) for `QuestionnaireGovernanceResult`, `QuestionnaireReleaseResult`, `QuestionnaireSummary`,
   `QuestionnaireGovernanceEvent`, and `QuestionnaireRevisionTimelineEvent`. Confirmed each of the three
   result schemas is now a single flat `type: object` with its own `properties`/`required`/
   `additionalProperties: false` — no `allOf` remains on any of them — and that the `events` field on
   `QuestionnaireGovernanceResult` correctly references `QuestionnaireGovernanceEvent` while
   `QuestionnaireSummary`'s `events` correctly references the differently-shaped
   `QuestionnaireRevisionTimelineEvent` (the two are for different endpoints and are legitimately
   different shapes now, not silently incompatible under the same name).
2. **Traced the schema against the real server response shape** (`projectQuestionnaire` in
   `questionnaire-scope.ts` and `resultForGovernance` in `questionnaire-governance-workflow.ts`) to
   confirm the server actually emits exactly the field set each schema now declares — not just that the
   schema is internally satisfiable in the abstract, but that it matches production output.
3. **Ran the single new test by name** (`mounted release and governance responses satisfy their
   published closed schemas`, in `apps/strapi/tests/questionnaire-governance.integration.test.ts`) —
   compiled fresh and executed via `node --test --test-name-pattern`, not taken on faith. It passed,
   driving real HTTP `POST .../release` and `POST .../return_to_review` requests through the mounted
   Strapi app and validating the live JSON responses against the schemas as published today.
4. **Confirmed the test is not vacuous**: checked out the pre-fix blob (`git show aa976b5^:...`) and
   confirmed the old `QuestionnaireReleaseResult` schema had no top-level `properties` key and
   `additionalProperties` was `undefined` — meaning the new test's
   `assert.equal(schema.additionalProperties, false, ...)` line would have failed against the old,
   broken schema. The test genuinely exercises the CR-02 defect class, not a tautology.
5. **Read the `contract-catalogue.integration.test.ts` diff**: the old assertion literally checked
   `Array.isArray(schema.allOf)` as the *expected*, correct shape (asserting the bug was present); the
   new assertion checks `schema.allOf === undefined` and `schema.additionalProperties === false`. This
   test also compiled and ran clean.
6. **Regression sweep for "nothing else regressed"**: ran the full Strapi suite fresh
   (`node --test ... dist/tests/authorization.policy.test.js .tmp/tests-dist/tests/*.test.js`, once),
   the full web suite fresh (`pnpm test`, once), both full typechecks fresh, `pnpm api:check` (regenerate
   + diff the generated client against the corrected spec), byte-identity of the capability catalogue
   copies, and `git status --short`. All independently reproduced the numbers the task description
   reported.
7. **Checked for other instances of the same defect class** in `specification.json` (searched every
   remaining `allOf` usage in the file) to rule out a partial fix. Found one pre-existing, unrelated
   instance (`QuestionnaireRevertResult`, used by the older `revert_to_draft` endpoint, not part of
   Phase 06.8's governance/release surface or CR-02's named scope, untouched by commit `aa976b5`) —
   recorded as an advisory-adjacent observation below, not a gap of this phase (out of scope: it predates
   06.8, is unaffected by this fix, and no Phase 06.8 must-have or roadmap success criterion depends on
   it).
