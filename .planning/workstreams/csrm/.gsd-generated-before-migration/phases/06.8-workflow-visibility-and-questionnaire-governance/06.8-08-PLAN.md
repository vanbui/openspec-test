<objective>
**As a** Requestor or Security Analyst, **I want to** open one assessment request and see its whole
operational picture — what state it is in, what is required next, and a concise summary of every
related record I am allowed to see — **so that** I can act on the record without hunting through six
screens, and without either of us seeing something we should not.

Purpose: criterion 6 and D-10. Plan 07 delivered the stepper; this plan delivers everything beneath
it. The specific discipline D-10 imposes is that each summary **links** to its existing
authoritative screen and never embeds a duplicate editor, so the hub adds no second place to edit
anything.
Output: one shared hub component, one added descendant count on the server relationship projection,
and a widened browser journey covering all three relationship states at both widths.
</objective>

In `relationship-scope.ts`, add `controlImplementationCount` to the available assessment relation:

In `request-domain.ts` add the count to the available assessment relation type. In

phase still parses, and keep the union discrimination on `availability` exactly as it is.

Create `request-hub.tsx` exporting `RequestHub`, taking the parsed request, the parsed lifecycle and
an explicit href map the route supplies. Render two bands.

The first band is the compact operational summary: the request number and title, the assessment
type, the business criticality, the due date, the submitted date when present, and the owner; then
the next required action, taken from the server lifecycle rather than recomputed, stated as one
sentence with its record link when the lifecycle supplies one. Keep it to a single scannable block —
this is the "where does this stand and what do I do" band, not a second copy of the request form.

The second band is six summaries in this order: questionnaire, assessment, risks, controls,
information systems, information assets. Each is a compact card carrying a heading, one line of
substance, and at most one record link. Questionnaire: its number and derived state when available,
linked. Assessment: its number and status when available, linked. Risks: the residual rating counts
from the assessment relation with the rating named in text beside each count, linked to the
assessment's identified risks. Controls: the control-implementation count, linked to the same
destination as the risks summary since control implementations are contextual to a risk. Information
systems and information assets: the count and the names already present on the request, with no link
because the request itself is their authoritative context, and an explicit line when none are
selected.

Each summary obeys the three-state rule exactly: for `available`, render the substance and the link;
for `absent`, render a plain sentence saying the record does not exist; for `unavailable`, render
nothing at all — no heading, no placeholder, no greyed card — because the existence of the record is
itself protected. Never infer a link from an identifier that happens to be in the payload; render a
link only for `available` and only when the route supplied an href.

Embed no editor and no mutating control. The hub contains no form, no select and no button; the
existing request workflow actions block stays exactly where it is and is not absorbed.

Render the hub on the Requestor request detail page beneath the stepper, replacing the current ad
hoc overview and relationship sections, and keep the workflow actions section untouched at the
bottom. Pass Requestor-scoped hrefs, gated on the same capability checks the page already applies.
Use semantic tokens only and the existing detail, record-link and rating primitives.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Strapi request read → browser | The relationship projection decides which related records this actor may learn exist. |
| browser → linked detail screens | Each summary link targets a screen whose own server-side checks remain authoritative. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06.8-37 | Information Disclosure | unavailable relationship summaries | high | mitigate | An unavailable relation renders nothing at all — no heading, no placeholder, no count — and the component test asserts absence from the accessible tree, so the existence of a protected record is not leaked by the shape of the page. |
| T-06.8-38 | Information Disclosure | descendant control count | high | mitigate | The count is emitted only for an available assessment relation, which already requires the existing openable rule, so a Requestor learns nothing about an unreleased assessment's controls. |
| T-06.8-39 | Elevation of Privilege | summary links | high | mitigate | A link is rendered only for an available relation and only when the route supplied an href gated on the capability that route already resolves; the target screens keep their own server-side checks, so a guessed URL is still refused by Strapi. |
| T-06.8-40 | Elevation of Privilege | duplicate editor in the hub | medium | mitigate | D-10 forbids embedding a duplicate editor; a scan and a component test assert the hub contains no form, select or button in any state, so the hub cannot become a second mutation surface. |
| T-06.8-41 | Tampering | actor drift inside a shared component | medium | mitigate | The only actor-shaped difference is one declared boolean prop; a scan rejects an actor comparison inside the hub, so the two actors cannot come to render different truths from the same record. |
</threat_model>
