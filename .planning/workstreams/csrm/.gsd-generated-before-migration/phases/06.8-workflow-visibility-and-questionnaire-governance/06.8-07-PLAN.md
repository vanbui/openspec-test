<objective>
**As a** Requestor or Security Analyst, **I want to** see at a glance exactly where this assessment
request stands and what is required next, **so that** I stop guessing at lifecycle state from a
single status badge and the two of us are looking at the same truth.

Purpose: criterion 1 and D-01. The eight visible steps do not map one-to-one onto any stored
enumeration, so the projection derives them from `requestStatus`, the questionnaire release facts
added in plan 01, the per-answer submitted envelopes, and the assessment status together with the
release readiness plan 02 made authoritative. The contract-gap record states plainly that no schema
change is approved or needed for this.
Output: one pure server derivation, one published lifecycle projection on the request read, and one
shared read-only stepper on both request detail routes.
</objective>

## The eight steps and exactly how each is derived

D-01 fixes the visible vocabulary. These are derivations over facts that already exist; no
enumeration gains a value.

| # | Step key | Step label | Entry condition |
| --- | --- | --- | --- |
| 1 | `draft` | Draft | `requestStatus` is `draft`. |
| 2 | `submitted` | Submitted | `requestStatus` is `submitted` or later and the request has no questionnaire. |
| 3 | `questionnaire-generated` | Questionnaire generated | a questionnaire exists and its release timestamp is absent. |
| 4 | `questionnaire-released` | Questionnaire released | the questionnaire's release timestamp is present and not every active question's answer is submitted. |
| 5 | `questionnaire-submitted` | Questionnaire submitted | every active question's answer is submitted. |
| 6 | `assessment-drafted` | Assessment drafted | an assessment exists and is not reviewed-and-ready and not released. |
| 7 | `assessment-reviewed` | Assessment reviewed | the assessment status is `in-review` and its release readiness is met. |
| 8 | `assessment-released` | Assessment released | the assessment carries the complete release triple: status `approved`, an approver, and an approval date. |

Rules the derivation must follow:

- The current step is the **highest-numbered step whose entry condition holds**, so a record
  returned to an earlier editable state — a request reverted to draft, a questionnaire returned to
  analyst review, an assessment regressed by plan 02 — correctly moves the stepper back rather than
  latching forward.
- Step 3 is analyst-only content in the sense that only an analyst can act on it, but the step
  itself is visible to both actors, because hiding it would leave a Requestor unable to tell why
  nothing is required of them yet.
- `requestStatus` `closed` marks all eight steps completed and carries a `terminal` value of
  `closed`, named in text beside the stepper. `closed` is not a ninth step.
- The `nextAction` is actor-aware: it states the one thing required of **this** actor, or says that
  the work sits with the other party, and carries an href only to a screen this actor is authorised
  to open.

| T-06.8-32 | Information Disclosure | next-action hrefs | high | mitigate | An href is attached only when the existing relationship rules already declare that record openable to this actor, so the stepper can never offer a Requestor a link to an unreleased questionnaire or an unreleased assessment. | T-06.8-35 | Tampering | client-side re-derivation | medium | mitigate | The browser renders server labels and states; the strict parser rejects an unknown step key, an unknown step state or a step list of the wrong length, so a drifted payload fails loudly instead of rendering a wrong step. |
