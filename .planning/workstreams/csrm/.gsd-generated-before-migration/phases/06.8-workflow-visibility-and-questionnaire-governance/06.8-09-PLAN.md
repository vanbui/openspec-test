<objective>
**As a** Security Analyst, **I want to** open my request queue and see only the work waiting on me,
with named filters for everything else; **and as a** Requestor, **I want to** see my requests grouped
by lifecycle state on my dashboard — **so that** neither of us has to read a whole list to find the
one thing that needs doing.

Purpose: criterion 7, D-11 and D-12. Both halves reuse machinery that already exists — the derived
lifecycle from plan 07, the in-memory generation job registry, and the owner-scoped list's existing
status query parameter — so the net new work is the bucket predicates and two presentations.
Output: four server-side queue buckets, a queue filter control, and lifecycle-state dashboard cards.
</objective>

## The four buckets and exactly how each is selected

Each bucket is a predicate over the lifecycle step plan 07 derives, not a re-derivation from raw
columns.

| Bucket | Meaning | Selection |
| --- | --- | --- |
| `requires-attention` (default) | The next required action belongs to an analyst. | The derived current step is `submitted`, `questionnaire-generated`, `questionnaire-submitted`, `assessment-drafted` or `assessment-reviewed`, **and** no generation job is active for the request. |
| `awaiting-requestor` | The next required action belongs to the Requestor. | The derived current step is `draft` or `questionnaire-released`. |
| `generation-in-progress` | A questionnaire generation job is running or queued for this request. | The in-memory registry reports an active job for the request id. |
| `released` | Work already released to its Requestor. | The request status is `approved` or `closed`. |

The base status set differs by bucket. The three action buckets keep the existing reviewable status
set. The `released` bucket replaces it with `approved` and `closed`, because released requests are
not in the reviewable set at all today — which is exactly why released work currently cannot be
found from this screen.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser query string → Strapi queue route | The bucket name is actor-supplied and selects which status set and predicate the server applies. |
| Strapi queue read → browser | The queue is an explicitly authorised analyst surface; the dashboard is owner-scoped for every actor. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06.8-42 | Elevation of Privilege | queue scope versus dashboard scope | high | mitigate | The queue keeps its existing analyst collection-scope grant and the dashboard keeps the owner-scoped reads; the bucket is applied inside the already-authorised scope and can never widen it. The Phase 06.3 separation of My lists from review surfaces is unchanged. |
| T-06.8-43 | Input Validation (ASVS V5) | bucket query value | high | mitigate | The bucket is validated against a frozen four-value tuple in the server's closed filter parser and again in the client's closed query schema; anything else is refused with the existing query error. |
| T-06.8-44 | Information Disclosure | authoritative totals | medium | mitigate | The total and page count are computed from the filtered set, so a count can never reveal the size of a slice the analyst is not looking at, and paging cannot walk past the bucket into unfiltered rows. |
| T-06.8-45 | Information Disclosure | queue row content | medium | mitigate | The queue projection stays at its existing five fields; a scan asserts the field count so a bucket cannot smuggle extra record content into the list. |
| T-06.8-46 | Denial of Service | load-then-filter over the authorised scope | medium | mitigate | The scope is loaded in bounded pages using the same pattern and page bound as the existing questionnaire collection, so a composite predicate cannot become an unbounded read. |
| T-06.8-47 | Repudiation | volatile generation-job signal | low | accept | The generation-in-progress bucket reads the in-memory single-process registry, which RESEARCH.md records as an accepted guarantee for this deployment. It is a transient hint, never an authorization input, and the code records the limitation. |
</threat_model>
