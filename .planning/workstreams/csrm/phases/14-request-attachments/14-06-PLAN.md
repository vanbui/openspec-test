## Phase Goal

**As a** Requestor or Security Analyst, **I want to** attach supporting files to a request at any point, **so that** the assessment can use the vendor pack, data flows and spreadsheets the business already has.

This plan's slice: Jane adds a file to her draft and sees it listed, and after submission she and Bob add files with their notes, through Strapi and the web's typed layer. Nobody else can list or add, and every refused file is refused with its reason and leaves nothing behind.

<objective>
Create the approved content type (D-01) and serve `GET` and `POST /api/v1/assessment_requests/{requestId}/attachments` with the window, the note link, the readers, the limits under the per-request lock, screening and quarantine at upload (D-10 to D-19), their grant, contract, matrix rows and inventory (D-03, D-38), and the web's typed schema and service registered in the parity guard.

Purpose: COLLAB-02 criteria 1 to 3 at the API; ROADMAP success criteria 2 and 3 for the list and upload.
Output: one content type with no core route; two operations end to end to the typed service.

Edits Strapi source? Yes. Changes the specification? Yes. Runs Playwright? No. Regenerates `served-operations.json`? Yes.
Scope note: 20 files: eight are the new API (the schema, the operations, the route, the controller and four services); five the contract chain (the spec, the generated client, both catalogue copies and the served inventory); four the Strapi proofs (the matrix rows, the catalogue test, the rules unit test and the integration test); three the web's typed schema, service and parity guard. They change together because a served operation, its grant and its typed client must land in one commit for `api:check`, the catalogue `cmp`, the served inventory and the parity guard to stay green; splitting further would repeat the chain (accepted, as 12-PLAN-CHECK records for similar plans).
</objective>

## Recorded planning decisions

- **Folder**: `apps/backend/src/api/csrm-request-attachment/` with `content-types/csrm-request-attachment/schema.json`, `routes/request-attachments.ts` (the standalone router of `my-request-status-summary.ts`; no `createCoreRouter`), `controllers/request-attachments.ts`, `services/`, `operations.ts`. `CSRM_REQUEST_ATTACHMENT_OPERATIONS = { list: "GET:/api/v1/assessment_requests/{requestId}/attachments", upload: "POST:/api/v1/assessment_requests/{requestId}/attachments" }` (14-07 to 14-09 add `download`, `setRemoval`, `setAiInput`, `getAiText`). Routes use `auth: { strategies: ["content-api-token"] }` and the policies `global::csrm-app-enabled` and `{ name: "global::csrm-authorization", config: { operation } }` only (never `requireRequestOwnership`).
- **Schema**: as "Recorded planning decisions" of 14-01 and the approved record: `draftAndPublish: false`; relations without `inversedBy`; `file` single media `private: true`; `aiText` `private: true`.
- **Rules** (`attachment-rules.ts`, pure): `attachmentWindow({ requestStatus }) → "intake" | "after-submission" | "closed"` (`draft` → intake; `acceptsNotes(status)` → after-submission; `RELEASED_REQUEST_STATUSES` → closed); `acceptsAttachments(request, caller)`; `addRefusalFor({ request, caller, activeCount, storedCount, configured }) → reason | null` in the order `ATTACHMENTS_NOT_CONFIGURED`, `ATTACHMENTS_CLOSED`, `REQUEST_NOT_SUBMITTED` (intake and the caller is not the requestor), `ATTACHMENT_LIMIT_REACHED` (active ≥ 20), `ATTACHMENT_LIFETIME_LIMIT_REACHED` (stored ≥ 60); `noteAcceptsAttachments({ note, requestId, callerId, now }) → null | "ATTACHMENT_NOTE_INVALID"` (same request, the caller is the author, `now - postedAt ≤ 60 minutes`); `attachmentStateOf(record) → "removed" | "blocked" | "pending" | "unavailable" | "available"` in that precedence (`unavailable` when `scanStatus` is `clean` and the media relation is empty); `canRemoveAttachment` and `canRestoreAttachment` (14-08 completes them). Active means `scanStatus` `pending` or `clean` and `removedAt` null; stored means every record.
- **Event log** (`attachment-event-log.ts`, the 06.8 posture): `ATTACHMENT_EVENT_LOG_SCHEMA_VERSION = 1`, `ATTACHMENT_EVENT_LOG_MAX_EVENTS = 200`, events `{ schemaVersion, type: "uploaded" | "quarantined" | "scan-verdict" | "blocked" | "removed" | "restored" | "ai-included" | "ai-excluded", by: string | null, at, engine?, verdict?, detection? }`, `parseAttachmentEventLog`, `appendAttachmentEvent` (throws `AttachmentEventLogError` → `HISTORY_UNAVAILABLE` at the cap or on a malformed log), never read by a gate.
- **Projection** (`attachment-projection.ts`): `projectAttachment(record, viewer)` → `{ documentId, fileName, fileType, byteSize, state, uploadedBy: Person | null, uploaderPart, uploadedAt, note: { documentId, postedAt } | null, removedBy: Person | null, removedAt: string | null, detection: string | null (blocked only), actions: { download, remove, restore } }`; `projectAddFacts(...)` → `{ canAdd, refusal, window, needsNote, remaining, activeCount, storedCount, limits: { maxBytes, maxActive, maxStored }, allowedTypes }`. Never `sha256`, the hash, the storage key, a URL or `aiText`.
- **Service** (`request-attachments.ts`): `listRequestAttachments({ strapi, request, caller })` (no lock; at most 60 records, newest first by `uploadedAt` then `id`; `meta: { total, removed, add }`); `uploadRequestAttachment({ strapi, request, caller, upload: { filepath, originalFilename, size }, noteId })` in 14-RESEARCH Pattern 2's order: not configured → 409; `addRefusalFor` pre-check → 409; note pre-check (after submission: missing → `ATTACHMENT_NOTE_REQUIRED`; on a draft: present → `ATTACHMENT_NOTE_INVALID`; otherwise `noteAcceptsAttachments`) → 409; size over 26,214,400 → 413 and zero → 400 before reading; read the bytes; `screenAttachment` (refused → 413, 415, 400 or 422 with `details.detection`); `createAttachmentStorage(strapi).put`; `withRequestLock` re-checks the window, the note, the active and stored counts with `strapi.db.query` (never raw knex), then creates the record (`scanStatus` `clean` or `pending`, `scanCheckedAt`, `scanEngine`, `scanAttempts` 0 or 1, `uploaderPart` from `authorPartFor`, `eventLog` with `uploaded` and, when pending, `quarantined`); a refusal inside the lock calls `put`'s `remove` before answering 409. Every outcome calls `logSecurityEvent` (`attachment.refused` with the reason and detection, `attachment.uploaded`, `attachment.quarantined` with the cause). `RequestAttachmentsError(status, reason, details?)`; 422 bodies are `{ data: null, error: { status: 422, name: "UnprocessableEntityError", message, details: { reason, detection } } }`.
- **Controller**: `list` and `upload` load the request (`requestor`, `requestStatus`, `revertedAt`) by `requestId`; a missing request or `canUseRequestNotes` false → 404 `CSRM request attachments were not found.`; `upload` refuses with 400 unless `ctx.request.files` has exactly the key `file` (not an array) and `ctx.request.body` has no key other than `noteId` (a string of 1 to 255 characters).
- **Spec**: paths `/v1/assessment_requests/{requestId}/attachments` `get` (`assessment-workflow/list-request-attachments`) and `post` (`assessment-workflow/upload-request-attachment`, request body `multipart/form-data` `RequestAttachmentUploadRequest` `{ file: { type: string, format: binary }, noteId? }` with `additionalProperties: false`, following `AdministrationImportPreviewRequest`); components `RequestAttachmentType`, `RequestAttachmentState`, `RequestAttachmentPart`, `RequestAttachmentActions`, `RequestAttachment`, `RequestAttachmentAddFacts`, `RequestAttachmentListMeta`, `RequestAttachmentListResponse`, `RequestAttachmentResponse`, all closed; upload responses 201, 400, 403, 404, 409, 413, 415, 422 (`AssessmentWorkflowErrorResponse`); list 200, 403, 404.
- **Catalogue**: `function.risk_assessment_requests.attachments_api` (`Assessment Request Attachments API`, `Requestor and Security Analyst request attachments. This API-only Function intentionally has no menuPath.`, `roleIds: ["role.security_analyst", "role.requestor"]`) with `.api.01` `List Assessment Request Attachments` and `.api.02` `Upload Assessment Request Attachment`, sourceEntities `CsrmAssessmentRequest`, `CsrmRequestAttachment`; design note 6 amended: request attachments are the recorded entity of `docs/contract-gaps/phase-14-request-attachments.md`. The grant is written both ways in both catalogue copies: the Function's `roleIds`, and the `functionIds` of `role.security_analyst` and of `role.requestor` each gain the Function's id (the seeder `seed-csrm-data.ts` and `contract-catalogue.integration.test.ts` read the role's `functionIds`).
- **Web**: `features/attachments/attachments-schema.ts` (zod, closed, mirroring the components) and `attachments-service.ts` (`import 'server-only'`; `listRequestAttachments(requestId)`; `uploadRequestAttachment(requestId, file, noteId?)` building a `FormData` with `file` and `noteId` and passing it through `bodySerializer: (body) => body as FormData`, the administration pattern; `responseParserModule` registered in the parity guard).
