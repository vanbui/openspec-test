**Known infrastructure facts.**
1. **Shared `dist`.** The orchestrator's dev Strapi (1337) and Next (3000) may run during planning. Everything that compiles Strapi shares `apps/backend/dist`: the Strapi suite, a single Strapi file, `served-operations:write` and Playwright. All of these wait until the servers are stopped. A task executed while they run records those proofs as pending for the plan's end.
2. **No live scanner, store or model.**
   - Both harnesses run `NODE_ENV=development` with `CSRM_ENVIRONMENT=development` (`strapi-http-harness.ts:491-492`; `playwright.config.ts:203-208`), so the development scanner double is allowed in them.
   - ClamAV is proved only against `fake-clamd-server.ts`, and S3 only against `fake-object-store.ts`.
   - `CSRM_AI_PROVIDER=deterministic` stays pinned.
3. **No EICAR on disk.** Suites use the CSRM test signature. The one EICAR unit test decodes the string in memory, and no source, test, fixture or compiled file spells it (research Pitfall 7).
4. **Storage directories.** Each harness pins its own temporary storage directory: the Strapi harness under `.tmp/`, Playwright beside the run's database under `apps/backend/.tmp/` (`playwright-attachments-{id}`), kept with it when a run fails and removed with it when a run passes (stage B, IN-607; it was under the run's temporary root, which every run deleted). Formidable's temporary files go to the OS temp directory and are removed by the cleanup middleware. A run never writes under `apps/backend/public/uploads/`.
5. **Body limits.** `next.config.ts` sets `serverActions.bodySizeLimit` and `experimental.proxyClientMaxBodySize` to `'26mb'`. Without the second, uploads over 10 MB arrive truncated (research Pitfall 1). A test of the configuration asserts they are equal.
6. **Windows Vitest** can fail with `EPERM: rename`. Rerun that file alone before treating it as a real failure.
7. **The base changes first.** Phases 10, 11, 12 and 13 execute before Phase 14 and change the files this phase edits: the conflict reasons, the navigation guard, the status mapping, the context builder, the run envelopes, the notes service and the composer. Re-run the plan check before executing.

## Sampling Rate

- **After every task commit:**
  - run the touched web test files by path;
  - run `typecheck` when types change, and `api:check` after any spec change;
  - run the touched Strapi files by path, dev servers stopped.
- **After every plan wave:**
  - run the full web suite, `typecheck` and `api:check`;
  - run the full Strapi suite after every plan that edits Strapi (14-02 to 14-11; each of those plans' closing task already runs it);
  - run each UI plan's targeted Playwright spec once at its end (14-12 to 14-16; their tasks already run `e2e/request-attachments.spec.ts` on both projects).
- **Before `/gsd-verify-work`:** the full suite must be green. That is the phase gate above (plan 14-17, task 14-17-03), recorded with counts, duration, the flaky count and the clean `git status`.
- **Max feedback latency:** 120 seconds for the task-level quick runs. The tasks that close a Strapi plan run the full Strapi suite (about 12–17 min), and the UI tasks run the production-build Playwright spec, so those exceed it by design.
