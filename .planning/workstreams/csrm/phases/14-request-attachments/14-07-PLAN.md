## Phase Goal

**As a** Requestor or Security Analyst, **I want to** attach supporting files to a request at any point, **so that** the assessment can use the vendor pack, data flows and spreadsheets the business already has.

This plan's slice: a file reaches a reader only when it is clean and intact. Bob downloads Jane's data-flow document through one authorised operation with hardened headers and a digest check; a file still waiting for its malware check, blocked or tampered with never leaves Strapi; and a quarantined file is re-scanned until it is released or blocked.

<objective>
Serve `GET /api/v1/assessment_requests/{requestId}/attachments/{attachmentId}/content` (the contract's first binary response) with the readers, the state refusals, the digest check and the D-23 headers (D-23); build the web's shared file-response validator and the typed binary service call with the parity guard's file-response mode (D-24); and build the in-process re-scan scheduler with its boot and destroy hooks, releasing or blocking quarantined files (D-13, D-21).

Purpose: COLLAB-02 criteria 1 and 3 for downloads; ROADMAP success criterion 2 ("cannot download by any URL"); the file-transfer module Phase 19 reuses.
Output: one operation end to end to the typed service, one shared web module, one scheduler.

Edits Strapi source? Yes. Changes the specification? Yes. Runs Playwright? No. Regenerates `served-operations.json`? Yes.
Scope note: 20 files: seven Strapi sources (the download operation's four API files, the stored-file sender, the re-scan scheduler and `index.ts`'s boot and destroy hooks); five the contract chain; four the Strapi proofs (the matrix rows, two integration files and the re-scan unit file); four the web's file-response validator with its test, the typed service and the parity guard. They change together because the download and the re-scan both release or refuse a file by its scan state, and the binary response, its grant and the web validator must land in one commit for `api:check`, the catalogue `cmp`, the inventory and the parity guard's file-response mode to stay green (accepted, as 14-06).
</objective>

## Recorded planning decisions

- **Operation**: `CSRM_REQUEST_ATTACHMENT_OPERATIONS.download = "GET:/api/v1/assessment_requests/{requestId}/attachments/{attachmentId}/content"`; route `GET /v1/assessment_requests/:requestId/attachments/:attachmentId/content`, handler `download`.
- **Download** (`readRequestAttachmentContent({ strapi, request, caller, attachmentId })`): the attachment must belong to the request in the path (`assessmentRequest` equals it), else 404; `attachmentStateOf` → `removed` 409 `ATTACHMENT_REMOVED`, `blocked` 409 `ATTACHMENT_BLOCKED`, `pending` 409 `ATTACHMENT_QUARANTINED`, `unavailable` 409 `ATTACHMENT_UNAVAILABLE`; `createAttachmentStorage(strapi).read(fileId)` (`STORAGE_FILE_MISSING` → 409 `ATTACHMENT_UNAVAILABLE`); SHA-256 mismatch → 409 `ATTACHMENT_INTEGRITY_FAILED` and a warn-level `attachment.integrity_failed`; then the controller sets `Content-Disposition: attachment; filename="{ascii}"; filename*=UTF-8''{encoded}` (non-ASCII, `"` and `\` replaced by `_` in `filename`; `encodeURIComponent` then `'()*` percent-encoded in `filename*`), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'; sandbox`, `ctx.type = ATTACHMENT_MEDIA_TYPES[fileType]` and `ctx.body` to the verified `Buffer` (14-RESEARCH Code Example 7, Pitfall 15), and logs `attachment.downloaded`.
- **Shared download** (`apps/backend/src/csrm/files/send-stored-file.ts`, Phase 20 reuses it): `readVerifiedStoredFile(strapi, { fileId, sha256 })` reads through the storage port and returns the bytes or `{ failure: "missing" | "integrity" }`; `contentDispositionFor(name)` builds the `attachment; filename=…; filename*=UTF-8''…` value; `sendStoredFile(ctx, { fileName, mediaType, bytes })` sets the four headers, the type and the body. The attachment download calls these three.
- **Spec**: path `/v1/assessment_requests/{requestId}/attachments/{attachmentId}/content` `get`, operationId `assessment-workflow/download-request-attachment`; the 200 response declares eight media types (`application/pdf`, the three OOXML types, `text/csv`, `text/plain`, `image/png`, `image/jpeg`), each `{ "type": "string", "contentMediaType": "<type>" }`, and the four headers; 403, 404 and 409 use `AssessmentWorkflowErrorResponse` (14-RESEARCH Pitfall 12).
- **Catalogue**: `function.risk_assessment_requests.attachments_api.api.03` `Download Assessment Request Attachment`.
- **Re-scan scheduler** (`rescan-scheduler.ts`, generic, Phase 20 reuses): `RESCAN_BACKOFF_MINUTES = [1, 5, 15, 60]` then every 60, `RESCAN_MAX_ATTEMPTS = 24`; `createRescanScheduler({ listPending, rescan, timers = { setTimeout, clearTimeout }, logger })` → `{ start(): Promise<void>` (rescans every pending item once, then schedules each by its attempts), `schedule(id, attempts)`, `stop()` (clears every timer) `}`; every timer is `unref()`'d; an item at `RESCAN_MAX_ATTEMPTS` is not rescheduled and logs one error.
- **Attachment wiring** (`request-attachments.ts`): `rescanPendingAttachment({ strapi, attachmentId })` reads the bytes and scans outside the lock, then under `withRequestLock` re-checks `scanStatus` is still `pending` and writes: clean → `scanStatus: "clean"`, `scanCheckedAt`, `scanEngine`, event `scan-verdict`, `attachment.scan_verdict`; infected → `createAttachmentStorage(strapi).remove(fileId)`, `scanStatus: "blocked"`, `scanDetection`, event `blocked`, warn-level `attachment.blocked`; not scanned → `scanAttempts + 1` (a `limits` cause logs an error naming the deployment requirement) and returns `still-pending`. `startAttachmentRescans(strapi)` builds the scheduler with the configured scanner and starts it (a no-op when attachments are unconfigured); `stopAttachmentRescans(strapi)` stops it. Uploads stored `pending` call `schedule(id, 1)`. `apps/backend/src/index.ts` calls `startAttachmentRescans(strapi)` at the end of `bootstrap()` and gains `destroy({ strapi }) { stopAttachmentRescans(strapi); }`.
- **Web validator** (`apps/csrm/src/lib/files/file-response.ts`, no directive): `type FileSignature = "pdf" | "png" | "jpeg" | "zip" | "text"`; `FileResponseRule = { contentTypes: readonly string[]; maxBytes: number; isSafeName(name): boolean; signatures: readonly FileSignature[] }`; `ATTACHMENT_RESPONSE_CONTENT_TYPES` (the eight); `attachmentFileRule(type)` (exactly that type's media type; the name has no `/`, `\`, C0 control or bidirectional override, is 1 to 255 characters and ends with the type's extension, `.jpg` or `.jpeg` for JPEG; at most 26,214,400 bytes; the type's signature, `zip` for the three OOXML types and `text` for CSV and TXT); `parseContentDispositionFileName(header)` (`filename*=UTF-8''…` decoded first, then `filename="…"`); `validateFileResponse({ contentType, contentDisposition, bytes }, rule) → { ok: true, fileName, contentType, bytes } | { ok: false, failure: "type" | "name" | "size" | "signature" }`. Phase 19 adds its export rule beside `attachmentFileRule`.
- **Web service**: `downloadRequestAttachment(requestId, attachmentId, recordedType)` calls the operation with `parseAs: "arrayBuffer"`, reads `content-type` and `content-disposition` from the response, and returns `{ data: { fileName, contentType, bytes: Uint8Array } }`, `{ error: TransportError }` for a 4xx or 5xx, or `{ error: { kind: "file-check", failure } }`. The parity guard's `mode` gains `'file-response'`, with this module registering the download operation and the test asserting the spec's 200 media types equal `ATTACHMENT_RESPONSE_CONTENT_TYPES`.
