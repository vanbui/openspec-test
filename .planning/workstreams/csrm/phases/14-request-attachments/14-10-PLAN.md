## Phase Goal

**As a** Requestor or Security Analyst, **I want to** attach supporting files to a request at any point, **so that** the assessment can use the vendor pack, data flows and spreadsheets the business already has.

This plan's slice: when Bob generates, the AI reads the security pack he included, as information and never as instructions, and nothing of the data-flow document he did not include; the run record says which files were used, how much of each was sent, and still finds a file removed later.

<objective>
Extend Phase 12's context builder with the attachment blocks inside the untrusted data block, the per-run attachment bound and the job failure that names the included files (D-33, D-34); add the run summary's v3 attachments section with its closed parser and the run read's resolved names (D-35); and prove a generation through the fake OpenAI-compatible server (D-39).

Purpose: COLLAB-02 criterion 5 and ROADMAP success criterion 5 ("the run record shows it; excluded files never reach the provider").
Output: one builder extension, one summary version, one read projection, one failure detail.

Edits Strapi source? Yes. Changes the specification? Yes (the run read and the job failure shapes). Runs Playwright? No. Regenerates `served-operations.json`? No (no route or grant changes).
Scope note: 16 files: eight Strapi sources (the prompt helper, the prompt sections, the builder and its loader, the run record and its controller, and the two job registries); the spec and the generated client; three Strapi proofs (the builder unit test, the guardrails unit test and the fake-server integration test); three web parsers with the parity guard. They change together because the v3 summary is written by the builder and read by the run record, the run read and the web parser, and the `CONTEXT_TOO_LARGE` files detail is raised by the builder and stored by both registries; a split would publish an envelope version nothing reads, or a failure detail nothing stores (accepted, as 14-06).
</objective>

## Recorded planning decisions

- **Helper** (`prompt-data.ts`): `promptDataBlock(label, attributes, value)` renders `<label k="v" …>escaped</label>` with the same `&`, `<`, `>` escaping as `promptDataTag`; `label` must match `^[a-z][a-zA-Z]*$`, attribute names `^[a-z][a-zA-Z]*$`, values integers or `^[a-z0-9-]+$` strings (anything else throws); `promptDataTag` is unchanged.
- **Builder** (`assessment-context.ts`): `RequestorDataSection` gains kind `attachments` with items `{ sequence, type, part, text, kept, available, truncated, documentId, sha256 }`; `ATTACHMENT_CONTEXT_BOUNDS = { "questionnaire-generation": 30_000, "assessment-draft": 60_000 }` over the sum of `kept`; over it, or over `CONTEXT_BOUNDS`' total with any attachment included, `AssessmentContextTooLargeError` gains `attachmentDocumentIds` (the included files) and its `safeMessage` says files hold more text than can be sent; `ContextSummaryV3 = ContextSummaryV2 & { schemaVersion: 3, attachments: { included: [{ documentId, sha256, type, part, charactersSent, charactersAvailable, truncated }], bound } }`.
- **Prompt** (`prompt-sections.ts`): inside `<requestorData>`, after the other Requestor sections, each file as `promptDataBlock("attachment", { n: sequence, type, part, truncated: "true" | "false", kept, available }, text)` whoever uploaded it; nothing for zero files.
- **Loader** (`assessment-context-loader.ts`): reads the request's attachments with `aiTextIncluded: true`, `scanStatus: "clean"`, `removedAt: null` and `aiText` not null, ordered by `uploadedAt` then `id`, with `documentId`, `fileType`, `uploaderPart`, `sha256`, `aiText`, `aiTextFacts`; never `fileName`.
- **Run record** (`ai-run-record.ts`): `parseContextSummary` accepts `schemaVersion` 1, 2 and 3 closed (v1 and v2 give `attachments: { included: [], bound }`); a malformed attachments section parses as none and fails safe; `projectAiRun` accepts resolved names. The controller (`csrm-ai-run.ts` `findRun`) loads the summary's attachment ids in one query and adds `fileName`, `requestId` and `removed` per entry; a missing record gives `fileName: null`.
- **Job failure**: both registries store `failure.attachmentDocumentIds` from the error; their analyst-only projections add `failure.attachments: [{ documentId, fileName }]` resolved in one query when the code is `CONTEXT_TOO_LARGE`.
- **Spec**: `AiRunContextSummary` gains `attachments` (`AiRunContextAttachments`, closed, items with `documentId`, `sha256`, `type`, `part`, `charactersSent`, `charactersAvailable`, `truncated`, `fileName` nullable, `requestId`, `removed`); the generation job failure component(s) gain optional `attachments` (`[{ documentId, fileName }]`).
- **Web**: `ai-assistance-schema.ts` parses `contextSummary.attachments`; `assessment-schema.ts` parses the job failure's `attachments`; both closed, registered in the parity guard.
