## Phase Goal

**As a** risk owner, **I want to** decide each of my risks, accepting it or approving its treatment, within my authority once the analyst submits the final assessment, and as a Security Analyst I want an explicit review, a colleague's approval for the most serious outcomes, and one confirmed step that releases the assessment and closes the request, **so that** every closed request carries accountable acceptance and independent review.

This plan's slice: the assigned analyst can mark the assessment reviewed and undo it, ask a named colleague to approve when a residual risk is Critical, and that colleague can approve; nobody who raised the request, owns or approves a risk, or is not the named colleague can do any of it.

## Recorded planning decisions

- **Operations** per 17.1-01 "Operations": `markReviewed`, `undoReview`, `listPeerApprovers`, `setPeerApprover`, `approveAsPeer`, added to `CSRM_ACCEPTANCE_OPERATIONS` (created here). Mark reviewed, undo, asking and approving return `{ data: AssessmentReviewState }`; the read returns `{ data: ActiveUserSummary[] }`.
- **`AssessmentReviewState`** (spec component; `projectReviewState`, which 17.1-09 embeds in the analyst detail): `{ state, reviewedAt, reviewedBy, withdrawal: { at, by, edit } | null, changed: { assessmentChanged, changedRiskNumbers, addedRiskNumbers, withdrawnRiskNumbers }, peerApproval: { state, required, reason: { threshold, riskNumbers }, approver, requestedAt, approvedAt, approvedBy } }`, people as `ActiveUserSummary`, `additionalProperties: false`.
- **Order inside each act** (`withAssessmentMutation` with `transition: "none"`; serialise, transaction, request lock then assessment lock, Phase 13's order): `assertAssignedAnalyst` (refusals `OWN_REQUEST` 403, `REQUEST_UNASSIGNED` 409, `NOT_ASSIGNED_ANALYST` 403); the guard (`ASSESSMENT_NOT_MUTABLE`, `RESPONSE_ROUND_OPEN`, and the owner rule; 17.1-06 adds `ACTOR_IS_EXECUTIVE_APPROVER` and 17.1-07 `ACCEPTANCE_ROUND_OPEN`); then the act's own rule. Approving as peer skips `assertAssignedAnalyst` and checks, in order, `OWN_REQUEST`, `NOT_PEER_APPROVER` (not the named colleague, the assignee included), `PEER_APPROVER_NOT_ELIGIBLE` (re-checked with `peerApproverEligibility`), `REVIEW_NOT_CURRENT` (the token differs or the review is not current).
- **Mark reviewed.** `loadSubmissionFacts(strapi, assessmentDocumentId)` (exported; 17.1-07's submit reuses it) builds 17.1-02's facts; `projectSubmissionReadiness(facts, { forReview: true })` not ready → 409 `REVIEW_NOT_READY` with the outstanding keys. Writes `reviewedBy`, `reviewedAt`, `reviewWithdrawnAt` and `reviewWithdrawnBy` null, and a `reviewed` entry with `reviewFingerprints`. Undo with `{ reviewedAt }` equal to the stored value: clears `reviewedBy` and `reviewedAt`, appends `undone`; otherwise `REVIEW_NOT_CURRENT`.
- **Asking.** `{ approverId | null, expectedApproverId | null }`; `expectedApproverId` must equal the stored `peerApprover` (`REVIEW_NOT_CURRENT` otherwise, the stale-view refusal); requires a current review and a policy that needs approval (`PEER_APPROVAL_REQUIRED` is never returned here; asking when not required is 409 `REVIEW_NOT_READY` with key `peerApproval`); `approverId` eligible (`PEER_APPROVER_NOT_ELIGIBLE` with the reason); writes `peerApprover`, `peerApprovalRequestedAt`, a `peer-approval-requested` entry and the notification to the colleague; a replaced colleague's unread `peer-approval-requested` is read by the `replace-peer-approver` reversal; `approverId: null` serves the Undo (clears the ask).
- **Approving.** `{ reviewedAt }`; writes `peerApprovedBy`, `peerApprovedAt`, a `peer-approval-given` entry, `peer-approval-given` to the assignee, and the `approve-as-peer` acting read of the colleague's request.
- **The read.** At most 50 by display name, `q` 1–100 after trim (Phase 13's `assignable_analysts` shape), filtered through `peerApproverEligibility`; human Security Analyst only; a non-analyst gets the policy's 403.
- **Assignment exclusions** (17-06's pattern): the named-participant input of `isEligibleAssignee`, the assignment actions and the note AI-input mark include each active risk's `executiveApprover`, refusing with `ACTOR_IS_EXECUTIVE_APPROVER` (403 or 409 as Phase 17 returns `ACTOR_IS_RISK_OWNER`).
- **Functions** per 17.1-01: `function.assessment_review.review_api` (`.api.01` POST review, `.api.02` POST review/undo) and `function.assessment_review.peer_approval_api` (`.api.01` GET peer_approvers, `.api.02` PUT peer_approver, `.api.03` POST peer_approval), `role.security_analyst` only; five literals in `HUMAN_ANALYST_ONLY_OPERATIONS` with `humanAnalystDenialMessage` lines; one design note.
