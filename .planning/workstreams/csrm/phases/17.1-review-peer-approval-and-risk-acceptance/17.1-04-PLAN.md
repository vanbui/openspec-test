## Phase Goal

**As a** risk owner, **I want to** decide each of my risks, accepting it or approving its treatment, within my authority once the analyst submits the final assessment, and as a Security Analyst I want an explicit review, a colleague's approval for the most serious outcomes, and one confirmed step that releases the assessment and closes the request, **so that** every closed request carries accountable acceptance and independent review.

This plan's slice: saving no longer records a review (UAT-040). Every content edit, by any route, withdraws a recorded review and says what changed, so the explicit "Mark reviewed" that 17.1-05 serves always attests the content that is submitted.

## Recorded planning decisions

- **The new table** (research "Explicit Review"; PATTERNS "transitionForAcceptedEdit"). `transitionForAcceptedEdit(current, edit)` keeps its name, its throw and its first row; its input loses `reviewedBy` and `releaseReady` and gains `{ reviewedAt, reviewWithdrawnAt }` and the `EditDescriptor`; it returns `{ assessmentStatus, requestStatus, withdrawReview: { at, by, entry } | null }`. Withdrawal fires on "a recorded review not yet withdrawn" (`reviewedAt` set, `reviewWithdrawnAt` null), not on "a current review", so the transition needs neither the assignee nor the rounds, and an already stale review is closed honestly by the first edit.
- **Descriptor type.** `EditDescriptor` per 17.1-01 "Envelopes", exported from `assessment-workflow.ts`. `withMutableAssessmentMutation`'s accepted-edit form requires it (a discriminated option, so omitting it is a type error); `transition: "none"` takes none.
- **Descriptors per path.** Assessment PATCH `{ target: "assessment", kind: "fields" }`; risk create `created`; risk update `fields` (and `owner` when only `riskOwner` changes; 17.1-06 adds `executive-approver`); control implementation create, update and removal `control-added`, `control-updated`, `control-removed`; withdrawal and reinstatement `withdrawn`, `reinstated`; owner nomination batch `owner` per risk (the first risk's descriptor names the batch); accepted AI units and suggested controls `ai-accepted`; response decisions that create a control implementation or change an owner `response-accepted`. Rejections, dismissals, response rejections, notes, assignment, reading and AI enqueue use `transition: "none"` or never reach the transition.
- **The withdrawal write.** In the same transaction as the edit, under the lock already held: `reviewWithdrawnAt` (the edit's clock), `reviewWithdrawnBy` (the editor's IdamBox User), a `withdrawn` entry `{ action: "withdrawn", by, at, edit }` appended to `reviewLog` (parsed with `parseReviewLog`, written back as v1); when `peerApprover` is set, the `review-withdrawn` reversal read for that colleague (19.1's `readNotificationsOnReversal`). Nothing changes the peer facts: validity is derived (17.1-02's `peerApprovalState`).
- **Interim release readiness.** `validateReleaseReadiness`'s `reviewedBy` check becomes "`reviewedAt` set and `reviewWithdrawnAt` null and `reviewedBy` set"; its key and label are unchanged until 17.1-10 replaces v1 release. Tests that release v1 call `setReviewFactsFixture` first (`git grep -ln "/release\`" apps/backend/tests` finds them; each is changed the same way and listed in the summary).
- **The editor's superseded-review notice** stops appearing because no regression happens; 17.1-13 retires it from the web.
