#### Explicit review (decision 17; ASSESS-14; UAT-040)

- **D-05:** "Mark reviewed" is the assigned analyst's act alone, through Phase 13's `assertAssignedAnalyst` (its D-10: current assignee, active, the human role, not the requestor, and from Phases 17 and 17.1 not a risk owner or executive approver), human Security Analyst only. It is offered once every submission requirement is met except the review and the peer approval (D-19; ASSESS-14 criterion 1), and refused otherwise with `REVIEW_NOT_READY` and the outstanding keys. It writes `reviewedBy`, `reviewedAt`, clears the withdrawal facts and appends a `reviewed` entry with the section fingerprints (D-08), in one transaction under the assessment's serialisation and lock. It changes no status. It is reversible: an Undo toast withdraws the review, recorded as undone by the reviewer (G-4). It is not offered while any round is open.
- **D-06:** The accepted-edit transition (`transitionForAcceptedEdit` behind `withMutableAssessmentMutation`, 06.8 D-13) is replaced, in the same place:
  - an accepted content edit moves an assessment from `draft` to `in-review`, and its request from `risk-assessment-drafted` to `under-review`, as today, and otherwise leaves both unchanged; there is no regression to `draft` and no release-readiness input;
  - it never stamps a reviewer;
  - when the review is current, the first such edit withdraws it in the same transaction: `reviewWithdrawnAt`, `reviewWithdrawnBy` (the editor) and a `withdrawn` log entry naming what was edited (the assessment's fields, or a risk by number, with the edit's kind). Later edits record nothing more in the review facts.
  - A legacy D-13-regressed row (`draft`, `under-review`, a reviewer) moves to `in-review` on its next edit, as the second row of today's table does.

  **Reversibility:** costly - every mutation path runs the transition.
- **D-07:** What withdraws a review is exactly what Phase 16 D-23 calls a content edit, and nothing else: assessment and risk field edits, risk create, withdrawal and reinstatement, control implementation create, update and removal, owner nomination (Phase 17 D-42), executive approver naming (D-15), accepted AI units and suggested controls, response decisions that create a control implementation or change an owner (Phase 17 D-42), and Phase 18's bulk edits. Rejections, dismissals, response rejections, notes, assignment changes, naming a peer approver, recall, and the participants' decisions withdraw nothing. A peer approval is valid only with the review it approved (D-14), so withdrawing the review withdraws it too (G-15: "any edit withdraws 'Mark reviewed' and a Critical peer approval").
- **D-08:** "Changed since review" (decision 17: "show what changed"; ASSESS-14 criterion 2). The `reviewed` log entry records a fingerprint of the assessment's own fields and of each active risk with its control implementations, over every analyst-editable field, from the one fingerprint module (D-37, review scope). Once the review is withdrawn, the analyst detail marks each section whose current fingerprint differs ("Assessment details", or each risk by number), plus risks added or withdrawn since, and states who withdrew the review, when and by which edit. An edit later reverted shows the withdrawal with no differing section, honestly. These are analyst-only working facts (Phase 17 D-26).
- **D-09:** A review counts for submission only while it is current: `reviewedAt` set, not withdrawn, recorded by the request's current assignee (Phase 13 D-11's recommendation, settled), and recorded after the latest acceptance round closed (G-15: the analyst "must mark the assessment reviewed again, with peer approval where needed, before round n+1"). Currency is derived from these facts at read time, so a reassignment or a recall writes nothing to the review; the readiness line says why the review no longer counts ("Reviewed by Bob before reassignment"; "Reviewed before round 1 was recalled").
- **D-10:** Legacy facts. `reviewedBy` without `reviewedAt` is v1's save-driven stamp, not a review: an assessment under review when this phase deploys reads as not reviewed, and its analyst marks it reviewed explicitly. Released assessments keep their `reviewedBy` as recorded and are not re-read. The editor's "Completed review withdrawn" notice (06.8) retires with the regression.

#### Peer approval (decision 17; G-1; G-11; ASSESS-14 criteria 3 and 4)

- **D-11:** The review policy lives in one configuration point, a pure module beside the scale (proposed `apps/backend/src/csrm/review-policy.ts`), read through one function and never inlined: peer approval is required when any active risk's residual rating is Critical (decision 17's default). Its value set is the one Phase 22 needs (`critical`, `high`, `all`, `off`); this phase ships the default in code, with no environment variable, so Phase 22 has one source to take over. The server projects "peer approval required" with its reason; the web never computes it.
- **D-12:** After "Mark reviewed", when the policy needs it, the assigned analyst asks a named colleague: a picker over the eligible-colleague read (D-03 item 2; searchable, bounded, `documentId` and `displayName` only), "Ask {name} to approve". It writes `peerApprover` and `peerApprovalRequestedAt`, appends to the log and notifies the colleague (D-54). Asking another colleague replaces the request; it is reversible, so it confirms with an Undo toast. Asking is the assigned analyst's act (`assertAssignedAnalyst`) and needs a current review.
- **D-13:** An eligible peer approver is an active IdamBox User holding the human Security Analyst role and its grants, not the service identity, and not: the request's assigned analyst or the reviewer of record (decision 17: "a second Security Analyst"); the request's requestor (G-1, `OWN_REQUEST`); a risk owner or executive approver on the assessment (G-11). The read returns exactly this set, and naming anyone else is refused with `PEER_APPROVER_NOT_ELIGIBLE`. Eligibility is checked again at approval.
- **D-14:** Only the named colleague approves (`NOT_PEER_APPROVER` for anyone else, including the assignee, whose approval would be no second pair of eyes), only while the review is current, through a confirmation that names the Critical risks and says what the approval attests (G-4: governance-significant). It writes `peerApprovedBy` and `peerApprovedAt` and appends to the log. An approval counts only for the review it approved (`peerApprovedAt` after `reviewedAt`, by the still-named colleague, still eligible), so a withdrawn or newer review, or another colleague asked, needs a fresh approval. There is no peer "reject" in this phase: a colleague who will not approve tells the assignee, who edits (withdrawing the review) or asks another colleague (deferred: peer comments).

#### Executive approvers (decision 8; G-11; G-12; G-14)

- **D-15:** The executive approver is a fact on the risk (`executiveApprover`, D-01), named by any human Security Analyst on the request, through the editable guard, while no round is open, with the people search (two characters, Phase 17 D-52 and D-55): per risk on the risk update, or "Set one executive approver for every High and Critical risk" through the batch (D-03 item 3; G-14: "or one approver for all of them in one step"). Each change is recorded in Phase 16's risk history (a field change with who, when, the old and new person; the record amends `phase-16-risk-withdrawal-and-history.md`), is a content edit (D-07), and confirms with an Undo toast, never a dialog (G-4).
- **D-16:** An eligible executive approver is an eligible person under Phase 17 D-16's one predicate (an active IdamBox User who is not the service identity) and is not: the risk's owner (G-14: "a different person from the risk owner"); the request's assigned analyst, the reviewer of record or the named peer approver (G-11). The Requestor may be named. Refusals: `EXECUTIVE_APPROVER_NOT_ELIGIBLE` with the reason detail; renaming the owner to the current approver is refused the same way (`OWNER_NOT_ELIGIBLE`, Phase 17's code).
- **D-17:** An executive approver is named only on a risk whose residual rating needs one (High or Critical under decision 8's defaults, read from the appetite, D-58); naming one on another risk is refused with `EXECUTIVE_APPROVER_NOT_NEEDED`. An edit that moves a risk's residual rating below High clears its executive approver in the same transaction, recorded in the risk history as a consequence of the rating change, and the editor says so; a risk moved to High or Critical shows "Executive approver" as outstanding in submission readiness. Participation then always means a needed approver (G-12: "Participation is current").
- **D-18:** Executive approvers are participants (G-12): Phase 17's one participant predicate gains the part `executive-approver` with their risks, so they read the whole assessment from the gate on, find it in "My risk assessments" with their part, and print and export it once released, through Phase 19's predicate (Phase 17 D-22, D-28, D-29). G-11 holds both ways: a named executive approver is refused every analyst act on that assessment (the guard, D-23, `ACTOR_IS_EXECUTIVE_APPROVER`), is never eligible as its assignee (Phase 13 D-06's predicate gains it) or its peer approver (D-13), and keeps their analyst reads; the UI withholds those controls and says why.

#### Submission (G-13; ASSESS-24 criterion 1)

- **D-19:** Submission readiness is its own server projection in the established readiness shape (scope, key, label, state, destination; Phase 10 D-35's summary), and "Submit final assessment" refuses with `SUBMISSION_NOT_READY` and the outstanding keys. It requires:
  - an assigned request, and the caller its assigned analyst (Phase 13 D-10);
  - an editable assessment, no response round open (Phase 17 D-14), no acceptance round open, no AI job running (so nothing lapses, as Phase 17 D-10);
  - the assessment's summary, overall rating and overall rationale, and at least one active risk (Phase 16 D-13's rule);
  - on every active risk: a risk statement, inherent and residual likelihood, consequence and rating, an eligible owner (Phase 17 D-16, D-17, D-20), the analyst's recommendation (D-20), and, where the rating needs one, an eligible executive approver (D-16, D-17);
  - "AI proposals reviewed" (Phase 12 D-21) and "AI proposals decided" (Phase 16 D-42); "No response round open" and "Responses decided" (Phase 17 D-14, D-41);
  - a current review (D-09) and, where the policy needs it, a valid peer approval (D-14);
  - Phase 17.2 adds "Every contest point answered".

  "Mark reviewed" reads the same projection without its last two items (D-05). v1's release readiness retires into this projection and the release-and-close readiness (D-41); research names the published fields.
- **D-20:** The analyst's recommendation (G-14: "The analyst's values pre-fill the form as a recommendation"). Per active risk, submission requires `treatmentAction` with its advice text in `treatmentPlan` (for Treat, what to do; for Accept, why the risk can be retained: Phase 12 D-11's convention), and refuses a recommended Accept on a risk with a planned control implementation (the owner could not choose it; Phase 12 and 16's 2026-10-01 confirmations). The recommended treatment owner and resolve date are optional pre-fills, because naming the business's treatment owner is the first line's decision (G-17 rejected the analyst naming every owner). `targetDate` is no longer required: no decision rests on it, and G-16 moves the due state to `treatmentResolveDate`.
- **D-21:** "Submit final assessment" is the assigned analyst's act, human Security Analyst only, behind a confirmation (G-4) that lists who decides which risks (each owner by name with their count, and each executive approver with theirs), says that editing locks until the round is recalled or the assessment is released and closed, and takes an optional message to the participants (plain text, at most 2,000 characters, never sent to the AI; Phase 17 D-09's bound). In one transaction, under the assessment's serialisation and lock, it:
  - opens acceptance round n (D-22);
  - writes Phase 17's gate fact when no round ever wrote it (Phase 17 D-11; ASSESS-22 criterion 1);
  - evaluates every standing decision against its risk's fingerprint and voids the changed ones (D-38);
  - sets each active risk's decision state (D-33);
  - writes the notifications (D-54).

#### Acceptance rounds and the lock (G-13; ASSESS-24 criteria 2, 3 and 5)

- **D-22:** An acceptance round is a row of Phase 17's round entity with `kind` `acceptance` (D-01 item 3), numbered from 1 per assessment and kind, never reused, recording opened by and when, the message, closed by and when, the outcome (`recalled`, or `completed` by release and close; 17.2's `returned`) and the outcome reason. An assessment has at most one open round of either kind: a response round cannot open while an acceptance round is open, and release-for-response readiness gains "No acceptance round open" (Phase 17's seam). Rounds never close on their own; the stage is analyst-controlled. The round is the submission record (G-15's "submissions").
- **D-23:** The lock lives in the one guard (Phase 16 D-22, which Phase 16's research names `assertAssessmentEditable({ assessment, actor })`), whose order is fixed: not editable (`ASSESSMENT_NOT_MUTABLE`), a response round open (`RESPONSE_ROUND_OPEN`), an acceptance round open (`ACCEPTANCE_ROUND_OPEN`), the actor a named risk owner (`ACTOR_IS_RISK_OWNER`) or a named executive approver (`ACTOR_IS_EXECUTIVE_APPROVER`) of that assessment. While an acceptance round is open Strapi refuses, by any route, every analyst content mutation of the assessment, its risks and their control implementations: assessment fields, risk create and update, owner and executive approver naming, control implementation create, update and removal, withdrawal and reinstatement, AI enqueue and every AI decision, response decisions, opening a response round, and Phase 18's bulk edits and imports, which go through the same guard (ASSESS-24 criterion 2). A job reaching execution or completion records its proposals as lapsed (Phase 16 D-22, D-40). **Reversibility:** costly - every mutation path reads it.
- **D-24:** Allowed while an acceptance round is open: every read; the deciders' acts (D-31); recall, and release and close, by the assigned analyst; reassignment but not unassignment (Phase 13 D-11, `ASSIGNMENT_REQUIRED`); notes (the request stays `under-review`, inside Phase 13's window); Phase 17.2's contest replies and "kept" answers. A reassignment during a round leaves the round and its decisions as they are, and the new assignee inherits recall and release and close; their release confirmation is their own attestation of the content that was reviewed and accepted.
- **D-25:** "Recall round {n}" is the assigned analyst's act, human only, with a reason (trimmed, 1 to 500 characters, Phase 16's reason parser) in its confirmation dialog, which says that deciders can no longer act in the round and that decisions already recorded stand only while their risks stay unchanged (G-4: it pauses the first line's work). In one transaction it closes the round as `recalled` with the reason, by whom and when; records nothing on any decision (they stand provisionally, D-38); and notifies the participants (D-54). The assessment is editable again, and the next submission needs a fresh review (D-09). Recall needs no unanswered-points rule; 17.2's send-back closes a round as `returned` through the same reopening path.

#### The risk decision (G-14; decision 8; ASSESS-20)

- **D-26:** Each active risk takes one decision, with authority by its residual rating whichever the choice, read from the appetite's one configuration point (D-58):

  | Residual rating | Who acts | Valid when | Review interval | Exception |
  |---|---|---|---|---|
  | Low, Moderate | the risk owner decides | the owner's decision stands | 12 months | no |
  | High | the risk owner decides, then the named executive approver approves that decision | both stand, the approval naming the owner's current decision | 6 months | no |
  | Critical | the risk owner proposes, then only the named executive approver decides | the executive approver's decision stands | 3 months | yes: `isExempted` and `exemptionReviewDate` three months out (D-43) |

  The rating is the one locked by the round (D-23). A decision is "valid" exactly when its acts stand under this table and their fingerprints match the risk (D-37); the server derives it, and the web shows it.
- **D-27:** **Accept** retains the risk with no further treatment. It needs a rationale (plain text, required; at High and Critical the field asks why treatment is not practicable, G-14), and is offered only for a risk with no planned control implementation, because the residual rating counts planned controls (G-14); otherwise Strapi refuses it with `ACCEPT_NOT_AVAILABLE`, and the form says the risk's planned control must be carried out, so Treat is the choice (Phase 17.2 adds "contest the rating" to that sentence).
- **D-28:** **Treat** commits to a treatment plan: the plan (required), a treatment owner found by name through the hardened people search (required; an eligible person under Phase 17 D-16; defaulting to the risk owner; G-17), a resolve date (`treatmentResolveDate`, required, after today and within a bound research sets) and an optional rationale. The treatment starts at `Not Started` when the decision reaches the risk at release (D-43; G-14). The form shows the resolve date as a date only: no due-soon or overdue marker (G-16's seam: Phase 20 owns the due state).
- **D-29:** **High.** The owner decides (Accept or Treat), then the named executive approver approves that exact decision: "Approve decision", with an optional comment, behind a confirmation. The approver cannot substitute another choice (that would make them the decider), and there is no decline (G-14): an approver who disagrees leaves it unapproved and, from Phase 17.2, raises a contest point. The owner may revise until release (D-35); a revision supersedes the approval, and the approver is asked again (D-54).
- **D-30:** **Critical.** The owner proposes, with the same form and rules as a decision; then only the named executive approver decides, as a time-limited exception: the form is pre-filled from the owner's proposal, the approver may decide as proposed or differently (Accept or Treat, with every field the choice needs), and the rationale is required, because an exception always records why. Once the approver has decided, the owner's proposal is closed for the round (`DECISION_NOT_AVAILABLE` for a later proposal); the approver may revise until release. The confirmation says that it records an exception reviewed within three months.
- **D-31:** Only the named person acts (G-14: "Strapi checks the caller against the risk's `riskOwner` or named executive approver, never a role"). The decision operation is a participant operation through the Requestor birthright (D-59), so no Security Analyst grant reaches it as such. Strapi refuses, with persistence unchanged:
  - a reader who is not a participant: 404 (Phase 17 D-24), including an unrelated Requestor and anyone naming a missing risk;
  - a participant who is not the risk's owner or approver (for example the Requestor on another owner's risk): 403 `DECISION_NOT_PERMITTED`, because they can read the risk;
  - any Security Analyst who is not named on the risk, the assigned analyst included (who can never be named, G-11): 403 `NOT_A_PARTICIPANT` where they take no part, `DECISION_NOT_PERMITTED` where they do;
  - the service identity, whatever it holds: 403 (a decision is a human act; Phase 17 D-32's posture);
  - an act out of sequence or no longer open (an approval before the owner decided, a proposal after the approver decided, a decision on a withdrawn risk, any act with no round open): 409 with the closed reason (`DECISION_NOT_AVAILABLE`, `RISK_WITHDRAWN`, `ACCEPTANCE_ROUND_NOT_OPEN`).

  An analyst who is named as an owner or approver (anyone but the assignee may be, Phase 17 D-20) decides from their own decision panel on the analyst page through the same operation (Phase 17 D-27, D-37), and loses their analyst acts on that assessment (D-18). The UI offers decision controls only where they are allowed.
- **D-32:** The decision record (`CsrmRiskDecision`, D-01 item 4) is one immutable row per act: the risk, the assessment and the acceptance round; the actor and their part (`risk-owner`, `executive-approver`); the act (`decide`, `propose`, `approve`, `void`); the choice; the rationale or comment; for Treat the plan, the treatment owner and the resolve date; the residual rating and the authority the act exercises (`risk-owner`, `risk-owner-with-executive-approval`, `executive-exception`); the review date on the act that completes the authority (D-36); the fingerprint and the snapshot of the decided content it was computed from (D-37); a revision number and the row it supersedes; for an approval, the decision row it approves; for a void, the rows it voids and its cause (`risk-changed` with the round, or `risk-withdrawn`); `createdAt`. A revision or a void adds a row; no row is ever updated or deleted (G-14: "nothing is overwritten"). Rows follow the assessment record's retention. **Reversibility:** one-way - the authority record the third line relies on.
- **D-33:** The risk's decision state is one server-owned current fact (D-01 item 2), so the gates, the lists, the counts and Phase 20's reminders read a column, never parse the rows (the 06.8 posture): `awaiting-owner`, `awaiting-executive`, `decided`, or none outside the acceptance flow. Submission sets it for every active risk after the voids; each act updates it in the same transaction; a recall leaves it; a withdrawal clears it (D-39); release and close leaves `decided`. A pure function derives it from the risk's rows and is the single definition; the stored fact is its cached result, written in the same transaction as the rows, and the integration tests prove they agree.
- **D-34:** Recording decisions (G-4).
  - **Preparation:** the decider prepares each of their risks' decisions in a form pre-filled with the analyst's recommendation (D-20), kept for the browser session with Phase 10's navigation guard (no lost input; Phase 13's UI-D18 posture), with nothing written until they record.
  - **Recording:** one or several prepared decisions are recorded together behind one confirmation that lists each risk, its choice, its authority and its review date, and for Accept says that the risk is retained without further treatment (G-4: accept is governance-significant).
  - **The API batch** (1 to 200 items) is all or nothing in one transaction under the assessment's serialisation and lock; every item carries the round number the decider saw (`ACCEPTANCE_ROUND_CHANGED` when it moved), and an approval carries the decision row it approves (`DECISION_CHANGED` when the owner revised meanwhile), so nothing is decided on a stale view. Repeating an applied act is a no-op.
- **D-35:** Revisions. Until release, while a round is open, a decider can revise their own act: a new row with the next revision number superseding the previous one, behind the same confirmation. An owner's revision of a High decision supersedes its approval and asks the approver again; an owner cannot revise a Critical proposal once the approver has decided (D-30). The revision trail shows under each risk for every participant and analyst (G-12: "the decisions and their history").
- **D-36:** Each completing act records its review date: its own date plus the appetite's interval for the risk's residual rating (12 months for Low and Moderate, 6 for High, 3 for Critical; decision 8), computed on the server, shown in the confirmation, and not chosen by the decider in this phase (deferred: an earlier review date). For Critical, the same date is the exemption's review date (D-43). Research fixes the calendar arithmetic and the time zone, conservatively.

#### Fingerprints and voids (G-15; ASSESS-24 criterion 4)

- **D-37:** One pure fingerprint module (proposed `apps/backend/src/csrm/decision-fingerprint.ts`) computes a SHA-256 over a canonical, versioned serialisation, in two scopes:
  - **the decision scope**, the risk's decision-relevant content: exactly what the participant projection discloses for the risk (D-47), its owner and executive approver, the analyst's recommendation, and each of its control implementations as disclosed. It excludes assessment-level fields (G-15: "A change only to assessment-level fields voids nothing"), analyst-only working fields (`comments`, `escalationDetails`, AI provenance, readiness, review facts), server-owned decision, withdrawal and exemption facts, and timestamps. This is G-15's "every field of the risk (its owner and executive approver included), its control implementations and its treatment fields", read as every field the decider reads: a decider decides on what they can see, and a change they cannot see must not void their decision or hint that a hidden field exists;
  - **the review scope** (D-08): every analyst-editable field of the assessment and of each risk with its control implementations.

  Each decision row stores its fingerprint and the snapshot it was computed from, so Phase 17.2's before-and-after view diffs the snapshot against the current content without walking the history. **Reversibility:** costly - stored fingerprints are compared across releases of the code, so the serialisation is versioned and a change of scope is a new version that never voids a decision on its own.
- **D-38:** Voids happen when round n+1 opens, never during the analyst's rework (ASSESS-24 criterion 4: "stays valid only while its risk matches"): submission compares each standing act's fingerprint with its risk's current fingerprint; each changed risk's standing acts get one `void` row, cause `risk-changed`, marked "superseded by a change in round {n+1}", kept in the history; its state returns to `awaiting-owner`; and its deciders are told to decide again (D-54). Unchanged risks keep their acts and state. A risk added since, or reinstated, starts at `awaiting-owner`.
- **D-39:** Withdrawing a risk (Phase 16, only possible between rounds) voids its standing acts at once, cause `risk-withdrawn`, and clears its state; a reinstated risk is decided again (Phase 16's seam S-6, adopted: a risk that left the assessment and came back is not the risk that was decided). No notification is sent and participants see neither the void nor the risk, because they never learn that a withdrawn risk exists (Phase 16 D-08); the analyst's view shows the void.
- **D-40:** Between rounds the analyst editor shows, per risk, whether its recorded decision will stand at resubmission or be voided ("Changed since {owner} decided in round {n}: they will decide again"), derived from the fingerprints at read time, so the analyst sees the cost of each edit before resubmitting (G-4). A decider whose decision was voided sees, in round n+1, that it no longer stands because the risk changed, and decides again; Phase 17.2 adds each changed field before and after from the stored snapshot (ASSESS-26 criterion 3).

#### Release and close (G-13; ASSESS-25)

- **D-41:** Release-and-close readiness, its own projection in the same shape: the caller the assigned analyst; an acceptance round open; every active risk `decided` with valid acts (D-26, D-33); and, from Phase 17.2, no contest point open. Strapi re-checks everything in the transaction, including that the content still matches the submitted fingerprints, and refuses with `RELEASE_NOT_READY` and the outstanding risks by number and the person each waits on (ASSESS-25 criterion 1).
- **D-42:** "Release and close" is the existing release operation in place: same URL, same Function, same `HUMAN_ANALYST_ONLY_OPERATIONS` membership, new preconditions and effects (its catalogue name and description change, D-60). It is the assigned analyst's act (`assertAssignedAnalyst`), behind a confirmation that says what it does: the assessment becomes read-only for everyone, the request closes, each risk takes its owner's decision, and the next review date (G-4; ASSESS-25 criterion 1). In one transaction under the assessment's serialisation and lock it:
  - sets the assessment `approved` with `approvedBy` (the releasing analyst), `approvalDate` and `assessmentDate`, and the request `closed` (G-13);
  - closes the acceptance round as `completed`;
  - writes each active risk's decision to its JDL fields (D-43);
  - sets `nextReviewDate` to the earliest decision review date, unless the analyst set an earlier one (G-13);
  - notifies every participant (D-54).

  It then re-reads the record and confirms the release, as today's release does. **Reversibility:** one-way - a closed request with an immutable released record.
- **D-43:** The decision reaches the risk record at release, not at decision time. Before release, the risk's treatment fields hold the analyst's recommendation and the decision lives in its rows; this keeps the first line's decision and the second line's content apart while rounds repeat, keeps fingerprints stable within a round, and leaves the analyst's rework editing their own advice. At release each active risk's fields take its valid decision:
  - **Accept:** `treatmentAction` `Accept`, `treatmentPlan` the acceptance rationale (Phase 12 D-11's convention), and `treatmentOwner`, `treatmentResolveDate` and `treatmentStatus` cleared, because an accepted risk has no treatment (G-16);
  - **Treat:** `treatmentAction` `Treat`, `treatmentPlan`, `treatmentOwner`, `treatmentResolveDate` from the decision, `treatmentStatus` `Not Started` (G-14);
  - **Critical, either choice:** `isExempted` true and `exemptionReviewDate` the decision's review date; otherwise `isExempted` false and `exemptionReviewDate` cleared.

  Each change is recorded in Phase 16's risk history with the decision as its source (a new source in the dated amendment to its record), so the analyst's recommendation stays on the record.
- **D-44:** `isExempted` and `exemptionReviewDate` record the executive's exception, so from this phase the analyst's risk update refuses them on a risk of an unreleased assessment (`DECISION_FIELD_NOT_WRITABLE`), the editor no longer offers them, and only release and close writes them (Phase 20 decides their maintenance after release). `treatmentAction`, `treatmentPlan`, `treatmentOwner`, `treatmentResolveDate` and `treatmentStatus` stay writable as the recommendation.
- **D-45:** The released predicate accepts an owning request in `approved` (released before this flow) or `closed`, in Phase 19's one place (its D-14, as widened to participants by Phase 17 D-29), so the released detail, its risks and control implementations, "My risk assessments", its rating summary, the export and the A4 report all follow (G-13; ASSESS-25 criterion 3). Every other reader that equates a released request with `approved` takes `closed` too, through that predicate where one exists; known today: `releasedAssessmentQuery` and `isReleasedAssessmentForOwner` (`assessment-scope.ts`) and `assessmentIsOpenable` (`relationship-scope.ts`). Already correct: the review queue's `RELEASED_REQUEST_STATUSES`, the request lifecycle (`closed` is terminal), the status summary, and the insight and register readers, which key on the assessment's own release triple (the throughput report's request-status rows count `approved` and `closed` separately, labelled through D-53). Research lists the rest, with a test that a closed request reads as released on every route. A request released before this flow still reads "Released" (decision 16; SC5).
- **D-46:** After release the whole assessment aggregate stays immutable (Phase 4; decision 9), the decision rows included; Phase 20 tracks the treatment from the released fields. No path writes request `approved` any more: v1's transition retires with no second release path. The catalogue's reserved `submit_for_approval` ("Transitions the assessment from draft to in-review status") and `approve` intents stay unserved, their `served-operations.json` reasons naming "Submit final assessment" and release and close, because serving either name would put a second meaning on a word the product reserves (root `CONTEXT.md`, "Submit final assessment": avoid "Submit for approval").

## Summary

Phase 17.1 turns v1's single analyst release into a second-line review, a maker-checker approval, a first-line decision per risk under delegated authority, and a closing step. Almost every rule lands on code that already exists and that Phases 12 to 19.1 reshape first: the accepted-edit transition (`transitionForAcceptedEdit`, today's save-driven reviewer stamp and D-13 regression), the one editable guard (Phase 16's `assertAssessmentEditable`), the assignment predicate (Phase 13's `assertAssignedAnalyst`), the participant predicate and round entity (Phase 17), the released predicate (Phase 19) and the notification service (Phase 19.1). The work is therefore mostly **wiring new facts into existing seams**, plus four genuinely new pieces: a pure fingerprint module, the appetite's authority table and review policy as configuration points, a pure decision-state derivation, and the `CsrmRiskDecision` record.

The code read this session settles several of the CONTEXT's delegated questions. `exemptionReviewDate` is a `datetime` while `nextReviewDate` and `treatmentResolveDate` are `date`s, so review dates are computed as UTC calendar dates with the repository's existing `addUtcMonths` (which clamps month ends) and converted to an instant only for the exemption. Request `closed` already exists in the Strapi enum, the review queue's released statuses, the status summary and the web's status mapping (neutral, lock icon); the readers that still equate "released" with request `approved` are exactly `releasedAssessmentQuery`, `isReleasedAssessmentForOwner` and `assessmentIsOpenable`, plus the lifecycle's terminal label. The current transition table *requires* a stamped reviewer on its second and third rows, so removing the stamp without rewriting the table would make every second edit a 409 (Pitfall 1). The service identity holds the Requestor birthright, so a birthright decision operation needs an explicit service-identity refusal in the service, and an analyst calling it is labelled actor `requestor` by the policy (Pitfalls 3 and 4).

**Primary recommendation:** plan the three contract-gap records and their checkpoint first, with the pure modules beside them (fingerprint, appetite functions in `risk-scale.ts`, `review-policy.ts`, decision-state derivation, review currency, eligibility predicates, the two readiness projections and the new transition table, all unit-tested against literal expectations); then the schema; then review and peer approval; then executive approvers and the G-11 guard rule; then rounds, the lock, recall and voids; then decisions; then release and close with the released predicate in every reader; then the reads; then the UI; then the fixtures, the journey's second slice, the second spec and the gate. Every new mutation runs inside one `withAssessmentMutation` (serialise, transaction, row lock, guard), and every derived state the lists need (the risk's decision state) is a cached column written in the same transaction as the rows it derives from.

### Review dates and the time zone (D-36)

- **Rule:** a completing act's review date is `addUtcMonths(utcToday(now), reviewIntervalMonths(rating))`, computed once on the server in the act's transaction from the same clock reading that stamps `recordedAt`.
- **Why UTC calendar dates:** the repository's insights already define "today" as the UTC calendar date with every rule taking it explicitly (`utc-date.ts` header: "A calendar date is a `YYYY-MM-DD` string that names one UTC day") [VERIFIED: utc-date.ts:1-8], and Phase 20's reminders and Phase 11's due states compare `date` columns with that `today`. A second convention would make a review "due" a day early or late depending on the reader.
- **Conservatively:** `addUtcMonths` clamps a missing month end to the last day (31 August + 6 months = 28 or 29 February), never rolling forward into the next month [VERIFIED: utc-date.ts:113-122]. For the operator's zone (east of UTC) the UTC date is never later than the local date, so the review date is never later than the local calendar would give.
- **The exemption:** `exemptionReviewDate` is a `datetime`, so release writes `utcDateToInstant(reviewDate).toISOString()` (UTC midnight). Every reader shows it by its UTC calendar date (`toISOString().slice(0, 10)`), never converted to the viewer's zone, so it reads the same date as the decision's review date everywhere (Pitfall 5).
- **The assessment's next review date** (`date`): at release, `min(analyst's nextReviewDate if set, earliest completing act's reviewDate over active risks)`, compared as `YYYY-MM-DD` strings.
- **Display:** the web shows review and resolve dates as dates (X-3's date form), never as instants.

## Peer Approval (D-11 to D-14)

- **Validity:** `peerApprovedBy` equals the named `peerApprover`, `peerApprovedAt > reviewedAt`, the review current, the approver still eligible. Recommendation: also bind the *ask* to the review (`peerApprovalRequestedAt ≥ reviewedAt`), so a fresh review means asking again, which re-sends `peer-approval-requested`; the UI offers "Ask {name} again" in one step (Open Question 5).
- **Reversal reads (19.1 D-21):** asking another colleague, or the review being withdrawn, reads the former colleague's unread `peer-approval-requested`, because the work no longer waits for them.

## Executive Approvers (D-15 to D-18)

- **Naming** goes through the editable guard (so it is refused during any round), is a content edit (withdraws the review), records a risk-history field change, and is refused on a rating that needs none (`EXECUTIVE_APPROVER_NOT_NEEDED`) and for ineligible people (`EXECUTIVE_APPROVER_NOT_ELIGIBLE`, with a reason detail: `is-risk-owner`, `is-assigned-analyst`, `is-reviewer`, `is-peer-approver`, `inactive`, `service-identity`).
- **Rating-driven clearing (D-17)** belongs in the one inner risk update (`updateRiskInMutation`), because every path that changes `residualRating` passes through it: the editor, the register's PATCH, Phase 12's and 16's AI unit acceptance and Phase 17's residual reassessment. Recorded as a history consequence of the rating change.
- **G-11 both ways (D-18):** the guard gains `ACTOR_IS_EXECUTIVE_APPROVER` after Phase 17's `ACTOR_IS_RISK_OWNER`; Phase 13's `isEligibleAssignee` and this phase's peer eligibility exclude named approvers; Phase 17's participation predicate gains the part `executive-approver` with the approver's risks.

## Acceptance Rounds, the Lock and Recall (D-21 to D-25)

**Submit, in one serialised transaction:** re-evaluate submission readiness (refuse `SUBMISSION_NOT_READY` with keys) → compute the next number as `max(number) + 1` for kind `acceptance` under the assessment lock → create the round → write Phase 17's gate fact when unset → for each standing act, compare its fingerprint (under its own version) with the risk's current fingerprint; one `void` row per changed risk (cause `risk-changed`, `voidRoundNumber` n+1) → derive and write every active risk's `acceptanceState` → notifications (one per recipient: `decision-voided` replaces `acceptance-requested` for a decider who had acts voided).

**The lock's route inventory** (every one must call the guard; a static test in the Phase 16 style proves each handler reaches it):

|---|---|

Allowed during an open round (D-24): reads, decisions, recall, release and close, reassignment (unassignment refused with Phase 13's `ASSIGNMENT_REQUIRED`), notes, and Phase 17.2's replies.

## The Risk Decision (D-26 to D-36)

**Act sequencing per rating** (the pure module the service and the projections share):

| Rating | Allowed acts, in order | State after |
|---|---|---|
| Low, Moderate | owner `decide` (revisable) | `decided` |
| High | owner `decide` → executive `approve` (naming the owner's standing decide); an owner revision supersedes the approval | `awaiting-executive` after the owner; `decided` after the approval; back to `awaiting-executive` on revision |
| Critical | owner `propose` (revisable until the executive decides) → executive `decide` (pre-filled, revisable) | `awaiting-executive` after the proposal; `decided` after the executive's decision |

- **Validity** (single definition, used by state, readiness and release): every act of the risk's required sequence is standing (not superseded, not voided), its fingerprint equals the risk's current fingerprint under its version, and the approval names the owner's standing decision.
- **Refusal order in the service** (D-31), with persistence deep-equal: not a participant and not a Security Analyst → 404; the service identity → 403; a Security Analyst not named on the risk → 403 `NOT_A_PARTICIPANT` when they take no part, `DECISION_NOT_PERMITTED` when they do; a participant not named on that risk → 403 `DECISION_NOT_PERMITTED`; then the 409s (`ACCEPTANCE_ROUND_NOT_OPEN`, `ACCEPTANCE_ROUND_CHANGED`, `RISK_WITHDRAWN`, `DECISION_NOT_AVAILABLE`, `DECISION_CHANGED`, `ACCEPT_NOT_AVAILABLE`). A missing risk id in the batch is 404 for the whole batch (Phase 16's batch rule).
- **Accept with a planned control** (`controlStatus === "Planned"` on any of the risk's control implementations) is refused with `ACCEPT_NOT_AVAILABLE`, for the owner and for the Critical executive alike.
- **Treatment owner** must be an eligible person (19.1's predicate); it defaults to the risk owner in the form, never on the server.

## Fingerprints and Voids (D-37 to D-40)

- **One module, two scopes**, `apps/backend/src/csrm/decision-fingerprint.ts`: `decisionFingerprint(risk, version?)` and `reviewFingerprints(assessment, risks)`. Each scope is an explicit **frozen field allowlist per version**; a unit test asserts that the v1 decision allowlist equals the participant projection's risk and control-implementation allowlists today, so a later projection change fails the test and forces a deliberate v2 instead of silently voiding every decision at the next submission (Pitfall 6).
- **Decision scope v1:** the risk fields the participant projection discloses (Phase 10 D-34's released fields plus issue statement, cause, impact and both rating rationales, per the Orchestrator Confirmation), `riskOwner` and `executiveApprover` as `documentId`s, the recommendation (`treatmentAction`, `treatmentPlan`, `treatmentOwner`, `treatmentResolveDate`), and each control implementation as disclosed (control `documentId`, status, owner, due date, effectiveness), sorted by `documentId`. Excludes assessment-level fields, `comments`, `escalationDetails`, provenance, review and decision facts, withdrawal and exemption facts, timestamps.
- **Canonical form:** an object with sorted keys; absent and `null` both serialised as `null`; strings as stored (the write parsers already trim); relations as `documentId` strings; dates as `YYYY-MM-DD`; arrays sorted by a stable key; `JSON.stringify` of that object; `sha256:` + lowercase hex.
- **Voids** happen only at submission (D-38) and at withdrawal (D-39, cause `risk-withdrawn`, no notification, invisible to participants). Between rounds the analyst detail computes "will stand or be voided" per risk from the same comparison (D-40).

## Release and Close (D-41 to D-46)

One serialised transaction: assigned analyst (`assertAssignedAnalyst`) → the round is open and is the one the caller saw → release-and-close readiness re-evaluated (every active risk `decided` with valid acts, fingerprints matching) → assessment `approved`, `approvedBy`, `approvalDate`, `assessmentDate`; request `closed` → round `completed` → each active risk's JDL fields from its valid decision (Accept: `treatmentAction` Accept, `treatmentPlan` = rationale, treatment owner, resolve date and status cleared; Treat: plan, owner, resolve date, `treatmentStatus` `Not Started`; Critical: `isExempted` true and `exemptionReviewDate` = the review date's UTC midnight; otherwise `isExempted` false and the date cleared), each recorded in Phase 16's risk history with source `decision` → `nextReviewDate` → notifications. Then re-read and confirm with `isReleased`, as today.

### Pattern 1: Pure rule, cached fact, one writer
**What:** the decision state is computed by one pure function from the risk's rows and rating, and stored in `acceptanceState` by the only code paths that change those inputs, in the same transaction. **When:** any derived value that lists, counts or SQL need (Phase 17's response status precedent). **Proof:** an integration helper recomputes the state from the rows after every test path and asserts equality.

### Pattern 2: Allowed actions from the operation's own predicates
**What:** the analyst detail's `actions` array is built by calling the same predicate functions the operations call (`assertAssignedAnalyst`, readiness, eligibility, the guard) in a non-throwing mode, returning `{ action, allowed, reason? }`. **Precedent:** Phase 13's `allowedAssignmentActions` [CITED: 13 plan "Item fields"].

### Pattern 3: Compare-and-set on every governance act
Undo carries `reviewedAt`; asking carries `expectedApproverId`; approving carries `reviewedAt`; decisions carry `roundNumber`, `approvesDecisionId` and `revisesDecisionId`; release carries `roundNumber` and `lastDecisionId`. A stale view gets a closed 409 and the UI refreshes with the prepared input kept.

### Anti-Patterns to Avoid
- **Gates that parse logs:** `reviewLog` narrates; gates read `reviewedAt`, `reviewWithdrawnAt`, the peer facts and `acceptanceState` (06.8).
- **Role checks for deciders:** the decision operation checks the risk's named people, never a role (G-14).
- **A second release path:** the existing release operation becomes release and close in place; no path writes request `approved` (D-46).
- **Computing authority, intervals or the threshold in the web:** the server projects them (D-58).
- **Nested serialisation:** inner functions never call `serializeAssessmentMutation` again (Phase 16 Pitfall 1: a hang to the 600 s timeout).

## Common Pitfalls

### Pitfall 1: The transition table still requires a reviewer
**What goes wrong:** removing the stamp leaves rows two and three requiring `isRelation(current.reviewedBy)`, so an `in-review` assessment with no reviewer refuses every edit with 409. **How to avoid:** rewrite the table as above, with a unit test per row including "in-review, under-review, no reviewer → in-review". **Warning signs:** "CSRM assessment edit transition is invalid." on a second edit.

### Pitfall 2: A content path that skips the withdrawal
**What goes wrong:** a mutation path writes content with transition `none` (or outside the wrapper), so the review stays current over changed content. **How to avoid:** the edit descriptor is a required argument of every inner content function; an integration test per D-07 item proves withdrawal, and one per non-content act proves none.

### Pitfall 3: The service identity reaches a birthright operation
**What goes wrong:** every identity holds the Requestor birthright (`loadEffectiveGrants`), so the agent reaches `risk_decisions` through the policy. **How to avoid:** the service refuses an identity holding `Security Analyst Agent` with 403 before any record read; a matrix row and an integration test prove it.

### Pitfall 4: Analysts arrive as actor "requestor"
**What goes wrong:** the policy sets `assessmentRequestActor` to `requestor` when the grant comes from the birthright, so an analyst calling the decision operation looks like a Requestor and gets 404, where D-31 needs 403 `NOT_A_PARTICIPANT`. **How to avoid:** the service computes "holds the human analyst grant" separately (Phase 17 D-24 needs the same; reuse its helper).

### Pitfall 5: The exemption date shifts by a day
**What goes wrong:** `exemptionReviewDate` is a datetime; showing UTC midnight in a viewer zone west of UTC shows the previous day. **How to avoid:** write UTC midnight, read and display its UTC date; Phase 20's reminders compare UTC dates.

### Pitfall 6: Fingerprints that change on their own
**What goes wrong:** deriving the field list from the live projection constant, key-order differences, `undefined` vs `null`, unsorted control implementations, or a relation sometimes populated and sometimes an id, make an unchanged risk look changed and void decisions. **How to avoid:** frozen per-version allowlists, the canonical form above, a normaliser that maps populated relations to `documentId`, literal golden hashes in unit tests, and a test that loading the same risk two ways gives one fingerprint.

### Pitfall 7: Stored state drifts from the rows
**How to avoid:** one derivation, called by every writer (submit, decision batch, withdrawal, reinstatement, recall leaves it, release leaves it); an assertion helper in the integration suite.

### Pitfall 8: A route that escapes the lock
**How to avoid:** the route inventory above, a static test that every mutating handler of the aggregate reaches `assertAssessmentEditable`, and an integration test per route during an open round expecting `ACCEPTANCE_ROUND_OPEN` with persistence deep-equal.

### Pitfall 9: Peer eligibility checked only at naming
**What goes wrong:** the colleague becomes a risk owner or approver between asking and approving. **How to avoid:** re-check at approval (D-13) and in the validity used by readiness.

### Pitfall 10: Concurrent writes inside one transaction on PostgreSQL
**What goes wrong:** `Promise.all` of Document Service calls on one transaction connection is deprecated in node-postgres and throws in pg 9 [CITED: github.com/strapi/strapi/issues/27645 title]. **How to avoid:** sequential awaits inside every transaction (the existing workflow already does).

### Pitfall 11: The holder keyed only on the step
**How to avoid:** follow Phase 17's fact-based holder; the acceptance holder needs the pending-act predicate.

### Pitfall 12: SQL and oracle diverge
**How to avoid:** change `review-queue-repository.ts`, `selectReviewQueueBucket`, `applyRequestHolder` and the `my_risk_assessments` filters with their equivalence fixtures in the same plan (Phase 7 D-21, D-30).

### Pitfall 13: Closed reads "Assessment released"
**What goes wrong:** today's lifecycle maps `closed` to the "Assessment released" step. **How to avoid:** the `closed` terminal key and a test per terminal state.

### Pitfall 14: An unedited or legacy-regressed assessment is still `draft`
**What goes wrong:** release requires assessment `in-review` and request `under-review`; an assessment never content-edited (or a D-13-regressed row) is `draft`. **How to avoid:** keep `assessmentStatus` in submission readiness with a label that says an edit is needed; owner nomination (a content edit, Phase 17) normally moves it first.

### Pitfall 15: Changing the released query but not the in-memory guard
**What goes wrong:** `releasedAssessmentQuery` and `isReleasedAssessmentForOwner` must both accept `closed`; changing one returns 404 for closed requests. **How to avoid:** route both through Phase 19's predicate; the walk-every-route test.

### Pitfall 16: Release side effects outside the transaction
**How to avoid:** risk fields, history rows, round outcome, next review date and notifications all inside the one transaction; a forced failure after the last write leaves everything unchanged (integration test).

### Pitfall 17: Visible "Accept" outside a decider's control
**What goes wrong:** the analyst's recommendation select shows "Accept". **How to avoid:** the UI-SPEC words the recommendation ("Recommend accepting", "Recommend treatment" or similar); a copy guard test (Phase 12's confirmation, D-66).

### Pitfall 18: The approver not cleared on every rating path
**How to avoid:** clear in `updateRiskInMutation`, the one inner risk update every path uses.

### Pitfall 19: The Critical approver deciding before a proposal
**How to avoid:** the sequence module refuses `decide` by the executive on Critical until an owner proposal stands (`DECISION_NOT_AVAILABLE`), which keeps "the owner proposes, then the approver decides".

### Pitfall 20: Idempotency mistaken for revision
**How to avoid:** a byte-equal repeat is `unchanged`; any difference with `revisesDecisionId` is a revision; a difference without it is `DECISION_CHANGED`.

### Pitfall 21: Phase 18 bulk naming bypassing eligibility
**How to avoid:** expose the eligibility predicates from one module so Phase 18 imports them.

### Pitfall 22: The journey's state lost between Playwright projects
**What goes wrong:** sharing module-level state across `describe.serial` tests breaks across the two projects. **How to avoid:** one test per project, slices as functions over a context.

### Pitfall 23: Duplicate round numbers
**How to avoid:** compute `max + 1` under the assessment row lock inside the transaction.

### Pitfall 24: The inventory regenerated with servers running
**How to avoid:** `served-operations:write` only with ports 1337 and 3000 free; `cmp` the catalogue copies.

### Pitfall 25: A notification destination the web parser rejects
**How to avoid:** add the decision view's path shape to 19.1's destination parser in the plan that adds the kinds.

### Pitfall 26: The release confirmation and the last revision race
**How to avoid:** release carries `lastDecisionId`; a newer row refuses with `DECISION_CHANGED` and the dialog refreshes.

import { createHash } from "node:crypto";

const DECISION_SCOPE_V1 = Object.freeze({
  risk: Object.freeze([/* the participant projection's risk allowlist today, frozen here */]),
  people: Object.freeze(["riskOwner", "executiveApprover", "treatmentOwner"]),

function canonical(value: unknown): unknown {
  if (value === undefined || value === null) return null;
  if (Array.isArray(value)) return value.map(canonical);
  if (typeof value === "object") {
    const record = value as Record<string, unknown>;
    if (typeof record.documentId === "string") return record.documentId; // a populated relation
    return Object.fromEntries(Object.keys(record).sort().map((key) => [key, canonical(record[key])]));
  }
  return value;
}

export function fingerprintOf(snapshot: Record<string, unknown>): string {
  return `sha256:${createHash("sha256").update(JSON.stringify(canonical(snapshot))).digest("hex")}`;
}
