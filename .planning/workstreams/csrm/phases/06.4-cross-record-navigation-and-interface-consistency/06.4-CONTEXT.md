# Phase 06.4 Context: Cross-Record Navigation and Interface Consistency

This phase makes the workflow read as one product. Nothing here is a new
capability: every record it links to already exists, and every rule it enforces
is already enforced in Strapi. The work is to stop making people navigate by
memory, and to stop the same control behaving differently on different screens.

The decisions below are locked. They were established by reading the code, not
by inference, and each one records where the gap actually is.

## D-01 — Only the identifier or title opens a record

**Located.** Redundant row-level open controls exist in exactly two files:

- `apps/web/src/features/assessments/assessment-list.tsx` — both the card
  variant and the table variant render `Open {assessmentNumber}` as a button-styled
  `Link` in a trailing cell.
- `apps/web/src/features/assessments/released-assessment.tsx` — the same
  `Open {assessmentNumber}` button on each released card.

`request-table.tsx`, `questionnaire-list.tsx` and `questionnaire-review-list.tsx`
already open from the record itself; their button-styled links are page-level
actions ("New request") and empty-state actions ("Return to workspace"), which
stay exactly as they are. The scope of this criterion is therefore small and
specific — do not sweep every `buttonVariants` link in the codebase.

The replacement is the identifier or title as the link, with the whole row
responding to hover and the link remaining the single keyboard target. The
affordance has to be evident without hovering, so the link needs a resting
visual treatment, not hover-only underlining.

## D-02 — A link to a related record is capability-checked and record-scoped

A link appears only where the signed-in actor is authorised to open that record,
and Strapi still refuses on the way in. Two failure modes to avoid, both of which
this project has already produced once:

- Do not infer authorisation from the presence of data in a payload. Use the
  established capability adapter, and keep the server as the authority.
- Do not render a link that leads to a permission-denied screen. A link the
  actor cannot follow is worse than no link, because it reads as a fault.

## D-03 — The assessment tile reports contextual Risk counts

The request's assessment tile shows how many contextual Risks sit at each rating
— Low, Moderate, High, Critical — and opens the assessment.

`projectAssessmentRatingSummary` and the `/v1/my_risk_assessments/rating_summary`
route already establish how a rating tally is projected and served. Follow that
shape rather than inventing a second one, and keep the count bounded and
server-computed; do not fetch the Risks and count them in the browser.

Counts carry the same non-colour-only treatment as every other risk signal in
this product: the rating is named in text, not conveyed by colour alone.

## D-04 — Release readiness names the record, and shows the whole requirement set

**Located, and this is the substantive correctness item in the phase.**

The server already knows precisely what is missing.
`validateReleaseReadiness` in
`apps/strapi/src/api/csrm-assessment/services/assessment-workflow.ts` emits
paths such as `risks[3].riskOwner`.

The client throws that away. `releaseReadinessPresentation` in
`apps/web/src/features/assessments/assessment-domain.ts` matches
`/^risks\[(\d+)]\.(.+)$/` and then uses only the field name, so the analyst is
told "Risk owner" with no indication of *which* Risk, and every risk-scoped item
links to the same `#identified-risks` anchor.

Two things must change together:

1. The outstanding item must identify the specific record — the Risk's own
   number, not an array index, which is meaningless to a person and unstable
   across reordering. An index is an implementation detail of the validator; the
   interface must speak in the identifiers the product uses everywhere else.
2. The screen must present the **complete** requirement set with each
   requirement's state, not only the unmet ones. An analyst needs to see what
   release demands before starting, which is impossible when the list only
   appears as things go wrong and shrinks as they are fixed.

If carrying the identifier requires the projection to change shape, that is a
contract change and follows D-07. It is not a datamodel change.

## D-05 — The reversal control is the same control everywhere

**Located.** "Return to draft" exists in four places and is inconsistent in three
ways:

- `assessment-detail.tsx:84` — `<Button variant="outline">`, no wrapper.
- `questionnaire-detail.tsx:52` — `<Button variant="outline">`, wrapped in
  `<div className="mb-6">`.
- `questionnaire-review.tsx:79` — a raw `<button className={buttonVariants({ variant: 'outline' })}>`
  rather than the `Button` component.
- `request-form.tsx:275` — `<Button variant="outline">`, no wrapper.

All four must use the standard primary treatment and sit in the same position on
the Questionnaire and the Request detail screens. The raw `<button>` is a latent
divergence and should become the shared component regardless.

The reversal confirmation's reason field must occupy the full dialog width. The
field is rendered in `confirm-dialog.tsx` inside a `grid gap-2` and carries no
width constraint of its own, so the cause is upstream of the textarea — verify
in the browser at both mobile and desktop widths before changing anything, and
fix the actual constraint rather than adding a width to the textarea.

## D-06 — No datamodel change is expected

Every record, relation and field this phase needs already exists. This is
navigation, projection and presentation over records the product already stores.
If a schema change appears unavoidable, stop and justify it in
`docs/contract-gaps/` before making it.

## D-07 — Response changes are registered with the parity guard

Phase 06.3 established `contract-response-parity.test.ts` and the
`responseParserModule` inventory: every client response parser is declared and
checked against the published OpenAPI shape, in three modes, including every
nullable field served as null. That guard exists because four defects across
06.1–06.3 shared one shape — the server succeeded and the client reported
failure because a closed schema and the payload had drifted.

Any response this phase adds or changes must be declared in that inventory, and
any place the client is deliberately narrower than a shared contract component
must declare the path and the reason. A new response that is not registered is
an incomplete change.

Route, catalogue and contract parity rules are unchanged: both catalogue copies
byte-identical, `docs/references/specification.json` updated, and web
declarations regenerated with `pnpm --filter @csrm/web api:generate`. Never
hand-edit generated output.

## Verification notes carried forward

- The Strapi integration suite runs one file at a time. Concurrent execution
  deadlocks, and the runner now carries a real per-test timeout so a future
  deadlock fails readably instead of hanging.
- Never run the web and Strapi suites concurrently: the heavy component tests
  starve and fail as timeouts rather than on any assertion.
- A Radix popover or dialog portals outside the element that triggered it, so a
  test scoped to the trigger's container will not find it, and a page-wide
  `.first()` match can resolve to the dialog's own control once the page behind
  it is inert.
