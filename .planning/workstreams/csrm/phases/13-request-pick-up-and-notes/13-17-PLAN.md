## Phase Goal

**As a** Security Analyst, **I want to** pick up a request and exchange notes with the Requestor on it, **so that** ownership is clear and new information has a home at any point.

This plan's slice: the server tells an analyst, for the questionnaire and for the assessment, which notes changed the AI inputs since that record was last generated, and the questionnaire and assessment reads say who holds the request and how many notes it has.

<objective>
Implement D-29's "AI inputs changed" signal in one module and serve it on the analyst's request read and in the `generation` block of the questionnaire and assessment reads; add the assignee and the notes figures to those reads' request summary (D-16, D-25).

Purpose: success criterion 5 ("which Phases 12, 15 and 16 read"); REQ-08 criterion 1 on the questionnaire and assessment pages.
Output: one signal module, three read changes, their parsers.

Edits Strapi source? Yes. Changes the specification? Yes. Runs Playwright? No. Regenerates `served-operations.json`? No.
</objective>

## Recorded planning decisions

- **Module** `apps/backend/src/csrm/ai/ai-inputs-signal.ts`: `CONTEXT_WIDE_AI_OPERATIONS = ["questionnaire-generation", "assessment-draft"]` (a doc comment says Phase 15's questionnaire proposals and Phase 16's "Suggest more risks" join it and risk-scoped operations never do); the pure `aiInputsChanged({ markedNotes, baseline })` where `baseline` is `{ kind: "run", includedNoteIds }`, `{ kind: "generated-date", at }` or `null`, returning `null` for no baseline, otherwise `{ count, notes: [{ documentId, part, sequence, postedAt, change: "marked" | "unmarked" }] }` (sorted by sequence) — with a run, `marked` = marked and not included, `unmarked` = included and no longer marked; with a generated date, `marked` = currently marked notes whose latest marking event in `aiInputLog` is after it; and the async `loadAiInputsChanged(strapi, { requestDocumentId, baselineRunId, generatedDate })`, which reads the baseline run, uses it only when it is completed and its operation is in `CONTEXT_WIDE_AI_OPERATIONS`, parses its summary with `parseContextSummary`, falls back to `generatedDate` when there is no such run, and reads the marked notes. Each target keeps its own run resolver, the one its `generation.runId` already uses, so the signal's baseline is always the run the read names: the questionnaire's baseline run is the one `latestCompletedGenerationRun(strapi, questionnaireId)` resolves (`questionnaire-scope.ts`, a query over runs for operation `questionnaire-generation`; it may be widened to take the context-wide operations that write a questionnaire, and only this resolver may be widened); the assessment's baseline run is the one its `aiProvenance` names, `parseAssessmentAiProvenance(document.aiProvenance)?.runId` (`csrm-assessment/services/ai-provenance.ts`), the same `runId` that `projectAssessmentGenerationFacts` serves, never a query over runs. `projectAssessmentGenerationFacts` stays synchronous: the assessment controller (and the request `findOne` for `aiInputs.assessment`) awaits `loadAiInputsChanged` and hands the result to the projection.
- **Shapes.** Spec component `AiInputsChanged` = `{ count: integer, notes: AiInputsChangedNote[] (maxItems 500) }`, `AiInputsChangedNote` = `{ documentId, part, sequence, postedAt, change }`, closed. `AiGenerationFacts` gains `aiInputsChanged: AiInputsChanged | null` (required). The request read gains `aiInputs: { questionnaire: AiInputsChanged | null, assessment: AiInputsChanged | null } | null`, null for any viewer who is not a human analyst. The analyst questionnaire and assessment reads' request summary (`QuestionnaireAssessmentRequestAvailable` and `AssessmentRequestSummary`) gain `assignment: { assignee: ActiveUserSummary | null, pickUp: "allowed" | "own-request" | "not-offered" } | null` and `notes: { total: integer, unread: integer } | null`, null on a Requestor's read.
- **Web.** The web parser of `AiGenerationFacts` is the shared `.strict()` `aiGenerationFactsSchema` in `features/ai-assistance/ai-generation-facts-schema.ts` (`questionnaire-schema.ts` re-exports it and `assessment-schema.ts` imports it): it gains the required, nullable `aiInputsChanged`, closed, with the `AiInputsChanged` parser beside it, which `request-schema.ts` reuses for `aiInputs`; the boundary guard's entry for the module (`aiAssistanceZodModules` in `src/lib/performance/zod-client-boundary.test.ts`) names the request schema among its importers; every web test that parses a served `generation` block through it (`questionnaire-schema.test.ts`, `assessment-service.test.ts`, `released-assessment-route.test.ts`) gains `aiInputsChanged`. `questionnaire-schema.ts`, `assessment-schema.ts` and `request-schema.ts` parse the request summary fields and `aiInputs` closed; `ai-assistance-domain.ts` (zod-free) exports `type AiInputsChanged` and gains nothing else: it is in `/app/risks/{documentId}`'s client graph (through `risk-editor.tsx`), which had 406 bytes of headroom under its 300,000-byte budget at Phase 12's final gate, so its Phase 13 change is a type export only, erased at build, with no function, constant, string or runtime import; `request-domain.ts` exports the request summary fields' types; `setNoteAiInputAction` (13-06) also revalidates `/app/review/questionnaires/{questionnaireId}` and `/app/review/assessments/{assessmentId}` paths by layout (`revalidatePath('/app/review/questionnaires', 'layout')` and the assessments equivalent).
