## Phase Goal

**As a** Security Analyst, **I want to** pick up a request and exchange notes with the Requestor on it, **so that** ownership is clear and new information has a home at any point.

This plan's slice: the notes a Security Analyst marks reach the AI as untrusted data, every generation records which notes it used without their text, and nothing unmarked ever leaves Strapi.

## Recorded planning decisions

- **Section.** Phase 12's extension point already declares the kind: `RequestorDataSection = { kind: "request-fields" | "answers" | "notes" | "attachment-text"; values: PromptValue[] }` (`assessment-context.ts:11` at `7d889a3`). This plan reuses that `notes` kind and its `values: PromptValue[]` shape; neither the type nor the shared renderer changes. The structured notes sit beside the section: `type ContextNote = { documentId: string; part: "requestor" | "security-analyst"; sequence: number; postedAt: string; body: string }` and `AssessmentContextRecords.notes?: ContextNote[]`, which feed the bound and the v2 summary. `buildAssessmentContext` sorts them by `sequence` and appends one `{ kind: "notes", values }` section as the last Requestor data section (after the request fields and, for the draft, the answers), whose values are, per note, three `PromptValue`s with constant labels, the `answer.*` precedent: `{ label: "note.part", value: part }`, `{ label: "note.sequence", value: String(sequence) }`, `{ label: "note.body", value: body }`. `CONTEXT_BOUNDS.markedNotes = 50`. `loadAssessmentContextRecords` reads the request's notes with `changesAiInputs: true` into `records.notes` (through the Document Service on `api::csrm-request-note.csrm-request-note`, filtered by the request's documentId, fields `documentId`, `authorPart`, `sequence`, `postedAt`, `body`, sorted `sequence:asc`, limit 51).
- **Rendering.** The shared `renderRequestorDataBlock` (`prompt-sections.ts`) renders the section as it renders every section: `<sectionKind>notes</sectionKind>`, then per note `<field>note.part</field><value>requestor</value>`, `<field>note.sequence</field><value>1</value>` and `<field>note.body</field><value>…</value>`, each tag written by `promptDataTag`, which escapes `&`, `<` and `>`. So each note's text is its own delimited, escaped `<value>` inside the untrusted `<requestorData>` block, labelled only by its part (the closed enum) and sequence (a server integer) under constant field labels; the analyst's notes go in the same untrusted block (they can quote the Requestor). 13-RESEARCH's `<note part="…" n="…">` attribute form is not used: `promptDataTag` writes no attributes, and this plan never weakens it.
- **Bounds.** More than 50 marked notes, or a user prompt over the operation's budget, throws `AssessmentContextTooLargeError` before the run is created, with `safeMessage` `The AI context is too large. {n} notes are marked as changing the AI inputs (notes {sequences}); unmark some and try again.` when notes are marked, and the existing message otherwise. Note text is never truncated (06.7 D-10).
- **Summary v2.** `ContextSummaryV2` = v1's fields with `schemaVersion: 2` and `notes: { included: [{ documentId, part, sequence, postedAt, characters }], marked: number, bound: 50 }`; `buildAssessmentContext` always emits v2. `parseContextSummary` accepts v1 (projected with `notes: { included: [], marked: 0, bound: 50 }`) and v2, closed, failing safe to null; the 64 KB bound still applies.
- **Spec and web.** `AiRunContextSummary` gains `schemaVersion` (enum `1`, `2`) and `notes` (`AiRunContextNotes`, closed) as required in the projection (the server projects v1 as described); `ai-assistance-schema.ts` parses it.
