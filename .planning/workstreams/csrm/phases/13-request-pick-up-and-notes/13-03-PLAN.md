This plan's slice: a Security Analyst can pick up, assign, reassign or return a submitted request through Strapi's one assignment operation, safely under concurrency and separation of duties, reachable from the web's typed layer.

## Recorded planning decisions

- **Lock module.** `request-lock.ts` exports `withRequestLock<T>(strapi: RequestLockStrapi, requestDocumentId: string, work: (trx: unknown) => Promise<T>): Promise<T>`: one module-level tail map, then `strapi.db.transaction`, then `SELECT id … WHERE documentId = ? FOR UPDATE` through `strapi.db.queryBuilder(UID)` with `.transacting(trx)` (the query shape of `lockRow` in `questionnaire-row-locks.ts`), then `work(trx)`. `revertRequestToDraft` switches to it; `serializeRequestRevert`, `lockRequest` and `requestRevertTails` are deleted.
- **Lock order** (CR-101). Three other paths lock the same request row `FOR UPDATE`: `lockRequestAndQuestionnaire` and `lockQuestionnaireAndRequest` (`apps/backend/src/api/csrm-questionnaire/services/questionnaire-row-locks.ts`; generation, governance and answers; the request row, then the questionnaire row) and `lockAssessmentRequest` (`apps/backend/src/api/csrm-assessment/services/assessment-workflow.ts`; the draft). `withRequestLock` takes only the request row, as the first row of its transaction. It is never called inside one of those transactions, and its `work` never calls one of them or `withRequestLock` again, so every transaction that locks the request row takes it first and none waits for it while holding a questionnaire row. `request-lock.ts` imports neither module; a doc comment states this order and names the three paths.
- **People.** `request-people.ts` exports `PERSON_FIELDS = ["documentId", "displayName"]`, `projectPerson(value): { documentId: string; displayName: string } | null` and `resolvePeople(strapi, documentIds): Promise<Map<string, Person>>` (one bounded `findMany` on `api::idambox-user.idambox-user` with `fields: PERSON_FIELDS`, at most 1,000 ids).
- **Eligibility.** `request-assignment-policy.ts` exports `EligibilityUser = { documentId; accountStatus; roles: RoleGrant[] }` and `isEligibleAssignee(user, { requestorDocumentId })`: `accountStatus === "active"`, `hasHumanAnalystOperation(user.roles, listAnalystReviewRequests)`, no role named `SECURITY_ANALYST_AGENT_ROLE_NAME`, `user.documentId !== requestorDocumentId`. The role names come from `csrm-authorization.ts` (new exports `HUMAN_SECURITY_ANALYST_ROLE_NAME` and `SECURITY_ANALYST_AGENT_ROLE_NAME`), never duplicated literals. A doc comment says Phase 17 adds the G-11 exclusion here.
- **Actions.** Stored actions `ASSIGNMENT_LOG_ACTIONS = ["pick-up", "assign", "reassign", "unassign"]`; viewer actions `ASSIGNMENT_VIEW_ACTIONS = ["pick-up", "assign", "assign-to-me", "reassign", "unassign"]`. `deriveAssignmentAction(current, target, actorDocumentId)`: null→actor `pick-up`; null→other `assign`; A→B (B may be the actor) `reassign`; A→null `unassign`; same → `null` (no-op). `allowedAssignmentActions({ requestStatus, requestorDocumentId, assigneeDocumentId }, viewer: { documentId; humanAnalyst })`: `[]` when the viewer is the requestor, not a human analyst, or the status is `draft`; unassigned → `["pick-up", "assign"]`; held by the viewer → `["reassign", "unassign"]`; held by another → `["assign-to-me", "reassign", "unassign"]`; `unassign` removed when the status is in `RELEASED_REQUEST_STATUSES`.
- **Order of guards inside the lock** (13-RESEARCH §E step 3, Pitfall 5): missing request → 404; caller is the requestor → 403 `OWN_REQUEST`; status `draft` → 409 `REQUEST_NOT_SUBMITTED`; current assignee differs from `expectedAnalyst` → 409 `ASSIGNMENT_CHANGED`; target not eligible → 409 `ASSIGNEE_NOT_ELIGIBLE`; target null and status released → 409 `ASSIGNMENT_REQUIRED`; same target → 200 no-op; log at its cap → 409 `HISTORY_UNAVAILABLE`; otherwise one `documents.update` with the four facts. The target's user record (roles populated to `functionApis`) is read inside the lock with `strapi.documents`, which joins the transaction.
- **Log.** `assignment-log.ts` copies the 06.8 posture (`questionnaire-governance-log.ts`): `ASSIGNMENT_LOG_SCHEMA_VERSION = 1`, `ASSIGNMENT_LOG_MAX_EVENTS = 1_000`, `ASSIGNMENT_REASON_MAX_LENGTH = 500`; `parseAssignmentLog(value)` (null → `[]`, exact keys, bounded strings, ISO instants, frozen copy; malformed or over cap → `AssignmentLogError`); `appendAssignmentEvent(value, event)` returns a new `{ schemaVersion, events }`; `readAssignmentHistory(value)` returns the events newest first or `null` when malformed (fail safe). The header comment says the log is never read by an authorisation decision.
- **Body.** `{ data: { analyst: string | null, expectedAnalyst: string | null, reason?: string } }`, exact keys; ids 1 to 255 characters; `reason` trimmed, 1 to 500 characters, C0 controls other than newline refused; anything else → 400.
- **Predicate.** `assertAssignedAnalyst({ request: { requestorDocumentId, assigneeDocumentId }, caller: { documentId; humanAnalyst }, callerUser: EligibilityUser })` returns void or throws `AssignedAnalystRefusal` with `reason` `REQUEST_UNASSIGNED` (status 409) when nobody is assigned, or `NOT_ASSIGNED_ANALYST` (status 403) when someone else is, the caller is not eligible any more, or the caller is not a human analyst. The two reason constants are exported from this module only; they join the published lists in Phase 17.1.
