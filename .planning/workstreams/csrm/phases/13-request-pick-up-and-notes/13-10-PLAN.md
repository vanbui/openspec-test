**As a** Security Analyst, **I want to** pick up a request and exchange notes with the Requestor on it, **so that** ownership is clear and new information has a home at any point.

This plan's slice: the Requestor and the Security Analyst write to each other on the request page, see who wrote what and when, and see what is new to them.

## Recorded planning decisions

- **Structure.** `NotesSection({ requestId, requestNumber, viewer: "requestor" | "analyst", draftOwnerKey })` is a Server Component that calls `listRequestNotes(requestId, { limit: 20 })` and renders the `DetailSection` titled `Notes` (`h2`, id `notes`) with the §8.1 description and count line, then the client `NotesThread` with the served notes and meta. Both pages render it last: the Requestor page after its existing sections; the analyst page as the sibling after `AssessmentDetail`. A failed read renders the compact `We couldn’t load the notes` with `Try again` (a `router.refresh()`), and the composer still renders when the request read's `notes.accepting` is true.
- **Note item.** `NoteItem` renders an `li` with an `article` `id="note-{documentId}"` `tabIndex={-1}`: the author's name (`--text-body` at 500), then `{part} · ` and `LocalInstant` in a `<time dateTime>` (`--text-caption`, `--color-text-secondary`), the X-17 dot and `New` when `unread`, and the body (`whitespace-pre-wrap`, `[overflow-wrap:anywhere]`) as React text. A body that overflows ten clamped lines (measured `scrollHeight > clientHeight` after layout) gets `Show full note` / `Show less` (ghost, small, `aria-expanded`); the full text stays in the DOM and prints whole.
- **Composer.** `NoteComposer` (`'use client'`): label `Add a note` for a textarea with id `note-composer`, three rows growing to twelve then scrolling, no `maxLength`, `aria-keyshortcuts="Control+Enter Meta+Enter"`; the §8.3 hint for the viewer (Requestor, analyst, requesting analyst from `meta.viewerPart`); `Add note` (primary) with the X-7 `Ctrl` `Enter` / `⌘` `Enter` hint from 768px; validation through `validateNoteDraft`. The analyst's AI checkbox and the session-kept draft arrive in 13-11.
- **Posting.** `NotesThread` holds the list; `Add note` appends a pending note with `Adding…` at the §5 pending opacity, clears the textarea and keeps focus, calls `addRequestNoteAction`, and on success replaces the pending note and announces `Note added.` once in a visually hidden polite region; on failure removes it with the `--duration-base` opacity transition, restores the text with the cursor at the end and shows family L's copy as the field error (`Try again` beside `Add note` for a retryable failure); a 404 calls `router.refresh()` so the page shows its refusal state; a second press while pending does nothing.
- **Read.** An `IntersectionObserver` on the first unread note calls `markRequestNotesReadAction({ requestId, throughNoteId })` once per view with the newest loaded note; the result changes nothing visible; failures are ignored.
- **Earlier notes.** `Show earlier notes ({m})` (outline, small; `m` = `meta.total` minus the loaded count) above the list calls `listRequestNotesAction({ requestId, before: <oldest loaded sequence> })`, shows `Loading…` with its inline 16px spinner, inserts the notes above without moving the viewport and focuses the first inserted note; a failure shows `We couldn’t load earlier notes.` with `Try again` in its place.
- **Domain additions** (`notes-domain.ts`): `notesDescription(viewer)`, `notesCountLine(total, unread)`, `composerHint(viewerPart, isAnalyst, ownRequest)`, `notesClosedLine(closedReason, viewer)`, `notesEmptyState(viewer, accepting)`, `noteHeader(note)`, `hubNotesFigure(summary)`; every string verbatim from §5.1 and §8.
- **Hub row.** `request-hub.tsx` adds `Notes` after the assignee row, from the request read's `notes`: a `RecordLink`-styled figure link to `#notes` reading `{n} {note|notes}` followed by the X-17 `{k} new` and named `{n} {note|notes}, {k} new`; with none and `accepting`, a link `Add a note` to `#note-composer`; otherwise `No notes`.
- **Skeletons.** `NotesSkeleton` (a heading line, two note blocks with a header line and two body lines, and a textarea block) is added to both request pages' `loading.tsx`.
- **Print.** The composer, toggles and `Show earlier notes` carry `data-print="hidden"`.
- **Budget** (the performance budget, `e2e/performance.spec.ts`): `NotesThread`, `NoteItem`, `NoteComposer` and the unread marker ship in `/app/requests/{documentId}`'s first load, which delivered 265,797 bytes of JavaScript against its 300,000-byte budget in the desktop baseline at the 2026-10-09 plan check (`apps/csrm/.tmp/performance/baseline-desktop.json`; 13-09-SUMMARY records the figure after 13-09's shell change). Task 3 measures every key route after the work. If a route breaches its budget, the fix is at the source, before the commit: for example, `NotesThread` loads `NoteComposer` with `next/dynamic` (as 13-09's block loads its picker), so a page whose notes are closed, like the measured released request, never downloads it. Never add a budget override or change `PERFORMANCE_BUDGETS` or `ROUTE_BUDGET_OVERRIDES`; if no source change brings the route back within budget, stop and report the measured figures as a blocker.
- **375 runs.** Task 3 adds `**/request-notes.spec.ts` to the mobile project's `testMatch` in `apps/csrm/playwright.config.ts` and titles each journey with `@journey` (the mobile project's `grep`), so its journeys run at 375 as well as 1440; the comment above `projects` gains this file (and `request-pick-up.spec.ts`, if 13-08 left the comment as it was) and why each can run twice against one database (each journey creates its own request, or only reads a seeded released one).
