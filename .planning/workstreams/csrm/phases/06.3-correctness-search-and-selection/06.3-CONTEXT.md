# Phase 06.3: Correctness, Search, and Selection - Context

**Gathered:** 2026-09-07
**Status:** Ready for planning
**Source:** Operator-supplied plan-phase orchestrator context, derived from the post-06.2 application review and a live inspection of the running application

<domain>
## Phase Boundary

Deliver UX-01, UX-02 and UX-03: correct the owner scoping of the three
`my`-prefixed screens for every actor, fix the released-assessment read failure
and make that class of failure diagnosable, and give every remaining list and
record picker server-backed search, filtering and selection.

The phase covers the authorization scope decision in `csrm-authorization`, the
searchable selection of Information Systems and Information Assets on a Risk
Assessment Request, the Risk owner lookup on the analyst Risk editor, search and
status filtering on My Questionnaires, My Risk Assessments and the three analyst
review screens, and the released-assessment defect.

It does not cover cross-record navigation, the assessment risk-count tile,
release-readiness wording, or the interface consistency pass. Those are Phase
06.4. It does not touch AI provider work, which is Phase 06.5.

</domain>

<decisions>
## Implementation Decisions

### D-01 — Owner scoping is the phase's correctness core

The `my`-prefixed screens must be owner-scoped for every actor. Requestor is a
birthright role, so a Security Analyst who raises a request is a Requestor for
that record and must see it, its questionnaire and its released assessment in
those three screens, and must see no other Requestor's records there.

The cause is located. In `apps/strapi/src/policies/csrm-authorization.ts`, both
`requireRequestCollectionScope` and `requireQuestionnaireCollectionScope` test
`explicitAnalystOperation` first and resolve `"all"`, falling through to `"own"`
only when the actor is not an analyst. Because the analyst holds these operations
through an analyst-granted Function, an analyst asking for "my requests" receives
the organisation-wide collection. This was confirmed against the running
application: signed in as the Security Analyst, My Requests listed six requests
including another Requestor's.

The dual-purpose flag is the defect. A route whose meaning is "mine" should
resolve owner scope unconditionally rather than inferring it from the actor's
role. `grants.requestorId` is the acting user's own id and is populated for every
authenticated identity, so owner scope is always resolvable.

The organisation-wide analyst view already has its own separate flags
(`requireAnalystRequestCollectionScope` and the analyst review operations) and its
own routes. Those keep the wide scope and must not change. Prove both halves:
an analyst sees their own record in the `my` screens, and does not see another
Requestor's record there.

### D-02 — Selection follows the existing bounded server-backed combobox

Information Systems and Information Assets on a Risk Assessment Request become a
searchable multi-select supporting zero, one or many selections. The Risk owner
field on the analyst Risk editor becomes a lookup over IdamBox users.

Both follow the bounded server-backed owner combobox delivered in Phase 4 rather
than introducing a second pattern. That component already solves the hard parts:
a bounded result set, debounced server-side search, keyboard operation, and
retaining a selected record whose value falls outside the current result page.
Reuse or generalise it; do not write a parallel picker.

The Risk owner must persist the selected identity, not typed text.

### D-03 — Search and filtering stay server-side

My Questionnaires, My Risk Assessments and the three analyst review screens each
gain search and status filtering consistent with My Requests: server-backed,
paginated, with result counts, an empty-filter recovery path, and preserved
paging. The filter vocabulary for each screen is that record's own status set,
not a shared invented one.

Filtering client-side over a partial page would misreport totals, so the query
builder work belongs in Strapi. `collection-scope.ts` already holds the
established search, filter, sort and pagination builder for requests; extend that
approach rather than hand-rolling per-route query parsing.

### D-04 — The released-assessment failure, and the guard that generalises it

`docs/contract-gaps/phase-06.3-released-assessment-read-failure.md` records the
diagnosis. `releasedAssessmentDetailSchema` fails closed on four separate
conditions — the status not being `approved`, or any of `assessmentDate`,
`approvalDate` or `approvedBy` being null — and every one of them renders as
"We couldn't load this risk assessment". A contract mismatch, an incomplete
release fact and a genuinely unavailable service are therefore indistinguishable
on screen.

Reproduce the failure against a released assessment owned by the signed-in
Requestor and record which condition actually failed before fixing it. The seed
currently has one approved assessment and it belongs to the other Requestor, so
the phase will need a development-gated fixture or an existing record reassigned
in dev data to reproduce as `jane.doe@idambox.com`.

Then make the class diagnosable: in development a schema mismatch must not
present as a service outage.

### D-05 — Contract-to-client-schema parity is the highest-value new guard

Four defects across Phases 06.1 and 06.2 shared one shape: the server completed
the operation and the client reported failure, because a closed Zod schema and
the payload it parsed had drifted. The existing parity tests compare served route
against catalogue grant against the OpenAPI document. Nothing compares the
OpenAPI document against the Zod schemas that parse its responses, which is
exactly where all four drifted.

Add that check in this phase. It is worth more than any single fix it would have
caught, and this phase adds several new response shapes that would otherwise
widen the same gap.

### D-06 — No schema change expected

This phase is scoping, querying and selection over records that already exist, so
it should need no change to any `schema.json`. If one appears unavoidable, state
it in the plan with a justification and a `docs/contract-gaps/` record before the
change, as Phases 06.1 and 06.2 did.

</decisions>

<constraints>
## Constraints

- Typed `openapi-fetch` service layer only; no raw fetch in pages and no frontend
  API facade. Server-side authorization stays authoritative in Strapi.
- Every new or changed route appears in both catalogue copies byte-identically, in
  `docs/references/specification.json`, and in regenerated web declarations via
  `pnpm --filter @csrm/web api:generate`. Generated output is never hand-edited.
- Semantic design tokens only. WCAG 2.2 AA. Responsive 375-1440px. Strict
  TypeScript. Status and risk are never conveyed by colour alone.
- Keycloak stays disabled.
- Responses carry bounded projections rather than raw Strapi documents, and any
  relation a response exposes must be populated.
- New browser coverage clears transient toasts before clicking beneath them, does
  not assume the first click on a client island reached by navigation lands, and
  uses named locators rather than bare role queries.

</constraints>
