# Phase 06.3 Plan 05: Contract integrity and released assessment correction Summary

Closed the phase's headline defect at its source, installed the contract-to-client-schema parity guard the phase context locked as D-05, and repaired a route registration fault that was failing every Strapi integration test.

## Accomplishments

- **Contract-to-client-schema parity guard.** `contract-response-parity.test.ts` synthesises payloads straight from `docs/references/specification.json` and feeds them to the real client parsers exported by the services. It runs three modes: contract-required properties only, every declared property, and every nullable property served as null. Where a client is deliberately narrower than a shared contract component, the parser table declares the path and the reason, and the guard fails when a declared narrowing no longer corresponds to a real rejection — so a narrowing cannot outlive the drift it documents.
- **Released assessment read failure fixed at the source.** The nullable mode reproduced the defect mechanically: `RequestorReleasedAssessmentDetail` declared `assessmentDate`, `approvalDate` and `approvedBy` as nullable and accepted every `assessmentStatus`, while the client refinement rejects all four. The contract now declares the released facts non-null and the status `const: "approved"`, and `releasedAssessmentQuery` filters `assessmentDate: { $notNull: true }` beside the existing `approvalDate` filter. Release rules were not weakened: the release transition already writes all four facts in one update, so an incomplete legacy row is simply excluded and the Requestor gets an honest "not found".
- **Three more contract drifts found and fixed.** `controlStatus`, `effectivenessRating` and `overallControlEffectiveness` were declared as unconstrained strings in the response components while both the Strapi datamodel and the client restrict them to the same four values. The contract now carries the enum, matching the declaration the same file already used elsewhere.
- **Diagnosable failures.** `normalizeResponseParserError` tags a parse failure as `response-contract-mismatch`, and the released detail route names the failing operation in development only; production keeps the neutral message.
- **Route registration repaired.** The new selector routes were spread into the core router's own route list, which drops the auth scope Strapi fills in on the core-router path and failed registration for the whole server — every Strapi integration test was failing on `Invalid route config config.auth.scope is a required field`. Each selector route is now its own router beside the untouched core router.
- **Selector authorization hardened.** The policy and the Administration controller each carried their own copy of the "is this a selector call" predicate, and the copies had diverged. They now share one module. The divergence happened to fail safe in both directions, but it sat one edit away from letting a Requestor holding only the selector grant reach the full inventory list.
- **Service analyst agent scope asserted.** Plan 01 tightens the Security Analyst Agent's My-route scope from `all` to `own` along with the human analyst, and the new test covers it.

## Found by running the app, and fixed

The browser pass turned up three further breaks that no test covered:

- **My Risk Assessments failed on every first load.** The page always sends
  `q=`, and the collection route rejected an empty search term as a malformed
  query, so the screen showed "We couldn't load your released risk assessments"
  before the user typed anything. The collection services now omit an empty
  term, matching the request and questionnaire services, and the route treats a
  blank term as the absence of a search rather than a bad request.
- **The analyst could not open their own released assessment.** Plan 01 gives an
  analyst a My list scoped to their own records, but `/v1/risk_assessments/{id}`
  serves them the analyst DTO (`actor: "analyst"`) while the page parsed the
  Requestor-only schema, so every open ended in the contract-mismatch state.
  This is the reported "We couldn't load this risk assessment" in its second
  form. The released screen now parses the contract's `actor` union and keeps
  the released facts it renders, which is what the contract's discriminator was
  there for.
- **The inherited inventory routes answered 500.** The selector service replaced
  the core service file, so `createCoreController`'s `find` had no service to
  resolve and `/api/csrm-information-systems` and `/api/csrm-information-assets`
  threw. The core service is the default export again, with the selector helpers
  as named exports beside it.

- **Selector hydration could never be authorised.** `POST
  /v1/information_{systems,assets}/selected` asserts a reference-data scope, but
  `requireReferenceDataScope` was declared in the policy's config type and never
  implemented, so no route could grant it and every hydration answered 403. The
  option is implemented now and both hydration routes declare it. The test
  covering these routes had never passed.
- **The selector predicate was too loose to keep agents off the Administration
  list.** Distinguishing the two capabilities on `q` alone made a query like
  `?populate=*&page=0` read as a selector, which the Security Analyst Agent
  holds, so a malformed Administration query was parsed instead of refused. A
  call now counts as a selector only when it is an explicit search or a bare
  page and never when it orders the collection, which is the mark of an
  Administration list. Every other query shape, `populate` included, is
  authorised as Administration and so is still denied before it is parsed.

- **Analysts had lost the questionnaire review list.** Owner-scoping every My
  route was applied to the questionnaire collection as a whole, but
  `/v1/questionnaires` and `/v1/questionnaires/review_summary` are the analyst
  review surfaces, not My lists — they exist precisely because
  `/v1/my_questionnaires` is the owner-scoped one. Both are marked as review
  collections now and keep the wider scope their explicit analyst grant carries,
  while every My list stays owner-scoped for every actor.

- **The Risk Register pickers came back empty.** They read shared collection
  routes and parsed a closed `{ data }` envelope, but those routes are paged now
  and answer with pagination meta, so the register could not be filtered by
  assessment, risk type or control. The pickers are covered by the parity guard
  now, which is the same drift class it was built for.
- **The relation search box had no accessible name in Chrome.** Wrapping the
  input in a label was not producing one, so the control was unnamed for anyone
  using a screen reader; it carries an explicit label now.

- **Enter in the relation search box submitted the whole form.** The handler
  only prevented the default when a result was already available, so pressing
  Enter before the debounced search returned submitted the request instead of
  choosing a system. Enter now always belongs to the combobox.

The `AnalystRiskDetail` enum fields (`dataClassification`,
`controlEffectiveness`, `riskVelocity`, `treatmentAction`, `treatmentStatus`)
were declared as unconstrained strings too, and the guard caught them as soon as
the analyst branch came under test.

## Deferred

- `QuestionnaireGenerationJob` is declared as one flat object with optional per-state fields while its sibling `AssessmentDraftJob` is a discriminated `oneOf`, and the client models both as unions. Recorded as a declared narrowing and documented in `docs/contract-gaps/`. Restructuring it belongs to the phase that owns questionnaire generation; nothing serves such a payload today.

## Notes

Plan 05 was interrupted part-way and resumed later: plans 01, 02, 03, 04 and 06 had already produced summaries, and the released-detail diagnostics and the list search controls had landed. The parity guard, the source fix, the route repair, the authorization corrections and the tests described above were completed in the follow-up pass, which is why several of the findings here are defects in the earlier plans rather than new work.

Both suites must be run one at a time. Running the web and Strapi suites concurrently starves the heavier component tests and they fail as timeouts rather than on any assertion.
