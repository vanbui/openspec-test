<objective>
Add opt-in, idempotent CSRM bootstrap data to the Strapi backend and verify that it creates the locked CSRM application, application roles, matching reusable roles, and Jane/Bob IdamBox users without adding later-phase Keycloak, CSRM content types, or frontend behavior.
</objective>

<context>
Phase 2 builds on the Phase 1 Strapi backend and core authorization model. Existing seed behavior lives in `apps/backend/src/bootstrap/seed-core-data.ts` and is invoked from `apps/backend/src/index.ts`. This plan adds a separate CSRM seed path controlled by `IDAMBOX_SEED_CSRM=true|false`, not by `IDAMBOX_SEED_CORE`.
</context>

<must_haves>
<truths>
- **D-01:** `IDAMBOX_SEED_CSRM=true|false` must be the only Phase 2 activation flag for CSRM seed behavior.
- **D-02:** `IDAMBOX_SEED_CSRM` must be independent from `IDAMBOX_SEED_CORE`.
- **D-04:** The Strapi `Application` record must use `name: "IdamBox CSRM"`.
- **D-05:** The Strapi `Application` record must use `slug: "idambox-csrm"`.
- **D-06:** The application description must expand CSRM as Cybersecurity Risk Manager.
- **D-07:** The only Phase 2 CSRM application roles are `Security Analyst` and `Security Analyst Agent`.
- **D-08:** Matching reusable `Role` records must exist for `Security Analyst` and `Security Analyst Agent`.
- **D-09:** Jane Doe `jane.doe@idambox.com` must be active with no role assignments.
- **D-10:** Bob Doe `bob.doe@idambox.com` must be active and assigned to the reusable `Security Analyst` role.
- **D-03:** Seed behavior must be idempotent across repeated Strapi boots.
- **D-11:** Phase 2 verification must include static checks plus idempotency-focused verification.
- **D-12:** Verification must prove seed definitions, `IDAMBOX_SEED_CSRM` configuration, relationship targets, and duplicate-prevention behavior.
- Effective access must continue to derive through `IdamBoxUser -> Role -> ApplicationRole -> Application`.
- Phase 2 must not implement Keycloak, Strapi-to-Keycloak provisioning, CSRM assessment collections, or a Next.js frontend.
</truths>
</must_haves>

<threat_model>
**Assets:** IdamBox user records, role assignments, CSRM application-role definitions, local seed controls.
**Threats:**
- HIGH: CSRM seed data runs unexpectedly because it is folded into the broader `IDAMBOX_SEED_CORE` flag.
- HIGH: duplicate users or roles are created on repeated Strapi boots.
- HIGH: Jane receives an implied requestor role that expands authorization scope beyond Phase 2.
- MEDIUM: Bob is linked directly to an application role instead of through the reusable Role model.
- MEDIUM: seed docs imply Keycloak or frontend login behavior exists before later phases.
**Mitigations:**
- Gate CSRM seed code behind `IDAMBOX_SEED_CSRM=true`.
- Use lookup-before-create behavior for application slug, application role name plus application, role name, and user email.
- Create Jane active with no roles.
- Assign Bob through the reusable `Security Analyst` Role only.
- Keep docs explicit that Keycloak and the CSRM app are later phases.
**Residual Risk:** Live Strapi boot verification may require a local environment outside sandbox limits; static and type verification are the required baseline.
</threat_model>
