## Summary

Five open questions, five answers:

1. **The target vocabulary** is a grouping over the one participant projection allowlist. It has four kinds: assessment fields (5 targets), the whole risk, risk fields (15 targets) and a control implementation. Field keys are today's attribute names, read this session. A unit test makes every allowlisted field belong to exactly one target or to a named exclusion, so a later widening of the projection fails the test instead of silently growing or shrinking what can be contested.
2. **The snapshot** is a slice of the raiser's own projection output, never of the raw rows. Its versioned envelope carries two numbers: `schemaVersion` for the envelope shape and `fieldSetVersion` for the allowlist it was cut from. 17.1's decision snapshots map their `fingerprintVersion` onto the same field-set table, so one comparison module serves both voids and points across versions.
3. **A removed control implementation:** Strapi 5.51.0 stores a unidirectional `manyToOne` in a link table whose foreign keys are `onDelete: 'CASCADE'`, and SQLite runs with `pragma foreign_keys = on`. So `deleteControlImplementation` removes the point's link row in the same statement, the point's `controlImplementation` reads `null`, and the point row and its snapshot survive. The snapshot must therefore carry the target's ids. "No longer part of this assessment" is derived from the null link (or a withdrawn risk), never from a stored flag.
4. **The history read** groups events by time windows, one per round, rather than by round foreign key. Answers and replies during rework belong to no open round. Each window runs from one round's opening to the next round's (any kind, since at most one round is open at a time). The read serves the newest two windows by default and all windows on request, with about seven bounded queries per read whatever the window count, and a 5,000-event cap per read that never splits a window.
5. **The undo window** is 120 seconds on the server clock, measured from the act's `postedAt`. The undo is accepted only from the same person, as the next act on the point. The reversal reads on the shared reopening path read every unread `acceptance-requested`, `decision-voided` and `executive-approval-requested` on the assessment. Point-scoped reads parse `facts` in code, following 19.1's note-read pattern, never filtering JSON in SQL.

**Primary recommendation:** build the target vocabulary, the snapshot cutter and the comparison as pure modules over the projection's output, in wave 1 beside the record. Make every "is this target still there" question a read-time derivation over the snapshot's ids.

## 2. The snapshot and its versioning (D-04, D-14)

**Cut from the projection, not the rows.** The raise builds the raiser's participant projection, which it needs anyway to validate the target, and copies the target's slice of it. That alone guarantees "never more than the projection discloses". A snapshot built from raw risk rows would carry `comments` or `escalationDetails` the moment someone widened a populate (Pitfall 1).

**Envelope v1** (JSON attribute `targetSnapshot`, closed parser that fails safe as 06.8's envelopes do):

```text
{
  schemaVersion: 1,                  // envelope shape
  fieldSetVersion: 1,                // which participant field set it was cut from
  target: { kind, field | null, label,              // e.g. "R-003 · Treatment plan"
            assessmentId, riskId | null, riskNumber | null,
            controlImplementationId | null, controlNumber | null, controlName | null },
  fields: [ { key, value } ],        // key from §1's covers; value typed below
  controlImplementations?: [ { id, controlNumber, controlName, fields: [ { key, value } ] } ]
}
```

- **Values:**
  - text exactly as projected;
  - dates as `YYYY-MM-DD`;
  - ratings and enumerations as stored strings;
  - people, systems and assets as `{ documentId, label }`, which is Phase 16's history convention (16-RESEARCH: "relation values as `{ documentId, label }` captured at the time").

  Labels for field keys come from §1's table at read time. The `target.label` is stored, because D-04 says the snapshot keeps the labels as shown.
- **Sizes:** values are stored whole, because truncation would falsify the record (Phase 16's reasoning). The bound is the risk's own field bounds.
- **Versioning against 17.1:**
  - 17.1's decision rows store `fingerprintVersion` and a `snapshot` in canonical form, with relations as `documentId` strings (17.1-RESEARCH "Fingerprints and Voids": "relations as `documentId` strings; dates as `YYYY-MM-DD`").
  - Do not reuse the fingerprint version as the snapshot version. A fingerprint version can change for a canonical-form reason with no field change.
  - Instead, one table in the comparison module maps each version to its field set: `FIELD_SETS: Record<fieldSetVersion, { assessment: keys[], risk: keys[], controlImplementation: keys[] }>`, plus `FINGERPRINT_TO_FIELD_SET: Record<fingerprintVersion, fieldSetVersion>` (v1 → v1).
  - A unit test ties the current field set to the current decision allowlist and to §1's vocabulary.
- **One comparison** (`apps/backend/src/csrm/snapshot-comparison.ts`, pure). It takes a normalised "before" (a contest snapshot, or a decision snapshot normalised through its field set) and the participant-visible "now". It returns:
  - per field: `unchanged`, `changed` (before and after), or `not-recorded` (in the current field set but absent from the before's version);
  - per control implementation, matched by id: `added`, `removed` or `changed`, with its fields.

  How it compares:
  - People are compared by `documentId` and shown with the label the snapshot recorded, against today's label.
  - A decision snapshot holds ids only, so its labels are resolved with one batched user and control lookup at read time.
  - Fields present before but absent from the current field set are **omitted** for participants, because a narrowed projection must not re-disclose them [ASSUMED; record it in the contract-gap record].
- **The void comparison** rides 17.1's rounds-and-decisions read: each void row gains its `comparison`, computed by this module from its own snapshot. One projector (17.1-RESEARCH: "use one projector function, so the two can never disagree") means no second read and no second authorisation surface. The point sheet's comparison rides the point read.

## 3. A removed control implementation (D-04, D-10)

**What Strapi does** [VERIFIED: `@strapi/database` 5.51.0, read this session]:
- **Link tables cascade.** A unidirectional relation's join table gets two foreign keys, each declared `onDelete: 'CASCADE'` (`dist/metadata/relations.js:398-420`: `referencedTable: meta.tableName, onDelete: 'CASCADE'` and `referencedTable: targetMeta.tableName, onDelete: 'CASCADE'`).
- **SQLite enforces them.** Its dialect runs `pragma foreign_keys = on` on connect (`dist/dialects/sqlite/index.js:34`). The project's default client is SQLite: `env('DATABASE_CLIENT', 'sqlite')` [VERIFIED: `apps/backend/config/database.ts`]. PostgreSQL enforces them natively.
- **The entity manager does not clean incoming links itself.** Its `deleteRelations` loop skips regular relations when foreign keys are in use (`// do not need to delete links when using foreign keys` / `if (db.dialect.usesForeignKeys()) { continue; }`, `dist/entity-manager/index.js:1209-1290`). It deletes the row first (`this.createQueryBuilder(uid).where({ id }).delete()`, lines 381-383), and the database cascades the link rows.
- **Today's delete is a Document Service hard delete inside the assessment mutation:** `await input.strapi.documents(IMPLEMENTATION_UID).delete({ documentId: input.implementationDocumentId });` [VERIFIED: `control-implementation-workflow.ts:229-247`]. So the cascade runs inside the same transaction.
- **Nothing else is hard-deleted.** Risks are never hard-deleted (16-RESEARCH "No hard delete"), and a grep of `apps/backend/src` this session found only one other document delete, of questionnaire questions. IdamBox users, rounds and assessments have no delete path in CSRM code. Phase 16 does record a mounted core `DELETE` of a request, which leaves its assessment in place.

**Consequences for the plan:**
- After a removal, the point's row, its entries and its `targetSnapshot` stay; its `controlImplementation` populates as `null`. The link table name is short enough to keep: `csrm_contest_points_control_implementation_lnk` is 46 characters, under Strapi's 55 (17-RESEARCH Pitfall 5) [ASSUMED name until a fresh boot shows it].
- **Derive "No longer part of this assessment"** as `(kind === "control-implementation" && controlImplementation === null) || risk.withdrawn`. Never store a flag; there is no write path to keep one true. A reinstated risk shows its live target again (D-10) for free.
- **The snapshot carries the ids** (`target.controlImplementationId`, `target.riskId`), so markers, the history's links and the panel's target filter still name the removed target after its link is gone. Per-target counts for live content can join through the link. Points on removed targets appear only in the panel and the history, never as a marker, because there is no element to mark.
- **Keep the relation** rather than a bare id column. The cascade is exactly the wanted semantics: no dangling id, no FK error on delete, and the record survives. The contract-gap record's "Audit Semantics and Limitation" states it.
- **Proof:** an integration test raises a point on a control implementation, deletes the implementation between rounds, and asserts all of the following:
  - the point and entry counts are unchanged;
  - `controlImplementation` is null;
  - the snapshot is deep-equal to before;
  - the point reads "left the assessment" for the participant;
  - persistence of the other points is unchanged.

  A second test does the same for a withdrawn, then reinstated, risk.

## 4. The history read: events, grouping and pagination (D-15)

**Group by time windows, not by round foreign key.** Answers "changed", replies and resolutions happen between rounds, when no round is open. Decision voids caused by withdrawal have `round` null (17.1-RESEARCH: "Null only on a `risk-withdrawn` void between rounds"). At most one round of either kind is open per assessment (17-RESEARCH D-12: "There is at most one open round per assessment"). So the rounds of both kinds, sorted by `openedAt`, partition time:
- **Window `i`** runs from `openedAt(i)` up to `openedAt(i+1)`, or to now.
- **Participants** see one group per window, so the rework answers read as the end of round n's story.
- **Analysts** see the same window split at `closedAt(i)` into the round and a `Between rounds {n} and {n+1}` group (UI-SPEC §9).

**One read, about seven queries, whatever the window count:**

| # | Source | Filter | Notes |
|---|---|---|---|
| 1 | Rounds (Phase 17's entity, both kinds) | the assessment | Every round; few rows (Phase 17 bounds response rounds at 20, an [ASSUMED] figure) |
| 2 | Responses (Phase 17) | the selected windows' rounds, submitted only | `submittedAt` |
| 3 | Decision rows (17.1) | the assessment, `recordedAt` in range | Participants: drop rows on currently withdrawn risks and `risk-withdrawn` voids (17.1 D-39) |
| 4 | Contest points | the assessment, `raisedAt` in range | Plus the points referenced by query 5 |
| 5 | Contest entries | `point` in the assessment's point ids, `postedAt` in range | Uses the link table's index on the join column (`fkIndexName` index, `relations.js`) |
| 6 | Review log (analysts only) | the assessment's `reviewLog` envelope, parsed in code | 17.1 |
| 7 | Risk history (analysts only) | the assessment, `occurredAt` between `closedAt(i)` and `openedAt(i+1)` | Distinct risks per rework period, linked to Phase 16's sheet |

- **People:** resolved through one batched lookup (the 08 D-31 pattern that Phase 16's read uses).
- **Events:** a closed discriminated union by `kind`, sorted by `(at, sourceOrder, sequence)` within a window. The web words them (D-15).
- **Pagination by window.** The UI-SPEC's "newest two rounds render; `Show earlier rounds ({m})` loads the rest" maps to a closed query:
  - `rounds=recent`, the default: the two newest windows;
  - `rounds=all`;
  - a closed `show=everything|contest-points|decisions-and-rounds` filter.

  The response carries `earlierWindowCount`. The history page is server-rendered, so "Show earlier rounds" is a link to `?rounds=all` with a fragment on the first new h2, needing no client fetch. Print asks for `rounds=all`.
- **Volume:**
  - Realistic: five rounds and about 200 events (the UI-SPEC backstop).
  - Worst case with the bounds in §6: 100 points per round, 100 replies per point, and 17.1's 5,000 decision-row cap.
  - The read caps one response at **5,000 events**. It adds whole windows newest first until the next would pass the cap, always returning at least one window, and reports what remains in `earlierWindowCount`. A window is never split.
  - Bodies come back whole, because print needs them.
  - A volume test seeds 50 risks, three deciders, three rounds and 100 points with 10 entries each, and asserts one read of `rounds=all` stays under the integration suite's per-request budget [ASSUMED threshold; the planner fixes it].
- **Authorisation:**
  - Readable by participants (Phase 17's predicate, through release, G-12) and by human analysts.
  - The service identity gets 403 (D-19); anyone else gets 404.
  - The per-actor filtering is part of the projector, tested per actor.

## 5. The undo window, and the reversal reads

**Undo (D-09):**
- **Window:** `CONTEST_UNDO_WINDOW_MS = 120_000`, compared on the **server clock** inside the transaction: `now - entry.postedAt <= window`. Unit tests inject the clock. Two minutes covers X-14's 5-second toast, which pauses while hovered or focused [CITED: 12-UI-SPEC X-14 "follows the success timing (5s), pausing while hovered or while focus is inside it"]. That leaves a keyboard or screen-reader user reaching it with `Alt+T` ample time, while staying a slip correction rather than a reopen. Past it, the raiser still has recourse: reply, or a follow-up point in an open round. That is X-14's "can still be corrected on the page" for this domain.
- **Conditions, all inside the lock:**
  - the caller is the author of the act being undone;
  - that act is the point's last entry (compare-and-set on `expectedSequence`), and its kind is `resolved` or `withdrawn`;
  - it is inside the window;
  - the assessment is unreleased.

  Otherwise the refusal is 409 `UNDO_NOT_AVAILABLE`. An `undo` entry is never itself undoable, and needs no "which entry" field, because it always undoes `sequence - 1`.
- **Status derivation:** a pure fold over the entries. `undo` restores the status that held before the entry it undoes, so the fold keeps the previous status. The cached `status` is written in the same transaction, and a test proves the cache equals the fold (17.1 Pitfall 7's posture).
- **The raise's Undo** (D-06) is a `withdrawn` entry that must say truthfully "Withdrawn with Undo straight after it was raised" (UI-SPEC §5.3). Deriving that from timing would mislabel a deliberate quick withdrawal. Recommend an entry attribute `viaUndo` (boolean, default false). It is accepted only when the point has no entries yet (`expectedSequence = 0`), the caller is the raiser, and the raise is inside the window; otherwise `UNDO_NOT_AVAILABLE`. **This adds a field to D-01's entry list,** so it is an open question for the orchestrator.

**The shared reopening path (D-11, D-18; 17.1 D-25 and its confirmation "Recall's notification reads follow Phase 17.2 D-18"):** one inner function, for example `closeAcceptanceRoundAndReopen(trx, { round, outcome: "recalled" | "returned", actor, actorParts?, text })`, called by recall and by send-back inside the assessment lock. It runs these steps in order:
1. Close the round: `outcome`, `outcomeReason` (the recall reason or the send-back message), `closedBy`, `closedAt`, and the sender's parts on a return.
2. Write nothing on any decision. The review stops being current through 17.1's currency function (`latestAcceptanceRoundClosedAt`), so no write is needed.
3. Run the reversal read: every unread `acceptance-requested`, `decision-voided` and `executive-approval-requested` whose subject is the assessment, for every recipient. Reading all unread rows on the assessment, rather than filtering `facts.roundNumber`, gives the same result: an earlier round's rows were read when that round closed. It also needs no JSON parse.
4. Notify: `acceptance-round-recalled` (17.1) or `assessment-returned` (this phase), through `notify`, which refuses to run outside a transaction (19.1-03).

**Reads at the next submission** (17.1's submit transaction): every unread `assessment-returned` on the assessment is read. That is the assigned analyst's acting read and the participants' reversal read, in one call.

**Point-scoped reads** (`-raised`, `-answered`, `-replied`) follow 19.1-03's `readNoteNotificationsThrough` pattern:
- select the reader's unread rows of those kinds whose subject is the assessment;
- parse `facts` in code;
- update the ids whose `pointId` matches.

The withdrawal's reversal reads `-raised` for every `security-analyst`-part recipient of that point, not only today's assignee. Rows whose facts fail to parse stay unread: they cannot be matched to a point, and reading them would read other points' notifications [ASSUMED; this differs on purpose from 19.1's note read, which is "through sequence N"].

## Common Pitfalls

### Pitfall 1: A snapshot cut from raw rows
**What goes wrong:** analyst-only text (`comments`, `escalationDetails`) or an unconfirmed AI value lands in a participant-visible snapshot.
**How to avoid:** cut the snapshot from the projector's output (§2), and unit-test it against a risk carrying every analyst-only field.
**Warning sign:** the snapshot builder imports from the risk schema or populate, not from the projector.

### Pitfall 2: A thread cap that blocks the answer
**What goes wrong:** with 100 replies, the analyst cannot post the answer that resubmission needs (D-12).
**How to avoid:** cap replies only (§6), and test an answer on a full thread.

### Pitfall 3: Counting removed targets through the relation
**What goes wrong:** filters on `controlImplementation` miss points whose link the cascade removed, so the panel or history drops them.
**How to avoid:** list by assessment, and resolve targets from the snapshot ids (§3).

### Pitfall 4: Grouping history by `round`
**What goes wrong:** rework answers and withdrawal voids fall outside every group.
**How to avoid:** time windows (§4), with a test placing a between-rounds answer in the right group for each actor.

### Pitfall 5: Undo judged on the client clock
**What goes wrong:** a slow or skewed client accepts or refuses wrongly.
**How to avoid:** use the server clock in the transaction. The toast only offers the Undo, and Strapi decides.

### Pitfall 6: JSON filters on `facts` in SQL
**What goes wrong:** dialect-specific JSON operators differ between SQLite and PostgreSQL.
**How to avoid:** select by subject, kind and recipient, then parse in code (19.1-03's note read).

### Pitfall 7: Reversal reads outside the transaction
**What goes wrong:** `notify` throws outside a transaction (19.1-03), and a read written after commit can be lost.
**How to avoid:** both happen inside `closeAcceptanceRoundAndReopen`.

### Pitfall 8: A former raiser's points
**What goes wrong:** a raiser who stops being a participant cannot resolve, so their open point blocks until the analyst answers it.
**How to avoid:** this is intended (D-09). Prove that an answer unblocks it and that no one else can resolve it.
