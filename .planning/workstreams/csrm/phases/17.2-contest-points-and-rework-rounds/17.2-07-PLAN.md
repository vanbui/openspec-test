## Recorded planning decisions

- **Contest facts** (one helper `projectContestFacts({ points, risks })` in `assessment-scope.ts`, over `loadContestPointsForAssessment`): `{ counts: { open, answered, closed }, byTarget: [{ key, open, answered, closed }], byRisk: [{ riskId, open, answered, closed }] }`; `key` is `contestTargetKey`; `byRisk` rolls up every point on the risk, its fields and its control implementations; a point with `leftAssessment` counts in `counts` but in no `byTarget` or `byRisk` entry (there is no element to mark, research §3).
- **Target vocabulary for the raise form** (D-04: field labels are served, never composed by the web): the participant projection gains `contestTargetVocabulary` `{ assessmentFields: [{ key, label, covers }], riskFields: [{ key, label, covers }], controlImplementationCovers }`, served from `ASSESSMENT_TARGET_FIELDS`, `RISK_TARGET_FIELDS` and `CONTROL_IMPLEMENTATION_TARGET_COVERS` (17.2-02), so the form's options and "What you're contesting" values come from the server's one vocabulary.
- **Participant projection** gains `contestPoints` (the facts above), `latestRoundOutcome` (`{ number, outcome: "recalled" | "returned" | "completed", closedAt, closedByName, closedByParts, message }` for the latest closed acceptance round, or null), and `viewerContestActs` (`{ raise: { allowed, reason? }, sendBack: { allowed, reason?, ownOpenPointCount } }` from `raiseDecision` and `sendBackDecision`). **Analyst detail** gains `contestPoints` and `viewerContestAnswer` (`{ allowed, reason? }` from `answerDecision` with the viewer's facts and status `open`).
- **Decision comparisons** (`acceptance-projection.ts`). `listAcceptanceRounds` builds the participant-visible content now once (17-07's projector) and a batched label map (one user lookup and one control lookup); `projectRiskDecision` sets `comparison` (`SnapshotComparison`) on a `void` row from the voided act's snapshot (the act named in `voidsIds`), and on a standing act whose `decisionFingerprint(risk, act.fingerprintVersion)` differs from its stored fingerprint, through `normaliseDecisionSnapshot` and `compareSnapshot`; null otherwise. `projectViewerActs` sets `standsFromRound` to the act's round number when it stands into a later open round. Participants still never see rows on withdrawn risks or `risk-withdrawn` voids (17.1 D-39). No fingerprint or raw snapshot is ever projected.
- **Lists.** `listMyRiskAssessments` items gain `openContestPointCount` and `viewerAnsweredPointCount` (points the viewer raised with status `answered`); neither enters `filters[awaiting]` (D-16). Analyst list items gain `openContestPointCount`; `buildAssessmentCollectionQuery` gains the closed filter `filters[contestPoints]=open` (any other value 400), composable with `filters[assigned]=me`; the controller's query parser accepts it. The web list service passes `contestPoints`.
- **Status mapping** (`status-badge.tsx`). `contestPointFamily` `{ open: { MessageSquareWarningIcon, "Open", warning }, answered: { MessageSquareQuoteIcon, "Answered", info }, resolved: { MessageSquareCheckIcon, "Resolved", neutral }, withdrawn: { MessageSquareOffIcon, "Withdrawn", neutral } }` added to `statusPresentation` and `StatusFamily`; `returned` (`CornerDownLeftIcon`, "Returned", warning) joins the round-outcome values 17.1 put in the mapping (if 17.1 executed no round-outcome family, add `acceptanceRoundOutcome` with `recalled`, `completed` and `returned` using 17.1-UI-SPEC's labels). A badge whose list mixes families takes the accessible name `Contest point: {label}`.
- **Scope note (the pilot's pacing rule, recorded for the plan check).** 14 files in three tasks: three read shapes share the specification, the client and two parsers; the status mapping travels with the shapes that carry its values (17.1-09's precedent).
