## Phase Goal

**As a** Security Analyst, **I want to** tell the AI what to add, change or remove in a questionnaire and to have it propose follow-up questions without touching answered ones, **so that** the question list keeps up with new information while I stay in control.

This plan's slice: nothing moves on while a proposal is undecided, replacing a questionnaire can no longer lose anyone's work, the first generation can be steered, and the questionnaire reads tell the analyst what is fixed and what is open.

## Recorded planning decisions

- **Gates module.** `openProposalSummary(strapi, questionnaireId)` reads at most 101 completed runs of the two operations for the questionnaire (fields `documentId`, `operation`, `proposal`, `decisions`), folds each with `parseRunProposalFor`, `parseRunDecisionsFor` and `foldItemStates`, logs a damaged run once and counts it as no open item, and adds `activeQuestionnaireProposalJobs(strapi, questionnaireId).length > 0`; returns `{ openCount, activeJob, damagedRunIds }`. `assertNoOpenProposals(strapi, questionnaireId, refuse)` calls `refuse("AI_PROPOSALS_OPEN")` when `openCount > 0` or `activeJob`.
- **Where each gate runs.** Release: inside `releaseQuestionnaire`'s locked transaction, after `assertReleasable`, throwing `QuestionnaireGovernanceError(409, …, "AI_PROPOSALS_OPEN")`. Draft: `generateAssessment` before enqueueing (409 with the draft error's reason) and `persistAssessmentDraft` inside its transaction (job failure code `AI_PROPOSALS_OPEN`); the draft path keeps locking only the request row (15-RESEARCH §M: no questionnaire lock there). Replacement: `generateQuestionnaire` before enqueueing when `replaceUnansweredQuestionnaire` is true (409 `QuestionnaireGenerationWorkflowError` with the closed reason), and the replacing branch of `persistGeneratedQuestionnaire` inside its transaction (job failure codes).
- **Replacement order** (D-09; Q-1), the same at enqueue and in the locked transaction: released → Phase 10's existing refusal (`QUESTIONNAIRE_RELEASED`); `hasQuestionnaireAnswerEvidence` → `QUESTIONNAIRE_ANSWERED` (now a closed reason: a 409 at enqueue, and still the job failure code it is today in the transaction); `countAnalystChangesSinceGeneration(log, generatedDate)` above 0 → `QUESTIONNAIRE_HAS_ANALYST_CHANGES`; open set or active job → `AI_PROPOSALS_OPEN`. A null count (an unreadable log) is not an analyst change: it falls through to today's `HISTORY_UNAVAILABLE` job failure, so `questionnaire-generation.integration.test.ts`'s full-log and unreadable-log cases stay green unchanged. The `regenerated` event is unchanged apart from the instruction keys.
