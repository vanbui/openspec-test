## Phase Goal

**As a** Security Analyst, **I want to** tell the AI what to add, change or remove in a questionnaire and to have it propose follow-up questions without touching answered ones, **so that** the question list keeps up with new information while I stay in control.

This plan's slice: the analyst decides each proposal on its own, with Undo, and a confirmation can never land on an answered question or interleave with a Requestor's save.

## Recorded planning decisions

- **Body** (`parseQuestionnaireProposalDecisionBatch`): `{ decisions: [{ runId (1 to 255), item (`i-1` to `i-30`), action ("accept" | "reject" | "restore"), edits?, reason? }] }`, 1 to `QUESTIONNAIRE_DECISION_BATCH_MAX` (200, equal to Phase 12's `AI_PROPOSAL_DECISION_BATCH_MAX`); `edits` only on `accept`, closed keys `questionText`, `helpText`, `answerType`, `choices`, `required` and, for an addition only, `section` (`{ kind: "existing", key }` or `{ kind: "new", title }`), each validated by `parseQuestionMutationPayload`'s rules for that key; `reason` only on `reject`, 1 to 500 characters. Anything else is 400.
- **Check order** (inside `withQuestionnaireGovernanceLock`, all or nothing; 15-RESEARCH §L): requesting analyst → 403 `OWN_REQUEST` (before the lock); every named run exists, is completed, has a proposal operation and belongs to this questionnaire, else 404 for the batch; an item key absent from its run's proposal → 400; assessment exists → 409 `ASSESSMENT_STARTED`; draft job active → 409 `ASSESSMENT_DRAFT_IN_PROGRESS`; then per decision in the order sent: the state rule (accept, and restore of an accepted item, need `analyst-review` → 409 `QUESTIONNAIRE_RELEASED`), the fold (a damaged run's items and a `not-open` transition → 409 `AI_PROPOSAL_ALREADY_DECIDED`; `no-op` → counted unchanged), for accept only staleness against the in-memory working state (409 `AI_PROPOSAL_STALE`), then apply to the working definition (edits invalid → 400; definition invalid → 409 `DEFINITION_INVALID`; `preservesAnswers` or `keepsControllerValues` fails → 409 `ANSWERED_QUESTION_AFFECTED`; removal rules → `QUESTION_HAS_DEPENDENTS`, `LAST_ACTIVE_QUESTION`). Decisions earlier in the batch are visible to later ones (a confirmed change makes another item on the same question stale).
- **Apply** (D-22): an addition creates a `CsrmQuestion` with `questionText`, `helpText`, `answerType`, `options` from `questionOptions` with the section and order from `placeAddition` and the key from `allocateQuestionKey` on one `createBatchAllocation` for the batch, and `answer: null`; a change updates text, help text, answer type, choices and required through `candidateQuestion` and `validateDefinition`, never writing `answer`; a removal sets `options.deleted` `{ deletedAt, deletedBy }`. The accept event records `before` (the target's snapshot, for a change or removal), `applied` (`questionDocumentId`, `questionKey`, the new fingerprint) and `edits` (the field names whose value differs from the proposal).
- **Undo** (restore of an accepted item; D-23): allowed only in `analyst-review` while the question's fingerprint equals `applied.fingerprint` and it is unanswered, else 409 `AI_PROPOSAL_UNDO_UNAVAILABLE`; an addition is soft-removed (`QUESTION_HAS_DEPENDENTS` when a later question depends on it), a change writes `before` back, a removal clears `options.deleted`. Restore of a rejected item is allowed until the draft and returns it to open. Every restore appends a `restored` event with `applied` for an accepted item.
- **Governance events**: confirmation writes `question-added`, `question-edited` or `question-deleted` with `questionKey`, `questionText`, `runId`, `itemKey`, `aiEdited`; an Undo writes the reverse kind with the same source and `aiUndo: true`, and an undone removal writes `question-restored`. `by` is the deciding analyst. Rejects and the Undo of a rejection write decision events only.
- **Exports from the governance workflow.** `candidateQuestion`, `validateDefinition`, `questionOptions`, `questionByDocumentId`, `governanceConflict` and `appendQuestionEvent` become exported; `appendQuestionEvent` gains an optional `source: { runId, itemKey, aiEdited, aiUndo? }`; `addQuestionnaireQuestion` allocates its key with `allocateQuestionKey` so the key rule has one home.
- **Requestor re-check** (W-7). In `saveAnswers` and `submitQuestionnaire`, right after `loadWorkflow` inside `runQuestionnaireMutation`, refuse with `QuestionnaireWorkflowError(409, "CSRM questionnaire is not answerable.", "QUESTIONNAIRE_NOT_ANSWERABLE")`, the reason and message the module already serves, when `releasedAt` is not a non-empty string. It is proven mounted at the service (the harness's service fixtures below), never with in-memory unit fixtures. Requestor saves keep their own in-process tail; both paths take the questionnaire row lock, which with the re-check is sufficient (Planner's Discretion, D-25).
- **Harness helpers**: `decideQuestionnaireProposalsFixture(analystId, questionnaireId, body)` (returns `{ status, body }` from the service's errors as the route will map them), `questionnaireSnapshotFixture(questionnaireId)` (questions with answers, `releasedAt`, `governanceLog`, and every run's `decisions`, for deep-equal checks), `saveAnswersServiceFixture(requestorId, questionnaireId, body)` and `submitQuestionnaireServiceFixture(requestorId, questionnaireId, body?)` (call the services directly, past the policy).
