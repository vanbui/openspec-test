## Phase Goal

**As a** risk manager, **I want to** registers by assessment type that stay current after release, and as a risk or treatment owner I want to track each treatment to completion on evidence, **so that** oversight reflects what is actually being done.

This plan's slice: CSRM marks treatments Overdue by date and reminds the right person once per period, every day, at every start and inside each act, without ever writing a reminder twice.

<objective>
Build the reminder run (D-26): the server-written status first (D-08), then every kind's candidates from 20-02's rules, claimed exactly once in `CsrmReminderDelivery` (D-27) and written through 20-13's service with a system actor (D-25); the start-up run, the daily job in `Etc/UTC`, and the per-risk evaluation inside every treatment act and decision review. Seed SC5's time-relative fixtures behind the development double key (D-30). Pin the harnesses and record the new PostgreSQL constructs (R-08-37).

Purpose: SC5's in-app half (due within seven days reminds; past the date reads Overdue and escalates; a date change clears it; a decision waiting more than seven days reminds its decider) and NOTIFY-02 criterion 1.
Output: three reminder modules, the job registration, the bootstrap order, the fixture seed, the per-act hooks, the harness and Playwright pins, two integration proofs and the residual-risk record.

Edits Strapi source? Yes (dev servers stopped). Changes the specification? No. Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Subjects (`reminder-subjects.ts`, ids only, outside transactions, `REMINDER_BATCH_SIZE = 200`).** `selectStatusDriftRiskIds` (applicable open risks where the stored status differs from 20-04's derived status SQL); `selectTreatmentReminderRiskIds` (tracked, not complete, governing date on or before today + lead); `selectDecisionReviewRiskIds` (20-08's review state `due-soon`, `due` or `overdue`); `selectWaitingRoundIds` (17.1's open acceptance rounds with a pending act older than the waiting threshold); `selectAssessmentReviewIds` (released assessments whose `nextReviewDate` is on or before today + lead). Each pages by id.
- **Per subject.** One `strapi.db.transaction`: the request lock (`withRequestLock`), then the risk row `forUpdate` (`.transacting(trx)`), re-read and re-derive; if the stored status differs, `ensureReleaseBaseline` then write it with a `status-derived` row (source `scheduled-run`, actor null) — the baseline is written only before a change, never for a reminder alone; then build candidates with 20-02's rules, `collapseOnePerPerson`, drop recipients who fail readability (owner parts through `loadRiskPeople`, `decision-waiting` through the participant check, analysts through eligibility), and for each candidate `claimReminderDelivery` then, on a claim, `notify` with `actorDocumentId: null` and the one explicit recipient, then `linkDeliveryNotification`; an empty `notify` result marks the delivery `skipped` with `not-readable`. A failure in one subject is caught, counted and logged by kind only; the run continues.
- **Claim (`reminder-delivery.ts`).** `DELIVERY_UID = "api::csrm-reminder-delivery.csrm-reminder-delivery"`; `claimReminderDelivery(strapi, trx, { reminderKey, kind, periodKey, email })` inserts through `strapi.db.connection` with `document_id` (`randomUUID()`), `reminder_key`, `kind`, `period_key`, `email_status: "pending"` (every periodic kind emails; event kinds write no delivery row), `email_attempts: 0`, and `created_at`, `updated_at`, `published_at` as `Date`s, `.onConflict("reminder_key").ignore().returning("id").transacting(trx)`; returns the id or null. `linkDeliveryNotification` sets `notification`, `recipient`, `risk` and `assessment` through `strapi.db.query(DELIVERY_UID).update`. Column names are asserted against `strapi.db.metadata` in the integration test.
- **Run.** `runReminders(strapi, { now, trigger: "startup" | "daily" | "act" | "test" })` → `{ statusesWritten, remindersWritten, failures }`, steps in order: status drift, treatment reminders, decision reviews, decision waiting, assessment reviews; one line `strapi.log.info` of `{ event: "csrm.reminders.run", trigger, today, statusesWritten, remindersWritten, failures }` (no ids, names or addresses). `evaluateRiskReminders(strapi, { riskDocumentId, now })` runs the treatment and review steps for one risk inside the caller's transaction (nested transactions share it), with the request lock the act already holds. `runStartupReminders(strapi, now)` calls `runReminders` with `startup`, catches everything and logs one error line, never throwing.
- **Schedule.** `registerReminderJob(strapi, schedule, task)` in `reminder-schedule.ts`: when enabled, `strapi.cron.add({ csrmReminderRun: { task, options: { rule, tz: "Etc/UTC" } } })`, then asserts the named job's `nextInvocation()` is not null, else throws `ReminderScheduleError` (boot fails).
- **Bootstrap (`index.ts`).** After the existing seeds: `await seedTreatmentReminders(strapi)`, then (after `seedDevelopmentApiToken`) `await runStartupReminders(strapi, new Date())`, then `registerReminderJob(strapi, readReminderSchedule(process.env), ({ strapi }) => runReminders(strapi, { now: new Date(), trigger: "daily" }))`. `readReminderSchedule` runs in `register()` so an invalid value fails boot early. 20-15 adds the capture swap before the start-up run.
- **Per-act hooks.** `treatment-acts.ts` and `decision-review-act.ts` call `evaluateRiskReminders` at the end of each act's mutation (after the status write), so a date moved into the lead writes `treatment-due-soon` at once and a completed or re-dated treatment produces no further keys.
- **Fixtures (`seed-treatment-reminders.ts`).** Gate exactly as `seed-analyst-insights.ts` (`IDAMBOX_SEED_CSRM === "true"` and `developmentIdentityEnabled()`); `TREATMENT_REMINDER_FIXTURE` names two Project requests raised by Maya (Secondary Requestor), assigned to the Second Security Analyst: request A released and closed with risks `due-in-3` (Treat, treatment owner Morgan Lee, risk owner Maya, resolve today+3, Not Started), `overdue-2` (Treat, same people, resolve today−2, progress In Progress, stored In Progress), `later-30` (Treat, resolve today+30) and `review-due-3` (Accept, Moderate, risk owner Maya, a completing decision row with review date today+3); request B in an open acceptance round whose risk awaits Maya's decision since now−8 days. Reconciled at each start to `utcToday(now)`: dates, progress, stored status, closure and round facts reset by documentId, created when absent; history and deliveries are never deleted. Before writing it the executor greps `apps/csrm/e2e` for unread-count assertions on Maya, Morgan Lee and the Second Security Analyst and records the result; the phase spec (20-23) asserts these reminders by sentence and record number only.
- **Harness and Playwright.** The harness sets `CSRM_REMINDER_SCHEDULE=off` before `load()` and restores it; it exports `runRemindersAt(now)` loading `runReminders` from `dist`. `playwright.config.ts`'s Strapi `webServer.env` gains `CSRM_REMINDER_SCHEDULE: 'off'` (a run spanning 00:05 UTC must not fire a second evaluation mid-suite).
- **Residual risks.** `docs/security/phase-08-residual-risks.md`: R-08-37 lists `INSERT … ON CONFLICT (reminder_key) DO NOTHING RETURNING`, 20-15's compare-and-set `UPDATE` and 20-08's correlated `ORDER BY … LIMIT 1` subquery as constructs to run on PostgreSQL before a PostgreSQL deployment; R-08-36 records that the run is safe in two processes (row locks and the unique key); R-08-13 records the run's count-only log line.
