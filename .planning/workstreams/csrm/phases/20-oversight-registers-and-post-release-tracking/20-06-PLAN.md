## Phase Goal

**As a** risk manager, **I want to** registers by assessment type that stay current after release, and as a risk or treatment owner I want to track each treatment to completion on evidence, **so that** oversight reflects what is actually being done.

This plan's slice: a treatment owner, a risk owner or a Security Analyst moves a released risk's treatment from Not Started through In Progress to Complete on evidence, with notes, and the risk owner or an analyst changes its date, plan or owner with a reason, each recorded and each refused to everyone else.

<objective>
Serve the treatment acts (D-03 item 2): set progress, add a note, complete with evidence, reopen (with the completer's Undo), and change the resolve date, plan or treatment owner with a reason, per D-08 and D-10 to D-12, through 20-05's wrapper and repository and 20-02's refusal order (D-13, D-21), each with its history row (D-19) and the compare-and-set base (18 D-14). Register every Phase 20 reason (D-03 item 10) in both lists, the specification and family Y's copy (20-UI-SPEC §15). Publish, grant and prove the operations (D-02).

Purpose: SC2's Not Started → In Progress → Complete on evidence, SC5's "a date change with a reason clears it" and SC6's refusals, in the API.
Output: one service, a route and controller file, the operations, the contract chain, the reasons and their copy, and the integration proof.

Edits Strapi source? Yes (dev servers stopped). Changes the specification? Yes. Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Bodies (closed parsers, unknown keys 400).** Progress: `{ progress: "Not Started" | "In Progress", base: { progress } }`. Note: `{ text }` (1–2,000 after trim, plain text). Completion: `{ evidenceStatement, base: { progress } }`; a missing, blank or over-2,000 statement → 400 `TREATMENT_EVIDENCE_REQUIRED` (over the bound reads the same reason with the field error). Reopening: `{ reason?, undo?: true, base: { completedAt } }`; `undo` without a reason only for the completer within `COMPLETION_UNDO_SECONDS = 120` of `treatmentCompletedAt`, else 409 `COMPLETION_UNDO_UNAVAILABLE`; otherwise a reason of 1–500. Change: `{ field: "treatmentResolveDate" | "treatmentPlan" | "treatmentOwner", value, reason, base: { value } }`; a date after the rule's today and within 17.1's five-year horizon, a plan within the risk update's existing `treatmentPlan` bound, an owner id passing `isEligiblePerson` (409 `OWNER_NOT_ELIGIBLE`), a value equal to the current one 400.
- **Effects.** Each act: `viewerFromState`, `loadRiskPeople`, `decideRiskAct` (404 → 403 → 400 → 409), then `withReleasedRiskMutation({ actor: { documentId, part }, source: "post-release" })` where `part` is the viewer's first part in `RISK_PARTS` order or `security-analyst`; inside, re-read and re-check state (a stale base → 409 `TREATMENT_CHANGED` with the current facts), write the fields, `recordRiskHistory` with the act's kind (`progress-set`, `progress-noted` with the text in `reason`, `treatment-completed`, `treatment-reopened` with `undo` when undoing, `treatment-changed` with the reason), then `deriveTreatmentStatus` at the rule's today and, if it differs from the stored value, write it and a `status-derived` row. Reopen sets progress `In Progress` and clears the three completion facts. Progress may be set while Overdue; the status stays Overdue (D-08).
- **Result.** Every act answers 200 `{ data: TreatmentTracking }`: `{ riskId, applicable, tracked, closed, progress, progressRecordedInCsrm, status, dueState, resolveDate, plan, treatmentOwner: { documentId, displayName } | null, completion: { at, by: { documentId, displayName }, part, statement } | null, lastProgressUpdate: { at, by } | null }`; notes answer 201 `{ data: ProgressNote }` (`{ id, text, author: { documentId, displayName }, authorPart, notedAt }`).
- **Routes.** `routes/risk-tracking.ts` (content API, `content-api-token`, the `csrm-app-enabled` and `csrm-authorization` policies with the operation literal): `PUT /v1/risks/:riskId/treatment/progress` → `api::csrm-risk.risk-tracking.setProgress`; `POST /v1/risks/:riskId/treatment/notes` → `addNote`; `POST /v1/risks/:riskId/treatment/completion` → `complete`; `POST /v1/risks/:riskId/treatment/reopening` → `reopen`; `PATCH /v1/risks/:riskId/treatment` → `change`. The controller maps typed service errors to `safeError` with the reason; a missing risk is 404 `Not Found` with no reason, the same body a missing record gets.
- **Contract.** Spec tag `risk-tracking`, operationIds `risk-tracking/set-treatment-progress`, `…/add-progress-note`, `…/complete-treatment`, `…/reopen-treatment`, `…/change-treatment`; components `TreatmentProgressRequest`, `ProgressNoteRequest`, `TreatmentCompletionRequest`, `TreatmentReopeningRequest`, `TreatmentChangeRequest`, `TreatmentTracking`, `TreatmentTrackingResponse`, `ProgressNote`, `ProgressNoteResponse`, `TreatmentConflictResponse` (the conflict error plus `current: TreatmentTracking`); responses 200/201, 400, 403, 404, 409. Every Phase 20 reason from 20-01 joins `CONFLICT_REASONS` in both lists and the `reason` enum of both conflict response schemas, with a comment naming Phase 20.
