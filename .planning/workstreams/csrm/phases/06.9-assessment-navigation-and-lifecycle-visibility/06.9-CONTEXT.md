# Phase 06.9: Assessment Navigation and Lifecycle Visibility - Context

**Gathered:** 2026-09-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Make assessment navigation and lifecycle visibility complete for both actors: expose the full status vocabulary in Analyst lists, return assessment viewers to the originating Assessment Request, and add one shared read-only assessment lifecycle stepper to both assessment-detail surfaces. Strapi remains the production API and authorization boundary.

</domain>

<decisions>
## Locked Implementation Decisions

### D-1 (status filter)

On /app/review/requests the status <select> currently hard-codes four values and renders raw enum strings as option labels (apps/web/src/features/assessments/assessment-list.tsx:246 and :91). It must offer the complete seven-value request-status vocabulary from `requestStatuses` in apps/web/src/features/requests/request-domain.ts (draft, submitted, questionnaire-in-progress, risk-assessment-drafted, under-review, approved, closed) with human-readable labels taken from `requestStatusPresentation`, never raw enum text. The Queue filter and the Status filter stay orthogonal: choosing a queue must not silently truncate the status vocabulary. The Analyst assessment list at :310 likewise offers the full four-value `assessmentStatus` vocabulary with readable labels from `assessmentStatusPresentation`.

### D-2 (request link is served, not inferred)

The assessment detail projection carries no link to its originating request today (`assessmentDetailShape` in apps/web/src/features/assessments/assessment-schema.ts has no request field). The `assessmentRequest` oneToOne relation ALREADY EXISTS on the CsrmAssessment content type, so this is a controller/service projection plus an OpenAPI declaration, NOT a datamodel change. `/v1/risk_assessments/{id}` must project a bounded, closed request summary for both actors -- documentId, requestNumber, title, requestStatus -- declared in docs/references/specification.json with the web client regenerated from it. Record-level authorisation for that summary is the same rule that already authorises the assessment read; a Requestor must never learn about a request that is not theirs. Cross both sides of the contract in the same plan: a persisted or published shape change has a server side and a client parser side.

### D-3 (actor decides the destination)

The link target is derived from the existing discriminated `actor` field, not guessed from the route. A Requestor's link goes to /app/requests/{documentId}; an Analyst's goes to /app/review/requests/{documentId}. Use the existing RecordLink primitive.

### D-4 (lifecycle stepper is read-only and reuses the established pattern)

Add an AssessmentLifecycleStepper to the assessments feature, modelled directly on apps/web/src/features/requests/request-lifecycle-stepper.tsx and the derived-lifecycle approach Phase 06.8 established. Steps are derived from the four-value `assessmentStatus` enum -- Drafted, In review, Released (approved), Closed. It names the current state in text ("Current lifecycle state: X"), distinguishes completed / current / future by icon AND text label, and never by colour alone. It explains state only; it is NOT a second workflow-control surface and must carry no action buttons. Derivation belongs in a domain module, not in JSX.

### D-5 (both surfaces)

The stepper and the request link render at the top of BOTH assessment detail surfaces -- the Analyst editor at /app/review/assessments/[documentId] (AssessmentEditor) and the Requestor released view at /app/assessments/[documentId] (ReleasedAssessmentDetailView). One shared component, two callers; no parallel implementation.

### D-6 (fold in the recorded follow-up)

The two native selects in assessment-list.tsx style themselves with a literal class string instead of the shared `nativeSelectClassName`, so they carry no focus ring. This phase touches exactly those selects, so fix them to use the shared helper.

### Non-negotiable constraints

- No Strapi content-type schema change. Adding controllers, services, policies, routes and projections is fine; editing apps/strapi/src/api/*/content-types is not. The relation needed already exists.
- Keycloak stays disabled. Do not wire, enable or configure it.
- Typed openapi-fetch service layer only. No raw fetch in pages, no frontend API facade.
- Strapi stays authoritative for authorization. Navigation visibility is not security.
- Semantic design tokens only; no hard-coded brand colours in feature components. WCAG 2.2 AA, responsive 375-1440px. On tinted surfaces use text-foreground-secondary, never text-muted-foreground (4.42:1, fails AA).
- The five-state screen contract (loading / empty / populated / error / permission-denied) applies to every surface touched.
- Unit and end-to-end tests for both actors accompany every material workflow change. Do not delete or weaken an existing test to make new behaviour pass.
- Committed content carries no tooling attribution of any kind: commit messages, code comments, docs and planning files describe the work, never how it was produced.
- Do not touch .planning/STATE.md or .planning/state.json; the orchestrator owns those.

### Lessons carried forward from Phase 06.8

- contracts crossed in one direction only broke three surfaces last phase -- declare the server shape and the client parser together.
- Do not let a new surface displace an existing guarantee; the stepper and link are additions to these pages, not replacements for what they already show.
- Shared memoized test fixtures caused false passes; give new behaviour its own fixture rather than reusing one another test mutates.

### the agent's Discretion

- Exact module and test-file decomposition, provided all locked decisions, constraints, and established patterns are preserved.

</decisions>
