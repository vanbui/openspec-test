## Phase Goal

**As a** Requestor, a risk owner or a Security Analyst, **I want to** be told in the app when work waits for me and to open it in one step, **so that** nothing waits unseen between the people in the flow.

This plan's slice: the header shows how many notifications wait for the person, at every width. The capability, the header control with its exact count from the layout, and Phase 11's header changes that make room for it.

<objective>
Add the `notification:read` capability (D-37), start the unread summary in the layout without awaiting it (D-25), and render the header control with its count capsule and accessible name in its place (D-24, X-33). Make Phase 11's header changes the Orchestrator Confirmations assign here: the Alerts item takes `AlarmClock`, and below 768px `Menu` becomes an icon-only circle with an 8px header gap, with Phase 11's tests updated (UI-SPEC §1.3, §2). The analyst dashboard's Top alerts takes `AlarmClock` too (pilot ruling 2026-10-18). Phase 13 D-31's role-tag wrap from 375 to 767px stays (pilot ruling 2026-10-18). Home gains no widget (D-28). Both tight routes keep at least 5,000 bytes of headroom (pilot ruling 2026-10-18).

Purpose: success criterion 1's "sees the unread count rise in the header" and success criterion 3's "a failed count read shows no badge"; plan 19.1-08 adds the panel the control opens and the client store.
Output: the capability, the trigger, the layout and shell wiring, the header CSS, the Top alerts icon and the updated shell, layout and dashboard tests.

## Recorded planning decisions

- **Capability.** `capabilities` gains `'notification:read'`; `capabilityAnchors['notification:read'] = ['GET:/api/v1/notifications', 'GET:/api/v1/notifications/summary']`; the development map adds it to all four roles. Both anchors must be served operations with web callers: `strapi-capabilities.test.ts` (:144-156, "anchors every capability to served operations the web itself calls") requires each anchor to be a `docs/references/served-operations.json` row with a non-empty `webCallers`, which 19.1-04 regenerates after its typed service exists (Task 1's precondition). The agent: Strapi's `GET /api/v1/me/access` withholds the three notification operations from every service identity (G-1, pilot ruling 2026-10-18, proven in 19.1-04's `notifications.integration.test.ts`), so `capabilitiesFromOperations` never grants it `notification:read` and the bell never renders for it; the development map has no agent role.
- **Layout.** After `granted` is known, `const notificationSummary = can('notification:read', granted) ? getNotificationSummary().then((result) => (result.error ? null : result.data), () => null) : Promise.resolve(null)`, never awaited, passed to both `AppShell` renders (the permission branch passes `Promise.resolve(null)`). Type `Promise<NotificationSummary | null>` from `notifications-domain.ts`.
- **Trigger.** `components/shell/notification-trigger.tsx` (`'use client'`, no zod, no date library) exports `NotificationTrigger({ summary }: { summary: Promise<NotificationSummary | null> })`: a `button` with class `header-notifications`, a 16px `Bell` (`aria-hidden`), visually hidden text `Notifications` plus `, {n} unread` when n > 0, and inside `<Suspense fallback={null}>` a child that reads `use(summary)` and renders the capsule `<span class="notification-count" aria-hidden="true">` with `1` to `99` or `99+`. Null or 0 renders no capsule. The `, {n} unread` text and the capsule both sit in that Suspense child; the boundary wraps only the count inside the button, never the page content (pilot ruling 2026-10-18). Plan 19.1-08 adds the popup attributes, the open state, the on-demand frame and panel, and the count store this component reads; the control's first load stays the button and its count (pilot ruling 2026-10-18, C-B5).
- **Shell.** `AppShellProps.notificationSummary: Promise<NotificationSummary | null>`; `AppShell` renders `{can('notification:read', granted) ? <NotificationTrigger key={searchKey} summary={notificationSummary} /> : null}` directly after the quick-find control and before the role tag and the account menu. `searchKey` is the existing key `QuickFindTrigger` uses (the identity and the grants), so the control remounts for another person.
- **CSS (X-33).** `.header-notifications`: outline circle at the icon-button size from 768px and the touch-target size below, `position: relative`, `--color-bg-inset` fill when `[aria-expanded="true"]`; `.notification-count`: `--radius-full`, `--color-primary` fill, `--color-on-primary` text, `--text-caption` at 500, `tabular-nums`, min 16px high and wide, 4px horizontal padding, 2px `--color-bg-page` border, placed 4px outside the circle's top end corner (`inset-inline-end`); below 768px the header gap is 8px and every header control, including the `Menu` trigger, is an icon-only circle at the touch-target size with its label in `.sr-only`.
- **Phone fit and the longest persona (pilot ruling 2026-10-18, C-B7).** UI-SPEC §1.3's arithmetic used the Secondary Requestor (19 characters) as the longest role, but Phase 13 added `Second Security Analyst` (23 characters, about 209px on one line), which does not fit on one line at 375px beside three 44px circles. Phase 13 D-31's rule stays, as `header-role-layout.test.ts` pins it and UI-SPEC :417 says: from 375px to 767px the role tag has `flex: 0 1 auto` and `white-space: normal`, with no `text-overflow` and no `overflow: hidden`, so a tag that cannot fit wraps onto a second line inside the header with its full text shown; the ellipsis applies only below 375px. The three circles never shrink (`flex: none`, as `.header-search` today), so the tag is the row's only shrinking item and shrinks by wrapping. At 375px every development role's full tag text is visible, the Second Security Analyst's on two lines; no width from 320 to 1440 scrolls horizontally.
- **Icons (UI-D1; pilot ruling 2026-10-18).** In `navigation.ts`, the analyst profile's `Alerts` item uses lucide's `AlarmClock` (imported as `AlarmClockIcon`, as the file imports `BellIcon` today) instead of `BellIcon`. In `analyst-dashboard-presentation.ts`, `topAlerts.icon` becomes `AlarmClockIcon` too, because the design direction names no alert icon; this is the one-line change the pilot ruled, recorded in 19.1-UI-SPEC at UI-D1. The `Alerts` fixture in `mobile-navigation.test.tsx` takes `AlarmClockIcon` as well. Nothing else changes, so after this plan only the notification control uses the bell.
- **Route budgets (pilot ruling 2026-10-18, C-B5).** The control ships on every route, and at `b4aa1176` `/app/risks/{documentId}` delivers 262,456 bytes and `/app/requests/{documentId}` 289,383 of their 300,000-byte budget (`apps/csrm/.tmp/performance/baseline-desktop.json`); the shell's own figure, Home (`/app` as the Requestor), is 230,272. Both tasks run `e2e/performance.spec.ts` (desktop project, production build, dev servers stopped), and their verify then reads the run's records from that file: each tight route stays at or below 295,000 bytes (at least 5,000 under the budget), and the command prints the two routes and Home for the summary. The phase allows no budget override: `PERFORMANCE_BUDGETS` and `ROUTE_BUDGET_OVERRIDES` in `performance.spec.ts` never change. A route above 295,000 is fixed by making the control's first-load code smaller, never by an override.
- **E2E on the shared database (pilot ruling 2026-10-18, C-B6).** Playwright runs serially against a persistent database, and once 19.1-05 and 19.1-06 are in, other specs' assignments, releases and notes leave real notifications for every persona. This plan's E2E cases therefore assert the control's form, never a particular count: its accessible name matches `Notifications` optionally followed by `, {n} unread`, and a capsule, when shown, reads 1 to 99 or `99+` and is `aria-hidden`.
