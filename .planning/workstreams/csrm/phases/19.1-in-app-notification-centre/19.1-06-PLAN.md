## Phase Goal

**As a** Requestor, a risk owner or a Security Analyst, **I want to** be told in the app when work waits for me and to open it in one step, **so that** nothing waits unseen between the people in the flow.

This plan's slice: the questionnaire and assessment workflow tells each side when work arrives and clears it when they act or the work is taken back.

<objective>
Hook the three workflow events (D-11): `questionnaire-released` in `releaseQuestionnaire`, `questionnaire-submitted` in `submitQuestionnaire` with the Requestor's acting read (D-20), and `assessment-released` in the v1 `releaseAssessment`; the reversal reads in `returnQuestionnaireToAnalystReview` and `revertQuestionnaireToDraft` (D-21); and the initiator's acting read when `persistAssessmentDraft` makes the draft real (D-20). Prove atomicity (D-05), the exclusions including AI and job events (D-06), and "released again shows exactly one new".

Purpose: success criteria 2 to 4 for the questionnaire and assessment events in the API.
Output: three hot workflow services changed and their tests.

Scope note (D-41): the questionnaire family and the assessment family share this plan and wave, but each hot file has one owner and no other plan runs in this wave, which keeps D-41's serialisation; the pilot's pacing rule merges them.

Edits Strapi source? Yes (dev servers stopped). Changes the specification? No (D-03). Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Transaction (lane B W2).** The lock wrappers pass their transaction handle through to the work callback, without changing the lock order: `withQuestionnaireGovernanceLock`'s `work` becomes `(trx: unknown) => Promise<T>` and is called as `work(trx)` after `lockQuestionnaireAndRequest`; `runGovernanceMutation` passes the same `work` through; `runQuestionnaireMutation` and `runQuestionnaireReversal` call `work(trx)` after `lockQuestionnaire`. The callbacks that read notifications (return to review, submit, revert) take `async (trx) => …`; every other caller keeps its no-argument callback unchanged. The governance lock's doc comment is updated to say that raw knex inside the lock runs only with `.transacting(trx)` on the `trx` the lock passes to `work` (the notification reads); the Document Service and `strapi.db.query` stay the default. `withAssessmentLock` already passes `{ assessment, trx }`, and `persistAssessmentDraft` holds its own `trx`. Never `strapi.db.connection` or any handle outside the event's transaction (Pitfall 1).
- **Lock order (lane B W4).** `lockQuestionnaireAndRequest` takes the request row, then the questionnaire row (CR-101), before the work runs; nothing here reorders it. `notify`'s assigned-analyst rule takes a request-row `forUpdate` inside the same transaction, which re-locks a row the runner already holds.
- **Ids (lane B W3).** Every hook passes the documentIds the call site already holds; 19.1-03's repository resolves numeric row ids in its one private helper, `resolveRowIds` in `notification-repository.ts`, inside this transaction. No caller passes a numeric id. The field names below are 19.1-03's; where its executed names differ, use them and record it in the summary. `requestDocumentId` is the documentId of the request the loaded questionnaire or assessment belongs to; `now` and `at` are the event's own instant (`input.now ?? new Date()`, or the `Date` behind the ISO time the event writes).
- **Release.** In `releaseQuestionnaire`, inside its governance mutation's transaction after the release facts and the governance log are written: `notify(strapi, { kind: "questionnaire-released", actorDocumentId: input.actorDocumentId, requestDocumentId, questionnaireDocumentId: input.questionnaireDocumentId, at: new Date(releasedAt) })`. Releasing again after a return writes a new notification; the earlier one stays read.
- **Return to analyst review.** In `returnQuestionnaireToAnalystReview`, inside its transaction after `releasedAt` is cleared: `readNotificationsOnReversal(trx, { reversal: "return-questionnaire-to-review", subjectDocumentId: input.questionnaireDocumentId, now })`.
- **Submit.** In `submitQuestionnaire`, inside its transaction after every answer is stamped and the request status updated: `notify(strapi, { kind: "questionnaire-submitted", actorDocumentId: input.actorDocumentId, requestDocumentId, questionnaireDocumentId: input.questionnaireDocumentId, at })`, then `readNotificationsOnActing(trx, { act: "submit-questionnaire", recipientDocumentId: input.actorDocumentId, subjectDocumentId: input.questionnaireDocumentId, now })`. `input.actorDocumentId` is the submitting Requestor, the only caller the policy admits to submit.
- **Revert to draft.** In `revertQuestionnaireToDraft` (06.1, either party), inside its transaction after the answers return to draft: `readNotificationsOnReversal(trx, { reversal: "revert-answers-to-draft", subjectDocumentId: input.questionnaireDocumentId, now })`.
- **Assessment release.** In the v1 `releaseAssessment`, inside `withAssessmentLock`'s work after the release triple and the request status are written: `notify(strapi, { kind: "assessment-released", actorDocumentId: input.analystDocumentId, requestDocumentId: String(assessmentRequest.documentId), assessmentDocumentId: input.assessmentDocumentId, at: new Date(releasedAt) })`. Its readability is `whereReleasedAssessmentReadable` (lane B W5), the one released rule's SQL form that 19.1-03 adds beside `findReadableReleasedAssessment` in `released-assessment-read.ts`. Only 19.1-03's repository calls it, with the `viewerId` row id it resolves itself; this plan never calls it, never passes a `viewerId`, and adds no second form of the rule. Phase 17 adds participants as recipients and Phase 17.1 reuses the kind for release and close.
- **Draft act.** In `persistAssessmentDraft`, inside its transaction after the assessment is created: `readNotificationsOnActing(trx, { act: "persist-assessment-draft", recipientDocumentId: initiatingAnalystDocumentId, subjectDocumentId: questionnaireDocumentId, now })`. The enqueue writes nothing, a failed job reads nothing, and the early return for an existing assessment reads nothing.
- **The service identity (G-1).** No notification is written for the service identity: `notify` skips it at fan-out (19.1-03, `isEligiblePerson`). Task 1 pins this at the release hook, and Task 3 asserts that no notification row names the service identity across the file.
- **Tests.** `notification-events.integration.test.ts` drives the release, return, submit, revert, assessment release and draft operations over HTTP with the deterministic providers, reading results through `GET /api/v1/notifications` per person; atomicity uses `withDocumentWriteFailure(NOTIFICATION_UID, "create", 1, …)` and the existing workflow failure injectors (`withQuestionUpdateFailure`, `withDocumentWriteFailure` on the workflow's own uid).
