## Recorded planning decisions

- **Actions.** `markAllNotificationsReadAction(input: unknown)` (zod `.strict()`: `asOf` an ISO instant) and `undoMarkAllNotificationsAction(input: unknown)` (`markedAt` an ISO instant), each calling `markNotifications` with the `{ all: true, asOf }` or `{ undo: true, markedAt }` form and returning the mark result; no revalidation.
- **Marks hook.** `notification-marks.tsx` (`'use client'`, imported only by the on-demand panel and the Notifications page, with family T from `notification-refusal-copy.ts`): `useMarkAllWithUndo({ items, asOf, onApplied })` applies read to every shown unread item and a −n overlay at once, calls the action, settles with the returned `unread` and `asOf`, and when `changed > 0` shows the X-14 toast (`successToast`) `Marked {n} notification as read` or `Marked {n} notifications as read` with `Undo`; Undo applies unread to the same items and +n at once, calls the undo action with `markedAt`, and confirms `Marked {n} notification as unread` or `… notifications as unread`; failures roll back with T3 or T4. `useMarkNotification()` marks one item read or unread with the overlay, a polite status `Marked as read` or `Marked as unread`, rollback with T1 or T2, and T6 with removal on 404 (used by the page in 19.1-10).
- **Refresh points.** In `NotificationCount` (19.1-08's bell count, mounted once in the header; no provider): a `usePathname()` effect that skips the first render and, on each change, calls `getNotificationSummaryAction()` single-flight (a change while one is in flight queues one more, never more), adopting by `asOf` and calling `fail()` on an error; a `window` listener for `NOTIFICATIONS_STALE_EVENT` that triggers the same re-read. No `setInterval`, `setTimeout` loop or polling. `notification-count.tsx` exports `NOTIFICATIONS_STALE_EVENT = 'csrm:notifications-stale'` and `signalNotificationsMayHaveChanged()`, which dispatches it. The signal lives in the count module, not in `notifications-domain.ts`, because the count module already ships with the control on every route: the notes thread on `/app/requests/{documentId}` then adds no module to that route's first load, and the domain's value exports (kinds, views, the destination check) stay off it (C-B5).
- **Notes thread.** `notes-thread.tsx` imports `signalNotificationsMayHaveChanged` from `@/features/notifications/notification-count` and calls it after `markRequestNotesReadAction` resolves `ok`; nothing else in the thread changes (Phase 13 UI-D15 keeps the read silent).
- **Route budgets (pilot ruling 2026-10-18, C-B5).** As 19.1-07 records. Task 1 changes only on-demand modules (the panel, the marks hook) and Server Actions; Task 2 changes the first-load count module and the notes thread on the tightest route, so Task 2 runs `performance.spec.ts` and its verify requires `/app/risks/{documentId}` and `/app/requests/{documentId}` at or below 295,000 bytes in this run's records, printing both and Home. The phase has no budget override: a breach is fixed by trimming the first-load code in this phase.
- **E2E on the shared database (pilot ruling 2026-10-18, C-B6).** As 19.1-08's "Spec" records: each journey creates its own records titled `{purpose} {project} {Date.now().toString(36)}`, opens them with `?q={number}`, finds its notifications by that title, reads each persona's count from the control's accessible name at the start of the step, and asserts only changes from it. A toast's figure is asserted against the count read just before the action, never against a constant.
