## Phase Goal

**As a** Requestor, a risk owner or a Security Analyst, **I want to** be told in the app when work waits for me and to open it in one step, **so that** nothing waits unseen between the people in the flow.

This plan's slice: notifications are written to the right people inside an event's transaction, and each person's list, count and marks are exact and limited to what they may read now.

<objective>
Build the notification service (`notify`, D-05 to D-08) and the repository whose one SQL readability predicate feeds the list, the total, the unread count and "Mark all as read" (D-13 to D-15), with every `readAt` write: marks, Mark all as read bounded by `asOf`, Undo by the single read time, and the acting, reversal and note reads (D-18 to D-22). Prove readability against a semantic oracle (D-14), and the SQL form of Phase 19's released rule against its Document Service form, and record the PostgreSQL constructs in R-08-37. Every public function takes documentIds; numeric row ids are resolved in one private helper (the pilot's ruling on lane B W3). No notification is ever written for the Security Analyst Agent or any service identity (G-1).

Purpose: the operations (19.1-04) and the event hooks (19.1-05, 19.1-06) only call these two modules, passing the documentIds they already hold.
Output: two services, the SQL form of the released rule beside Phase 19's filters, the oracle and parity tests, service tests, harness helpers and the residual-risk entry.

Edits Strapi source? Yes (dev servers stopped). Changes the specification? No. Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Service.** `notification-service.ts` exports `type NotificationEvent = { kind: NotificationKind; actorDocumentId: string; requestDocumentId: string; questionnaireDocumentId?: string; assessmentDocumentId?: string; assigneeDocumentId?: string; note?: { documentId: string; sequence: number; authorPart: NotificationPart }; at: Date }`, `NotificationServiceError`, and `notify(strapi, event): Promise<number>`. It throws `NotificationServiceError` when `strapi.db.inTransaction()` is false, for an unknown kind, and for an event missing the relation its kind's subject needs. Recipient rules by the registry's `recipients`: `new-assignee` (the event's `assigneeDocumentId`, part `security-analyst`); `requestor` (the request's requestor, part `requestor`); `assigned-analyst` (take the request row lock with the `lockAssessmentRequest` shape, `queryBuilder(REQUEST_UID).select(["id"]).where({ documentId }).forUpdate().transacting(trx)`, then read the request's `assignedAnalyst`; none when unassigned; part `security-analyst`); `note-other-part` (author part `security-analyst` → the requestor in part `requestor`; author part `requestor` → the assigned analyst after the row lock, part `security-analyst`). Candidates are loaded through the Document Service with `accountStatus` and role names, and each candidate's `registeredSourceService` is set from `isRegisteredSourceServiceUser(strapi, documentId)` (`apps/backend/src/iam/identity/source-principal.ts`, as `loadEligibilityUser` in `request-assignment.ts` does), because the existing `isEligiblePerson` refuses a registered source service only when that flag is `true`; the actor and every candidate failing `isEligiblePerson` (imported unchanged from `apps/backend/src/csrm/people/eligible-person.ts`) are dropped, so no row is ever written for the Security Analyst Agent or any registered source service identity (G-1); duplicates collapse to one. Each write is `strapi.documents(NOTIFICATION_UID).create` with relations by documentId, `facts` from `buildNotificationFacts`, and `notifiedAt` from `event.at`. `notify` never calls `withRequestLock` (it runs inside whichever lock the event holds) and never runs for an AI run or a job event (D-06).
- **Ids (the pilot's ruling on lane B W3).** Every public function of `notification-service.ts` and `notification-repository.ts` takes documentIds (the recipient, the request, the subject, the notifications) and never a numeric row id. The numeric row ids the SQL joins on are resolved in exactly one private helper of `notification-repository.ts`, `resolveRowIds(db, { users?, requests?, questionnaires? })`: one `SELECT id, document_id … WHERE document_id IN (…)` per table it is given, bound with `.transacting(trx)` when it runs inside the caller's transaction. A documentId that resolves to nothing matches no row (an empty read, a write that changes nothing, or `NotificationNotVisibleError` for a mark by id), so existence is never revealed. 19.1-04 passes the recipient documentId the policy resolved, and 19.1-05 and 19.1-06 pass the documentIds they already hold.
- **Repository.** `notification-repository.ts` takes `db`: `strapi.db.connection` for reads outside a transaction and the caller's `trx` for everything inside one; every raw query inside a transaction calls `.transacting(trx)`. `type NotificationReadScope = { recipientDocumentId: string; analystKinds: readonly NotificationKind[]; asOf: Date }`. The private `readableQuery(db, recipientRowId, scope)` builds the base (`csrm_notifications n`, inner join of the recipient link on `idambox_user_id = recipientRowId`, inner join of the request link and `csrm_assessment_requests r`, left joins of the questionnaire and assessment links and rows, `n.notified_at <= asOf` bound as a `Date`) and the readable OR: `requestor` part with `questionnaire-released` (questionnaire row present, `q.released_at` not null, the request's requestor link names the caller), `assessment-released` (`whereReleasedAssessmentReadable` on `a` and `r` for the caller's row id), `note-added` (the request's requestor link names the caller); `security-analyst` part with `n.kind` in `scope.analystKinds` (an empty list matches nothing) and, for `questionnaire-submitted`, the questionnaire row present. Every public read and write resolves the recipient through `resolveRowIds` first, then composes `readableQuery`. `readableNotifications(db, scope): Promise<string[]>` returns the readable notifications' documentIds newest first (the oracle compares it). `listNotificationsPage(db, scope, { view, page, pageSize })` returns `{ rows: NotificationRow[], total, unread, pageCount }` with order `n.notified_at DESC, n.id DESC`, and `total` and `unread` from one aggregate statement (`COUNT(*)`, `SUM(CASE WHEN n.read_at IS NULL THEN 1 ELSE 0 END)`) parsed by a private `wholeCount` in `notification-repository.ts` with the same rule as `request-status-summary.ts`'s (that one is module-private, not exported, so it is copied here with a comment naming its origin rather than exported, and `request-status-summary.ts` is not changed; lane A W6); in the `unread` view `total` equals `unread`. `countNotifications(db, scope)` returns `{ total, unread }` from the same statement. Rows map SQLite integer and PostgreSQL `Date` times to `Date`, and parse `facts` from text when needed.
- **Writes.** `markNotificationsById(trx, scope, notificationDocumentIds, read, now)`: select the readable rows whose `n.document_id` is among them; if fewer come back than were sent, throw `NotificationNotVisibleError` before any write; then `UPDATE csrm_notifications SET read_at = now WHERE id IN (…) AND read_at IS NULL` for read, `SET read_at = NULL WHERE id IN (…)` for unread; return the number changed. `markAllNotificationsRead(trx, scope, markedAt)` runs one `UPDATE … SET read_at = markedAt WHERE id IN (readable AND unread) RETURNING id` with `scope.asOf` the view's `asOf`. `undoMarkAllNotifications(trx, scope, markedAt)` sets `read_at = NULL` on the caller's readable rows whose `read_at` equals `markedAt`. `readNotificationsOnActing(trx, { act, recipientDocumentId, subjectDocumentId, now })` and `readNotificationsOnReversal(trx, { reversal, subjectDocumentId, formerAssigneeDocumentId?, now })` read the kinds `NOTIFICATION_ACTING_READS` and `NOTIFICATION_REVERSAL_READS` name, by subject link and `read_at IS NULL` (the change-assignee reversal also by recipient and part); the subject documentId resolves through `resolveRowIds` as the registry's subject (request or questionnaire). `readNoteNotificationsThrough(trx, { readerDocumentId, requestDocumentId, throughSequence, now })` selects the reader's unread `note-added` rows for the request (at most `NOTES_PER_REQUEST_MAX`), parses each envelope in code, and updates the ids whose `noteSequence` is at most N, including any whose envelope fails to parse (research Open Question 5). Every time is bound as a `Date`.
- **Released rule in SQL** (the pilot's ruling on lane A B7 and lane B W5: one module, one rule). `released-assessment-read.ts` gains, beside `RELEASED_ASSESSMENT_FILTERS`, a frozen module-private table of the same release facts as SQL, typed `satisfies Record<keyof typeof RELEASED_ASSESSMENT_FILTERS, …>` so a fact added to the filters without its SQL form fails `tsc`: `assessmentStatus` → `{a}.assessment_status = 'approved'`; `approvalDate` → `{a}.approval_date IS NOT NULL`; `assessmentDate` → `{a}.assessment_date IS NOT NULL` (the rule that keeps a partially written legacy row out, lane A B7); `approvedBy` → an approver link exists (`csrm_assessments_approved_by_lnk`, the shape the module-private `assessmentReleased` of `review-queue-repository.ts` uses); `assessmentRequest` → `{r}.request_status = 'approved'`. The exported `whereReleasedAssessmentReadable(builder, { assessmentAlias, requestAlias, viewerId })` applies every entry plus the readable rule for a Requestor (the request's requestor link names `viewerId`, the viewer's numeric `idambox_users` row id the notification repository resolved). Its comment names it the SQL form of the same two rules, says Phase 17 widens "readable" and Phase 17.1 widens "released" in both forms together, and names the parity test. 19.1-06 consumes it by this name.
