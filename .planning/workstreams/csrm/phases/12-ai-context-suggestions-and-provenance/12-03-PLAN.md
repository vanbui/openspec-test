**As a** Security Analyst, **I want to** have the AI work from everything the Requestor gave and show where each proposal came from, **so that** I can trust, check and correct its output quickly.

This plan's slice: the one assessment context both AI operations will use, built from everything the request holds and nothing it should not send.

## Recorded planning decisions

- **Source keys.** `request.{field}` for each included, non-blank request field; `answer.{questionKey}` for each included question; `system-{n}` and `asset-{n}` for the selected systems and assets, numbered from 1 in name order (code-unit order, then documentId). The model sees only these keys; the adapters map them back (D-15).
- **Bounds** (planner's discretion within D-06): `CONTEXT_BOUNDS = { riskTypes: 60, riskTypeDescriptionCharacters: 500, applicableControlsPerType: 20, libraryShortlist: 80, controlCandidates: 150, controlNameCharacters: 255, systems: 100, assets: 100, questionLabelCharacters: 300, draftPromptCharacters: 200_000, questionnairePromptCharacters: 100_000 }`.
- **Answer rendering.** Single and Multi select render their choice labels (multi joined with `; `), Boolean renders `Yes` or `No` (seeded questionnaires keep Boolean answers), Date renders the ISO date, and an empty or null answer renders `Not answered`.
- **Ranker** (planner's discretion within D-06 and D-12): lowercase words of three or more letters, a fixed stop list, IDF over the ranked library, score as the sum of matched terms' IDF, ties broken by the document id in code-unit order. Pure, dependency-free.
- **The submitted-answer rule has one home.** `submittedQuestionAnswers(questionnaire)` moves into the loader (same active, visible and submitted-envelope checks as today's `submittedAnswers`, same 409 when a visible answer is not submitted) and returns `{ questionKey, sectionTitle, questionText, helpText, answerType, value, answerLabel }`. `assessment-workflow.ts` maps it to its existing `{ questionKey, value }` shape until plan 12-06 switches the draft to the builder.
- **Harness fixture.** `seedUatALikeFixture()` on the harness creates, through the Document Service: the three seeded Risk Type names plus a fourth, `Payment Integrity`, each with applicable controls; a 12-control library whose names include file integrity, segregation of duties and backup testing; three information systems (an internet-facing HR and payroll platform, a finance system, an identity provider); one Restricted asset holding employee personal and bank details; a Project request owned by the seeded Requestor with those systems and the asset selected, third-party involvement, and regulatory requirements naming the Privacy Act 1988 and tax file number obligations; and a submitted questionnaire whose answers describe unsigned payment files, partial segregation of duties and an untested pay-run fallback. It returns `{ requestId, questionnaireId, systemIds, assetIds, riskTypeIds, controlIds }`. `buildAssessmentContextFixture(input)` calls `buildAssessmentContextFor` on the running instance.
