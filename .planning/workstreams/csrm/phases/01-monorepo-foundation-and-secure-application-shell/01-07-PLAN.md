<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| authenticated identity -> Strapi policy | Trusted Keycloak-to-IdamBox state selects the persisted user and grants. |
| IdamBox role graph -> operation decision | Explicit and birthright roles cross into a FunctionAPI authorization decision. |
| client collection query -> Strapi core find | Untrusted filters cross a trusted own/all authorization scope before database access. |
| client JSON -> CsrmAssessmentRequest create | A writable relation can attempt to impersonate another Requestor. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-07-02 | Spoofing | inactive IdamBox User | high | mitigate | Load and reject `accountStatus != active` before any grant evaluation. |
| T-01-07-03 | Information disclosure | assessment-request collection | critical | mitigate | Have the policy emit own/all scope and force own scope through an ANDed trusted Requestor predicate before core find. |
| T-01-07-04 | Tampering | create Requestor relation | critical | mitigate | Overwrite client ownership with trusted `ctx.state.idamboxUser.documentId` before core create and deny absent identity. |
| T-01-07-05 | Elevation of privilege | route operation mismatch | high | mitigate | Centralize the five actual GET/POST/PUT/DELETE `/api` identifiers, including DELETE, and use them in router policy configuration. |
