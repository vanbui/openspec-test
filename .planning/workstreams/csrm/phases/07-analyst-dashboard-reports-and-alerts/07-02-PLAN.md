## Phase Goal

**As a** Security Analyst, **I want to** have a data-driven dashboard, reports, and alerts covering my review queues, high and critical risks, and overdue treatments, **so that** I can prioritise analyst work from live workload signals.

<objective>
Three vertical slices. Each one crosses the Strapi projection, `specification.json`, the regenerated client, the closed parser and tests in one task (D-08):

1. **Requestor status summary (D-05, D-28, D-22).** Serve the catalogue-reserved `GET /api/v1/my_requests/status_summary` as an owner-scoped database group-by, and make the Requestor dashboard read it once instead of seven times.
2. **Treatment due state (D-04, D-26).** Project `treatmentDueState` on every Risk Register row from the plan 01 rule, and retire the web's date-only `isRiskOverdue`.
3. **Risk state filter (D-36).** Add a closed `state` filter (`open` | `closed`) to the Risk Register, so every open-exposure tile and row in plans 06-08 links to a list with an equal total.

Purpose: these are the carried-forward D-22 follow-up and the two Risk Register contract changes that later dashboard and report figures link to.

Output:
- one new Strapi route, controller and service;
- a Risk Register projection and predicate change;
- three published contract changes, a regenerated client and updated web parsers and UI;
- tests at every seam.
</objective>

## Recorded planning decisions

- **Separate files for the summary route and controller.** They live in their own files in the `csrm-assessment-request` API (`routes/my-request-status-summary.ts`, `controllers/my-request-status-summary.ts`), following the `csrm-information-asset/routes/selected.ts` precedent. The core controller and router stay untouched, so plan 03's D-21 rewrite shares no file with this plan.
- **Operation constant.** The operation is exported as a separate constant, `myRequestStatusSummary`, rather than added to `CSRM_ASSESSMENT_REQUEST_OPERATIONS`. That keeps the object other modules read unchanged.
- **Summary keys** are camelCase, like `QuestionnaireStatusSummaryResponse`: `draft`, `submitted`, `questionnaireInProgress`, `riskAssessmentDrafted`, `underReview`, `approved`, `closed` and `total`. `total` is the sum of the seven parts.
- **`today` is a required input** to `listRiskRegister` and `projectRiskRegisterItem`, not an internal clock read (D-02). The three existing callers are updated deliberately: the controller, `risk-register.unit.test.ts` and `risk-register-seed.integration.test.ts`.
- **Where `state` sits in the `/v1/risks` parameter list.** It goes immediately after `mitigationStatus`, before `targetDateFrom`. The Phase 5 contract test pins the ordered parameter names, and its regex `targetDateFrom\?: string;\s+targetDateTo\?: string;\s+sort\?:` must stay true. The ordered-name assertion is updated deliberately.
- **The overdue marker keeps its current look in this plan.** Only its condition changes, to `treatmentDueState === 'overdue'`. The dense urgency presentation (UI-SPEC §9 item 4, UI-D13) needs `AlertUrgencyBadge`, which plan 05 creates.
