## Phase Goal

**As a** Security Analyst, **I want to** have a data-driven dashboard, reports, and alerts covering my review queues, high and critical risks, and overdue treatments, **so that** I can prioritise analyst work from live workload signals.

<objective>
Close the carried-forward review-queue follow-up (D-21).

Today the controller scans up to 1,000 reviewable requests in pages of 100 and classifies them in memory, so beyond that bound the queue reports what it read, not the truth. Replace the scan with database predicates:
- each bucket is expressed over `requestStatus` and the derived lifecycle facts, as `EXISTS` subqueries;
- the in-memory generation registry is applied as a bounded id-set predicate.

The page, the total, and the dashboard's bucket counts (plan 08) all come from one definition, and all are exact at any volume. The in-application rule stays as the semantic oracle that an equivalence test checks the SQL against (D-30).

Purpose: DASH-01's review queues must be exact before the dashboard counts them.

Output:
- a knex review-queue repository;
- a validation-only query parser;
- the registry id snapshot;
- a harness generalisation and new fixtures;
- unit and mounted proofs.

No contract change: the endpoint, parameters and item shape stay as published.
</objective>

## Recorded planning decisions

- **Split validation from query construction.** `buildAnalystReviewCollectionQuery` becomes `parseAnalystReviewQuery`. It performs exactly the same validation and returns either `{ kind: "outside-queue", pagination, bucket }` or a parsed read: `{ kind: "read", pagination, bucket, statuses, title?, requestNumber?, dueDate?, sort }`, where `statuses` is the queue set intersected with the requested status. It no longer returns Document Service query objects, because nothing would consume them. `review-queue.unit.test.ts` is updated deliberately to assert the same cases on the parsed read. The mounted G-5 matrix is the unchanged behavioural proof.
- **Registry cap.** The registry's active-id snapshot is guarded by `MAX_ACTIVE_GENERATION_REQUEST_IDS = 1_000`. Exceeding it throws `QuestionnaireGenerationCapacityError`, which the controller does not catch, so the request fails closed with a generic 500 and no data. The cap is unreachable in practice. The registry is process-local, so the generation-in-progress bucket is exact for a single Strapi process; plan 09 records that for Phase 8.
- **The generic harness helper `createFixtureDocument(uid, data)`** (a closed union of CSRM uids) is added here, so plans 04, 06 and 08 build their fixtures without further harness edits.
- **Null ordering.** Ordering reproduces SQLite's native order (NULLs first ascending, last descending) with explicit `CASE` terms, which also keeps the SQL PostgreSQL-portable. `r.id` is the final tiebreak.
- **Plan dependencies.** This plan depends on no Phase 7 plan (wave 1). Plan 04 depends on it for the exported status sets, and plan 08 for `countReviewQueueBucket`.
