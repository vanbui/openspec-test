## Phase Goal

**As a** Security Analyst or risk manager, **I want to** export any list I can see and to import spreadsheets without fighting the format, **so that** CSRM fits the Excel work around it.

This plan's slice: the one export pipeline and its vocabulary. A filtered register goes from its own parser, scope and repository to a file named after the view and date, with the columns the screen shows, the words the screen uses, and one log line, before any route serves it.

<objective>
Build the export pipeline in Strapi (D-05, D-17), the view registry with the Risk register as its first view (D-05, D-36), the vocabulary of columns, fixed tables, import columns and labels with its parity-tested web copy (D-06, D-07, D-31, D-33), the time-zone and file-name helpers and the About sheet (D-07 to D-10), and the export and import events on Phase 14's security event log (D-18). Every rule is proven with a fake repository and no HTTP (D-38).

Purpose: every later export is a thin adapter over this module (19-RESEARCH "codebase-design"), and Phases 18, 20, 21 and 22 add views to the same registry (D-36). It builds on the outputs D-35 names (Phase 10's zone and reasons, Phase 11's columns and markers, Phase 13's assignee, Phase 14's file modules, Phase 16's withdrawn-risk exclusion), all built at `bdd0f698`.
Output: four export modules, the vocabulary in two byte-identical copies, the extended event log and the register's export parser, each proven at its seam.

Edits Strapi source? Yes (new modules; the register parser gains an export variant; the event log gains members). Changes the specification? No. Runs Playwright? No.
</objective>
