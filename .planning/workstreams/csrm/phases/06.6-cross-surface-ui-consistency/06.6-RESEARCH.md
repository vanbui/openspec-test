## Summary

This is a presentation and regression-harness phase, not an API, schema, or authorisation phase. The existing shared `DataTable` already owns desktop tables, mobile cards, sorting, filters, footer pagination, density, skeleton rendering, and button-based disabled pagination. Its current required callback/filter props prevent direct migration of several card/raw-table surfaces, so the safe implementation seam is the locked backwards-compatible optional-prop extension—not a second table component. [VERIFIED: apps/web/src/components/csrm/data-table.tsx:50-75, 201-212, 270-384]

The codebase has a safe E2E fixture mechanism: only an attested local Playwright runtime may resolve a closed set of presentation states, and guarded pages authorise/load before applying fixtures. Reuse that mechanism for comparative state coverage; do not create a query-controlled fixture shortcut or make fixtures bypass a capability check. [VERIFIED: apps/web/src/lib/testing/e2e-ui-state.ts:8-12] Verbatim state union: `'populated' | 'loading' | 'empty' | 'error' | 'permission'`. [VERIFIED: apps/web/src/lib/testing/e2e-ui-state.ts:20-50, 58-67; apps/web/src/lib/testing/e2e-ui-state-route-authorization.test.tsx:49-70]

**Primary recommendation:** Plan this as an ordered shared-foundation migration: update the design/tokens and `RecordLink`, extend states and `DataTable`, migrate all locked surfaces and their unit tests, then add the comparative E2E contract plus a static anti-hand-roll guard.

### Pattern 1: Single record-navigation wrapper

**What:** Add `RecordLink` at `src/components/csrm/record-link.tsx`, wrapping `next/link`; expose normal link props/class composition only where necessary for layout (for example, card target sizing), while the component—not a feature—owns colour, font weight, underline, focus/hover treatment and transition. [VERIFIED: 06.6-CONTEXT.md:25-39]

**When to use:** Every identifier/title whose destination is that record, including list cells, mobile cards, dashboard lists and detail related/back links. Do not use it for action links such as “Clear filters” or “Try again.” [VERIFIED: 06.6-CONTEXT.md:25-28]

**Implementation skeleton:**

```tsx
// Contract source: 06.6-CONTEXT.md D-01; design values come from globals.css tokens.
import Link, { type LinkProps } from 'next/link';
import { cn } from '@/lib/utils';

export function RecordLink({ className, ...props }: LinkProps & React.ComponentPropsWithoutRef<'a'>) {
  return <Link {...props} className={cn('/* shared semantic-token treatment */', className)} />;
}
```

The skeleton deliberately does not invent new literal design values; the locked CSS contract supplies the concrete tokens. [VERIFIED: 06.6-CONTEXT.md:29-39]

### Pattern 2: Optional DataTable capabilities, not capability emulation

**What:** Make only the locked props optional: `filters`, `onSortingChange`, and `onPageSizeChange`. Render their controls only when the relevant prop exists; preserve existing required behavior for present callers. Add `stickyFirstColumn` as an opt-in. [VERIFIED: 06.6-CONTEXT.md:49-58]

**When to use:** Card/raw-table migrations whose server contracts lack a sort, page-size, or filter capability. The feature still maps its already-supported controls to its existing URL state. [VERIFIED: 06.6-CONTEXT.md:51-57]

**Why this fits the codebase:** `DataTable` currently computes filter chips directly from a required `filters` array, invokes a required sorting callback from `useTable`, and always renders rows-per-page controls. [VERIFIED: apps/web/src/components/csrm/data-table.tsx:50-75, 196-212, 235-264, 347-384]

### Pattern 3: State primitive owns structure; feature supplies facts/actions

**What:** Extend the existing `states.tsx` exports rather than create feature state blocks. Its no-prop rendering remains compatible for existing route-level use; its parameterised mode takes noun, filtered/action data, retry and area. [VERIFIED: apps/web/src/components/states/states.tsx:4-42; 06.6-CONTEXT.md:61-82]

**When to use:** All DataTable `stateSlots` and any feature-level loading/empty/error/permission path. Use optional description only for a documented domain fact, not to restore bespoke copy. [VERIFIED: 06.6-CONTEXT.md:61-82]

### Pattern 4: Comparative browser contract through the attested harness

**What:** New E2E helpers should sign in, set 375/1440, visit existing routes with the existing `?__e2eState=` fixture selector, select only visible variants, read root CSS variables/computed styles, and compare every surface to the first reference before checking the reference token. [VERIFIED: apps/web/e2e/design-system-conformance.spec.ts:33-62, 64-105, 160-189; 06.6-CONTEXT.md:117-132]

**When to use:** The phase contract, including populated, empty, error and permission fixture states; preserve the page authorisation-before-fixture order. [VERIFIED: apps/web/src/lib/testing/e2e-ui-state-route-authorization.test.tsx:49-70]

## Common Pitfalls

### Pitfall 1: Breaking DataTable callers while making props optional

**What goes wrong:** Optional props are dereferenced in filter, sort, or page-size paths, causing runtime errors or an accidental control with no server behavior.  
**Why it happens:** Current props are all required and direct calls exist. [VERIFIED: apps/web/src/components/csrm/data-table.tsx:50-75, 201-212, 235-264, 347-384]  
**How to avoid:** Guard control rendering and callbacks per optional prop; retain the full behavior for existing request/risk/admin callers; add unit cases for absent and present capability sets. [VERIFIED: 06.6-CONTEXT.md:49-58]  
**Warning signs:** A migrated review list shows a sorter/page-size UI despite no corresponding URL/service contract.

### Pitfall 2: Treating hidden responsive variants as visible test targets

**What goes wrong:** An E2E locator sees both rendered DOM variants and asserts the hidden one.  
**Why it happens:** `DataTable` renders both `[data-slot="data-table-mobile"]` and `[data-slot="data-table-desktop"]`, hiding one with responsive classes. [VERIFIED: apps/web/src/components/csrm/data-table.tsx:270-343]  
**How to avoid:** Scope assertions to `:visible`, exactly as the existing conformance suite explains. [VERIFIED: apps/web/e2e/design-system-conformance.spec.ts:99-102, 203-212]  
**Warning signs:** A test passes at 375px despite finding a desktop table, or fails strict mode due to two matching links.

### Pitfall 3: Breaking E2E fixture security or authorisation proof

**What goes wrong:** A fixture query makes a protected route render before capability denial, or works on an ordinary server.  
**Why it happens:** Fixture use is intentionally gated by environment variables, a nonce, local temporary directory placement, and freshness. [VERIFIED: apps/web/src/lib/testing/e2e-ui-state.ts:20-42]  
**How to avoid:** Reuse—not weaken—the closed harness; retain unit assertions that authoritative denial has no `data-ui-state` boundary. [VERIFIED: apps/web/src/lib/testing/e2e-ui-state-route-authorization.test.tsx:61-70]  
**Warning signs:** Requestor test sees a fixture boundary on an analyst-only route, or the ordinary-server proof fails.

### Pitfall 4: Sticky column loses its visual row association

**What goes wrong:** The first cell sticks but keeps a surface background during hover/selection, creating a discontinuity; it can also be obscured by later cells without a stacking context.  
**Why it happens:** Existing cells are plain table cells and row visual states are class-based. [VERIFIED: apps/web/src/components/csrm/data-table.tsx:323-339]  
**How to avoid:** Implement the D-04 first-cell/header styles in the shared table with explicit background inheritance/variants, z-index and the required right `--border` hairline; test geometry after scrolling fully right. [VERIFIED: 06.6-CONTEXT.md:84-96, 125-128]  
**Warning signs:** Sticky identifier overlaps content, becomes transparent, or exits the scroll region bounds.

### Pitfall 5: Static guard produces false positives

**What goes wrong:** A regex blocks legitimate detail alerts or misses a hand-rolled state reintroduced with different copy.  
**Why it happens:** Feature source contains other semantic error/permission content that is not a list state. [VERIFIED: apps/web/src/features/dashboard/requestor-dashboard.tsx:134-140, 224-240]  
**How to avoid:** Scope the guard to list features and explicitly recognise imports/usages of shared primitives plus prohibited state helper declarations/known state container patterns; add a fixture file or focused negative test proving the detector catches a reintroduced block. [ASSUMED]  
**Warning signs:** The guard prevents valid domain alerts, or a new list state is added without importing `states.tsx`.

// Pattern source: apps/web/e2e/design-system-conformance.spec.ts:160-189
async function computedLinkContract(locator: Locator) {
  return locator.evaluate((node) => {
    const style = getComputedStyle(node);
    return {
      color: style.color,
      fontWeight: style.fontWeight,
      textDecorationLine: style.textDecorationLine,
      textDecorationColor: style.textDecorationColor,
    };
  });
}
