## Summary

This is the third review pass on commits `bf599b0`, `0b43347`, `02c7821` (base `85fb33d`). The
mandate for this pass was narrow and specific: (1) re-derive, from the source rather than from the
prior review's account, whether any other field carried by `QuestionMutationPayload` is subject to
the same "object spread can't delete a key" defect class that produced CR-01/CR-03/the
visibility-clear bug, and (2) independently re-verify CR-01 and CR-03 are genuinely closed with no
regressions.

**Field-by-field audit of `candidateQuestion` (questionnaire-governance-workflow.ts:472-495).**
`QuestionMutationPayload` carries eight optional fields: `questionText`, `answerType`, `helpText`,
`required`, `section`, `order`, `choices`, `visibility`. Commit `02c7821` destructures `choices` and
`visibility` out of the base `...question` spread and rebuilds both explicitly from the payload-vs-prior
computation. I traced the remaining six:

- `questionText`, `required`, `answerType`, `order` are each assigned as a literal key
  (`payload.x ?? question.x`) directly on the returned object, never spread from a base that could
  carry a stale value underneath a conditional add. `required`/`order` correctly use `??` rather than
  `||`, so `false`/`0` survive a payload edit rather than falling back to the prior value — verified
  this is not a masked falsy-value bug.
- `section` is assigned via `payload.section ? payload.section : question.section` — also a literal
  key, not a partial merge. `parseQuestionMutationPayload` (line 79) only ever accepts a fully-formed
  section record (`key`, `title`, `order` all required), which is always a truthy object when present,
  so the truthy check behaves identically to an `undefined` check here; there is no falsy/empty
  section value the API can express, so there is nothing to clear and no bug.
- `choices` and `visibility` are the two fields that are genuinely optional-and-clearable
  (`choices` can be absent because the answer type stopped being a select type; `visibility` can be
  explicitly `null` to clear a condition). Both are now excluded from the base spread and rebuilt from
  scratch. I confirmed the two exclusions compose correctly with each other: editing only `visibility`
  on a select question still retains `choices` (computed independently from `answerType`/`payload.choices`,
  not from the base spread), and vice versa.
- `deleted` (on `QuestionnaireDefinitionQuestion`, not part of the payload) is not destructured out of
  the base spread, but `editQuestionnaireQuestion` (line 544) already refuses to edit a `question` that
  has `deleted` set, before `candidateQuestion` is ever called — so `question.deleted` is always
  `undefined` at this call site and there is no reachable path where a stale `deleted` marker could
  survive an edit.
- `answer` (also not in the payload) is intentionally carried through the base spread unchanged;
  answer-clearing is handled separately in `editQuestionnaireQuestion` (lines 552-570) by writing
  `answer: null` directly to the Strapi update payload when required, not by mutating the return of
  `candidateQuestion`.
- `helpText` never flows through `candidateQuestion`/`questionOptions` at all — it is written directly
  in `editQuestionnaireQuestion`'s Strapi `update({ data: { ...(payload.helpText !== undefined ? {...} : {}) } })`
  call (line 566), which is a genuine partial-merge write to the document service, not a JS object
  spread over a stale in-memory base. Because the update call only ever contains freshly-computed keys
  (never a spread of a prior record), there is no equivalent defect available for `helpText` — an
  explicit `helpText: null` in the payload is correctly forwarded and clears the field, and an absent
  `helpText` correctly leaves the stored value untouched (the intended "don't touch" semantics for a
  key that was never destructured from a stale base in the first place).

No other field on `QuestionnaireDefinitionQuestion` reachable through `QuestionMutationPayload` is
built via a conditional add-only spread over a base that already carries the prior value. The defect
class is closed for this function.

I also checked `addQuestionnaireQuestion` (lines 508-535), which builds a brand-new question object
field-by-field rather than spreading an existing record — there is no "prior value" to leak, so the
same defect class does not apply there, including for its own `payload.visibility`/`payload.choices`
conditional adds.

**Independent re-verification of CR-01 and CR-03.** I read `deleteQuestionnaireQuestion` fresh
(lines 449-470): it loads the definition, resolves the target question, and refuses with 409 both when
another active question's `visibility.questionKey` still points at it and when
`activeQuestionnaireDefinition(definition).length <= 1` — the exact CR-01 guard, unconditional and
evaluated before any write. For CR-03, I re-read the `candidateQuestion` choices computation
(lines 474-477) and confirmed the payload-absent-and-non-select path resolves `choices` to `undefined`,
which after the `choices` key's removal from the base spread now correctly omits `choices` from the
returned object rather than retaining the prior array.
