## Deviations from Plan

None in implementation scope. The test commands could not launch child processes in the
execution sandbox, so the suites were run afterwards outside it. That external run and the
browser check found three defects the typechecks could not:

1. The contract-to-client-schema parity guard rejected the detail payload. The contract types a
   lifecycle step key as a bounded string and caps the array at 50, because the eight steps are a
   derived presentation vocabulary rather than a stored enumeration, while the client pins the
   exact eight keys and the exact length. That narrowing is deliberate and is now declared on the
   `request.getRequest` parity entry with its reason, as the Phase 06.3 rule requires.
2. The stepper unit test asserted a capitalised step label against a fixture that produced a
   lowercase one, counted state labels with a regex that also matched the heading, and mutated
   `className` as a string, which throws on the SVG icons. The fixture now derives the label it
   asserts, the state labels are read from the list through a dedicated test id, and the colour
   sensitivity check rewrites the `class` attribute instead.
3. The stepper laid its eight steps out as an eight-column grid from the `md` breakpoint, which
   left roughly 85px per step at 768px. It now stacks on mobile and steps 2, 4 and 8 columns up
   to `xl`, and uses a visible ring indicator for the current step rather than a bare dot.

## Verified in the browser

Both actors were driven against the running application on the same request
(`RAR-DEV-QUES-001`, current step "Assessment drafted"). Both see the identical eight steps with
the same completed/current/future assignment; the Requestor is told the work is waiting with the
other party, and the Security Analyst is given "Complete the assessment review." linked to
`/app/review/assessments/{id}`. No console error and no horizontal overflow at 375px or 1440px.
