<objective>
**As a** Security Analyst, **I want to** work on a generated questionnaire in the browser — read it,
correct its questions, then release it — **so that** the Requestor only ever sees questions I have
approved, and I never have to guess which of my actions the Requestor can see.

Purpose: criteria 3, 4 and 8. The server side is complete after plans 01, 03 and 04; today the
analyst review screen is a dead end for any questionnaire that is not yet submitted, so none of that
capability is reachable. This plan completes the vertical.
Output: five typed service functions, five Server Actions, one analyst governance panel, and the
review route rewired around the analyst-only state.
</objective>

## Locked decisions this plan implements

| Decision | How this plan honours it |
| --- | --- |
| D-05 | The analyst review screen shows the generated questionnaire and its question editor before release; the Requestor screen shows nothing until released, which Strapi already enforces. |
| D-15 | The panel offers exactly one backward transition, labelled as returning the questionnaire to analyst review, and the question controls are only rendered while the questionnaire is in analyst review. |
| D-16 | The return control prompts for a mandatory reason. The release control and the question controls do not. |
| D-08 | Cleared answers returned by an edit are surfaced to the Analyst in plain language naming the question and the reason. |

the mounted Strapi operation, and make the pre-release questionnaire reachable at all.

In `questionnaire-service.ts`, extend `questionnaireSummarySchema` with the optional nullable
`release` object of a timestamp plus a documentId and nullable display name, and the optional
nullable `revision` object of an event count and last event timestamp, matching the components plan
01 published. Add a `governanceResponseSchema` for the mutation responses: the questionnaire header,
the release object, the full question list, and a cleared-answer array of question key and
explanation. Add `releaseQuestionnaire(documentId)` using the existing `read` helper over the typed
client's release path, parsing the response through that schema. Register the new parser in
`contractResponseParsers` with the component name plan 01 published, so the existing
contract-to-client parity guard covers it — an unregistered parser is exactly the gap Phase 06.3
added that guard for.

In `questionnaire-actions.ts`, add `releaseQuestionnaireAction(input)` taking only a document id,
validated by a strict schema with that single key. On failure reuse `serviceFailure` so the status
vocabulary stays identical to the existing actions, adding a message for the 409 case that says the
questionnaire is already released or is no longer eligible and to reload. On success revalidate the
same path set `revalidateQuestionnaireReversalPages` uses, because a release changes what the
Requestor's own list, dashboard and request detail show.

Create `questionnaire-governance.tsx` as a client component exporting `QuestionnaireGovernance`. For
this task it renders only the release affordance: a heading naming the questionnaire's governance
state in text, a short line stating that the questionnaire is visible to Analysts only until it is
released, and a confirmation dialog whose confirm action calls the release Server Action and then
refreshes the router. No reason is collected. Carry state in text and an icon, never colour alone,
and use semantic tokens only. Surface a failed action through the dialog's error message rather than
a toast, matching the existing revert control.

In `questionnaire-review.tsx`, replace the `awaiting-submission` dead end with a real analyst state.
Add an `analyst-review` value to `QuestionnaireReviewState` meaning an authorised, not-yet-released
questionnaire, and render for it: the page header with the questionnaire title and number, the
request relationship link, the governance panel, and the question definition through the existing
`QuestionnaireRenderer` in read-only mode. Keep `awaiting-submission` for the distinct case of a
released questionnaire the Requestor has not submitted yet, and keep every other safe state
discarding its inputs exactly as it does today.

In the review route, remove the early return that short-circuits every non-submitted questionnaire.
Read the questionnaire header, then always read the questions, then choose the state from the
projection: no release fact means `analyst-review`; a release fact with a questionnaire state other
than submitted means `awaiting-submission` with the governance panel rendered as well; a submitted
questionnaire means `submitted`. Preserve the existing 403, 404, error and empty handling so all
five screen states stay deliberate.

In the Server Actions module add `returnQuestionnaireToAnalystReviewAction`,
`addQuestionnaireQuestionAction`, `editQuestionnaireQuestionAction` and
`deleteQuestionnaireQuestionAction`. The return action validates a document id plus the shared
mandatory-reason schema and reuses the existing reversal revalidation set. The three question
actions validate their payloads with the same strict schemas the service uses, reuse
`serviceFailure` for status mapping, and revalidate the analyst review path and the request paths.
Extend the action result union so a successful mutation carries the cleared-answer list, because the
panel has to tell the Analyst what was cleared. Keep every module-level export a function: this file
carries the server directive, and Phase 06.4 recorded a real defect caused by exporting an object
from such a module.

In the governance panel add, in this order: a control that returns the questionnaire to analyst
review, rendered only when the release fact is present, using the existing confirmation dialog with
a required reason and wording that says editing requires returning it to review first; and a
question editor rendered only when the release fact is absent. The editor lists the questions grouped
by section in definition order, marks each deleted question in text as removed from the active
questionnaire and retained for the record, and offers per-question edit and delete controls plus one
add control. Editing opens a form pre-filled from the current definition; saving calls the edit
action and, when the response carries cleared answers, renders a persistent list naming each cleared
question and its explanation until the Analyst dismisses it. Delete uses the confirmation dialog
with no reason and wording that says the question and its answer are retained in the revision
history. Reuse the existing form and dialog primitives and the renderer's presentation of sections;
do not build a second question presentation.

Keep every decision the server makes on the server: the panel renders controls based on the
projection it was given and reports whatever the action returns. It must not predict a refusal, and
a refused action must show the server's message rather than hiding the control.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Server Action | Analyst-supplied question definitions and reasons enter the process; the action is the only entry point. |
| Server Action → Strapi content-api | The typed client carries the validated body; Strapi remains the authorization authority. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06.8-22 | Elevation of Privilege | analyst governance panel | high | mitigate | The panel renders controls from the server projection only; every mutation is refused or allowed by Strapi. Navigation visibility is never the gate, and removing a control is never relied on as a denial. |
| T-06.8-23 | Input Validation (ASVS V5) | question mutation bodies | high | mitigate | Each outbound body is validated by a strict client schema before it leaves the process, and re-validated by the server's closed parser from plan 04; the unsupported upload answer type is excluded on both sides. |
| T-06.8-24 | Tampering | Server Actions module shape | medium | mitigate | Every export of the actions module stays a function, the defect class Phase 06.4 found in a module carrying the server directive. |
| T-06.8-25 | Information Disclosure | cleared-answer explanations | medium | mitigate | Explanations are generated server-side from the definition change and name the question and the reason only; no stored answer value is echoed into an explanation. |
| T-06.8-26 | Information Disclosure | unregistered response parser | medium | mitigate | Every new response parser is registered in the contract parity list, closing the Zod-layer gap the Phase 06.3 guard exists to catch. |
</threat_model>
