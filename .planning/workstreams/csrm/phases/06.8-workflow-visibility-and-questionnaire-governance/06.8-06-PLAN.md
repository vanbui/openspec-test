<objective>
**As a** Requestor or Security Analyst, **I want to** see a dated history of what changed on this
questionnaire at the depth my role needs, **so that** I can tell what happened to my answers without
asking anyone, and evidence of every revision survives.

Purpose: criterion 5 and D-09. Plans 01, 03 and 04 write the events; this plan is the only thing
that makes them readable. It also resolves the documented limitation in `revert-audit-summary.tsx`,
whose own comment states that only the most recent reversal is persisted — a statement that is no
longer true for questionnaires and must not be left contradicting the timeline beside it.
Output: one actor-scoped server projection, one shared timeline component rendered at two depths,
and a reconciled reversal summary.
</objective>

## Locked decisions this plan implements

| Decision | How this plan honours it |
| --- | --- |
| D-09 | Both actors see a dated timeline. Analysts get question-level and answer-level detail; Requestors get a plain-language summary of what requires review. |
| D-02 | The timeline renders every persisted event in order; no entry is hidden or collapsed away, so a later record never erases an earlier one. |
| Contract-gap record, audit semantics | The log is scoped to one questionnaire and readable only through the same ownership and collection-scope checks as every other questionnaire read. No separate unscoped history endpoint is added. |
| D-14 | The timeline is a read of the narrative log; it is never consulted for an authorization decision, and the release gate keeps reading the dedicated facts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-06.8-27 | Information Disclosure | revision timeline read | high | mitigate | The timeline is served by the existing questionnaire read, so it inherits the ownership check for a Requestor and the collection-scope grant for an analyst. | T-06.8-30 | Tampering | timeline as an authorization input | high | mitigate | D-14: the timeline is a narrative read only. The release gate keeps reading the dedicated release facts, and this plan adds no authorization decision that consults the log. |
| T-06.8-31 | Input Validation (ASVS V5) | unknown future event kind | medium | mitigate | An unrecognised kind is dropped rather than rendered as an unlabelled entry, and the projected list is bounded to the parser's 1000-entry limit. |
