<objective>
**As a** Security Analyst, **I want to** add, correct and remove questions on a questionnaire I have
returned to review, **so that** the Requestor answers the right questions while every question I
removed and every answer I invalidated stays on the record.

Purpose: criteria 3 and 4, and decisions D-05, D-06, D-07 and D-08. The hardest constraint is that
D-07 forbids the hard-delete the existing regeneration path uses, and the contract-gap record forbids
a schema change for it — so the deletion marker lives inside the already-versioned `CsrmQuestion`
`options` JSON envelope.
Output: three mounted analyst operations, a version-2 question envelope, one active-definition
helper that every consumer reuses, and the D-08 answer-revalidation rule built on the existing
validator.
</objective>

## Locked decisions this plan implements

| Decision | How this plan honours it |
| --- | --- |
| D-05 | Analysts can view, edit, add and delete questions. Each operation is a separately granted API-only Function published in plan 01. |
| D-15 | All three mutations are gated on `assertQuestionnaireInAnalystReview` from plan 03. None of them performs a backward transition of its own. |
| D-07 | Deletion is a marker inside the existing versioned `options` envelope. The question row and its answer are never deleted, and the question is excluded from the active set, from progress, from submission and from assessment input. |
| D-08 | The existing `isQuestionnaireValueValid` decides whether an answer survives an edit. Nothing else validates it. A cleared answer records a plain-language explanation. |
| Contract-gap record | No schema change. `CsrmQuestion` keeps exactly its current attributes; only the meaning of the JSON envelope's own contents grows. |
| RESEARCH pitfall 2 | The regeneration hard-delete path stays exactly as it is and is never reused by a governance mutation. |
