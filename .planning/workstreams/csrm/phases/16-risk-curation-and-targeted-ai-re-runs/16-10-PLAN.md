## Phase Goal

**As a** Security Analyst, **I want to** withdraw wrong risks and ask the AI to rewrite one risk or propose missing ones, **so that** the draft ends up complete and correct without rebuilding it by hand.

This plan's slice: the human decision. A proposed risk is added or rejected, each rewrite change is confirmed or rejected with stale and Accept checks inside the transaction, Undo works where it is honest, and release waits until every proposal is decided.

<objective>
Extend Phase 12's decision operation with run-scoped targets (D-39) on Phase 15's fold (D-40): add a suggested risk (D-33), confirm a change with the stale check (D-37) and the Accept rule (D-38, G-14), reject with a reason, restore for Undo; take the transition only for content (D-23); refuse the requesting analyst (`OWN_REQUEST`) and withdrawn risks; supersede a withdrawn risk's open changes (D-40); record per-field run references (D-25, the assumption-delta promotion); add the `aiProposalsDecided` readiness requirement and release gate (D-42); and widen Phase 13's AI-inputs baseline (D-28).

Purpose: ASSESS-10 criteria 1 and 2, ASSESS-09 criterion 2 ("a rejected AI proposal is recorded as rejected") and success criterion 3 in the API.
Output: the decision extension, the readiness gate, the provenance and signal changes, the widened request contract and mounted proofs.

Edits Strapi source? Yes. Changes the specification? Yes (the decision request). Runs Playwright? No.
</objective>

## Recorded planning decisions

- **Decision entry.** `parseAiProposalDecisionBatch(body)` accepts, beside 12-12 and 12-13's entries, `{ target: { kind: "proposal", runId, item }, action: "accept" | "reject" | "restore", reason? }` with `runId` 1 to 255, `item` matching `^s-[1-8]$` or `^u-[a-z-]{3,40}$`, and `reason` (trimmed, 1 to `RISK_PROPOSAL_REASON_MAX_LENGTH` 500) only with `reject`; `reject` on a Phase 12 target and `dismiss` on a proposal target are 400; the batch stays 1 to 200 entries.
- **Order** (leak-safe, the 15-07 shape): parse (400) → for a batch naming any proposal: the viewer raised the request → 403 `OWN_REQUEST` (before the wrapper, read-only) → `withMutableAssessmentMutation({ transition: (result) => result.contentChanged ? "accepted-edit" : "none" })` → every named run exists, is completed, is a risk-proposal run and belongs to the path's assessment, else 404 for the whole batch; an unknown item in a valid run → 400 → Phase 12's targets as today → for each proposal decision in the order sent: fold the run's events plus those already decided in this batch; `nextState` → skip a `no-op`, refuse `not-open` with `AI_PROPOSAL_ALREADY_DECIDED`; for a change, the risk active (`RISK_WITHDRAWN`); for accept of a change, `isUnitStale` (`AI_PROPOSAL_STALE`); for restore of a confirmed change, the risk still holds the event's `applied.values` (else `AI_PROPOSAL_UNDO_UNAVAILABLE`); restore of an added risk → `AI_PROPOSAL_UNDO_UNAVAILABLE` → after all decisions, for each risk with confirmed units: `aiAcceptCheck({ residualRating: residualRatingAfter(current, confirmedUnits), plan, hasPlannedControl: riskHasPlannedControl(implementations) })` for any confirmed unit with `aiAccept` → 409 `AI_ACCEPT_NOT_PERMITTED` or `AI_ACCEPT_WITH_PLANNED_CONTROL` → write. Any refusal rolls back the whole batch (persistence deep-equal).
- **Apply** (`applyRiskProposalDecisions` in `risk-proposal-decisions.ts`, called inside the mutation, never serialising): add → `createRiskWithinMutation` with the proposed fields and `source: { kind: "ai-run", runDocumentId, proposalItem }`, `initialRiskAiProvenance(risk, runId)` with the suggested controls as Phase 12 suggestions, event `accepted` with `applied: { riskDocumentId }`; confirm → one `updateRiskWithinMutation` per unit in order with `source: { kind: "ai-run", ... }` (which skips Phase 12's edited marking for AI sources), `markFieldsConfirmedFromRun(provenance, fields, runId, actor, at)`, event `accepted` with `before: { riskDocumentId, values: base, fieldFacts }` and `applied: { riskDocumentId, values: proposed }`; restore of a confirmed change → `updateRiskWithinMutation` with `before.values` and a history row with `undo: true`, field facts set back to `before.fieldFacts`, event `restored`; reject → event `rejected` with `reason`; restore of a rejection → event `restored`. One `appendAiRunDecisions` per run. `contentChanged` is true when any add, confirm or restore of a confirmed change applied.
- **Provenance.** `markFieldsConfirmedFromRun` sets each field's fact to Phase 12's confirmed state with `by`, `at` and `runId`; `fieldRunId(provenance, field)` returns `fact.runId ?? envelope.runId`; `parseRiskAiProvenance` accepts the optional `runId` on a field fact (the approved amendment).
- **Supersession on withdrawal.** `withdrawRisks`, after applying, loads the assessment's runs with `loadRiskProposalRuns` and appends `superseded` (`by` the withdrawing analyst, cause `{ kind: "risk-withdrawn", riskDocumentId }`) to every open change of each applied risk, in the same transaction; this is not a content change of its own.
- **Readiness.** `validateReleaseReadiness(value, facts?)` and `projectReleaseReadiness(value, facts?)` take `facts: { openAiProposals: number }`; when it is above zero, `aiProposalsDecided` is missing; the projection adds the assessment-scope requirement key `aiProposalsDecided`, label `Decisions on AI proposals`, destination `ai-proposals`, state met or outstanding. `releaseAssessment` computes `openRiskProposalSummary` inside its transaction and passes it; the analyst detail handler does the same. The pre-edit transition keeps `validateReleaseReadiness(assessment)` without facts (field completeness only, as its comment says).
- **AI inputs baseline** (D-28, the pilot ruling above; 16-PLAN-CHECK iteration 2, B5). Today the assessment's baseline is the run its `aiProvenance` names (`assessmentAiInputsChanged` in `assessment-scope.ts`, also called by the request controller's `requestAssessmentAiInputs`), so a list change alone never moves it. Two changes, both needed: (1) in `ai-inputs-signal.ts`, `CONTEXT_WIDE_AI_OPERATIONS` gains `risk-suggestions` (the loader accepts only a context-wide completed run as a baseline); `risk-rewrite` is never context-wide; (2) in `assessment-scope.ts`, add `latestCompletedAssessmentContextRun(strapi, assessmentId)`, following `latestCompletedQuestionnaireContextRun` in `questionnaire-scope.ts`: one `findMany` on `api::csrm-ai-run.csrm-ai-run` filtered by `assessment.documentId`, `operation` `$in` `["assessment-draft", "risk-suggestions"]` and `status` `completed`, fields `documentId` and `completedAt`, sorted `completedAt:desc`, `id:desc`, limit 1; `assessmentAiInputsChanged` passes `baselineRunId: run?.documentId ?? parseAssessmentAiProvenance(document.aiProvenance)?.runId ?? null` with the `generatedDate` fallback unchanged, so every assessment without a completed suggestions run reads exactly as today. `projectAssessmentGenerationFacts` keeps `runId` from `aiProvenance` (the draft run), as the questionnaire keeps `generation.runId`. The request controller needs no edit: it calls `assessmentAiInputsChanged`.
- **Spec.** `AiProposalDecisionRequest`'s entry becomes `oneOf` the Phase 12 entries and the closed `AiProposalRunDecision` (`target` `{ kind: "proposal", runId, item }`, `action` enum `accept`, `reject`, `restore`, `reason` `maxLength: 500`); the response is unchanged.
