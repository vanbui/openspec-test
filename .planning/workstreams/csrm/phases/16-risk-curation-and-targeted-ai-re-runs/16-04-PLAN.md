## Phase Goal

**As a** Security Analyst, **I want to** withdraw wrong risks and ask the AI to rewrite one risk or propose missing ones, **so that** the draft ends up complete and correct without rebuilding it by hand.

This plan's slice: the seam every later mutation uses. One guard that Phases 17 and 17.1 extend, a lock core and transaction-scoped inner functions that batches can call, every existing change recorded in the risk history, withdrawn risks read-only, and the proof that nothing deletes a risk.

## Recorded planning decisions

- **Guard.** `assertAssessmentEditable(input: { assessment: unknown; actor: { documentId: string } })` throws `AssessmentWorkflowError(400)` for a blank actor, then calls `assertMutableAssessment(input.assessment)` (409 `ASSESSMENT_NOT_MUTABLE`). `isAssessmentEditable(input)` returns false instead of throwing on the 409 (a 400 still throws). The function comment states: Phase 17 adds G-11's rule (a nominated risk owner of the assessment is refused) and Phase 17.1 the acceptance-round lock (ASSESS-24), both here, with their own closed reasons.
- **Lock core.** `withAssessmentLock(strapi, assessmentDocumentId, work)` is the existing `serializeAssessmentMutation` → `strapi.db.transaction` → `lockAssessment` → `findOne({ populate: assessmentReleasePopulate })` sequence (404 when absent), calling `work({ assessment, trx })`. It applies no guard and no transition. Never nest it for the same assessment.
- **Mutation wrapper** (16-PLAN-CHECK iteration 2, W2). `withMutableAssessmentMutation({ strapi, assessmentDocumentId, analystDocumentId, transition?, mutate })` keeps its executed signature: `transition` is already `AssessmentMutationTransition | ((result: T) => AssessmentMutationTransition)` (default `accepted-edit`; assessment-workflow.ts, the `selectedTransition` line). It becomes `withAssessmentLock` + `assertAssessmentEditable({ assessment, actor: { documentId: analystDocumentId } })` + capture `{ assessmentStatus, requestStatus, reviewedBy, releaseReady: validateReleaseReadiness(assessment).ready }` + `mutate` + (when the selected transition, `transition(result)` for a function, is `accepted-edit`) `transitionForAcceptedEdit(captured, analystDocumentId)` and its writes. No `appliesEdit` or other second option is added: a caller whose result may change nothing passes `transition: (result) => result.changed ? "accepted-edit" : "none"` (as `decideAiProposals` already does with `result.contentChanged`). Existing callers keep their behaviour.
- **Inner functions.** Each takes `{ strapi, assessment, actorDocumentId, source }` plus its own input, where `source` is `{ kind: "analyst" }` or `{ kind: "ai-run", runDocumentId, proposalItem? }`, and returns `{ ...record, changed: boolean }`:
  - `createRiskWithinMutation({ ..., fields })`: the existing `createWithRiskNumber` path, then `recordRiskHistory` kind `created` (no `changes`).
  - `updateRiskWithinMutation({ ..., riskDocumentId, fields })`: re-read the risk with its assessment inside the transaction (`CSRM Risk ancestor changed.` 409 as today), `assertRiskActive(risk)`, `resolveRelations`, Phase 12's edit marking, the update, then `riskChanges(before, after, RISK_WRITABLE_FIELDS)` with relation labels resolved from the loaded owner, type, system and asset; an empty list writes no row and returns `changed: false`.
  - `createControlImplementationWithinMutation`, `updateControlImplementationWithinMutation`, `removeControlImplementationWithinMutation` (12-13 created the first and third): each loads the risk, `assertRiskActive`, writes, and records `control-implementation-added`, `-updated` (only when fields changed) or `-removed` (with every removed value) carrying `control: { documentId, controlNumber, name }`.
  - `assertRiskActive(risk)` throws `AssessmentWorkflowError(409, "CSRM Risk has been withdrawn.", "RISK_WITHDRAWN")` when `isActiveRisk(risk)` is false.
  - The HTTP-facing `createAssessmentRisk`, `updateRisk`, `createRiskControlImplementation`, `updateControlImplementation` and `deleteControlImplementation` become the wrapper (`transition: (result) => result.changed ? "accepted-edit" : "none"`) plus one inner call with `source: { kind: "analyst" }`.
- **Draft persistence.** Inside `persistAssessmentDraft`'s transaction, each created risk gets one `created` row with `source: { kind: "ai-run", runDocumentId: <the draft run> }` and the drafting analyst as actor.
- **Phase 12 decisions.** In `decideAiProposals`, before any write and for every named risk, `assertRiskActive` refuses the whole batch with `RISK_WITHDRAWN`; a suggestion added as a planned control goes through `createControlImplementationWithinMutation` with `source: { kind: "ai-run", runDocumentId: <the risk's provenance run> }`. Field confirmations and dismissals change no value and write no history row (D-19, UI-D23).
- **Controllers.** The risk and control implementation controllers map `AssessmentWorkflowError.reason` into `error.details.reason` with the same `safeError(ctx, status, message, reason?)` shape 12-11 gave the assessment controller.
- **Request deletion.** In the request controller's `delete` override, after the existing existence and authorisation checks and before 13-06's and 14-08's checks, a request whose `assessment` relation is set (any assessment state) is refused 409 with `reason: "REQUEST_HAS_ASSESSMENT"` and the message `CSRM assessment request has a risk assessment.`; the order means a request with an assessment, notes and files reports `REQUEST_HAS_ASSESSMENT`.
- **Static guard.** `risk-no-delete.unit.test.ts` reads every `.ts` file under `apps/backend/src`; per file it collects identifiers bound to `"api::csrm-risk.csrm-risk"` or `"api::csrm-risk-history-event.csrm-risk-history-event"` and variables bound to `documents(<uid or alias>)` or `db.query(<uid or alias>)`; it fails on `.delete(` or `.deleteMany(` reached from either, on raw SQL matching `/delete\s+from\s+["`]?csrm_risk(s|_history_events)\b/i`, and on any route object with `method: "DELETE"` whose path starts `/v1/risks`. A synthetic snippet test proves the scanner flags each pattern.
