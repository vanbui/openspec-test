<objective>
Add production-only Keycloak OIDC sign-in to the CSRM web app (`apps/csrm`, package `@csrm/web`) behind a new flag, `CSRM_AUTH_OIDC_ENABLED` (default false). The OIDC session adapter plugs into the existing `SessionAdapter` seam and replaces the development identity bridge, never runs alongside it. The work uses Auth.js v5's Keycloak provider and the pre-seeded confidential client `idambox-csrm`. Sign-out ends the Keycloak session (RP-initiated logout).

- **D-01, web side only.** Do not modify `apps/backend`. Strapi-side Keycloak token verification is the follow-up.

In OIDC mode the web never sends `x-csrm-dev-identity` and never falls back to the development session. Strapi denials render the existing permission-denied or unavailable states.
- **D-03, follow-up issue.** Write it as a draft markdown GitHub issue at `.planning/quick/260929-u0w-add-production-only-oidc-sign-in-to-the-/260929-u0w-FOLLOWUP-ISSUE.md`. Never run `gh issue create`.

<assumption_delta_decision>
Signal: a second authentication method (the OIDC session) now sits beside the development identity bridge.
Primary noun: `Session`, a signed-in person with a `displayName`.
Decision: **promote**. `Session` becomes the general representation. `developmentRole` becomes an optional detail that only the development-bridge variant carries, and an OIDC session never has one. The two modes are mutually exclusive through the single `resolveSessionRuntimeMode` predicate, so they are never added side by side.
Invariant test (accepted and included in Task 1): in OIDC mode, `getSessionAdapter()` is the OIDC adapter, the development adapter's `current()` is null even with the development cookie set, and the Strapi transport never sends the development identity header (Task 2).
